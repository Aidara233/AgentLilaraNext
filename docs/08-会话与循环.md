## 1. 会话是什么：数据

> **会话 = 提供商配置 ⊗ 结构化记录。两半都是数据，没有行为。**

| 文件 | 内容 | 写入时机 | `formatVersion` |
|---|---|---|---|
| `spec.json` | 模型/提供商、提示词槽位引用、工具集、上限、初始状态 | 创建时一次，之后只读 | ✅ |
| `state.json` | 状态（见下）、游标、队列、等待原因、父子指针 | **每步原子重写** | ✅ |
| `history.jsonl` | 只追加：模型输出、工具调用与结果 | **每步追加一次** | ✅ |

三条要继承的（ALP 已验证过）：

- `I-02` 三件套 + 显式版本；
- **"停止"要拆成两个**：停**推进** ≠ 停**会话**。会话在磁盘上可以躺一辈子；
- **不需要 `status ∈ {Running, Crashed}` 这类判定**——每步落盘 ⇒ 任何记录都可续（ALP 靠 `ColdTimeoutSeconds` 杀会话的那套在这里不存在）。

**状态机只有两个状态**（借 ALP 的关键性质：会话孵化出来，**要么在跑，要么等着被再次激活**——**没有"卡在等用户输入"这一档**）：

| 状态 | 含义 |
|---|---|
| `Running` | 一步在飞 |
| `Dormant` | 没在跑，等**激活** |

⚠️ **"为什么没在跑"是数据，不是状态。** `Dormant` 携带一组字段：`awaiting`（等什么：用户消息 / 外部事件 / 定时 / 子会话汇报）、`activations`（谁能唤醒它）、`notBefore`（最早何时可醒）。

两个好处：

1. **激活源统一**：用户消息不再是特殊状态，它只是**一种激活源**，与定时器、外部事件、子会话汇报等价；
2. **"卡住"仍然是一等数据**（ALC 的要求）：写在 `state.json` 里，头重连、进程重启都只是重新读出来——只是它不再是一个状态，因此不会长出"等我从 WaitingForInput 里 restore 出来"这类分支。

### 1.1 `phase`：Running 的细粒度相位（观察用）

流式之后，"在跑"还能再分几档。它们是**数据字段**，不是新状态：

| 状态 | `phase` | 观感 |
|---|---|---|
| `Dormant` | — | **待命** |
| `Running` | `collecting` | 正在整理上下文 |
| `Running` | `awaiting-model` | 请求已发，等首增量 |
| `Running` | `thinking` | **推理流在走** |
| `Running` | `outputting` | **文本流在走** |
| `Running` | `tool-calling` | **拼装 / 执行工具** |
| `Running` | `persisting` | 落盘中 |

三条规定：

1. **`phase` 是数据，不是状态**——和 `awaiting` 一个道理（`X-15` 的同一条教训）：状态机永远只有两个值，细节留在字段里。
2. **`phase` 只用于观察**：它**不进记录**（模型看不到"我正在思考"），只是头与控制台的可读属性。
3. **相位变化发一个信号** `session.phase { sessionId, from, to }`——按 §3 它是**信号**（1→N、不等待），订阅者自己看。受限脚本可以订阅它做统计，但它拿不到会话内部状态。

⇒ 这也是"待命 / 运行"对外呈现的唯一窄接口：**头不需要知道步骤编号，只需要知道现在在干什么。**

## 2. 一次推进：过程「一步」

过程由**内核**持有（[`02` §2.1](02-图模块.md)）。它自己**不调任何端口**，只按序派发事件、把上一步结果搬进下一个事件的载荷。

```
步：
 ① emit    session.step.begin        { sessionId, stepNo }        ← 通知头，不等待
 ② dispatch session.need-context     → 订阅：channel.read(cursor)  ← 拿到新消息
 ③ call    session.build-prompt     ← **上下文组装归 session**（实现必须纯）
 ④ dispatch session.need-model       → 订阅：model.call            ← 唯一重试点
 ⑤ dispatch session.need-tools       → 订阅：tool.execute × N      ← 每个调用一次
 ⑥ dispatch session.need-apply       → 订阅：session.apply         ← 组装记录增量
 ⑦ dispatch session.need-persist     → 订阅：store.append + state  ← **原子边界**
 ⑧ dispatch session.need-output      → 订阅：channel.post          ← 有话说才投
 ⑨ 判定（内核）                       ← 继续 / 停 / 出队
```

三条要点：

1. **③ 归 session，不归内核。** 上下文的组装是**会话模块的行为**——只有它知道记录的槽位、贡献者名单、以及这一步该不该注入。内核只负责"按序发起"。⚠️ 它是一次**调用**（点对点、等返回），且实现必须**纯**：同一份贡献集合 + 同一个 `now` → 逐字节相同。**不许在这里挂信号**——信号是 1→N 无序的，把信号挂进渲染路径等于让纯函数"看时序"。
2. **⑦ 是原子边界**：`history` 追加与 `state` 重写必须同一次提交，不能一半新一半旧。
3. **⑨ 是内核判定**，不在图里（图不做"要不要执行"的判定，[`02` §5](02-图模块.md)）。

### 2.1 模型调用必须流式：增量进缓冲，完成才落盘

（用户裁定：吃过 ALC 的亏——**同步调用导致长响应容易超时**；所以肯定流式。做法是**流式接收到缓冲区，完成后再一次性送去处理**，这样也兼容同步调用。）

```
model.call ──增量──▶ 缓冲区（只在内存） ──完成──▶ 一次交给 ⑥ session.apply
```

四条规定：

1. **超时的单位变了**：不是"整个调用多久"，而是"**两次增量之间最大静默**"（idle timeout）。长回答不再超时；真卡住的连接很快被判定。
2. **增量只在内存里，绝不落盘。** 落盘的只有"完成的那些块"。
   ⚠️ 这条是前缀稳定的直接要求：**边流边写历史 = 每步都在改历史 = 缓存全废**。
3. **缓冲区把它们拼回"一块"**：文本增量 → 一个 text 块；工具调用分片 → 一个完整 tool_call；推理块 → 一个 reasoning 块（**逐字回传、原样保留**，那是协议要求）。消费方看到的仍是"一次完整的模型输出"。
4. **同步 provider 走同一条路**：把它的整包结果当成"一次很大的增量"灌进同一个缓冲区。⇒ **消费端代码只有一份**，这就是"兼容同步调用"。

顺带解决两个悬着的问题：**流式怎么进记录** → 不进，只有最终块进；**头能不能实时看** → 能，但那是**观察通道**（事件流），不是记录。

## 3. 信号与调用：两种跨模块交互（★已按裁定改写）

**上游把信号发完就不管；下游各跑各的——分支原则上互不干扰。**

| | **信号（signal）** | **调用（call）** |
|---|---|---|
| 形状 | 发布 / 订阅，1→N | 点对点，1→1 |
| 等待 | **不等待**（发完就走） | **等返回** |
| 返回值 | 无 | 有 |
| 分支关系 | **各跑各的，互不干扰** | 单一接收方 |
| 用在哪 | "有新消息了""会话建好了" | 过程里的取用 / 调模型 / 落盘 |
| 失败 | 记审计 + 计数 + 死信，不影响兄弟分支 | 该调用失败 ⇒ 过程拿到错误 |

⚠️ **两者不是"同一事件派发的两种模式"，而是两种机制。** 我上一版用"两种派发语义"把它们塞进一个词里——那等于让**每个订阅者都要回答"我这次要不要被等"**，是实现给自己挖的坑。

同一个方法**天然有两条进路**（因为它本来就是接口）：

1. **被订阅激活**：广播源调它，**参数跟随广播源**；
2. **被主动调用**：调用方给参数，**参数自定**。

⇒ 装配表因此有两类边：`signal` 边（谁订阅谁）与 `call` 边（谁被允许调谁）。**跨模块无论走哪条都在表里可见**，没有暗线。

两条并发规则：

- **信号分支并发、无序**；确定性靠"谁改状态谁负责"——**同一模块实例内部方法串行**，跨实例并发。
- **调用串行**：一个调用一个接收方，等它返回。

### 3.1 脚本的两种写法，不做显式区分

脚本只有一个入口，两种进法只是"进什么参数、要不要返回值"：

```js
function main(input, ctx) {
  // 信号进法：input = 广播载荷（含 $source 谁发的），返回值被忽略
  // 调用进法：input = 调用方给的参数，返回值被采用
  // ctx = 能力句柄 + 来源 + 审计上下文
  return undefined
}
```

⚠️ 刻意**不要求**作者声明"这是 onSignal 还是 handler"——那会逼出两套模板、两套文档、两套测试。也正因为不区分，**它能同时被两种方式驱动**，这正是"接口"的含义。

## 4. 记录的形状：三个槽位，块数恒定

借 ALC 的形（`I-13`）：

| 区 | 内容 | 持久化 | 渲染位置 | 变更频率 |
|---|---|---|---|---|
| **头槽位** | **系统块**：ALN 环境（框架 + 人设 + 准则），1 块 | ❌ | 最前 | 全局重载时一起换（§10.3） |
| **时间线** | 用户消息、模型发言、工具调用与结果 | ✅（工具结果的**快照**可回收，骨架永久） | 中段 | 只追加 |
| **本轮注入块** | 浮动（时间 / 记忆 / 状态）+ 本轮新消息（`11 §5`）；**浮动不落盘，新消息照常落盘** | 浮动 ❌ / 消息 ✅ | **永久尾部** | 每步 |

推论（每条都有代价，别当口号）：

- **块数恒定**（最多各 1 块）⇒ 缓存断点位置稳定；
- **系统块里每步都变的东西不许进**（时间、用量）；它们住本轮注入块；
- **开场消息是时间线的第 0 条**：一条 user 消息，内容是「激活原因 + 目标」，写入即不变——它不占独立槽位，但排在最前；
- **状态进槽位、事件进时间线**（归位规则）：状态天然可覆盖，事件天然不可变；
- **渲染必须是纯函数**：`render(贡献, now)`，`now` 在步开始时取一次并冻结。

## 5. 工具：显式封装，不是端口的投影（★已按裁定改写）

（用户裁定：**工具显式封装**，不靠一个"暴露标记"——那太草率；真逼急了可以给一个底层接口，但**不作为主要手段**。）

我上一版写"schema 从端口签名派生 + `exposesToModel` 标记"，**这条作废**。三条理由：

1. **两边契约性质不同**：端口是机制契约（类型化、进程内、随重构变）；工具是对外产品契约（JSON schema、稳定、面向模型）。耦合起来，**任何端口重构都会改到工具表**——而工具表是最贵的操作（在请求最前端）。
2. **端口签名里没有工具需要的东西**：描述、错误语义、幂等性、渲染方式、取消语义。
3. **标记法是"默认暴露、再挑出不暴露的"**，方向反了。**默认不暴露、显式封装**才安全。

所以：

> **工具 = 一份显式定义**：`name` + 描述 + 参数 schema + **实现绑定** + 渲染器 + 副作用声明。

| 部分 | 内容 |
|---|---|
| 声明 | 名字、描述、参数 schema（可手写，也可用生成器产出但必须可读） |
| **绑定** | 指向一个**已存在**的端口方法，或一段内核内建实现 |
| 渲染 | 结果 → 记录的块（纯函数） |
| 副作用声明 | 可重演 / 不可重演（决定有无指纹、能否回收） |

**防"声明了但没实现"（`X-11` 同型）**：加载期校验绑定目标存在（端口在描述符里 / 内建 id 在内核里），**接不上即失败**。

### 5.0 工具由谁提供（★2026-11 实现）

**实现归模块，名字归 spec，绑定按轮给。**

- **模块提供实现**：`speak` 归 Channel 侧（只有它知道绑定与被回复的那条消息），`wait` 归会话循环自身，
  将来的 `send_file` 归媒体模块。每个实现只做一件事，通过 `ISessionTool` 暴露 `Name` / `EndsTurn` / `ExecuteAsync`。
- **spec 只点名**：`SessionSpec.Tools` 决定这个会话能用哪些工具，以及模型看到的描述与 schema。同一份实现能被
  任意多会话复用，spec 里没有工具就是没有工具（`wait` 例外，见下）。
- **绑定按轮给**：宿主每轮构造一个 `ISessionToolbox`（"这一轮可用的实现"），随 `RunTurnAsync` 传入。
  `speak` 绑的是"正在被回复的那条消息"，它活不过那条消息，所以**没有需要注册/注销的长生命周期工具**。
- **装配错误在花掉一个 token 之前就失败**：spec 声明了、宿主没有实现 ⇒ 这一轮直接失败并列出可用工具
  （`X-11` 同型）；实现存在但这一轮的上下文不满足（比如在没有频道事件的会话里 `speak`）⇒ 返回**模型能读的工具错误**，
  因为"这里说不了话"是可改道的，"整轮死掉"不是。

> **`wait` 是唯一的内建工具**：它不需要任何外部能力，但必须永远可用——否则一个模型想不出下一步时，
> 除了耗尽上下文没有别的出路。它不进 `spec.Tools`，也不由模块提供。

**一切皆工具，包括说话**（ALP 的裁定）：只有工具调用能到达对面；一步只产出文本、没有调用任何工具，等于什么也没说。
这样"误输出"在结构上就不存在，而不是靠提示词请求它别乱说。

**一轮的形状**（实现即此）：

| 一步 | 做什么 | 落盘 |
|---|---|---|
| 有工具调用 | 逐个执行（串行），把结果还给模型继续 | **整块一次提交**：assistant(调用) + 全部结果。半轮（有调用没结果）在盘上不可能存在 |
| 没有工具调用，且本轮有能办事的工具 | 正文进时间线（`content`），**不进对话视图**；请求里追加一句"请用工具"的提示，继续循环 | 只有 assistant 那一条 |
| 没有工具调用，且本轮没有能办事的工具 | 旧语义：正文就是回复 | 一条 |
| 某个工具 `EndsTurn` | 结束这一轮 | 该工具所属的整块提交 |

没有**步数上限**：一个回合可以跑很多轮工具，这是"干得完"的前提。唯一的刹车是"连续多次谁也没听见"
（`TextOnlyNudgeLimit`，默认 3）：那是模型在自言自语，不是在干活。

**逃生舱**：一条底层 `invoke(address, args)` 式通道可以存在（调试、极端场景），但**默认不给模型**，且走同一套权限与审计。**它是后门，不是主路。**

**会话之间的两个工具（2026-11-12，`sessions.tools` 模块）**

`sessions.list` / `sessions.message` 这两个动作各封了一个名字：`sessions_roster` 与 `sessions_message`。理由是**用的频率**——
动作表那一对（`actions_list` / `actions_call`）对"一个月用两次"的动词是对的；对"一轮可能用两次"的不是。要先查 id、再查 schema
才敢开口的动词，模型实际上就不会用：它会自己猜一个 id，或者干脆把别人的活自己做了。

| 工具 | 答什么 | 走哪条路 |
|---|---|---|
| `sessions_roster` | 先答"你是谁"：id、**objective**（它被造成什么）、服务哪个频道、被信多深、走到第几步；再答"这台机器上还有谁"，同一组事实，外加 `busy`。 | **直接问管理器**（`ISessionManager.RosterAsync`）。会话是什么，只有管理器知道；让工具自己去解析 `module.json` 就是给"会话是什么"写第二份实现。 |
| `sessions_message` | 把手里的消息交给另一个会话；`wake` 让它现在就看一眼。 | **走控制面**（`sessions.message`）：同一份处理器、同一道等级闸门、同一条审计、同一句拒绝。它是**一扇写了名字的门**，不是第二份实现。 |

两条都 `ActsExternally = false`：把消息交给另一个会话，往**这一轮**的对话里什么也没写，所以这一轮的正文仍然是它的回答。

三处细节值得记下来：

1. **`busy` 不是猜的**，是那一轮的门本身（`SemaphoreSlim.CurrentCount == 0`），所以它和"唤醒会被跳过"是同一个事实读了两遍。
2. **"忙"在工具层被翻成"已经放在它那儿了，只是没叫醒"**。管理器把这件事报成**可重试的 `Conflict`**（消息先落盘、后尝试唤醒），
   照着原样说"失败了"会教模型再发一遍——而第二份正是没人想要的那一份。
3. **名册不把自己重复列一遍**：自己那块在最前面、标着 `← you`，下面只列别人。同一份名单里出现两次"你"，那个标记就没有意义了。

### 5.1 一次工具调用的五个阶段

```
① 权限检查（域 + 拓展 + 绑定授权）   ← 拒绝即返回"错误块"，不抛异常
② 审计开始（谁 / 什么能力 / 对象 / 触发来源）
③ 绑定调用（端口调用或内建实现；可能在子进程；超时与取消在这里）
④ 结果规范化（引用 + 快照 + 指纹；不可重演类冻结形态）
⑤ 渲染成块（纯函数）
```

**四条硬约束**：

1. **工具绝不抛异常**：一切错误转成"错误结果块"。否则一个坏工具能把推进器打崩。
2. **同一会话内工具串行执行**（v0）：顺序可预测、审计顺序清晰。并行只留给"显式声明无副作用"的工具。
3. **取消必须真的传下去**：每个工具都要响应取消，在飞的外部调用要被真正中断——否则"停止"只是改了状态。
4. **脚本不能动态注册工具**：脚本提供的工具必须进装配（显式登记）。否则工具表在运行期漂移，而它是最贵的操作。

### 5.2 两级超时：同步等待窗口 + 异步硬超时（★本轮新定）

（用户裁定：**所有工具都有同步等待时间和异步超时时间**。例如 `speak` 同步最多等 5 秒；超时就**直接承认超时、转入异步等待**，模型继续循环；异步超时则**强行掐掉**。）

```text
工具调用（落盘：一条事件 = 调用 + 结果，两面同体；构建请求时才拆成
          tool_use 块 + tool_result 块 —— 同 ALC）
  ├─ 同步窗口内完成        → 结果落在同一条事件里，模型看到确定结果
  ├─ 同步窗口超时          → 这条事件的结果字段写「已超时，转入异步」
  │                          模型继续循环（不被阻塞）；该调用转为后台在飞
  │     ├─ 异步期间完成    → 通过**占位工具**（系统通知类）单独起一次调用投递结果
  │     └─ 异步硬超时      → 强行取消；同样经该占位工具投递「已取消」
```

四条硬约束：

1. **同步超时必须"承认"，不能装作还在跑**。那条事件的结果字段要明说"超时、已转异步"，否则模型以为自己没拿到结果而重复调用。
2. **配对是结构性的，不需要占位块**。落盘时调用与结果是**同一条事件的两面**（`I-14`），只在**构建请求**时才拆成 `tool_use` + `tool_result` 两块。⇒ 不存在"悬空必须靠补一条合成结果来占位"这种事——那是把协议形态误当成存储形态。
3. **异步结果经占位工具投递，不回头改原事件**。做法与 ALC 一致：起一个专门的占位工具，把异步结果作为**它的一次完整调用**送进时间线。模型看到的是"（某工具）：上次那个调用的结果是……"，而不是一条被悄悄改写的结果。

### 5.3 占位工具是**普通工具**，不是一个特殊入口

**名字：`pending`**（用户已定）

理由三条：

1. **双向语义都成立**：系统推入的一次调用 = "某件在飞的事有结局了"；模型主动调一次 = "现在还有什么在飞"。两者都是"未结算"，一个词覆盖得住。
2. **短且无既有联想**：它在工具表最前端（`§5` 说的最贵操作），名字要短；`pending` 是模型熟悉的普通词，不会被误当成某种特殊协议入口。
3. **刻意不叫 `receipt` / `result`**：它的 payload 不止"回执"——还包括工具异步结局、"已取消"、"未确认"。叫 receipt 会让模型以为只有发送才有它。

⚠️ **名字是工具表的一部分，随工具集进版本**：改名的代价是目标会话的前缀缓存失效（`I-13`），所以要在写第一行代码前定下来。

（用户裁定：**占位工具作为普通工具出现**，防止模型觉得自己在调用一个不存在的工具；同时给它一个"主动调用也有意义"的行为。）

它和别的工具一样出现在工具表里、一样有描述与 schema，**不是内核隐藏机制**。这样处理有两层好处：

| 好处 | 说明 |
|---|---|
| **模型的世界里它有实体** | 异步结果总来自一个**表里存在的**工具 ⇒ 模型不会觉得"这个结果凭空出现、那个名字我没见过" |
| **不需要"隐身通道"** | 不必在渲染层伪造来源；系统投递与模型调用走同一个工具身份 |

**防滥用**：模型可能莫名其妙去调它。所以**模型主动调用时也要给出有意义的结果**——返回当前正在跑的异步任务清单（以及它们已运行多久、由哪次调用发起）。

⇒ 同一个工具因此有两种进入方式，语义互补：

```
系统推入的调用  → payload 是某次异步调用的结果（完成 / 已取消）
模型主动调用    → payload 是"当前有哪些异步任务在飞"的状态快照
```

⚠️ **两者的结果形状要一致**（同一套块结构），否则模型要学两套读法；差异只在内容：一个是"某件事的结局"，一个是"现在有什么在跑"。

⚠️ **它仍然是工具表里的一个位置**，而工具表在请求最前端（最贵的操作）⇒ 它随工具集一起进版本，不能运行时开关（`I-13`/§5 的代价一致）。
4. **异步硬超时是取消，不是失败**：要真的中断在飞工作（`OnCancel` 语义），并同样经占位工具投递「已取消」；否则后台会一直堆积。

⚠️ **异步不划算就不转**：若某工具的 `asyncDeadline <= syncWait`，说明"转异步"并不能换来更长的等待，**完全不进入异步路径**——同步窗口到点即按失败/超时结案。这条让"异步"只出现在真的能等更久的场景，避免为同一个时限维护两条路径。

**两个时间都是工具声明的一部分**（`syncWait` / `asyncDeadline`），不是内核一刀切：

| 时间 | 语义 | 由谁定 |
|---|---|---|
| `syncWait` | 模型愿意"卡在这一步"等多久 | 工具声明（可被会话上限收窄） |
| `asyncDeadline` | 转异步后最多活多久，到点强杀 | 工具声明（可被会话上限收窄） |

⚠️ **为什么必须让模型继续而不是干等**：一次 `speak` 卡住 30 秒，整个会话就停 30 秒；模型本可以在等待期间做别的。这正是"同步窗口要短、异步兜底要硬"的理由。

⚠️ **重复调用的诱因要正视**：模型看到"超时、已转异步"后很可能再调一次同一工具。所以工具必须声明**是否幂等**：不幂等的（发消息、发邮件）在转异步后应拒绝同一逻辑操作的第二次发起，或标为"疑似重复"交给模型判断——不能默默执行两遍。

⚠️ **这与 `§6` 的 `wait` 是两件事**：`wait` 是整个会话休眠；同步窗口是**单次工具调用**内核等多久。前者改状态，后者只影响这一步怎么结束。

### 5.4 预算属于谁：脚本的预算是脚本的（★2026-11-16 按裁定改正）

**裁定原话**：「脚本只管脚本吧，按理说会话激活本身就是终结指令了，毕竟会话运行是内部问题。」

原先 `ctx.session.activate(spec)` 在脚本 handler 里 `await` 整轮 turn（`GraphManager.ActivateSessionCoreAsync`），
于是**脚本 manifest 的 `timeoutMilliseconds` 变成了这一轮的寿命**——而它上限只有 60 秒（`GraphManager.cs:544`
校验 `1..60000`），`channel.chat` 里写的正是 `60000`。后果在部署里量到了：一轮做实事（14 次模型调用 + 5 次 `ssh`
执行）跑到 60.00 秒时被死线掐断，模型那次请求被 `cancelled`，回执一条都没发出去，会话休眠且没有自己的截止时间——
从外面看就是"莫名其妙停下了"。11-13 一天 7 次，11-16 两次。

现在的形状：

```text
脚本 handler（有预算：manifest.timeoutMilliseconds，≤60s）
  └─ ctx.session.activate(spec)
        ├─ 同步做完的：能力检查、事件与绑定核对、spec 校验、取/建那个 Session、审计 allowed
        └─ 把 turn 交出去，立刻返回 {ok:true, accepted:true, session:"s-…"}
                │
                └─ 宿主时间里跑（token = 事件泵的，**不是** handler 的）
                     ├─ 跑完 → 审计 completed/failed + 信号 session/activate
                     ├─ 被取消（宿主在关）→ 审计 cancelled
                     └─ 会话正忙 → 跳过（照 §6.2 的老规矩：不排队），原因进记录
```

四条规则：

1. **等到结果的那几个动词仍然受脚本预算约束**：`session.run` 的契约就是"跑一轮并拿回结果"，
   `session.message` / `session.open` 带 `wake` 时也是把这一轮的结果（`step` / `text`）带回来。**"我要结果"意味着"我的预算管着它"**，
   这是同一件事的两面，不是遗漏。
2. **交接之后只有记录作证**：没人 `await` 那个 turn，所以结束（完成/失败/取消/被跳过）必须写审计 + 一条
   `session / activate` 信号——包括"为什么"。这是"没有调用方"的代价，也是它唯一的替代品。
3. **取消的语义反过来了**：以前"handler 超时" → "turn 被砍"；现在 handler 超时只说明这个脚本超了预算，
   turn 用的是事件泵的 token，只在**宿主真的要走**时被取消，并且诚实地记成 `cancelled`。
4. **关机要等它**：`IGraphRuntime.WhenTurnsSettleAsync()` 让宿主在卸包之前最多等 10 秒，超时才取消——
   否则一次卸载会把一句只说了一半的话留在频道里。

## 6. 循环怎么结束：`wait`、急停与恢复（★已按裁定改正）

**没有 goal / iterate 轴。结束靠 `wait`；急停靠每个模块自带的响应方法；内核不设任何上限。**

### 6.1 `wait`：结束这一轮，不是结束工作

参数以 `SessionManager.WaitTool` 为准：

| 参数 | 语义 |
|---|---|
| `timeout` | 从现在起多少秒后叫醒自己（1..604800） |
| `at` + `timeZone` | 「下一个几点几分」——24 小时内最近的那一次；**`timeZone` 必填** |
| `until` | 绝对时刻（ISO-8601）。带偏移（`+08:00` / `Z`）就自足；不带偏移则必须给 `timeZone` |
| `release` | 配合任意一种截止时间：到点没人说话就归档（任何来消息都会取消它） |

三个时间参数互斥；全都省略 = "只等有人说话，没有自己的截止时间"。sweep 每 30 秒看一次，所以 `at`/`until` 的落点有最多 30 秒的滞后——这是刻意的，见 `SessionDeadlineHandler.Interval` 的注释。

**时区没有默认值**。`at` 缺 `timeZone` 直接拒绝，`until` 缺偏移又没给 `timeZone` 同样拒绝：不说哪个时区的「8 点」不是一个时间，猜出来的结果是"半夜被叫醒"而没人能解释。拒绝话术是写给模型看的——说清缺什么、怎么补，别让它去猜。

**提示词和唤醒便条都改过（2026-11-07）**。旧描述是"没有更多可说可做就调它"，配上唤醒便条的"没话可说可以继续等"，实机上的效果是模型把 `wait` 当收工按钮：被叫醒了、什么都没做、又睡回去。现在工具描述先给三条前置判据（对方问的答了没有、能自己查的查了没有、剩下的确实在等外部），唤醒便条则明说"被叫醒意味着该看一眼，而不是再睡一次"。`wait` 仍然是**唯一**结束回合的方式，这一点没变。

与 §1 两个状态的关系：`wait` 都把会话从 `Running` 放到 `Dormant{ notBefore }`，到点由 sweep 唤醒（`ActivationReason.DeadlineDue`）。

### 6.1.1 会话有两种"自己醒"，别混

| 谁要求的 | 机制 | 便条说的是 |
|---|---|---|
| **会话自己**（`wait` 里的截止时间） | `state.waitUntil` + 30 秒 sweep | "你自己在 … 声明的等待到期了" |
| **别人写下的规则**（`schedules.set` 的 `target: session`） | `state/schedules/rows` + 同一个 30 秒 sweep，`ActivationReason.ScheduleDue` | "一条定时规则（sch-…）在 … 到点了" |

**便条里带什么**：`wait` 那条只说自己声明过；规则那条带着行 id、到点时刻，以及当初写规则时的备注（`payload`）——"sch-4f2a"本身不是理由，让人去看一眼数据库再回来问"我为什么醒了"是白花一轮。备注明确标注为人写的备注，不是有人在说话。

两者都是"没有任何人说话"，也都是自己起来的一轮，但**承诺的来源不同**：一个是"我这轮之后还想看一眼"，一个是"有人安排了这个系统在没人的时候动"。便条必须说清是哪一种，否则模型会替对方编一句话出来。规则本身（语法、错过、时区）在 [`26`](26-定时与节奏.md)。

### 6.2 内核不设任何硬上限（★已按裁定改正）

我上一版写"兜底仍在内核：必须有最长存活 / 最大轮次 / 最大步数"，**这条作废**。

**限制全部交给脚本与会话策略，内核不判上限。** 理由就是机制/策略分离（`I-16`）：上限是**策略**，不同场景能差三个数量级；写进内核等于让内核记住一份它不该有的知识。

⚠️ 但这条必须配一个补偿，否则"软着陆"会变成"永不落地"——补偿不是上限，是下面这个。

### 6.3 急停：一颗按钮，不分段

（用户裁定：**急停就是急停**——紧急的时候立马拍下去的大红按钮；**要分段说明还不够紧急**，那该用别的机制去做。）

所以急停只有**一个动作**，没有阶段：

```
emergencyStop()      ← 一次广播，所有模块立刻执行
```

| 维度 | 规定 |
|---|---|
| 语义 | **立刻停**：不再产生新动作、不再推进、不再派发 |
| 每个模块做什么 | 自己实现 `OnEmergencyStop(deadline)`：**只要"停到最安全"，不要求"收拾干净"** |
| **允许破坏** | ✅ **明确接受**：停得快必然留尾巴（store 一旦停，adapter 的入站可能无处可放） |
| 超时 | 有 deadline；不响应的记为"未响应"，之后不再给它派活 |
| 幂等 / 不抛异常 | 同前 |
| 持久化 | 落在 `state` 里（重启仍是急停态） |
| 谁都能锁 / 只有人能解 | 不变 |
| 不走订阅表 | 不变（装配坏了也得停得下来） |
| 审计豁免 | 不变 |

⚠️ **"允许破坏"是这条设计的核心**：分段的代价是**慢**，而急停的全部价值在**快**。尾巴交给恢复去收——下一个。

### 6.4 恢复：`OnResume`，与急停对称

（用户指出：急停有破坏性——存储停了，适配器可能写不进去，得自己暂存；**恢复之后要把自己的暂存补交回存储**。）

```
resume()   ← 只有人能触发（与 unlock 分开：解锁只是"允许"，resume 是"真的恢复"）
```

每个模块提供 `OnResume(deadline)`，语义是**"把急停期间欠下的账还上"**：

| 模块 | 典型的还账动作 |
|---|---|
| adapter | 把急停期间积压的入站暂存**补交**；重建出站连接 |
| channel | 把缓存里没整理的补整理；游标对齐 |
| store | 重新打开写通道；接受补交的批次 |
| session | 把"停在半步"的会话标成可续，或按自己的策略丢弃 |

三条规定：

1. **顺序与急停相反（内→外）**：先让 store 能写，再让 adapter 补交——否则补交的批次无处落地。
2. **`OnResume` 也是必需成员**，与 `OnEmergencyStop` 同等。只做急停、不做恢复的模块，等于把尾巴永久留在系统里。
3. **恢复失败不自动重试到死**：如实上报（审计 + 状态），由人决定是否再试。**最保守：宁可留着欠账，也不要假装还清。**

⇒ 由此得到一组**对称契约**：`OnEmergencyStop` / `OnResume`——都是必需成员、都有 deadline、都幂等、都不抛异常（写进 [`01` §3.1](01-模块切分.md)）。

### 6.5 会话属性

| 属性 | 含义 |
|---|---|
| `objective`（**必填**） | 业务目标。做完按 §6.1 的 `wait(…, true)` 收摊。<br>**为什么必填**：一个会话若没有目标，它自己也不知道该干什么——"纯聊天"也要写成目标（如"陪这个人聊到他说停"）。它同时是开场消息（§10.2）的核心内容 |
| `continuation` | `until-done`（能跑就一直跑到没活）/ `one-step`（一步一激活） |
| `level` | 这个会话被信多深：`agent`（默认）/ `operator` / `full`。决定它能调哪些动作、能看见哪些工具、它写的脚本上限多深。<br>**运行中可以改，下一轮就生效**（`sessions.setLevel`），因为它是一份数据而不是一次装配；而**接口**的等级在代码里，改它要重新编译（脚本侧要重挂载）——这两件事刻意不对称，见 [`07` §9](07-域与权限分级.md) |
| `toolPolicy` | 等级之下的进一步收窄：`only`（这轮只要这几个）/ `deny`（永远别给这个）。<br>等级是天花板，策略是"天花板之下我还要更少"；不写 = 天花板允许的全给 |
| `modelProfile` | 这个会话用哪个模型档案。<br>**运行中可以换，turn 边界生效**（`sessions.rebind {id, profile}`）：模型每一步都按档案 id 查表，所以不需要重建会话、不丢历史。正在跑的那一轮会被拒绝而不是被抢——它是在旧档案下装配的，半途换会让同一轮的两个请求去了两个模型 |

⚠️ **等级只减不增**：没人能把自己升上去。给会话定级的动作本身受"只能授出 ≤ 自己"约束，而"改等级表"这个动作**不存在**。

```
继续 ⟸ 有未回传的工具结果 ∨ 队列有新事件 ∨ (until-done ∧ 策略未触限)
停   ⟸ wait(…, true) 到点未被激活 ∨ 显式 stop ∨ 锁定
```

⚠️ **`objective` 不决定"何时停"**，只决定"该做成什么"。停止的唯一入口是 `wait` / 显式 stop / 锁定——只有一条路，不并存两套判定。

## 7. 长了怎么办：加载边界 + 回收

三件不同的事，按代价从低到高，**顺序不能颠倒**：

| 手段 | 代价 | 丢什么 | 什么时候用 |
|---|---|---|---|
| **折叠**（`SessionReplay`） | 零（装配期渲染） | 没有：只把"有副本的东西"缩成提纲 | 每一轮，超出"最近 5 次激活"的旧工具往返 |
| **检查点**（`SessionCompaction`） | 一次模型调用 | 细节，永久 | 折叠之后**仍然**放不下时 |
| **回收**（`release` 一类） | 零 | 字节与知识一起，但由人/模型声明边界 | 任务边界 |

- **折叠不是压缩**：折叠只改"这一次请求带多少"，记录一个字不动，下一轮可以多带；被折的是"有副本的东西"——工具结果可以再取一次，写文件的正文就在那个文件里。模型留下的是提纲（哪个工具、哪个路径、多大），丢掉的是载荷。**工具调用与它的结果成对折**：只带一半的请求会被 provider 直接拒。
- **压缩 = 检查点**：摘要写进**一条时间线记录**（`role: system`，`coversUpTo` 指向它代表的最后一条），之后**只从最近的检查点开始装配**；记录一条不删（ALP 的"新会话接管"作废：`X` 台账里已有"会话轮替"作废项）。块数不变 —— 检查点不是新的一块，它只是时间线的第一条（`I-13`）。
- **为什么是检查点而不是滑动窗口**：请求逐字节喂给上游，缓存只认前缀（`I-10`）。滑动窗口每轮改前缀，等于每轮丢掉缓存；检查点是"走一段、跳一次"，全价只在跳的时候付一次。真实部署里那次 81k tokens 的请求，80.7k 是缓存读 —— 把钱省在"少带历史"上、再在"每轮全部失效"上花掉，可能净亏。
- **触发**：折叠之后估算仍超过窗口的 55% 才压；压的时候**最近 4 次激活不进摘要**（当前这一轮永远在最近里）。摘要只保三样：**已承诺 / 已做过 / 还悬着**，上限 2k 字，超了从中间砍（结尾那节是别处推不出来的）。再压时对上一份摘要只写一句"承上"，不重述。
- **一轮之内也有闸**：折叠管的是"开局带多少"，管不了一轮里工具结果往上堆。所以窗口 85% 以上**拒绝执行**（不是静默截断）非 `wait` 的调用，并把原因说给模型听 —— 唯一能结束这一轮的是它自己。
- **模型看得见余量**：浮动里一行"这一轮大约已用 X / 上限 Y（估算）"，70% 以上改成建议；`compact` 是每个会话都有的工具（与 `wait` 并列），由模型判断"这件旧事办完了、细节不再需要"。工具表恒定，不随需要出现又消失 —— 那会动前缀。
- **回收 = 失效窗口统一收尸**：前缀失效 / 主动压缩 / 资源释放 / 激活 都是触发源。
- **`release` = 作用域化的 `compact`**：任务边界上"保留知识、扔掉字节"，且它是**事件触发**的 GC，不是主动请求。
- **派生物单独有保留期**：`artifacts/model-calls` 每份都是整份请求，是盘上最大的一块（实测一天 42 MB），删了不损失任何事实。按天保留 7 天，定时清，只清这一类 —— 会话、归档、记忆是记录，记录不动。

## 8. 子会话

- **调度器不认识父子**：子会话不比别的优先，也不比它低——调度只看"谁可推进"。
- 派生树只出现在四处：注入地址、声明天花板、**权限收窄**（子不能比父宽）、树级并发配额。
- **父停 → 子停止推进，但记录还在**，可重新唤醒（因为会话是数据）。

## 9. 崩溃与失败

| 场景 | 行为 |
|---|---|
| 进程崩在步中途 | ⑦ 之前的东西一律不留；重启后该会话可续（读 `state` + `history`） |
| 某次订阅失败 | 该步失败；**不重试工具副作用**（副作用可能已发生） |
| 模型调用失败 | 唯一重试点在这里：瞬态错误重试（指数退避 + 抖动），非瞬态直接失败 |
| 用户中断 | 取消原样冒出去，**不算失败**；在飞工具收到取消钩子 |

⚠️ 一条铁律：**重试只发生在"还没执行任何工具"的那一段**。工具跑过再重跑 = 副作用跑两遍。

### 9.1 一条模型步的重试，现在已经这么实现

重试的单位是**一步**（`SessionManager.RunModelStepWithRetriesAsync`），不是一轮：一轮里已经提交过的工具往返不会被重跑，而一步的失败点都在"动手之前"。具体：

| 问题 | 答案 |
|---|---|
| 重试几次 | 首次 + 最多 **5** 次（`ModelRetries`），一次不难，五次够用——上游 429/5xx/断流这类抖动都在这段时间里过去 |
| 等多久 | 0.5 s 起，每次翻倍，封顶 **8 s**，再叠 0–250 ms 抖动（几百个会话同时被同一阵抖动叫醒时，不该一起再打一遍） |
| 什么算"可取" | **看供应商给的 `Error.Retryable`**：OpenAI Chat 把 429 / ≥500 / 传输异常标为可取，4xx（422 之类）标为不可取。Session 不再自己按 `ErrorCode` 重新猜一遍——猜错的方向两头都坏：把 4xx 重试六次是白等，把断流当致命是一次可恢复的抖动变成一轮白跑 |
| 谁决定"这轮没救" | 5 次用完仍然失败 → 这一轮按失败结束，像以前一样（信号、审计、`Result.Failure`）；**没变的还有一条**：`ClaimDeltaAsync` 的提交仍未执行，消息留给下一轮 |
| 期间模型看到什么 | 每一次失败在下一次尝试的请求里留一条 `（系统）上一次请求没有成功（第 n 次；最多还会再试 m 次）：<错误>（<细节>）` 的 user 注记。它明说"这不是谁在对你说话，也不是说这件事做不成了"，并告诉模型可以换做法 |
| 这条注记落盘吗 | **不落盘**。一次失败的尝试什么都没发生，把它写进 history 等于给时间线塞一句没人说过的话 |
| 留痕 | 每次失败的尝试一条 `model.request` 信号（`outcome: failed`），每次重试一条 `model.retry` 信号（含 attempt / of / error / delayMs） |
| 例外：模型调了这轮没给它的工具 | 也算**可取**（标 `Retryable`），因为这是模型唯一能自己改的错，而注记里会列出这一轮真正给了哪些工具。原来这里是直接判死一轮——等于把唯一有能力修的人赶走 |
| 例外：取消 | 不重试。取消是有人故意的，不是失败 |

## 10. 上下文注入：归 session，且系统提示词只请求一次（★已按裁定改写）

（用户裁定：**上下文注入是 session 模块的行为**；每轮这类时间点会要求各模块检查要不要提供提示词；**系统提示词一般只有最开始请求一次**——所以"破坏缓存"是 session 自己的行为，**合理且可控**。）

### 10.1 收集者是 session，不是内核

```
步 ③ ──call──▶ session.build-prompt
                  ├─ 逐个问装配表里登记的贡献者：这一轮你要不要提供片段？
                  ├─ 按槽位归并（同名字段归并、位置稳定、带来源）
                  └─ render(贡献集合, now)   ← 纯函数，逐字节可复现
```

- **谁问**：session 自己问——它是"上下文的所有者"；
- **问谁**：装配表里登记的贡献者（`call` 边，可见、可校验、加载期校验存在）；
- **问什么**：只问"这一轮要不要提供"，不问"你是什么"。

⚠️ 这同时解释了**为什么渲染该由模块做而不是内核**：只有 session 知道记录槽位、贡献者名单、以及这一步该不该注入。让内核替它算，等于把会话的知识搬进内核（违背 `I-16`）。

### 10.2 两档，不是三个时间尺度

| 内容 | 什么时候算 | 之后 |
|---|---|---|
| **系统块** | **全局重载时一次，所有会话共用** | 全局快照；重载一次，全部会话下次请求一起换（§10.3） |
| **首要提示词** | 会话创建时一次 | 写成**会话的第一条 user 消息**（激活原因 + 目标），写入即不变 |
| **时间线** | 步落盘时 | 只追加 |
| **浮动（尾）** | **每步都问** | 不持久化，每步替换 |

（用户裁定：**系统和首要分两块**，但**不是为了缓存**。）

两块各自装什么：

| 槽 | 角色 | 内容 |
|---|---|---|
| **系统块** | `system` | **ALN 自己的环境**：框架结构（有哪些模块/工具/规则）、人设、行为准则 |
| **首要提示词** | `user`（第一条消息） | **会话的激活原因 + 目标**——每个会话都因为一个目标而产生 |

⚠️ **首要提示词是 user 消息，不是第二段 system 提示**：它是会话的"开场正式发言"，也是记录里时间线的第 0 条。因此：

- 记录以 `user` 开头（多数 provider 的硬要求），**不需要额外的空占位**；
- 它天然"只追加"——写进去以后不动，与时间线共用同一条不变量；
- **块数恒定**仍然成立：`[system] [user#0] [时间线…] [浮动]`。

⚠️ **系统块是快照，不是"每步现算"**：它由全局快照提供，重载时统一换（§10.3）。不搞"每会话一份冻结副本 + 单会话重建"——那会让"改人设"变成逐个会话操作，而这恰恰是最需要一次改完的事（用户裁定：**功能需求远大于那点缓存损失**）。



### 10.3 全局重载：系统提示词是快照，但可以换

（用户裁定：**系统提示词要可变**——虽然与缓存冲突，但这是非常偶尔的事，可以接受；**功能需求远大于这点损失**，尤其需要紧急修人设、安全边界的时候。**依然使用全局快照，框架重载全局系统提示词的时候会一并更新。**）

```text
全局系统提示词源（文件 / 装配数据）
  → 渲染成字节 + 算指纹
  → 原子替换全局快照
  → 所有会话的下一次请求使用新快照
```

控制面接口（`10 §5.5`）：

```csharp
ValueTask<Result<ReloadResult>> ReloadSystemPromptAsync(string reason, CancellationToken ct);

public sealed record ReloadResult(
    string OldFingerprint,
    string NewFingerprint,
    bool   NoOp,               // 指纹相同 ⇒ 什么都没发生
    int    AffectedSessions);
```

三条约束：

1. **只有控制面能触发**：模型与脚本都不能改系统提示词（自举三样禁区之一，`05`）。
2. **原子替换**：新快照要么全生效、要么不生效；生成失败保留旧快照（`C11` 显式生效）。
3. **指纹相同即 no-op**：内容没变的重载不留变更记录、不制造冷窗口。

**代价如实记**：这是一次**全局冷窗口**——所有会话的下一次请求都不再匹配旧前缀。它之所以可接受，正是因为"非常偶尔"：改人设、改安全边界这种事本来就不该天天发生。

⚠️ **不再提供单会话 `rebuild-header`**：上一版设计的"恰好一个会话 + 二次确认 + 逐会话执行"听起来更安全，但它与"全局快照"直接冲突——既然系统块是全局的，就不存在"只换一个会话的头"这回事。留两个入口只会让人误以为单会话重建有效果。

⚠️ **不能声称"清空了供应商缓存"**：客户端删不掉远端缓存；头变了只是新请求不再匹配旧前缀，旧缓存由供应商按自己的策略过期。

### 10.3.1 ALC 的缓存行为核对（结论仍有效）

> 核查范围：ALC 当前工作树源码（非干净树；相关文件存在未提交修改）。这里只读检查，未运行测试。证据路径为仓库相对路径。

| ALC 当前做法 | 代码证据 | 对 ALN 的约束 |
|---|---|---|
| **头不是会话快照**：`Stepper.StepAsync` 每步读取 `PresetStore`、收集插件提示词，再调用 `SystemBlock.Render` | `src/Lilara.Core/Session/Stepper.cs:152-183`；`SystemBlock.Render` 每次 `Load` 两个提示词文件：`src/Lilara.Core/Session/SystemBlock.cs:164-174` | ALC 改一个共享预设文件，会影响**所有引用该 preset 的会话**下一次渲染；ALN 必须保留每会话快照，普通文件改动不能波及运行中会话 |

| **`requestFingerprint` 是诊断记录，不是失效器**：只哈希三槽位 + 工具表，写进 usage 账本 | 计算：`src/Lilara.Core/Session/Stepper.cs:761-770`；记录位置：同文件 `:313`；测试验证稳定头指纹：`tests/Lilara.Core.Tests/CacheStableTests.cs:253-276` | ALN 用它展示冷启动前后头指纹、审计，不得把“指纹变化”误称为已清理供应商缓存 |
| **当前没有 Responses 应用层续链**：每次从本地时间线全量构造 `input`，不发送 `previous_response_id` | `src/Lilara.Core/Protocol/OpenAi/OpenAiResponsesRequest.cs:10-24,72-81,93-95`；源码明确写“不用 `previous_response_id`” | 无需清除应用层 response chain。头部变化后，从首个变化字节起的新请求后缀不匹配；之前的共同前缀仍可能命中，远端旧缓存由供应商 TTL 回收 |
| **缓存测试证明的是“没变就逐字节稳定”**，没有测试“头重建命令如何让缓存失效” | `tests/Lilara.Core.Tests/CacheStableTests.cs:182-275` | ALN 需单独补验收：同一会话重建头 ⇒ 指纹变化、历史逐字节不变、只该会话的新请求前缀变化；其他会话指纹与请求字节不变 |

**ALC 的实际风险**：`preset.set` 是全局改文件，不是会话级动作；共享同一 preset 的会话会在各自下一步同时带上新头，供应商前缀缓存因此对这一组会话全部冷启动。这是“提示词共享引用 + 每步读取”的自然后果，不是某个缓存清理函数把全设备清空。

⚠️ **这是代码结构与前缀缓存规则推导出的影响范围，不是本轮实测的供应商命中率**：未向真实端点发请求，不能断言每个 provider 会损失多少缓存 token。端点策略、缓存断点和共同前缀位置会影响实际成本。

**ALN 的防线**：

1. 系统提示词是**全局快照**：重载一次，所有会话下次请求用新的（§10.2 / §10.3）。
2. 不做单会话头重建；也不把"改一个源文件"当生效——**必须显式重载**。
3. 重载只改系统块；**不改历史、不重跑工具、不动开场消息**。
4. 若将来的协议适配器维护本地"续链"状态，契约必须有**按 sessionId 丢弃单链**的能力。
5. 供应商端缓存无法由客户端精准删除；对外只说"这些会话的下一次请求将按新前缀重新建立命中"，不能说"已清空缓存"。

**结论**：ALC 的病是"每步重读文件"——等于每次请求都可能换头，且范围不可控。ALN 改的是**入口**：只在显式重载时换，一次换全部，指纹没变就是 no-op。

### 10.4 三条推论

系统提示词的生成与注入由会话模型管理，**换掉的时机**只有一个入口：用户显式重载（§10.3）。三条推论：

1. **浮动每步变 = 每步全价**（`I-13` 已记）：已知成本，不是缺陷；
2. **系统块全局共享**：它不随会话变化，所以不存在"这个会话的系统块和那个会话的不一样"；
3. **全局重载 = 一次全局冷窗口**：代价一次性、全局、可见、可审计——因为"非常偶尔"，这个交换划算。

⇒ **系统提示词重载与普通脚本热重载是两件事**：后者改逻辑与订阅表，前者改所有会话共用的同一块前提。

### 10.5 收集点与钩子

| 收集点 | 时机 | 贡献到 |
|---|---|---|
| `OnSessionStart` | 会话创建（**唯一一次**） | 系统块 + 开场消息（原因 + 目标） |
| `OnCollectPrompt` | **只在全局重载时** | 系统块——⚠️ **不是每步问**（`11 §2`） |
| `OnCollectTail` | 每轮 | 本轮注入块的字段（仍在末尾） |
| `OnCollectTimeline` | 步开始 | 时间线（事件型追加，带来源） |
| `OnBeforeModelCall` | 调模型前 | 本次请求参数（不落盘、审计） |
| `OnModelDelta` | 流中 | 只读观察（UI / 统计 / 静默超时监控） |
| `OnAfterToolCall` / `OnStepEnd` | 工具后 / 步后 | 观察 + 写 inbox |
| `OnSessionEnd` | 结束 / 释放 | 归档、清理外部资源 |

⚠️ 运行中"临时想插入"的内容，先写各自 inbox，在下一个收集点被取走——**收集在边界、暂存在途中**，见 §10.5 约束 1。

| 钩子 | 何时 | 能做什么 | 归到哪 |
|---|---|---|---|
| `OnSessionStart` | 会话创建 | 建初始状态 | 头（一次性） |
| `OnCollectPrompt` | pre-render | 贡献首要提示词片段 | 头（拼成 1 块） |
| `OnCollectTail` | pre-render | 贡献浮动字段（态势 / 模式 / 提醒 / 插件贡献） | 尾（字段集） |
| `OnCollectTimeline` | step-start | 把 inbox 里的事件变成时间线事件 | 时间线（追加） |
| `OnBeforeModelCall` | ④ 之前 | 改**本次**请求参数（不落盘、必须审计） | — |
| `OnModelDelta` | 流中 | **只读观察**增量（UI / 统计 / 静默超时监控） | 不进记录 |
| `OnAfterToolCall` | ⑤ 之后 | 观察结果、触发后续、写 inbox | 时间线或 inbox |
| `OnStepEnd` | ⑦ 之后 | 观察本步结果 | inbox |
| `OnSessionEnd` | 结束 / 释放 | 归档、清理外部资源 | — |
| `OnEmergencyStop` / `OnResume` | 急停 / 恢复 | 已定，见 §6.3 / §6.4 | — |

### 10.6 五条约束

1. **钩子只提供"渲染的输入"，不实现渲染。** `OnCollectTail` 看起来像"挂到渲染"，但它产出的是**数据**；渲染仍是内核的纯函数 `render(贡献集合, now)`。这条区分不成立，§10.1 就被绕过去了。
2. **贡献必须声明槽位**，不能"你自己找地方放"。槽位决定持久化与成本（`I-13`），**选槽位就是选生命周期**。
3. **贡献必须带来源**（谁贡献的），渲染时可按模式 / 预设裁剪——没有来源就没法裁剪。
4. **顺序是纯函数** `(priority, id)`，不依赖注册顺序（同 §3 的订阅规则）。
5. **钩子不许“否决”这一步**：只允许贡献与观察。需要“叫停”的场景走急停或权限轴——否则一个慢钩子或坏钩子能卡死整条链。
6. **`OnCollectPrompt` 是纯、只读贡献者**：只基于显式输入快照返回提示词片段，不写状态、不触发信号、不执行副作用。全局重载可以安全地重跑它；通用 `OnSessionStart` 不重跑。

### 10.7 与"禁区"的关系

| 位置 | 能挂钩吗 | 为什么 |
|---|---|---|
| 渲染**实现** | ❌ | 渲染必须纯 |
| 渲染**输入**（`OnCollect*`） | ✅ | 提供数据，不执行渲染 |
| 请求参数（④ 之前） | ✅（不落盘、审计） | 改"这次怎么发"，不改"记录长什么样" |
| 工具执行前后（⑤） | ✅ | 最自然的钩子点（字段映射、统计、补充条件） |
| 落盘（⑦） | ❌ | 原子边界，不让脚本参与 |
| 判定（⑨）/ 急停顺序 | ❌ | 内核预设 |

⇒ 一句话：**脚本能改"怎么算、怎么发"，不能改"记录长什么样、什么时候停"。**
