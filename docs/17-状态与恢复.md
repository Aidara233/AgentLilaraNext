# 17 · 状态与恢复（重启前后必须是一样的）

> 最后更新：`25499d7`
>
> 这是一篇**现状**文档：代码在，可对照。设计层面的"该不该这样分层"见
> [`01`](01-模块切分.md) 与 [`02`](02-图模块.md)；这里只回答一个问题：
> **进程被关掉（或被强杀）再来一次，什么东西必须还在，由谁负责让它还在。**

---

## 1. 一条原则

> **状态归产生它的组件，路径归宿主；改了就写，不等退出。**

三个推论，都写进了代码：

1. 组件不拼路径，只给"我要一个作用域（scope）和一个键（key）"，落盘位置由宿主决定（`IStateStore`）。
2. **不靠"退出时保存"**。退出时保存等于"被强杀就丢"，而强杀是被杀毒、断电、任务管理器最常见的样子。所有状态都在**变化的那一刻**写。
3. 因此**没有 flush 协议**，也暂时不需要：没有缓冲着的状态，就没有要冲的东西。等第一批高频状态（journal）出现，再加 `IFlushableState` 与关闭阶段的 flush 阶段——那时它才有参与者。

---

## 2. 三样东西，存两处

| | 谁写 | 在哪 | 语义 |
|---|---|---|---|
| **spec / 意图** | 人 | `adapters/` `channels/` `models/` `api/` `scripts/` 下的文件 | 精确恢复；缺了就是缺了 |
| **state / 记忆** | 程序 | `aln.db` 的 `state(scope, key, value)` 表 | 尽力恢复；坏了降级并**说出来** |
| **data / 流水** | 程序追加 | `aln.db` 的 `message` / `audit` / `queued_message` 表；`sessions/` `artifacts/` `logs/` 仍是文件 | 崩溃最多丢末尾一条未提交的记录 |

判据：**人能手动编辑的进文件，只有程序知道的进数据库。** 混在一起的代价是"这段配置到底是谁写的"永远说不清，而恢复逻辑必须知道。

### 为什么这些行不是文件

早先每个键一个 JSON、每个频道每天一个 JSONL。问题不在数量，而在**这些行是用来问的，不是用来看的**：

- "这个频道见过这条平台消息吗？" 从"扫一遍当天的文件"变成唯一索引上的一次查询；
- "把消息写下来，同时写一条未完成的标记" 从"两次可能失败一半的写"变成**一个事务**（`IAtomicWork`）；
- 崩溃一致不再靠"每个文件 write-then-rename"逐处小心翼翼，而是 WAL + 事务这一个地方。

`state(scope, key)` 的 scope/key 仍过 token 校验，`message` 上有 `(owner, at)` 普通索引和 `(owner, platform_message_id)` 唯一索引——**一条平台消息在一个拥有者名下只可能有一行**，这就是接收幂等的落点。

`queued_message(queue, owner, event_id, platform_message_id, conversation, sender, text, at, payload)` 是"一个拥有者正在攒的一串待处理消息"：QQ 入站日志、频道未答完标记各占一个 queue，**一条消息一行**。所以"追加一条"是一次 insert、"确认一条"是一次 delete、"重启会重投哪些"是一条 select，"谁在某群里说了什么还没处理"是一句 where；容量上限也是库里的 `LIMIT -1 OFFSET n` 删旧。`payload` 保留原始记录，重投时原样送出。

`journal_mode=WAL` + `synchronous=NORMAL`：**进程被杀**（这套状态故事真正关心的那种）不会丢已提交的东西，掉电最多丢最后一次提交。

## 3. 状态清单

| 组件 | 位置（`aln.db` 的 `state` 表，scope / key） | 写时机 | 强杀后 | 谁恢复 |
|---|---|---|---|---|
| 参数（窗口等） | `<组件地址编码>` / `<参数名>` | `params.set` 应用成功之后 | 在 | `ParameterRegistry.RestoreAsync`，在频道复活**之后**（注册先于恢复） |
| 频道 delta 游标 | `channel.delta` / `<频道实例名>` | 每次 `TakeDeltaAsync` | 在 | 读时自然恢复；游标坏了就**重放**而不是跳过 |
| 挂载规则 | `graph` / `mounts` | 每次增删、每次预算扣减 | 在 | `GraphManager.LoadAsync` → 解析成挂载；目标不在就先挂着"等" |
| 脚本状态 | `script.<编码>` / `<key>` | `ctx.state.set/delete` | 在 | 脚本自己读；宿主不知道值的含义 |
| 频道期望状态 | `channel.desired` / `<频道地址编码>` | `channels.start` / `channels.stop` | 在 | `ChannelManager.StartAsync(lifecycle)`，按"人上次的意思"而非默认值复活 |
| 已接受未答完的消息 | `queued_message` 表，queue=`channel.pending`，一行一条（key=event id） | **accept 时**写（与消息同一事务），事件轮结束（settle）时清 | 在 | 启动末尾 `ReplayPendingAsync`：用同一 event id 把叫醒重投一次 |
| 邮箱在途输入 | 不在库里：`io/<类型>/<实例>/inflight/` | 读到即"认领"（inbox → inflight） | 在 | 适配器启动时 `ReclaimAsync` 把它们退回 inbox，重新投递 |
| QQ 入站消息 | `queued_message` 表，queue=`qq.inbound`，一行一条（key=event id） | **收到就写**，事件轮结束（settle）时删 | 在 | 适配器连上平台后 `ReplayWhenConnectedAsync` 用原 event id 重投 |

**启动收据**：谁恢复了什么，由 `IRestoreReporter` 记一条，宿主在启动末尾打印。一段真实输出：

```
restored graph: 1 mount rule(s) → 0 mount(s); 1 rule(s) waiting for their target; 0 bundle mount(s)
restored graph: 1 waiting rule(s) applied to channel.conversation#chat-auto
restored graph: 1 waiting rule(s) applied to channel.conversation#qq-private-1664093638
restored channels: 2 revived running, 0 kept stopped as they were left
```

第一行说"规则在、目标还没到"，后两行说"目标到了，挂上了"。**一条都没打印**，才是"状态静默消失"的样子——所以它必须打印。

## 4. 挂载：持久化的是规则，不是结果

### 4.1 三个正交的轴

原来的 `MountMode`（`default` / `manual`）回答的是**"谁挂"**，不是寿命，也不是作用域。现在拆成三件事：

| 轴 | 取值 | 含义 |
|---|---|---|
| **source** | `bundle` / `manual` | 随包自动挂（不落盘，每次重新推导）/ 人点名挂（落盘） |
| **lifetime** | `budget: null` / `budget: N` | 永久 / 最多 N 次（`1` 就是一次性） |
| **scope** | `instance` / `type` / `module` | 一个实例 / 某类型的所有实例 / 某模块下的所有类型 |

`state` 表里 scope=`graph`、key=`mounts` 的那一行存的是**规则**（下面只是把值展开来看）：

```json
{"schema":1,"rules":[{"id":"rc7a60aa8","scriptId":"channel.chat",
  "scope":{"kind":"type","selector":"channel.conversation"},
  "source":"manual","createdAt":"2026-11-01T11:29:57.97+00:00",
  "budget":null,"stateScope":"perTarget","remaining":null}]}
```

枚举写成名字、整体替换：这是人可以打开的文件，不是二进制缓存。

### 4.2 解析不出来的规则不删，叫 pending

`type`/`module` 作用域的规则允许**当前一个都匹配不上**——这正是"以后新建的频道自动获得"的表达方式。启动顺序是"图先起来、频道后复活"，所以正常重启时规则一定是先 pending、再在频道复活时被 `AttachAsync` 挂上（见上面收据的后两行）。

`instance` 作用域则**必须**指名一个存在的实例：往不存在的地址上挂不是意图，是打错字，这种要当场报错而不是安静地等一辈子。

`graph.list` 给出 `pending: true`，让"在等"和"挂了"两个状态在界面上可区分。

### 4.3 预算：先扣后用，按目标计

- 单位是**每个命中目标**的次数，不是整条规则的次数：`budget: 1` + `type` 作用域 = "每个频道各一次"，这比"总共一次"有用得多。
- 扣减发生在**handler 执行之前**，并立刻落盘。代价是崩溃时可能少跑一次；收益是**绝不会把"只准一次"的东西跑第二遍**。一次性动作宁可漏，不可重。
- 用完即卸载；`instance` 作用域的规则用完即删除，`type`/`module` 的规则保留并在 `remaining` 里记 0，重启不会复活。

### 4.4 卸载

- `graph.unmount {"rule": "<id>"}`：删规则，连带其挂载。
- `graph.unmount {"script": ..., "target": ...}`：删这一个实例上的挂载；若它是 `instance` 规则产生的，规则一并删除。`type`/`module` 规则比单个实例宽，**不会**被这种调用删掉——按 id 删才明确。
- `bundle` 挂载（`rule: null`）照旧：删了下次实例出现还会回来，因为它跟随包的生命周期，不是规则。

## 5. 脚本状态：`ctx.state`

```js
const seen = (await ctx.state.get('count')) ?? 0;
await ctx.state.set('count', seen + 1);
```

- 命名空间默认**按目标**：`script.<脚本 id>.<目标地址>`。两个频道就是两段记忆。
- 规则可声明 `stateScope: "shared"` → 命名空间按**规则**：`script.<规则 id>`。去重表、限流窗口、模式开关这类"真是一件事"的东西用它。
- 按目标时键的是 **脚本 + 目标**，不是规则 id：卸载再挂回来，记忆还在。
- 键由宿主编码成合法文件名，值不超过 64 KB——这是脚本的记忆，不是 artifact 仓库。**没有额外能力位**：它只写自己的命名空间，不产生外部副作用。

## 6. 频道的期望状态

`Running` 既是事实也是**愿望**：`channels.stop` 之后重启又自己跑起来，是把人的决定静默撤销。所以：

- `start`/`stop` 落盘（`{"running":false}`）；落盘失败时内存里的改动保留，但返回"重启会恢复原样"的错误。
- **停机流程不改写**它：关掉整个进程不是"把所有频道停掉"这个决定。
- `destroy` 删除它：否则同地址的新频道会继承一个不存在的频道留下的"停着"。

## 7. 入站：什么时候才算"处理完了"

一条消息从平台到回复，要跨过两个"不算完"的边界。两边各有自己的一句实话：

**① 适配器："我发布了事件" ≠ "事件被处理了"。**
所以邮箱读到的输入先被**认领**：`inbox/x.ready.json` → `inflight/x.json`（一次 rename）。认领之后：

- 别的读者看不到它，不会重复发布；
- 事件 id 对应的确认登记在 `IInboundAcks` 里，**事件轮结束之后**才由 settle 把它移到 `processed/` 或 `rejected/`；
- 进程在这中间死掉，文件就留在 `inflight/`——适配器下次启动先 `ReclaimAsync` 把它退回 inbox，于是它会被再投一次，只再投一次；
- 发布本身就失败（队列满）则 `ReleaseAsync` 立即退回，不算失败输入，下次轮询再试。

**② 频道："我接受进历史" ≠ "这一轮跑完了"。**
所以 accept 会先写一条 pending 标记（`queued_message` 里 queue=`channel.pending`、key=event id 的一行，与消息**同一个事务**，内容足以重建叫醒：event id、平台消息 id、绑定、文本、时间），然后才把 `channel.message.accepted` 入队。事件轮结束时 settle 清掉它。启动末尾，`ReplayPendingAsync` 把还留着的标记用**同一个 event id** 重投一次——于是"接受了但没答完"那一条会自己接着跑，而不是安静地躺在历史里。

**③ 适配器："从 socket 读到了" ≠ "这一条已经交出去了"。**
文件邮箱那一侧有收件箱可以认领，WebSocket 没有：OneBot v11 的正向连接**不会重放**，事件一读出来就只存在这个进程里。所以 QQ 适配器把收到的消息先写进 `queued_message` 表（queue=`qq.inbound`，key 就是 event id），再发布事件；事件轮结束时 settle 把它删掉。启动时若还有残留，就等**连上平台之后**用原 event id 重投一次。

"连上之后"是刻意的：早于连接重投，那些消息引起的回复会撞上"还没有 socket 可发"，而失败的回复正是重投救不回来的东西。代价是重投会晚于新到的消息几十毫秒——顺序上不理想，但不会丢也不会重复回。

**接收是幂等的**：同一平台消息 id 二次到达不再追加历史、也不再发叫醒（叫醒归 pending 标记负责）。所以"重复投递"从危险变成了无聊。

这样整条链路才真正首尾相接：**socket → 日志 → 事件 → 认领/接受 → 回合 → 回复**，每一段断开都有东西把它接上。

**④ 回复本身也留痕。** 每次经频道发出去的回复都在 `message` 表里留一行：`direction=outbound`、`reply_to` 指向它回答的那条入站消息。于是"这条消息回过没有"是一个可以问的问题——重投前先查一次，回过的就把残留标记删掉、不再跑一轮。这就是最后一个窗口的关闭方式：**回复已经写出、标记还没来得及清**的那几毫秒里崩掉，重启时不会再回第二遍。

顺序是刻意的：**先发，后落行**。写行失败最多导致将来重投时多回一次；反过来"先落行后发"则会得到一个登记为已回、实际没发出去的消息——那是静默的丢失，比重复更糟。

## 8. 明确**不**持久化的东西

不列出来的"无缝"是骗人的。下面这些重启就没了，且都是刻意的：

| 东西 | 为什么可以丢 |
|---|---|
| 事件队列里还没分发的事件 | 队列是内存里的交接棒。两侧的输入都被接住了：**文件邮箱**靠"认领 + 回收"，**QQ** 靠入站日志 + 连上后重投。丢的只是"很多人都在排队时最后一个还没轮到"的那种瞬间，且它的来源仍然可重投 |
| 进行中的模型回合 | 已经产生的用户消息在频道历史里，pending 标记会让没答完的那一轮重投；半轮丢弃比半轮续跑更诚实 |
| 适配器连接与退避计数 | spec 还在，重连逻辑本来就会反复试；退避从零开始最多多试一次 |
| 模型 provider 的健康/失败计数 | 下一秒就能重新测出来 |
| 时钟订阅 | 由适配器启动时自己注册（`FileAdapter` 轮询、QQ 心跳），不是脚本资源；脚本有定时器能力那天，才需要按规则持久化 |
| `bundle` 挂载 | 跟随包：包在，挂载就能重新推导。只有**人**的意图需要写下来 |

## 9. 已知的缝

1. **`state` 的值仍是 JSON 文本**：那是组件自己的小状态（游标、挂载规则、参数），形状由组件定，宿主不该替它拆列。要按字段查的队列已经拆开了（`queued_message`），要查状态就等真有那个需求。
2. **模型请求超时没有独立参数**：它由 provider 自己的配置和调用方传入的 token 决定；会话一轮的时限也走 token。真要在运行中调，那是"每次调用带一个时限"，得先给会话加上这一层。
3. **secret 只写不读**：`accessToken` 这类值放在 spec 里，参数面板能写不能读回——把令牌倒进数据库并不是进步。

## 10. 验收

`tests/ALN.Tests/StateContinuityTests.cs` 里每个用例都搭一整张组件图、**丢掉对象图、在同一数据根上再搭一张**——这就是重启的样子：

| 用例 | 保证的事 |
|---|---|
| `Mount_rules_survive_a_restart_and_reach_a_channel_that_only_exists_afterwards` | 规则跨重启；先 pending 后被复活的目标解析；新目标自动获得 |
| `A_one_shot_rule_is_spent_before_it_runs_and_never_returns` | 一次性只跑一次，且规则用完即消失 |
| `Script_state_is_per_target_and_outlives_the_process` | 两个频道各记各的，重启后各自接着数 |
| `A_shared_state_scope_is_one_namespace_for_every_target_the_rule_reaches` | `shared` 是一条规则一段记忆 |
| `A_channel_somebody_stopped_stays_stopped_after_a_restart` | 停掉的频道不自己起来，且收据里说明 |
| `A_window_and_a_delta_cursor_are_still_what_they_were_before_the_restart` | 参数与游标一起活下来 |
| `A_message_that_was_accepted_but_never_answered_is_replayed_once_after_a_restart` | 接受了但没答完的那一轮，重启后接着跑一次，且只一次 |
| `The_same_platform_message_delivered_twice_is_answered_once` | 重复投递 = 一行历史、一次回复 |
| `A_claimed_input_that_was_never_acknowledged_is_offered_again` | 认领了没确认的邮箱输入，重启后被退回重投 |
| `A_journaled_message_can_be_read_back_and_forgetting_it_removes_it` / `The_journal_is_bounded_and_gives_up_on_the_oldest_first` | QQ 入站日志的读写、去重与有界丢弃 |
| `An_unreadable_journal_starts_over_instead_of_refusing_to_boot` / `Without_a_state_store_the_journal_is_honest_about_being_ephemeral` | 坏文件不拦启动；没有状态存储时明说自己不可持久 |
| `A_session_that_names_no_profile_uses_default_and_says_so` 等三条 | 会话不写 `modelProfileId` 时的解析：`default` 优先、否则 id 序第一个、没有就报清楚原因 |
| `SqliteStoreTests`（九条） | 单文件存储的底座：缺值与失败可区分、scope/key 必须是 token、重复平台消息是 Conflict 而不是第二行、事务失败什么都不留、提交后另一个连接看得见、`queued_message` 一行一条、可按字段查、容量丢最旧的、不同 owner 的日志互不干扰 |
| `The_same_platform_message_delivered_twice_is_answered_once` | 重投一次只回一次，并且回复在库里带着 `reply_to` 指向被回的那条 |
| `A_message_that_was_answered_is_not_answered_again_when_its_marker_survives` | 回复已发出、标记残留：重启后只清标记，不再回第二遍 |

另外在真实数据根上验过两次强杀：

- **期望状态**：`channels.stop` 一个频道 → 直接杀进程 → 重启，`channels.list` 里它仍是 `running:false`，另一个仍是 `true`；同时给文件邮箱丢一条消息，`channel.chat` 仅凭持久化的 `type` 规则就重新挂上并回了话。
- **入站在途**：停掉宿主后手工放一个 `inbox/*.ready.json` 和一个 `inflight/*.json`（模拟被崩溃的进程认领过的输入），再用 `sqlite3` 手写一行 `channel.pending` 状态；启动后收据里出现 `1 accepted message(s) replayed`，两个文件都被消费并进了 `processed/`，`inflight/` 与 `channel.pending/` 都清空。
- **QQ 入站日志**：用 `FakeOneBot` 起一个假 OneBot，跑一个临时数据根；先让它正常推一条消息（收到即回），确认 `qq.inbound` 在回合结束后被清空；再手工把一条"崩溃前收到但没交付"的 envelope 写进 `qq.inbound`，重启后它在**连上平台之后**被重投并正常回了话（`收到：这条是崩溃前收到但没交付的`），随后日志与 pending 都清空。
