# 17 · 状态与恢复（重启前后必须是一样的）

> 最后更新：`c9311dd`
>
> 这是一篇**现状**文档：代码在，可对照。设计层面的"该不该这样分层"见
> [`01`](01-模块切分.md) 与 [`02`](02-图模块.md)；这里只回答一个问题：
> **进程被关掉（或被强杀）再来一次，什么东西必须还在，由谁负责让它还在。**

---

## 1. 一条原则

> **状态归产生它的组件，路径归宿主；改了就写，不等退出。**

三个推论，都写进了代码：

1. 组件不拼路径，只给"我要一个作用域（scope）和一个键（key）"，落盘位置由宿主决定（`IStateStore`）。
2. **不靠"退出时保存"**。退出时保存等于"被强杀就丢"，而强杀是被杀毒、断电、任务管理器最常见的样子。所有状态都在**变化的那一刻**写。
3. 因此**没有 flush 协议**，也暂时不需要：没有缓冲着的状态，就没有要冲的东西。等第一批高频状态（journal）出现，再加 `IFlushableState` 与关闭阶段的 flush 阶段——那时它才有参与者。

## 2. 三样东西，存两处

| | 谁写 | 在哪 | 语义 |
|---|---|---|---|
| **spec / 意图** | 人 | `modules/` `api/` `scripts/` 下的文件 | 精确恢复；缺了就是缺了 |
| **state** | 程序 | `aln.db` 的 `state(scope, key, value)` 表 | 尽力恢复；坏了降级并**说出来** |
| **data / 流水** | 程序追加 | `aln.db` 的 `message` / `audit` / `queued_message` 表；`modules/`（会话）`memory/`（记忆）`artifacts/` `logs/` 仍是文件 | 崩溃最多丢末尾一条未提交的记录 |

判据：**人能手动编辑的进文件，只有程序知道的进数据库。** 混在一起的代价是"这段配置到底是谁写的"永远说不清，而恢复逻辑必须知道。

`memory/` 是按这条判据搬到文件里的：一个记忆组是**人可以编辑的一篇正文 + 一行行追加的碎片**（`21 §1`），
它的读取方式也是"按组读一遍、按 query 挑几条"，不是"按条件查一行"。旧 `aln.db` 的 `memory` 表留在原处但**没有读者**——
删表会连带删掉旧版写过的行，而清理不是让数据不可恢复的理由。组名、`block.md`、`lines.jsonl`、`history/` 的形状见 [`21`](21-记忆.md)。

`modules/<id>/` 里的会话目录是这条判据的一个例外，且是**故意的例外**：一段对话的历史是一行行追加的流水，它的读取方式也是"从头读一遍"，不是"按条件查一条"；把它塞进库里只会把"一次 append"换成"一次 insert 再读回全部"。它的元数据（属于哪个频道、最后一次说话的时间）就写在同一个目录里，见 §8。

`prompts/` 是第三条：它是**人写的文本**（提示词），按 `组/名字.md` 存放，每轮使用前重读——所以改一个文件下一轮就生效，不需要重启也不破坏会话。出厂默认在程序目录的 `resources/prompts/`，数据根里的同名文件覆盖它。约定与失败处理见 [`11 §6.0`](11-上下文拼接.md)。

### 为什么这些行不是文件

早先每个键一个 JSON、每个频道每天一个 JSONL。问题不在数量，而在**这些行是用来问的，不是用来看的**：

- "这个频道见过这条平台消息吗？" 从"扫一遍当天的文件"变成唯一索引上的一次查询；
- "把消息写下来，同时写一条未完成的标记" 从"两次可能失败一半的写"变成**一个事务**（`IAtomicWork`）；
- 崩溃一致不再靠"每个文件 write-then-rename"逐处小心翼翼，而是 WAL + 事务这一个地方。

`state(scope, key)` 的 scope/key 仍过 token 校验，`message` 上有 `(owner, at)` 普通索引和 `(owner, platform_message_id)` 唯一索引——**一条平台消息在一个拥有者名下只可能有一行**，这就是接收幂等的落点。

`queued_message(queue, owner, event_id, platform_message_id, conversation, sender, text, at, payload)` 是"一个拥有者正在攒的一串待处理消息"：QQ 入站日志、频道未答完标记各占一个 queue，**一条消息一行**。所以"追加一条"是一次 insert、"确认一条"是一次 delete、"重启会重投哪些"是一条 select，"谁在某群里说了什么还没处理"是一句 where；容量上限也是库里的 `LIMIT -1 OFFSET n` 删旧。`payload` 保留原始记录，重投时原样送出。

`journal_mode=WAL` + `synchronous=NORMAL`：**进程被杀**（这套状态故事真正关心的那种）不会丢已提交的东西，掉电最多丢最后一次提交。

## 3. 状态清单

| 组件 | 位置（`aln.db` 的 `state` 表，scope / key） | 写时机 | 强杀后 | 谁恢复 |
|---|---|---|---|---|
| 参数（窗口等） | `<组件地址编码>` / `<参数名>` | `params.set` 应用成功之后 | 在 | `ParameterRegistry.RestoreAsync`，在频道复活**之后**（注册先于恢复） |
| 频道 delta 游标 | `channel.delta` / `<频道地址>` | 每个**成功收尾**的回合（`ITurnCommit`） | 在 | 读时自然恢复；游标坏了就**重放**而不是跳过：失败的一轮不推进游标，消息下一轮还会再交一次 |
| 挂载规则 | `graph` / `mounts` | 每次增删、每次预算扣减 | 在 | `GraphManager.LoadAsync` → 解析成挂载；目标不在就先挂着"等" |
| 脚本状态 | `script.<编码>` / `<key>` | `ctx.state.set/delete` | 在 | 脚本自己读；宿主不知道值的含义 |
| 频道期望状态 | `channel.desired` / `<频道地址编码>` | `channels.start` / `channels.stop` | 在 | `ChannelManager.StartAsync(lifecycle)`，按"人上次的意思"而非默认值复活 |
| 已接受未答完的消息 | `queued_message` 表，queue=`channel.pending`，一行一条（key=event id） | **accept 时**写（与消息同一事务），事件轮结束（settle）时清 | 在 | 启动末尾 `ReplayPendingAsync`：用同一 event id 把叫醒重投一次 |
| 邮箱在途输入 | 不在库里：`io/<类型>/<实例>/inflight/` | 读到即"认领"（inbox → inflight） | 在 | 适配器启动时 `ReclaimAsync` 把它们退回 inbox，重新投递 |
| QQ 入站消息 | `queued_message` 表，queue=`qq.inbound`，一行一条（key=event id） | **收到就写**，事件轮结束（settle）时删 | 在 | 适配器连上平台后 `ReplayWhenConnectedAsync` 用原 event id 重投 |

不在 `state` 表里的那一样是**会话目录**（`modules/<id>/`）：`channel` / `lastActiveAt` / `waitUntil` 写在它自己的 `state.json` 里，理由见 §8。

**启动收据**：谁恢复了什么，由 `IRestoreReporter` 记一条，宿主在启动末尾打印。一段真实输出：

```
restored graph: 1 mount rule(s) → 0 mount(s); 1 rule(s) waiting for their target; 0 bundle mount(s)
restored graph: 1 waiting rule(s) applied to channel.conversation#chat-auto
restored graph: 1 waiting rule(s) applied to channel.conversation#qq-private-1664093638
restored channels: 2 revived running, 0 kept stopped as they were left
```

第一行说"规则在、目标还没到"，后两行说"目标到了，挂上了"。**一条都没打印**，才是"状态静默消失"的样子——所以它必须打印。

## 4. 挂载：持久化的是规则，不是结果

### 4.1 三个正交的轴

原来的 `MountMode`（`default` / `manual`）回答的是**"谁挂"**，不是寿命，也不是作用域。现在拆成三件事：

| 轴 | 取值 | 含义 |
|---|---|---|
| **source** | `bundle` / `manual` | 随包自动挂（不落盘，每次重新推导）/ 人点名挂（落盘） |
| **lifetime** | `budget: null` / `budget: N` | 永久 / 最多 N 次（`1` 就是一次性） |
| **scope** | `instance` / `type` / `module` | 一个实例 / 某类型的所有实例 / 某模块下的所有类型 |

`state` 表里 scope=`graph`、key=`mounts` 的那一行存的是**规则**（下面只是把值展开来看）：

```json
{"schema":1,"rules":[{"id":"rc7a60aa8","scriptId":"channel.chat",
  "scope":{"kind":"type","selector":"channel.conversation"},
  "source":"manual","createdAt":"2026-11-01T11:29:57.97+00:00",
  "budget":null,"stateScope":"perTarget","remaining":null}]}
```

枚举写成名字、整体替换：这是人可以打开的文件，不是二进制缓存。

### 4.2 解析不出来的规则不删，叫 pending

`type`/`module` 作用域的规则允许**当前一个都匹配不上**——这正是"以后新建的频道自动获得"的表达方式。启动顺序是"图先起来、频道后复活"，所以正常重启时规则一定是先 pending、再在频道复活时被 `AttachAsync` 挂上（见上面收据的后两行）。

`instance` 作用域则**必须**指名一个存在的实例：往不存在的地址上挂不是意图，是打错字，这种要当场报错而不是安静地等一辈子。

`modules.edge.list` 给出 `pending: true`，让"在等"和"挂了"两个状态在界面上可区分。

### 4.3 预算：先扣后用，按目标计

- 单位是**每个命中目标**的次数，不是整条规则的次数：`budget: 1` + `type` 作用域 = "每个频道各一次"，这比"总共一次"有用得多。
- 扣减发生在**handler 执行之前**，并立刻落盘。代价是崩溃时可能少跑一次；收益是**绝不会把"只准一次"的东西跑第二遍**。一次性动作宁可漏，不可重。
- 用完即卸载；`instance` 作用域的规则用完即删除，`type`/`module` 的规则保留并在 `remaining` 里记 0，重启不会复活。

### 4.4 卸载

- `modules.edge.unmount {"rule": "<id>"}`：删规则，连带其挂载。
- `modules.edge.unmount {"script": ..., "target": ...}`：删这一个实例上的挂载；若它是 `instance` 规则产生的，规则一并删除。`type`/`module` 规则比单个实例宽，**不会**被这种调用删掉——按 id 删才明确。
- `bundle` 挂载（`rule: null`）照旧：删了下次实例出现还会回来，因为它跟随包的生命周期，不是规则。

## 5. 脚本状态：`ctx.state`

```js
const seen = (await ctx.state.get('count')) ?? 0;
await ctx.state.set('count', seen + 1);
```

- 命名空间默认**按目标**：`script.<脚本 id>.<目标地址>`。两个频道就是两段记忆。
- 规则可声明 `stateScope: "shared"` → 命名空间按**规则**：`script.<规则 id>`。去重表、限流窗口、模式开关这类"真是一件事"的东西用它。
- 按目标时键的是 **脚本 + 目标**，不是规则 id：卸载再挂回来，记忆还在。
- 键由宿主编码成合法文件名，值不超过 64 KB——这是脚本的记忆，不是 artifact 仓库。**没有额外能力位**：它只写自己的命名空间，不产生外部副作用。

## 6. 频道的期望状态

`Running` 既是事实也是**愿望**：`channels.stop` 之后重启又自己跑起来，是把人的决定静默撤销。所以：

- `start`/`stop` 落盘（`{"running":false}`）；落盘失败时内存里的改动保留，但返回"重启会恢复原样"的错误。
- **停机流程不改写**它：关掉整个进程不是"把所有频道停掉"这个决定。
- `destroy` 删除它：否则同地址的新频道会继承一个不存在的频道留下的"停着"。

## 7. 入站：什么时候才算"处理完了"

一条消息从平台到回复，要跨过两个"不算完"的边界。两边各有自己的一句实话：

**① 适配器："我发布了事件" ≠ "事件被处理了"。**
所以邮箱读到的输入先被**认领**：`inbox/x.ready.json` → `inflight/x.json`（一次 rename）。认领之后：

- 别的读者看不到它，不会重复发布；
- 事件 id 对应的确认登记在 `IInboundAcks` 里，**事件轮结束之后**才由 settle 把它移到 `processed/` 或 `rejected/`；
- 进程在这中间死掉，文件就留在 `inflight/`——适配器下次启动先 `ReclaimAsync` 把它退回 inbox，于是它会被再投一次，只再投一次；
- 发布本身就失败（队列满）则 `ReleaseAsync` 立即退回，不算失败输入，下次轮询再试。

**② 频道："我接受进历史" ≠ "这一轮跑完了"。**
所以 accept 会先写一条 pending 标记（`queued_message` 里 queue=`channel.pending`、key=event id 的一行，与消息**同一个事务**，内容足以重建叫醒：event id、平台消息 id、绑定、文本、时间），然后才把 `channel.message.accepted` 入队。事件轮结束时 settle 清掉它。启动末尾，`ReplayPendingAsync` 把还留着的标记用**同一个 event id** 重投一次——于是"接受了但没答完"那一条会自己接着跑，而不是安静地躺在历史里。

**③ 适配器："从 socket 读到了" ≠ "这一条已经交出去了"。**
文件邮箱那一侧有收件箱可以认领，WebSocket 没有：OneBot v11 的正向连接**不会重放**，事件一读出来就只存在这个进程里。所以 QQ 适配器把收到的消息先写进 `queued_message` 表（queue=`qq.inbound`，key 就是 event id），再发布事件；事件轮结束时 settle 把它删掉。启动时若还有残留，就等**连上平台之后**用原 event id 重投一次。

"连上之后"是刻意的：早于连接重投，那些消息引起的回复会撞上"还没有 socket 可发"，而失败的回复正是重投救不回来的东西。代价是重投会晚于新到的消息几十毫秒——顺序上不理想，但不会丢也不会重复回。

**接收是幂等的**：同一平台消息 id 二次到达不再追加历史、也不再发叫醒（叫醒归 pending 标记负责）。所以"重复投递"从危险变成了无聊。

这样整条链路才真正首尾相接：**socket → 日志 → 事件 → 认领/接受 → 回合 → 回复**，每一段断开都有东西把它接上。

**④ 回复本身也留痕。** 每次经频道发出去的回复都在 `message` 表里留一行：`direction=outbound`、`reply_to` 指向它回答的那条入站消息。于是"这条消息回过没有"是一个可以问的问题——重投前先查一次，回过的就把残留标记删掉、不再跑一轮。这就是最后一个窗口的关闭方式：**回复已经写出、标记还没来得及清**的那几毫秒里崩掉，重启时不会再回第二遍。

顺序是刻意的：**先发，后落行**。写行失败最多导致将来重投时多回一次；反过来"先落行后发"则会得到一个登记为已回、实际没发出去的消息——那是静默的丢失，比重复更糟。

**⑤ 名字跟着消息一起落盘。** 入站那一行除了 `sender`（平台 id，身份）还写 `sender_name` / `sender_remark`（展示用：群名片→昵称，加括号里的备注）。只有一个理由：**名字事后取不回来**——适配器可能已经不在了、人可能已经改名，而一条明天才被读到的消息仍应说得清是谁说的。`channel.delta` 把这两列拼成 `名字(备注)` 交给会话，与实时注入用的是同一条规则（`ChannelMessage.Compose`）。在这之前写入的行没有名字，于是继续按 id 显示——迁移只加列，不动旧行。

## 8. 归档：一个回收站，不是一次删除

**为什么会话需要生命周期。** 适配器和频道的 spec 是**人写的文件**：文件在，它就在；文件删了，它就该消失。所以它们不需要"回收"——重启时全量启动一遍，谁存在谁就活，代价只有启动的那几毫秒。

会话不一样：它的 spec 不是人写的，是**脚本在运行时递进来的**（`session.activate` / `session.run`），目录名是类型 + 随机后缀（身份不从频道地址推导，C-01）。于是它会以几种方式变成没人要的死数据，而任何一种从外面都看不出来：所属频道被销毁了；脚本改过而 spec 不可变，同一个 id 永远撞 `Conflict`；或者很久没人跟它说话。

**但"收走"这件事没有长在会话里。** 会堆积的东西不止会话：`artifacts/model-calls` 按天堆、邮箱的 `processed/` 与 `rejected/` 从不清理、将来 `audit` / `message` 的行也会到需要腾地方的那天。它们需要的都是同一件事——**看一眼、搬走、再拿回来**——所以它是一个独立模块（`src/ALN.Archive`，包 `aln.archive`），带着一套"任何东西都能登记进来"的契约。回收站里没有 `DELETE`。

### 8.1 三种角色，一套接口

| 角色 | 谁 | 回答什么 |
|---|---|---|
| `IArchiveRegistry` | 动作、脚本（将来）、测试 | "有什么可以收？""收走它。""拿回来。" |
| `IArchiveSource` | 会堆积的那个组件（今天的 `session`） | "我这一类还有哪些可以收？""怎么搬走？""怎么搬回原位？" |
| `IArchiveSink` | 归档模块自己 | "放在哪？重名怎么办？凭证写什么？" |

切法只有一句：**每个东西自己知道怎么归档，模块只管三块——根目录、撞名、账单。** 于是"搬目录"（会话）、"导出成 jsonl 再删行"（将来 `audit`）、"按天打包"（`model-calls`）都能落到同一个接口上，模块一行都不用改。

登记与加载顺序无关：归档包在宿主启动早期加载，自己创建 registry 并用服务 id `archive.manager` 暴露；谁要登记就在自己的启动里 `Register`，不需要持有 `ALN.Archive` 的类型。会话在 bundled runtime 启动时登记 `SessionArchiveSource`——判定（"哪些会话没用了"）留在会话那边，**模块不猜内容**。

### 8.2 回收站长什么样

```
<dataRoot>/archive/<kind>/<条目名>/
  archive.json     ← 它是什么、来自哪（origin）、为什么进（reason）、多大、何时
  payload/         ← 原样搬进来的东西：一个目录，或者几个文件
```

- **条目名就是它的地址**：默认等于 source 的 id；被占了就加时间戳（`s-abc-20261102T103000Z`），再占就加序号。**绝不覆盖**——回收站里最不能发生的事，就是第二个进来把第一个顶掉。
- 所以一个条目有**两个身份**：`id`（回收站里的名字，唯一）和 `sourceId`（原来叫什么，恢复时用它放回原位）。合成一个字段，同一个 id 第二次进站就再也区分不开。
- `origin` 是给"数据库没了也要能人工搬回去"准备的：会话写 `modules/<id>`，将来别的 kind 写它自己的原位。
- 条目顺序按 `archivedAt`，一次 `archive.list` 就能看到"谁最早进来"。

真实的一段（`archive.move` 之后 `archive.list` 的输出，节选）：

```
{ "kind": "session", "id": "s-c534aecf…", "bytes": 2645,
  "archivedAt": "2026-11-02T10:28:14+00:00", "owner": null, "reason": "channel-unknown",
  "note": { "origin": "modules/s-c534aecf…" },
  "path": "E:\\Tools\\…\\storage\\archive\\session\\s-c534aecf…" }
```

### 8.3 目录里写进两样"给外面看"的元数据

> 只在两个时刻写：**会话第一次创建时**、**每轮结束时**。绝不扫描会话目录 去找它们——会话仍是惰性的，第一次被用到才碰盘。

`state.json`（`SessionState`）多了两个字段：

| 字段 | 含义 | 为什么必须落盘 |
|---|---|---|
| `channel` | 它服务于哪个频道地址（`channel.conversation#x`） | 会话 id 是类型 + 随机后缀，与频道无关，除此之外没人能看出这个目录属于谁 |
| `lastActiveAt` | 最后一次**跑完**一轮的时间 | 文件的 mtime 会被备份、杀毒、同步工具改掉；"多久没说话"不能靠猜 |

写 `lastActiveAt` 放在**回合末**而不是回合初：半路死掉的回合不该让一个被遗忘的会话看起来还活着。

另有 `waitUntil` / `waitRelease` 两个字段，只在 `wait` 声明时写（[`20 §2`](20-会话收尾.md)）：它们是"我要被叫醒"的唯一一份真相，扫描器只读这里。

> `supersededAt` 已经删掉：spec 不再匹配不再是死亡，而是"照旧跑、记一条 warn"（`10 §5.1`）。

### 8.4 销毁频道 = 把它的会话搬进回收站

`channels.destroy`（以及任何走 `ChannelManager.DestroyAsync` 的路径）把该频道自己的会话搬进回收站，靠的就是 `state.json` 里的 `channel`。理由是纯逻辑的：会话 id 由频道（和来源）推出来，spec 又不可变，所以**同地址的新频道会继承一个用不上的旧会话**——留着它，第一句话就会撞 `Conflict`。搬走就不是：新频道看到的是"没有会话"，从零开始。

**删频道不再等于"忘掉这段对话"**：数据在 `archive/session/` 里，`archive.restore` 能拿回来，只是它不再挡着任何人。

搬失败不算"销毁失败"：频道已经不在了，那条残留会在 `archive.list` 的候选里继续出现（`channel-gone`），由人再收一次。

### 8.5 搬与恢复：`archive.move` / `archive.restore`

```
> archive.move {"kind": "session", "ids": ["s-c534…"]}
{ "dryRun": true, "count": 1, "done": 0, "bytes": 2645,
  "items": [ { "kind": "session", "id": "s-c534…", "action": "archived", "done": false,
               "message": "channel-unknown" } ] }
```

- **两个动作都默认 dry-run**：缺参数不能成为把一段对话搬走（或搬回来）的原因；真做要显式 `"dryRun": false`。
- `archive.move` 不给 `ids` = 搬走这一类的全部候选；`archive.restore` **必须给 `ids`**——一次把回收站清空不是一个默认值，是一个决定。
- **恢复遇到占位就拒绝**（`Conflict`）：如果同一个 id 的会话已经被重建，把旧的搬回去相当于把两段历史拼成一段。拒绝之后条目仍在原地，取舍留给人和时间。
- 搬与恢复都持有该会话的**回合闸**：正在跑的那一轮要么先结束、要么先失败，不会出现"文件被抽走一半"。
- 条目只在**搬空之后**才消失（`Release` 拒绝删除还留着文件的条目）：半途而废的恢复必须还看得见。

会话的 `reason`（source 的判断，模块只记录、不解释）：

| `reason` | 含义 |
|---|---|
| `channel-unknown` | 早于 `channel` 字段写下的目录，没人能说它属于谁 |
| `channel-gone` | 所属频道已经不在 |
| `spec-superseded` | 有一轮因为 spec 不再匹配被拒，那段 spec 永远不会再对上 |
| `idle` | 超过窗口（默认 30 天，`0` 关掉这条规则）没说话 |

判定用的"还有哪些频道"由 source 从 `channels.list()` 取：会话存储不反过来依赖频道管理器，模块也不。
状态文件读不出来的目录**不判、也不列**：读不出来不是收走一段对话的理由，是需要人看一眼的理由。
它**不是定时任务**：没有第二条线程、没有启动扫描。运维在需要的时候叫一次，看清单，再决定。

### 8.6 会话目录里有什么

| 文件 | 内容 | 谁写 |
|---|---|---|
| `spec.json` | 创建时的 spec 快照（不可变） | 创建那一刻 |
| `state.json` | `status` / `stepNumber` / `revision` / `usage` + 上面三个元数据 | 每次提交（原子替换） |
| `history.jsonl` | 一行一条已提交记录；末尾半行会被修掉 | 每次提交（append） |
| `commit.pending.json` | 正在提交的那一轮；存在就说明上次崩在提交中间 | 提交期间，提交完即删 |

**磁盘是持久化的真源，不是每次读的地方。** 一个会话的 spec / state / timeline 在进程里留一份（`SessionRecord`），
第一次用它的那一轮从盘上读一次、顺带把 `commit.pending.json` 补完，之后整个进程期都记着：

- **提交不再重读 `history.jsonl`。** 上一版每次提交都全文重读一遍——而一轮有好几次提交，代价随对话长度做乘法。
  现在判断"该 append 哪几条"看内存里的 id 集合：这个进程是这些目录的唯一写者，而且写之前一定先加载过，
  所以内存里的东西**就是**盘上的东西。
- **写仍然一条不少**：breadcrumb → append（`WriteThrough` + `flushToDisk`）→ `state.json` → 删 breadcrumb。
  内存最后更新，所以提交中途抛异常时，记录不会声称自己有文件里没有的条目。
- **`commit.pending.json` 仍然存在，也仍然有用**：它是"上一次提交可能只做了一半"的唯一证据，重启后的第一次加载据此补完；
  这是唯一还会跟文件对账的地方。
- **搬走、恢复回来、删除时逐出这条记录**：目录动过了，记忆里那份就作废。
- 代价说清楚：**内存随"被访问过的会话总量"增长**，直到搬走/删除为止；一个长期运行、每天服务几千个一次性会话的宿主，
  会把它们的历史都留在内存里。要收的时候收（回收站），不靠淘汰算法猜。

`state.json` 仍然是"外面看得见的当前值"（`sessions.get`、维护动作照旧读盘），因为盘上的值永远是最新的——缓存省掉的是读，不是写。

### 8.7 刻意不做的事

| 不做 | 理由 |
|---|---|
| 在回收站里 `DELETE` | 一旦删了就不可逆；腾地方和"忘掉"是两件事，前者用搬走就够了。清理留给将来（脚本开能力位之后也是同一套接口） |
| 后台定时清扫 / 启动扫描 | 那会引入第二条线程和"启动时要遍历所有"的开销，正好抵消掉惰性。要收就在动作里收，一次，由人决定 |
| 给脚本开 `ctx.archive` | 接口已经够用（`IArchiveRegistry` 就是脚本届时要用的那套），但"脚本能删东西"是能力位与信任分级的事，不该在归档模块里顺手开 |
| 插件声明"我先于/后于频道恢复" | 现阶段没有真实的顺序需求；加一层声明式排序等于提前为想象中的问题付账 |
| 适配器与频道的回收 | 它们的 spec 是人的文件，全量启动就是全量恢复，没有"没人用的实例"这种东西 |
| 收走时做语义判断（"这段对话还有价值吗"） | 只认可验证的事实（频道不在、spec 已作废、太久没说话），不猜内容 |
| 在 `aln.db` 里加一张"会话索引"表 | 会话目录自己就是真源。多一份索引就要多一份"索引和目录不一致时听谁的"，而两者的更新本来就不是一个事务 |

## 9. 明确**不**持久化的东西

不列出来的"无缝"是骗人的。下面这些重启就没了，且都是刻意的：

| 东西 | 为什么可以丢 |
|---|---|
| 事件队列里还没分发的事件 | 队列是内存里的交接棒。两侧的输入都被接住了：**文件邮箱**靠"认领 + 回收"，**QQ** 靠入站日志 + 连上后重投。丢的只是"很多人都在排队时最后一个还没轮到"的那种瞬间，且它的来源仍然可重投 |
| 进行中的模型回合 | 已经产生的用户消息在频道历史里，pending 标记会让没答完的那一轮重投；半轮丢弃比半轮续跑更诚实 |
| 适配器连接与退避计数 | spec 还在，重连逻辑本来就会反复试；退避从零开始最多多试一次 |
| 模型 provider 的健康/失败计数 | 下一秒就能重新测出来 |
| 时钟订阅 | 由适配器启动时自己注册（`FileAdapter` 轮询、QQ 心跳），不是脚本资源；脚本有定时器能力那天，才需要按规则持久化 |
| `bundle` 挂载 | 跟随包：包在，挂载就能重新推导。只有**人**的意图需要写下来 |

## 10. 已知的缝

1. **`state` 的值仍是 JSON 文本**：那是组件自己的小状态（游标、挂载规则、参数），形状由组件定，宿主不该替它拆列。要按字段查的队列已经拆开了（`queued_message`），要查状态就等真有那个需求。
2. **模型请求超时没有独立参数**：它由 provider 自己的配置和调用方传入的 token 决定；会话一轮的时限也走 token。真要在运行中调，那是"每次调用带一个时限"，得先给会话加上这一层。
3. **secret 只写不读**：`accessToken` 这类值放在 spec 里，参数面板能写不能读回——把令牌倒进数据库并不是进步。

另外在真实数据根上验过两次强杀：

- **期望状态**：`channels.stop` 一个频道 → 直接杀进程 → 重启，`channels.list` 里它仍是 `running:false`，另一个仍是 `true`；同时给文件邮箱丢一条消息，`channel.chat` 仅凭持久化的 `type` 规则就重新挂上并回了话。
- **入站在途**：停掉宿主后手工放一个 `inbox/*.ready.json` 和一个 `inflight/*.json`（模拟被崩溃的进程认领过的输入），再用 `sqlite3` 手写一行 `channel.pending` 状态；启动后收据里出现 `1 accepted message(s) replayed`，两个文件都被消费并进了 `processed/`，`inflight/` 与 `channel.pending/` 都清空。
- **QQ 入站日志**：用 `FakeOneBot` 起一个假 OneBot，跑一个临时数据根；先让它正常推一条消息（收到即回），确认 `qq.inbound` 在回合结束后被清空；再手工把一条"崩溃前收到但没交付"的 envelope 写进 `qq.inbound`，重启后它在**连上平台之后**被重投并正常回了话（`收到：这条是崩溃前收到但没交付的`），随后日志与 pending 都清空。
