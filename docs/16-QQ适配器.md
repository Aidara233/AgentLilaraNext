# ALN QQ 适配器（OneBot v11 / 正向 WebSocket）

一条 QQ 账号接进来的全部做法，以及这一版**故意没做**的事。第一版的目标是：在真实群里收到一条文本消息、
按手动建好的频道跑一轮会话、把回答发回去——并且这条链路的每一步都能在信号日志里看到。

## 1. 前提：账号登录不在我们这边

QQ 协议不由 ALN 实现。账号登录、扫码、掉线重登都在 OneBot 实现里完成，ALN 只是它的一个 WebSocket 客户端。
任选其一（都支持 OneBot v11）：

| 实现 | 与本适配器的对接方式 |
|---|---|
| NapCatQQ | 配置「WebSocket 服务器」（正向），记下端口 |
| LLOneBot | 同上 |
| Lagrange.OneBot | `Implementations: ["ForwardWebSocket"]` |

在它那边要做三件事：

1. 开启 **正向 WebSocket**（即"WS 服务器"），记下端口，默认示例里写的是 `3001`；
2. 如果设了 `access_token`，把它填到本适配器的 `accessToken`；
3. 消息格式选 **array**（`message_format: array`）。选 `string` 也能用：CQ 码会被展开成同样的占位符，
   但 array 是唯一被测试覆盖的路径。

⚠️ 反向 WebSocket（它连我们）与 HTTP 上报**都不支持**。这不是遗漏：一个适配器要不要开监听端口是部署决定，
第一版只做"我们连出去"，重连、退避、超时都只有一条路要走。

## 2. 实例规格：`<DataRoot>/modules/adapter.qq#qq-1/module.json`

```json
{
  "id": "adapter.qq#qq-1",
  "type": "adapter.qq",
  "config": {
    "platformId": "qq",
    "accountId": "auto",
    "direction": "Both",
    "settings": {
      "endpoint": "ws://debian:3003",
      "accessToken": "与 OneBot 那边一致"
    }
  }
}
```

- 三个值要按真实情况改：`accountId`（bot 的 QQ 号，用于身份与日志）、`endpoint`、`accessToken`。
  **`accountId` 不用填真值**：连上后适配器会向平台要 `get_login_info`，把真实账号与昵称学回来，
  `adapters.list` 里 `account` 就是学到的值（`declaredAccount` 是文件里写的标签）。写 `"auto"` 即可。
- **名字即身份，类型在文件里**：目录名是 `id`（`module.json` 里的 `id` 必须与它逐字一致），
  用哪个实现只看 `type`——不从 `id` 推导，也不从目录推导（docs/22 §3.1）。
- `settings` 对核心是**不透明**的：核心只把它原样交给工厂，既不懂 `endpoint` 也不校验它。
  代价是这个文件里有明文令牌——和 provider 的 `config.configuration` 里的 api key 一样，
  属于"数据目录本身就是机密"的既有约定。它不会出现在任何动作的返回值里（`adapters.list` 的 DTO 不含 `settings`）。
- `endpoint` 只接受 `ws://` 或 `wss://`；写错、缺失都会在**启动时**失败并指名是哪个实例，而不是等到第一条消息。

## 3. 频道：手写，不自动创建

**第一版没有自动建频道**。一条消息到达时，先看有没有 Running 的频道绑定了
（`adapter.qq#qq-1` + 该会话 id）；**没有就直接丢弃**，并在信号日志里留一条 warn
（`aln.adapter.intake` / `no channel bound to this conversation; message dropped`）。

这么做是因为：陌生人第一条消息就能让核心长出频道、绑定适配器、开始扣模型调用，这不叫方便，叫失控。

频道规格：`<DataRoot>/modules/channel.conversation#<频道名>/module.json`

```json
{
  "address": "channel.conversation#my-group",
  "name": "我那个群",
  "maxMessages": 40,
  "bindings": [
    { "adapter": "adapter.qq#qq-1", "platformConversationId": "group-123456" }
  ]
}
```

改完重启核心即可（启动时按规格复活频道，并给频道发 `lifecycle.start`，挂在上面的脚本随之开始工作）。

### 一个绑定是一对，不是一种类型

- **频道是 master**：`channel.conversation#my-group` 里的 `my-group` 由你起名，进频道身份、日志、
  消息历史目录。核心不认识它的含义，也不从它推断任何行为。
- **另一半是适配器内部的 id**：`group-123456` 是 QQ 适配器自己的编址（群号、QQ 号加前缀防撞号），
  对核心只是一个不透明字符串，只用于「这条入站消息归哪个频道」和「回信发到哪」。
- **类型不写进任何契约**：群聊与私聊的区别只留在 QQ 适配器内部（选 `send_group_msg` 还是
  `send_private_msg`）。频道这一层看到的始终是「一个名字 + 若干绑定」。
- **行为由脚本决定**：想「群里只在被 @ 时回」，就在这个频道上挂一个判断 `event.mentionsSelf`
  的脚本；想「私聊过一会再回」，就挂另一个。同一个频道类型，两套策略，不新增类型。

### 适配器内部 id 的规则

`platformConversationId` 必须落在 `[A-Za-z0-9_-]`、长度 ≤128 范围内（Channel 侧的校验，
不是类型系统）。QQ 的群号与 QQ 号都是纯数字且可能撞号，所以适配器自己带前缀：

| 平台对象 | 会话 id | 状态 |
|---|---|---|
| 群 | `group-<群号>` | 支持（收发） |
| 好友私聊 | `user-<QQ号>` | 支持（收发） |

所以现在 `modules/channel.conversation#*/module.json` 里只能写 `group-...`。

## 4. 消息映射

入站一条消息变成 `AdapterEnvelope`（群聊与私聊都支持）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `PlatformConversationId` | `group_id` / `user_id`（私聊） | 适配器内部编址：`group-<群号>` / `user-<QQ号>` |
| `PlatformMessageId` | `message_id` | 用于对账与引用回复 |
| `Text` | `message` 段展开 | 见下表 |
| `Sender` | `sender.user_id` | 稳定 id：昵称会改，id 不会，所以身份只认它 |
| `SenderName` | `sender.card` → `sender.nickname` | 展示名。群名片优先，没有就昵称；都没有时为空，由下游退回 id |
| `SenderRemark` | `get_friend_list` 里这个人自己的 `remark` | **备注单开一栏**：它是这个账号给人起的名字，不是对方的名字，两者不该挤进一个字段 |
| `At` | `time` | 秒级 Unix；缺失时用本机时间 |
| `MentionsSelf` | `at` 段是否指向 `self_id` | **由适配器判定**：脚本不该拿昵称去比，`@全体成员` 也不算 |

### 谁叫什么：`ITargetNaming`

展示名的优先级是**群名片 → 昵称 → 账号 id**，备注**永远另加、永远不替代**前者（`小林(同事)`）。
这三件事的来源不同，所以分成三处：

- 群名片只存在于群里（同一个人在 A 群叫「组长」、在 B 群叫本名，两个都是对的），所以要问的是
  `get_group_member_info(group_id, user_id)`，**scope 是会话 id**；
- 昵称是账号级的，`get_stranger_info(user_id)` 就能拿到，也是群名片缺失时的回落；
- 备注是**账号级**的，只有 `get_friend_list` 带着，所以取一次、留一段时间（一张好友表不是每条消息都会变的东西）。

这三条都走 `ITargetNaming.ResolveAsync(targetId, scope)`——它存在的理由不是"再加一个可选接口"，而是
**入站事件里不一定带名字**（存量消息、配置里的 id、别的平台的事件类型）。拿不到就返回 `null`，
让调用方用自己的回落：把拿到的 id 原样包成 `TargetName` 返回，看起来像"解析成功"，其实是没查着。

⚠️ **发消息的路径不等名字**。一条消息比它的展示名重要，所以入站发布只做一次缓存查找（`Remembered`），
好友表在后台拉（`Nudge`）：**重启后的头几条没有备注，之后都有**。这个问题只有一个答案——不让名字拖慢消息。

段展开（模型看到的文本）：

| 段 | 文本 |
|---|---|
| `text` | 原文 |
| `at` | `@昵称`（无昵称时 `@QQ号`），`qq=all` → `@全体成员` |
| `image` / `face` / `mface` | `[图片]` / `[表情]` |
| `record` / `video` / `file` | `[语音]` / `[视频]` / `[文件]` |
| `json` / `xml` / `markdown` | `[卡片]` |
| `forward` / `share` / `location` / `contact` / `music` | `[合并转发]` / `[分享]` |
| `reply` | 不进入文本（`PlatformMessageId` 已承载引用信息） |
| 其他 | `[<类型名>]` |

⚠️ **占位符是刻意的**：文本永远是"[图片]"，**有没有真图、模型能不能看，是另一条路**——`image` 段里的 `url`
会被适配器取回来、入库、作为一个引用交给通道（见 §12）。取不到（没有 url、超时、太大）就只剩这行占位符，
这是刻意的降级：一条消息不该因为一张图取不到而丢掉。
`channel.chat` 的提示词里也写明了这一点。

**被忽略的事件**（正常路径，不是错误）：`meta_event`、`notice`、`request`、`guild` 等未纳入的消息类型、
`message_sent`（自己发出去的回声）、以及 `user_id == self_id` 的任何消息。
最后这条是硬要求：回声若被当成用户输入，bot 会自己跟自己聊。

出站：群里用 `send_group_msg`，私聊用 `send_private_msg`，由会话 id 的前缀决定——不发到"猜出来的"地方。
文本以 text 段发送（不是 CQ 字符串，所以消息里的 `[CQ:...]` 会被当普通文字发出去）。
`OutboundMessage.ReplyTo` 是纯数字时才拼 `reply` 段，否则丢掉——一个被平台拒绝的发送，比一条不带引用的发送更糟。

**一条回复 = 若干条平台消息，由回复的 `mode` 决定**：聊天窗口不是一篇文章——这儿的人是连着发两三条短句的，
而模型把整段写成一坨，读起来像在会话里塞了一份公函。所以「一条回复变成几条消息」是回复本身的属性：

```js
await ctx.channel.reply({ platformConversationId, text, mode: "segments" });  // 默认
await ctx.channel.reply({ platformConversationId, text, mode: "text" });      // 整段一条
```

- `segments`（**默认**）：**空行**是消息边界，一条条发；**单换行不是边界**，所以 `清单：\n1. 甲` 仍是一条消息，
  列表、短代码块活得下来。每段 `trim`，空段丢掉。**没有条数上限**——"别啰嗦"是提示词的事（`2风格/标准.md`
  要求一到三段），在代码里悄悄合并段会让这个模式名不副实。
- `text`：整段原样一条发出去。
- **未知模式直接拒绝**（`denied` + 审计），不回落成默认：脚本请求 `image` 却收到一条文本，看起来像成功了。
  这也正是**下一个模式**（长内容渲染成图片，或者发文件）要落的位置——加一个模式，Adapter 一行不用改。
- 引用（`replyTo`）只挂在**第一条**：后面几条是同一个回答的延续，每条都带箭头会把对话糊死。
- 每一条都是**独立的 adapter 调用 + 独立的出站记录**：适配器永远一次一条，
  `channels.send`（手动发）与 `ctx.adapter.send`（脚本直接发）**保持原样，不切分**——需要整段发的场合走它们。

会话里的 `send_message` 工具同样接受 `mode`（宿主照办，工具描述由脚本的 spec 给）：
模式属于工具参数，**不进系统提示词**（ALP 那条"能进工具描述的绝不进系统提示词"）。


### 手动发一条：`channels.send`

```json
{ "address": "channel.conversation#qq-private-1664093638", "text": "测试" }
```

这是 `messages.write` 能力下的动作，用途是**不等对方开口**就验证 Channel → Adapter → 平台这条边。
它要求频道恰好有**一个**绑定：多绑定时要选哪个会话属于策略，不属于这个动作——猜错就是发到别的群里。

## 5. 连接行为

- 连上后**什么都不先发**：动作必须由已经在跑的接收循环来收答案。曾经在接收循环启动前发 `get_login_info`，
  结果是自己等自己，超时十分钟也等不到。
- 断开后按 1s → 2s → 5s → 10s → 30s 退避重连，`State` 保持 `Running`（"有人在管它"），
  真实连接状态通过 `IAdapterHealth` 暴露：`adapters.list` 里多两个字段
  `connected`（是否真的连着）与 `detail`（最近一次错误或端点）。
  只有 `state` 的列表会在你最需要它的那一刻撒谎。
- 每次连接、断开、失败都写一条信号（`group: module`，`name: aln.adapter.qq`），WebUI 的信号页可见。
- 发送超时 10s；`retcode != 0` 会带上平台原因（禁言、不是群成员、频率限制）作为 `Unavailable` 返回，
  并写一条 warn。
- `message_id` 有一个 512 条的去重窗口：重连与在飞事件可能重复投递，重复回复比漏回更刺眼。

## 6. 回复策略：阀在脚本里，内容由 Session 去拉

仓库里是**样例**，不是内置脚本，而且现在是 `"mount": "manual"`——**没有默认给所有频道挂任何回复策略**：

| 样例 | 用途 |
|---|---|
| `samples/scripts/trusted/channel.chat` | 每条都理（私聊、或你确定要它随时说话的频道） |
| `samples/scripts/trusted/group.mention-only` | 群里只在被 @ 时理（判断 `event.mentionsSelf`） |

```cmd
xcopy /E /I /Y samples\scripts\trusted\channel.chat "%DATA_DIR%\scripts\trusted\channel.chat"
xcopy /E /I /Y samples\scripts\trusted\group.mention-only "%DATA_DIR%\scripts\trusted\group.mention-only"
```

挂载（即时生效，不用重启；脚本包本身是新加的才需要重启）：

```json
{ "script": "group.mention-only", "target": "channel.conversation#my-group" }
```

要点：

- **脚本是阀门，不是管子**：它只决定"要不要理"，然后用 `ctx.session.activate(spec)` 发一个**不带内容**
  的信号。模型看到的消息由 Session 在组装请求时向频道拉 delta（见 `11 §5.6`），所以一批消息能合成一轮。
- **`session.run` 与 `session.activate` 的分工**：前者把一条内容递进去（要求 `userInput` 与事件文本逐字相等），
  后者不带内容、纯唤醒。新写的策略应该用 `activate`。
- 会话 id 由框架按"频道 + 挂载目标"推导，所以同一个频道共享一段历史；换了 `modelProfileId` 或
  `prompts`（选了哪一组哪个文件）会被拒绝（`Session specification is immutable`）——**提示词的正文不在 spec 里**，
  改文件下一轮就生效；要换"用哪一套"才需要换 session id。
- 脚本超时的上限是 **60 秒**，也就是一轮模型调用必须在这个窗口里回完。

## 6.1 挂载作用域：instance 才是默认选择

挂载规则有两种 scope：

| scope | 含义 | 什么时候用 |
|---|---|---|
| `{ "kind": "instance", "selector": "channel.conversation#my-group" }` | 就这一个实例 | **默认**。一条频道一条规则 |
| `{ "kind": "type", "selector": "channel.conversation" }` | 这个类型下的**每一个**实例，包括以后新建的 | 只在"我确实要所有频道都一样"时 |

两条规则可以同时命中同一个目标，而**后加的不会顶掉先前的**——`GraphManager.ApplyRulesTo` 把每一条命中的规则都挂上去：

```csharp
foreach (var rule in _rules)
{
    if (!Resolves(rule, target)) continue;
    if (_mounted.Any(m => m.Package.Manifest.Id == rule.ScriptId && m.Target == target.Address)) continue;
    _mounted.Add(new(_packages[rule.ScriptId], target.Address, rule.Id, ...));
}
```

这是有意的：一个脚本记日志、另一个决定要不要回，是合法的组合。代价是**宽的会把窄的盖掉**，而且没有任何提示。

最典型的翻车：早先按类型挂了一条 `channel.chat`，后来想给某个群「只在被 @ 时说话」，又给那个群挂了一条 `group.mention-only`。结果两条都在跑，`channel.chat` 每条消息都 `session.activate`，那个群照样每条都回 —— `group.mention-only` 里那句 `if (!event.mentionsSelf) return;` 从挂上去那一刻起就是空转的。看起来像"仅限提及失效"，其实是"又多了一条每条都理的"。

**所以：不要用 type scope 挂 `channel.chat`。** 它一旦挂上，之后所有 `channel.conversation` 实例都自动"每条都回"，包括你打算只在被 @ 时才说话的群，也包括你以后才建的频道。要给一组频道同样的策略，就逐个挂 instance 规则；多写几行，换一个能一眼看清的表。

排查"某个频道为什么每条都回"：

1. `instances_show channel.conversation#<那个频道>` —— 输出里的 `scripts:` 和 `rule:` 行就是它身上现在挂着的东西，一数就知道是不是有两条策略；
2. UI 的 Scripts 页 →「当前挂载」，看有没有 scope 是 type 的规则扫到了它；
3. 找到宽的那条，`modules.edge.unmount { "rule": "<规则 id>" }` 卸掉，再按需要补 instance 规则。

## 6.2 一个频道上默认有哪些脚本

"默认"指 `"mount": "default"` —— 加载即挂，不需要任何规则：

| 脚本 | targetType | 做什么 |
|---|---|---|
| `adapter.channel-intake` | adapter | 把适配器收到的消息交给已经绑定这个会话的频道；没有频道认领就丢弃并记一条 warn |
| `model.smoke` | channel | 只回显 `/model <prompt>`、`/session <text>` 两个前缀，其他消息一概不理（它曾经每条都回，见它自己的注释） |

回复策略**不在默认里**：`channel.chat`、`group.mention-only` 都是 `"mount": "manual"`，不挂就没人唤醒会话。一个频道收到消息、存下来、然后安静着，是正常状态，不是故障。
- `modelProfileId` 写死成 `"default"`，按你 provider 的 `module.json` 里 里的 profile id 改。

### 内置的 `model.smoke` 变了

它原来挂在**所有频道**上，对每条消息都跑一次会话并回话。第一版有了真正的回复策略之后，
这意味着群里每条消息会被回两次，其中一条是"会话规格不可变"的报错。现在它只响应显式前缀：
`/model <提示词>`（单次模型调用）、`/session <文本>`（带 `send_message` 工具的一次会话），其余消息一律不管。

## 7. 本机演练：没有 QQ 号也能跑通整条链

```cmd
:: 1. 起一个假 OneBot（推一条群消息，收到 send_group_msg 就退出）
::    它在适配器自己的目录里：src\ALN.Adapter.Qq\dev\FakeOneBot
dotnet run --project src\ALN.Adapter.Qq\dev\FakeOneBot -- --port 3001 --group 123456 --user 20000 --text "在吗？用一句话回我就行"

:: 2. 另开一个窗口起核心
run-host.cmd
```

两条路都要验：

| 场景 | 期望 |
|---|---|
| 没有 `modules/channel.conversation#qq-123456/module.json` | 消息被丢弃；信号里出现 `no channel bound to this conversation; message dropped`，`conversation: group-123456` |
| 有这个文件 | 假 OneBot 打印 `<- send_group_msg group=123456 ...`，内容是模型的回答 |

2026-11-01 实测（本机，DeepSeek `default` profile）：

```
connected: 127.0.0.1:53881
pushing group message: group=123456 user=20000 text="在吗？用一句话回我就行"
<- send_group_msg group=123456 message=[{"type":"text","data":{"text":"在的，有什么事直接说吧。"}}]
```

证据落点：频道历史（`aln.db` 的 `message` 表，owner=`channel.conversation#qq-123456`）、会话 `modules/s-*`、

## 9. 入站日志：socket 不会重放

OneBot 的正向连接**不重放**：事件从 socket 读出来之后，只存在于这个进程里。所以适配器不是"收到就发布"，而是：

1. **先写下来**：`aln.db` 的 `queued_message` 表（queue=`qq.inbound`、key 为 event id、owner 为实例地址），`payload` 就是完整的 `AdapterEnvelope`，旁边几列（平台消息 id、会话、发送者、文本、时间）供人直接查；
2. 再发布事件，并把 `eventId` 登记给 `IInboundAcks`；
3. 事件轮结束时（宿主 settle），把这条从日志里删掉。

于是"崩在收到与处理之间"不再等于丢消息：下次启动读日志，**等连上平台之后**用原 `eventId` 重投一次。

几个刻意的选择：

- **连上之后才重投**。早于连接重投，这些消息引起的回复会撞上"没有 socket 可发"——而失败的回复正是重投救不回来的东西（这条是实测踩出来的：一开始在 `StartAsync` 里重投，日志里出现 `channel.bound-send` 失败、消息被 settle 掉）。代价是重投会晚于新到的消息几十毫秒。
- **有界**：最多 512 条未交付，超了丢最老的并告警。一个永远不确认的消费者不该把磁盘写满。
- **坏了就重来**：日志 JSON 读不出来时告警并当作空的，而不是拒绝启动或者重放半截数据。
- **没有状态存储也能跑**：`InboundJournal` 明说 `IsDurable == false`，此时适配器的行为回到"尽力而为"。

重投的消息按平台消息 id 在频道侧去重（见 `17 §7`），所以"重投 + 平台自己也重发"不会变成两条回复。

## 10. 未封装的动作：`adapters.raw`

OneBot 有一大堆我们没包的动作（`get_group_list`、`set_group_ban`、`get_stranger_info`、`set_group_card`……），
而逐个包一层的结果是：宿主每加一个动作就要跟着改代码，而 NapCat 那类桥接器加功能比我们发版快得多。

所以这里只开**一扇门**，动词原样透传：

```
POST /actions/adapters.raw
{"address":"adapter.qq#qq-1", "action":"get_group_list", "params":{}}
→ {"ok":true, "data":[{"group_id":…, "group_name":…}]}
```

回包是这个适配器把平台的答复原样带回来：`{ ok, retcode, message, data }`。**不过滤、不翻译、不重试**——
`retcode` 是唯一能说清"为什么不行"（被禁言、不是群成员、群号不对）的地方，把它翻成我们的错误码等于把有用的部分扔掉。
平台拒绝调用时，这次调用本身是成功的，拒绝在 `data`/`retcode` 里。

**等级是每台实例的一个数，不是每个动词一行**（`AdapterSpec.RawAccess`，在 `module.json` 的 config 里）：

```json
{ "rawAccess": "agent" }
```

- 缺省是 **full**：这条路是**方便**，不是新权限——它存在的理由是"桥接器加功能不该等我们发版"。所以缺省放在最深，配置只能往下调；
- 写了 `"rawAccess": "agent"` 就把整扇门开给模型，**NapCat 以后新增的动作自动可用**；
- 需要逐个例外时才写 `rawActions`（例：`{ "set_group_ban": "full" }`），它只用来点名少数几条，不是清单。

生效等级 = `rawActions[verb]`（写了就用它）→ 否则 `rawAccess`（缺省 `full`）。

这条是**代码里接口等级表的第一处例外**：一个动词的深度不是写死在 `AccessLevels` 里的，而是实例数据。护栏有两条，
都在读取点：① 判断发生在**处理器内部**（`AdapterManager.RawAsync`），所以它和别的拒绝一样只经控制面那一个执行点、留一条审计；
② 配置只能把门往下调，调不上去。动作本身登记在 agent 级，否则"模型可以调这个动词"这句话根本没法写出来。

**适配器侧只要说“能透传”**：实现可选接口 `IRawAdapter`（`RawAsync(action, params)`）。`QqAdapter` 实现了它，
`FileAdapter` 没有——它没有平台动词要透传，于是它的答复是"没有这扇门"而不是"拒绝"。

## 11. 已知缺口（明确列出）

- **语音/视频**：只作为占位符（`[语音]` / `[视频]`），不下载、不上传。图片的两条路见 §12。
- **发信里的 @**：`speak` 的 `blocks` 可以 at 一个人（发送者或平台号），**不能 at 全体成员**；
  旧的纯文本 `text` 路径仍然不支持主动 @。收到的 @ 会进文本。
- **限流**：没有令牌桶，也没有"发太快先等"的处理。真实群消息密集时可能触发平台侧限制，
  目前表现为 `retcode` 非零的 `Unavailable`。
- **多账号 / 主备切换**：一个实例一个账号，没有优先级与切换（`09 §2.3` 的设计还没落地）。
- **引用回复**：框架会传 `ReplyTo`，适配器会拼 `reply` 段，但回复策略（`channel.chat`）没有用它。
- **`accountId` 只是标签**：真身来自 `get_login_info`；本适配器不校验"文件里写的"和"实际上线的"是否一致
  （两个字段分开展示：`declaredAccount` 与 `account`）。
- **只认 array 格式被测试覆盖**：`message_format: string` 走 CQ 展开路径，逻辑在，但没有对着真实客户端验证过。

## 12. 图片：入站取字节、出站发段

两件事都落在适配器这一层，因为只有它知道桥接怎么给字节、怎么收段。

### 12.1 入站

`OneBotProtocol.ReadImages(root)` 从两种消息格式里读出**图片在哪**：array 格式的 `data.url`/`data.file`，
string 格式的 `[CQ:image,file=…,url=…]`（CQ 参数里的 `&#44;` / `&amp;` 要先还原，不然它不是一个 url）。

适配器随后去取字节，**按三条路依次尝试**（`LoadImageAsync`）：

| 路 | 什么时候用 | 护栏 |
|---|---|---|
| 段里的 `url` | 桥接已经把图放出来了 | 长度先看边读边看（32 MiB）、单张 15 秒超时；失败**不**是终点（见下） |
| `get_image`（用段里的 `file`） | 段里没有 url，或 url 取不到 | 回包可能是 `url`、`base64` 或**容器内路径**，三种都认 |
| `pathMap` 映射 | `get_image` 只给了容器路径 | 只能映射到宿主登记过的 scope，映射不出就不读 |

**真机上量到的一件事**：`get_msg` 里那条 `multimedia.nt.qq.com.cn` 的 url，用裸客户端 GET 是
`400 {"retcode":-5503010,"retmsg":"invalid rkey"}`；而 `get_image` 现换出来的 url 是 `200`，
字节数对得上（5,006,624）。所以直链会过期，**取不到时回退到 `get_image` 换一条新的**——这不是"容错"，
是"唯一能拿到图的路"。取不到就只留 `[图片]` 与一条日志：一张图不该让一条消息取不到。

### 12.1.1 图「没到」的时候：三层，各自有各自的证据

这一段是**两次静默失败的产物**，写在这里是因为这个症状极容易被记到别的层头上——它自己被记错过两次。

现象永远一样：模型一直说"我看不到图片"，而 `storage/media/` 是空的、`message.media` 列全是 NULL。
下游每一层都是对的（profile 声明了 `Vision`、策略是 `first`、`MediaImages.LoadAsync`、
`ImageBudget`、`RenderChannelContextAsync` 都在），它们只是在等一个永远不来的 `MediaRef`。
**所以「下游都对」不构成任何证据**：图没到，它们本来就没有东西可做。

**按这个顺序查，每一层都有自己的证据，不要跳。**

| 层 | 看什么 | 说明什么 |
|---|---|---|
| 1. 适配器认出图了吗 | `aln.adapter.qq` 的 `offered` / `fetched`，以及 `shape` | `fetched: 1` = 字节取到了。这一层通了，问题在下面 |
| 2. Channel 存了吗 | `storage/media/` 有没有文件、`message.media` 是不是 NULL | ingest 跑过就一定落盘；空说明**没跑到**或**没有 store** |
| 3. 装配给了 store 吗 | 启动报告里 `channels: this host has no media store…` | 有这一行 = `ChannelManager` 构造时漏了 `media` 参数 |

**第 3 层真的发生过，而且是空的 `storage/media` 的唯一原因。** `ChannelManager` 是主构造函数，`media` 是
第 14 个参数；`DefaultModulesPlugin` 里那次 `new ChannelManager(...)` 用位置参数填到 `types:` 就跳到了命名参数，
**`media` 从未传入，编译器不会报警**。于是每一条带附件的消息都在 `IngestAsync` 里被丢掉，写一条
`IRestoreReporter` 的 note —— 而启动报告早就打印完了，运行时写进去的 note 没有任何人再读第二次。
桥给了图、适配器取了 5.5 MB 字节、然后什么都没有。同一个文件里那句注释还写着 "the ChannelManager above gets
the same store through host services"：**它不会自己去拿。**

现在：装配传了 `media: media`，并且 `media` 为 null 时启动报告会明写一行。

**第 1 层不通的两种形状，修法相反：**

| 形状 | `ShapeOf` 说 | 该改哪 |
|---|---|---|
| 桥接把段降级成了文本：`{type:"text", data:{text:"[图片]"}}` | `message: [text]` | 桥接那边（它没给图） |
| 段是 `image` 但没 `url` 也没 `file` | `message: [image]` | 桥接那边（它给了个空壳） |
| 数组降级了、但 `raw_message` 里有完整 CQ 码 | `message: [text]; raw_message: image` | **我们这边**（已修，见下） |

**代码上的改动：**

1. **`ReadImages` 的双格式回退**。原来 array 分支找不到 image 段就 `return`，不看 `raw_message`；
   而 `ReadText` 在 array 产出空文本时会回退。同一个事件，文本拿到了 `[图片]`、图片却拿不到。
   现在两个分支都继续看 `raw_message`，并按「桥接给这张图起的名字（`file`）」去重，
   只有一边缺名字时才退到 `url` 比——所以一张图被两种写法描述也只取一次。
2. **`inbound pictures`（Info）**：`offered` 是段里数出来的张数，`fetched` 是真取到的张数。
   **小的是要紧的那个数**：桥接给了三张、取到一张，下游分不出这跟"他只发了一张"的区别。
   真机上见过 `offered: 2, fetched: 1`——QQ 会为一张图发两个 `image` 段，其中一个没有 `url` 也没有
   `file`（多半是缩略图或表情的前身），`LoadImageAsync` 会为它记一条 Warn。
3. **`a message says it carried a picture but the bridge offered nothing to fetch`（Warn）**：
   只在文本里出现 `[图片]` 时记，附 `shape` 和截断的 `text`（各 200 字符以内）。
   只认 `[图片]` 一个占位符：`[表情]` / `[语音]` / `[视频]` 这个构建本来就不取字节，
   对它们报警只会训练读日志的人忽略这一行。

**注意日志怎么 grep。** `SignalModuleLogger` 以前在调用方给了 `detail` 时**把消息文本丢掉**，只留结构化字段——
于是记录里只有 `{"file":"x.jpg","status":"400"}`，不含任何一句人话，按文字 grep 会一无所获，看起来像这条日志
根本没写。现在 `message` 总是被塞进 `detail`（除非 `detail` 自己已经带了同名键），所以：

```
grep -o '"offered":"[0-9]*","fetched":"[0-9]*"' storage/logs/signals-*.jsonl
grep -o '"shape":"[^"]*"' storage/logs/signals-*.jsonl
```

另外 **`an inbound envelope is large`（Warn，超过 1 MiB）**：一条消息在去频道的路上有多大，是**量出来的**，
不是假设的。日志里带 `bytes` / `attachments` / `attachmentBytes` / `shape` 四个数。
真机上见过 `bytes: 7403469, attachmentBytes: 5552260`——5.5 MB 的原图。

**但「太大所以撑爆脚本」是错的方向，实测已经否定它**：一个 8 MiB 的附件序列化成约 11 MB 的 base64，
在 16 MiB 的脚本预算里 `JSON.parse` 依然过得去。真正撑爆那个预算的是 `ctx.channel.accept()` **内部
宿主的**分配（Channel 在脚本的调用栈里写图、给消息做 JSON），机制见 `docs/25 §6.0.1`。
这条日志仍然要留着——payload 大小是"这条消息本来有多大"的唯一记录，只是它不是病因。


### 12.2 出站

`speak` 的 `blocks` 经 `BuildOutboundSegments` 变成段序列：

```json
[{"type":"reply","data":{"id":"4242"}},
 {"type":"at","data":{"qq":"20000"}},
 {"type":"text","data":{"text":"看这个"}},
 {"type":"face","data":{"id":"1"}},
 {"type":"image","data":{"file":"base64://…","sub_type":0}}]
```

- **引用段在最前**（"这条在回答那条"是最外层的话）；
- 图片读 `MediaRef` 指向的文件，**编码成 `base64://`**：桥接可能在另一台机器上，同机也不归我们写；
- 读不到 → 那一块以它的文字形态（`[图片：media/…]`）发出去，消息照常到；
- 只有引用、没有正文时补一条空文本段（OneBot 拒收空 `message` 数组）；
- **没有能力声明**：适配器不对外声称自己能发什么，也没有人在发送前问。段全都在这里渲染，
  所以这里就是"发得出发不出"唯一的答案所在；发不出的块它自己拒绝，降级的块把 locator 写进
  `SendResult.Detail`（`docs/28 §6.2`）。QQ 能发全部四种块，因此今天的代码里没有一条拒绝路径。

**没有验证的**：真机取图、真机发图、真实群的 at 与表情（见 `docs/28 §8`）。
离线测过的是**协议形状**（`QqMediaWireTests`：真 Kestrel 上的假桥接——入站取图、出站 `base64://`、
取不到时的降级、超过发送上限时的降级）。

### 12.3 真 NapCat 上已知会出问题的地方

形状对了仍然会出问题的，按"现在怎么办"写清楚：

| 问题 | 来源 | 现在怎么办 |
|---|---|---|
| **大图走 base64 会把桥接撑死**：~40 MB 的 base64 段让 NapCat 退出；5 MB+ 的图已经能看到内存压力 | NapCat issue #1526、AstrBot issue #6717（那边为绕开它改成走本地路径/URL）；本机实测 5 MB base64 用了 2.8 s | 出站图片压到 `QqAdapter.MaxOutboundImageBytes` = 8 MiB，超了退回 `[图片：…]` 文字段并记日志，**消息照常发** |
| **跨设备部署时 base64 不是官方推荐** | NapCat 官方《文件处理框架指南》 | **已做**：宿主 `--media-endpoint http://<可达地址>:<端口>` 开一个只读媒体门，出站优先发 URL。本机实测 NapCat 从另一台机器来取 5 MB 用了 **611 ms**（base64 是 2785 ms） |
| **入站 url 有时效**：`get_msg` 里的 CDN 地址对裸客户端报 `invalid rkey` | 本机实测（`400 retcode:-5503010`） | **已做**：直链失败自动回退 `get_image` 换新 url（实测 `200`，字节一致） |
| **只给 `file` 不给 `url` 的段**：只有 `get_image` 能解析，且它可能回**容器内路径** | 本机实测：`get_image` 回 `{file,url,file_size,file_name}` | **已做**：先吃回包里的 `url`；`base64` / data url 也认；只有路径时按 `pathMap` 映射到宿主 scope，映射不出就记日志、留文字 |
| **文件（不是图片）没做**：群文件/私聊文件要走 `upload_group_file` / `upload_private_file` | 同上 | 仍**没有做**（这一轮明确不做）；`record` / `file` 段在入站仍是占位符 |

### 12.4 三条路，默认走 URL

出站图片有三种走法，**默认是第一条**：

| 设置 | 行为 | 什么时候用 |
|---|---|---|
| `imageDelivery: "auto"`（默认） | 宿主有媒体门就发 URL，没有就 base64 | 绝大多数部署 |
| `imageDelivery: "url"` | **只**发 URL，拿不到就退回文字 | 想确认"我的桥接真的来取了吗" |
| `imageDelivery: "base64"` | 从不发 URL，永远 base64 | 桥接够不到这台机器（NAT、不同网段、没有路由） |

宿主那一侧：**媒体门默认开**，监听 5310，URL 里的主机名取本机局域网地址（优先 RFC 1918）。

- `--media-endpoint http://<host>:<port>` 换地址/端口（多网卡、反代、容器网络时用）；
- `--media-endpoint off` 关掉，一切回到 base64；
- 端口被占用不会让宿主起不来：打一行说明，所有发送退回 base64。

门本身的三道限制：只服务 `media` 与 `workspace`、只服务探测认得出是图片的文件、只认进程内随机 token；
超过 8 MiB 不服务。

**`pathMap`（可选）**：`容器目录=scope/目录`，多个用 `;`，最长前缀优先。只有 `get_image` 回容器内路径、
而你确实挂了共享卷时才需要；它只能映射到宿主登记过的 scope。

**验证状态**：出站 base64 / URL、跨机器取图、直链过期回退 `get_image`、入站整条链都有真机数据
（见上表；入站实测：真人发图 → `inbound: attachments=image/jpeg/99945B`）。

### 12.5 文件：`upload_*` 与四条传输路

**文件不是图片的一个变体。** 三个差别决定了这里的形状（`docs/28 §6.6`）：`upload_group_file` /
`upload_private_file` 是**独立动作**（群文件不进聊天流，聊天里不会出现任何东西）；上限由平台和磁盘决定而不是
桥接内存；base64 对几十 MB 就是事故，所以它只能是兜底而不是主路。

**`file` 参数各家不一样**，这是本节存在的原因：

| 实现 | `file` 接受什么 |
|---|---|
| NapCat | 资源规范的任意形式：`base64://`、本地路径、`file://`（它自己的哈希）、`http/https`、`data:`。它的文件文档还专门建议"开一个 HTTP 端口，用 URL 传文件" |
| go-cqhttp（OneBot 参考实现） | **本地文件路径**；要发 http 文件，得先调 `download_file` 把它落到本地 |

所以路不能猜，要配：适配器设置 `fileDelivery`。

| 值 | `file` 里是什么 | 说明 |
|---|---|---|
| `auto`（默认） | URL → 路径 → base64 | 按"谁付代价"排：本进程零拷贝优先，整份内存最后 |
| `url` | 媒体门上的地址 | 拿不到门就拒绝，不偷偷换路 |
| `path` | 桥接机器上的路径 | 靠 `pathMap` **反向**映射（宿主 `scope/path` → 桥接路径，最长前缀优先） |
| `base64` | `base64://…` | 只到 8 MiB |
| `two-step` | 先 `download_file {url, thread_count}`，再用它回答的本地路径 upload | 只认路径的实现用这个 |

**`download_file` 的 `thread_count` 是分片下载**，也就是它会发 `Range` 请求 —— 媒体门因此支持单范围 `Range`
（`docs/28 §6.6.2`）。真机上 `two-step` 比直接给 URL 还快（2240 ms vs 4193 ms，5 MB），因为它真的并行取了。

### 12.6 收文件：`get_group_root_files` 与 `get_file`

反方向有它自己的两个动作，而且它们不是对称的。

| 动作 | 参数 | 回答 | 谁有 |
|---|---|---|---|
| `get_group_root_files` | `group_id` | `files[]`（`file_id`/`file_name`/`file_size`/`busid`/`upload_time`/`uploader_name`）+ `folders[]` | **只有群**。私聊没有文件区——这是「私聊不能列」的**原因**，不是我们的选择 |
| `get_file` | `file_id`（群文件还要 `busid`） | `file`：一个 url、`base64://`、`data:`，或者**桥接自己磁盘上的路径** | 群和私聊都有 |

**`busid` 是必须的第二个数**：群文件的 `file_id` 单独不够，`busid` 说它在 QQ 的哪个文件系统里。所以适配器给的
handle 是 `<busid>|<file_id>`（外面再包 `f:`），只有适配器自己会拆。

**`get_file` 回答什么是这套 API 里最不统一的一处。** 它回的是**桥接宿主磁盘上的路径**——那是另一个进程的磁盘，
我们读不到，除非两台机器共享卷并且操作者配了 `pathMap`（§12.5 那张表的反向）。所以三条路都实现了，**认不出来时
说清是哪一条走不通、两条出路各是什么**，而不是给一个 `null`（`docs/28 §6.7`）。

**跨机部署的正解是直链，不是 `get_file`。** 这一节原先写「NapCat 的 `get_group_file_url` 没实现、NTQQ 不给直链」——
**那句是错的**，2026-11-11 在真机上被推翻：`get_group_file_url`（群）与 `get_private_file_url`（私聊）都在当前
action 表里，而且拿得到腾讯的下载直链，宿主自己 HTTP 取即可，不需要共享卷、不需要 `pathMap`、也不需要
`enableLocalFile2Url`（`docs/28 §6.8`）。

三个边界都是实测出来的：

- **按会话选动作**：群（文件区与群消息附件都行）用 `get_group_file_url(group_id, file_id)`；私聊用
  `get_private_file_url(file_id)`。私聊那个动作被问及群文件时**不报错**——它回 `retcode 0` 加一个
  `http://undefined:undefined…`，所以拿到 url 之后要判它是不是一个地址，不能信 `status`。
- **`group_id` 发字符串**：这个动作的 schema 是 `Type.String`，而隔壁的列表动作收数字。同一份方言两种写法。
- **`get_file` 的 `url` 字段不是直链**：它就是 `file` 的同一个本地路径（NapCat 源码里 `url: downloadPath`），
  所以「优先取 url」救不了任何东西；真正救得回来的是上面那条。

**真机（群 `616565017`，2026-11-09 与 2026-11-11 两次）**：`get_group_root_files` **可用**（29 个文件，`busid=102`，
名字/大小/时间/上传者齐），`upload_group_file` 也可用（31 字节，1338 ms，`transport=base64`）；`get_file` 回的是
**桥接容器里的路径**（`/app/.config/QQ/NapCat/temp/…`），宿主在另一台机器上读不到。**这一半在 2026-11-11 用直链
解决了**：`get_group_file_url` 回的 CDN 直链，本机取 4835 B / 223 ms、30 MiB 的 `boot.img` / 1.46 s；私聊附件走
`get_private_file_url` 同样通（4835 B / 152 ms）。开了 `enableLocalFile2Url` 的桥接还会在 `get_file` 的回答里附带
**裸 base64**（没有 `base64://` 前缀），那是兜底的最后一条。`group_upload` 的**形状**与 NapCat 自己的类型定义
一致（`file:{id,name,size,busid}`），但机器人自己上传没有触发通知，别人上传才能验证（`docs/28 §8`）。

**超时**：`requestTimeoutSeconds`（1–300）管一次普通动作；上传另有一个 `uploadTimeoutSeconds`（10–3600，默认 600），
因为"桥接把八十兆收进自己那边"不是一次普通请求。

**真机结果**（私聊，debian 上的 NapCat）：

| 场景 | 结果 |
|---|---|
| 5 MB，`url` | ✅ 4193 ms |
| 80 MB，`url` | ✅ 21192 ms（超过了旧的 64 MiB 字节面上限，说明链通了） |
| 5 MB，`two-step` | ✅ 2240 ms |
| 1 MB，`base64`（没有媒体门） | ✅ 3318 ms |

**顺序**：一条消息里"文字—文件"的顺序在 QQ 上兑现不了 —— 文字先作为消息出去，文件随后单独上传，
`SendResult.Detail` 会说明这一点。**降级**：走不出去的文件在 `Detail` 里按名字说明原因（读不到、没有可用传输路、
平台 retcode），不会静默消失；一块都没到则整条失败。
- **`accountId` 目前只是标签**：真身是 OneBot 那边登录的账号，本适配器不校验两者是否一致。
