# 34 · 白饭：按轮计的口粮

> 状态：**已实现**（`ALN.Rice` + 框架的每轮钩子 + 商店脚本 + 13 条测试）。真机未验，见 §7。

---

## 0. 它是什么

**Lilara 自己的米缸**：一个全局库存，**session 每运行一轮消耗 1 口**。

按轮次算，不按 token：一轮一口、整数、可预算、不会因为上下文长短而漂移。一**碗**是买一次的量，**一碗 = 100 口**（`RiceUnits.BitesPerBowl`），标价 **2 元一碗**。每轮吃 1 口，所以 2 元 = 100 轮，`每轮 0.02 元`；一次三十轮的对话 = 0.6 元，模型自己能算“我还剩几分钟”。

这与硬币是两层：**硬币是钱，白饭是时间**。硬币买饭，饭换轮次。

## 1. 为什么必须新增一个框架钩子

会话循环是 `while (true)`，只在模型不再调工具时停下。所以：

> 一个不能**拒绝一轮**的限制，不是限制。

浮动块说“还剩 0 口”、工具返回一个错误——这些都只能**描述**短缺。`IRoundAdmission` 是唯一能**据此行动**的地方：

```csharp
ValueTask<Result<RoundAdmission>> AdmitAsync(RoundAdmissionRequest request, CancellationToken ct);
// RoundAdmissionRequest(SessionId, StepNumber, Level)  →  RoundAdmission(Admitted, Note)
```

在每轮开始前问一次（`SessionManager` 的 `while` 顶部）。**拒绝不花一分 token**，因为请求根本没发出去。

## 2. 没饭了不阻拦会话（口是计量，不是闸门）

拒绝的结果是：**回合正常结束**，`Note` 成为这个会话最后说的话，写进历史。会话不挂起、不失败、不归档。

下一条消息照常唤醒它——补上饭就能继续。测试钉住了这条：

```csharp
Assert.Empty(model.Requests);                       // 一分没花
Assert.Equal("白饭用完了。", refused.Value!.Text);     // 人知道为什么
admission.Refuse = false;
var ran = await sessions.TurnAsync(...);            // 下一条消息照跑
Assert.Single(model.Requests);
```

## 3. 幂等：游标，不是窗口

一轮的标识是 `(sessionId, StepNumber)`，而 step 只增不减。所以米缸里只记**每个会话最后扣到第几步**：

```json
{ "bites": 86, "revision": 12, "charged": { "s-1": 14, "s-2": 9 } }
```

比硬币那边存 64 个键更省，也更准：**重试同一个 step 不会扣第二口**——框架自己的重试不该罚模型。

## 4. 谁能动米缸

| 谁 | 怎么动 | 深度 |
|---|---|---|
| 每轮 | 自动吃掉 1 口 | — |
| 模型 | 只能看（`rice_wallet`），不能加 | agent |
| 商店脚本 | `rice.add` / `rice.take` | **full**（`rice.control` 未登记 ⇒ full） |
| 人 | `//rice` 看、`//rice topup <口>` 补 | agent / **full** |

`rice.control` 不在 `AccessLevels` 里，于是自动是 `full`——这正是“脚本能印饭、模型不能”的那道闸，和 `coin.control` 同一个机制。

**商店脚本必须声明这个能力**：`samples/market/scripts/shop.rice/manifest.json` 里 `"capabilities": ["rice.control"]`。只有 `trusted`/`builtin` 目录的脚本过得了加载校验（因为那条校验要求 `能力等级 ≤ 目录等级`）。

## 5. 买饭走商店，不另开入口

| 货架 id | 名字 | 口数 | 碗 | 价格 | 每碗 |
|---|---|---|---|---|---|
| `rice-bowl` | 一碗白饭 | 100 | 1 | 2 | 2.00 |
| `rice-basin` | 一盆白饭 | 500 | 5 | 8 | 1.60 |
| `rice-pot` | 一锅白饭 | 2000 | 20 | 30 | 1.50 |
| `rice-bucket` | 一桶白饭 | 5000 | 50 | 70 | 1.40 |

```jsonc
{ "id": "rice-basin", "name": "一盆白饭", "price": 8, "script": "shop.rice", "stock": -1 }
```

`coin_buy rice-basin` → 扣 8 枚硬币 → 跑 `shop.rice` → 脚本调 `rice.add(500)`。三步都在硬币那边的现有事务里，白饭插件不用自己做商店。

**四个套餐共用一个脚本**（`shop.rice`）：货架决定卖什么、多少钱（`goods.json`），脚本决定一份补多少口（`main.js` 里的 `menu` 表）。这是有意分开的——价格是生意，口数是规格，改一个不用动另一个。代价是两边要对得上：货架上出现了脚本不认识的 id，脚本**抛错**、`coin_buy` 退款、什么也没补。宁可这次买不成，也不要收一桶的钱补一碗的饭。

`count` 会乘：`coin_buy rice-pot count=2` 是 60 枚硬币、4000 口。不乘就是收两份钱补一份饭。

## 6. 每轮注入

`rice.context` 每轮一行：`白饭：86 口（≈0.86 碗，还能跑 86 轮）· 每轮 1 口`。只读——浮动块可能渲染多次，绝不能在那里扣饭。

## 7. 没验证的部分

1. **真机零次**：没起过 host，没在真会话里跑过一轮。
2. **`shop.rice` 的对象传参：现在验过了**。`ctx.actions.call("rice.add", { bites: 500, reason: "…" })` 这种写法在真 Jint 下可行——`RiceShopScriptTests` 直接跑 `samples/market/scripts/shop.rice/main.js`，四种套餐各验一遍口数、`count` 乘算、以及"货架上的 good 脚本不认识"时抛错退款。**仍未验**的是它经过 `GraphManager.InvokeToolAsync` 的那一段（`WhyRejected`、能力名白名单、`WireName` 派生）：测试绕开了图，自己造了 `ScriptManifest`。所以"货架在真 host 里挂得上"和"买一次能拿到饭"这两件事，还得起一次 host 才算数。
3. **`IRoundAdmission` 只被一个 source 用过**：多 source 的聚合（id 顺序、首个拒绝即停）有单元测试，但没有两个真实插件同时注册过的场景。
4. **`charged` 永不清理**：每个跑过的会话在米缸里留一行，删掉的会话也会留着。量级很小（一行），但不回收就是不回收。
5. **饿着的时候不落系统提示**：`Note` 通过 `finalText` 变成模型的话，所以历史里是“模型说没饭了”。如果要区分“系统说”与“模型说”，得改历史写入路径。
6. **没有预警**：吃到最后一口时不会提前提醒。`rice_wallet` 随时可查，模型要么自己看，要么饿一次。
7. **容量/初始值**：初始 0（与钱包一致），没有 `rice.initial` 参数。

## 8. 模型看得到吗

看得到，两条路：

| 路径 | 时机 | 内容 |
|---|---|---|
| `rice.context`（浮动块） | **每轮自动**，不用问 | `白饭：86 口（≈0.86 碗，还能跑 86 轮）· 每轮 1 口` |
| `rice_wallet` 工具 | 想确认时调，免费 | `{ bites: 86, rounds: 86, thisSessionAtRound: 14, perRound: 1, bitesPerBowl: 100 }` |

数字口径是**口**（`bites`）：每轮吃 1 口，所以米缸里的数字**就是还能跑几轮**——这是模型唯一需要拿来做计划的数字。碗只在展示和购买时出现（一碗 = 100 口 = 2 元），折算写在括号里，避免模型拿"0.86 碗"去做整数运算。

浮动块是只读的：浮动块可能一回合渲染多次，在那里扣饭会让一轮吃两顿。

## 9. 更正：口是计量，不是闸门（2026-11-10）

第一版把 `RiceAdmission` 写成了**闸门**：0 口就拒绝这一轮。那看起来符合“限额”，实际违反了你说的“白饭耗尽不会导致会话中断”——拒绝一轮，会话就不回话了，而人只会看到“它不理我”。

现在的语义：

| 情况 | 行为 |
|---|---|
| 有饭 | 吃 1 口，正常跑 |
| **0 口** | **照常跑**，米缸记成负数（欠账） |
| 欠账 | 下次买饭/补饭先把欠的还上（`-3` + 100 = `97`） |
| 存储坏了 | 照常跑，只是这一轮没记上 |

`IRoundAdmission` 仍然用它——**它是“每轮恰好一次”的记账点**，而不是拒绝点。要不要真正的硬限额，是部署的决定；默认不开，因为让一个会话突然闭嘴比记一个负数糟糕得多。

代价要认：**白饭不再是约束**，模型可以一直透支。要“考察资源管理”，得靠浮动块与工具把数字摆在它面前（`白饭：-12 口（≈-0.12 碗，还能跑 -12 轮）· 每轮 1 口`），而不是靠拦它。

## 10. 为什么货架上是空的（2026-11-10，第二处）

把白饭放进 `storage/scripts/trusted/shop.rice/` 之后，启动日志仍然是：

```
market: rice-bowl: 脚本 shop.rice 不存在或不可当工具调用，不上架。
```

原因不在路径，在**能力白名单**。`GraphManager.AllowedCapabilities` 是一个封闭集合，`shop.rice` 声明了
`"capabilities": ["rice.control"]`，而 `rice.control` 不在里面 → `WhyRejected` 返回
"Unsupported capability" → 包根本不加载 → `CanRun` 找不到它 → 商品被剔除。

这是个设计上的漏洞，而不是配置错误：**一个"未登记 ⇒ full"的能力名，脚本声明不了**，因为脚本的能力必须在
白名单里。于是 `coin.control` / `rice.control` 这类"故意不登记"的名字，恰好是脚本永远用不到的名字。

修法是把这两个名字加进 `AllowedCapabilities`。安全性没有变化：它们仍然不在 `AccessLevels` 里，所以仍然是
`Full`，而 `tooDeep` 那条检查要求 `能力等级 ≤ 目录等级`——只有 `scripts/trusted` 与 `builtin` 的脚本能声明。

教训（两处都是同一个形状）：**货架为空是"商品被剔除"的唯一症状，而剔除的原因有三层**——
目录里没有脚本、脚本被 `WhyRejected` 拒了、脚本没有 `call`。三层都静默。要么让 `market:` 行说出是哪一层，
要么让剔除变成启动时的显式失败。
