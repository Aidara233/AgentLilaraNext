# 21 · 记忆：一个记忆组一具身体，碎片在它脚下

> 本文回答一个问题：**上一次学到的东西，怎么到下一次去，而不会变成一堆没人能核对的摘要。**

---

## 0. 一句话

记忆是**磁盘上的一个目录**：`memory/<记忆组>/` 里有 `block.md`（这一组的主体）和 `lines.jsonl`（碎片，只追加）。
平时上下文里只有**组名**；要打开某一组，才展开它的整棵树、读它的主体、把它引用的碎片原文贴上来。
整理不是后台任务——是模型看到"这一组攒了 400 条"时自己用文件工具做的事。

---

## 1. 两层，两个文件

| 层 | 是什么 | 长什么样 | 谁写 |
|---|---|---|---|
| **记忆块**（block） | 结论。一组的正文，几百行，人一眼能读完 | `block.md`，一篇一个文件，**整篇重写** | 模型（`fs_write` / 记忆工具） |
| **碎片行**（line） | 听到的、看到的。便宜、可重复、可以是错的 | `lines.jsonl`，**一行一条 JSON，只追加** | 模型（`remember`） |

为什么是两层而不是一层：把这两种东西放进一个文件，结局只有两个——把闲聊当知识复述，或者把结论降级成闲聊。
分开之后，块可以收紧（必须引用原文），碎片可以放宽（写就完了）。

为什么"碎片"是追加而不是"一条记录一次 upsert"：

- **追加是一次写**，没有"先读后写"的竞争窗口；两个回合同时记同一件事，不会互相覆盖。
- 重复本身就是信息："这件事他又提了一次"。曾经用 `repeats` 计数表达这件事，现在它就是两行——更便宜，也不会因为一次合并判断而丢掉一条原话。
- 行**写完就不再修改**，所以它可以被引用（§3）。

```
<dataRoot>/memory/
├── 关系-小林/                 ← 一级只能是目录（记忆组），根下不放文件
│   ├── block.md              ← 这一组的主体
│   ├── lines.jsonl           ← 活跃的碎片：只追加；折叠完搬走，下次追加自动重建
│   ├── history/
│   │   └── lines-2026-11.jsonl   ← 折叠后的碎片：不可变，照样能被引用
│   └── …                     ← 组内其它文件（模型整理出来的分册、附件），没人管你怎么放
└── 项目-ALN/
    ├── block.md
    └── lines.jsonl
```

**记忆组是主题，不是对话。** `关系-小林` 而不是 `2026-11-05 那个群`。碎片行里带 `src`（来源频道/会话）回答"这话是在哪说的"，
组的划分回答"这事关于什么"。两者分开，一段对话里学到的东西才能在另一段对话里被想起来。

## 2. 一条碎片行

```json
{"id":"l-3f2a9c11","text":"部署改到周五，因为周四客户开始冻结","at":"2026-11-05T09:12:31Z",
 "who":"小林(同事)","src":"channel.conversation#chat-auto"}
```

| 字段 | 为什么有它 |
|---|---|
| `id` | 正文引用它用的名字（§3）。随机而不是自增：两个进程写同一组不能撞号 |
| `text` | 归一化后的原话（空白折叠、去首尾）。**不做模糊合并**：`改到周五` 与 `改到周一` 必须是两行 |
| `at` | 排序靠时间衰减，所以时间不能猜。**没有时间的行直接跳过并计数**，而不是当作"现在"——那会把它推到每次检索的最前面 |
| `who` | 平台当时怎么称呼这个人（`名字(备注)`）。名字事后取不回来，而这一行比那段对话活得久 |
| `src` | 来源：频道地址、会话 id、工具名。给人看的注记，不是连接键 |

读的一侧**全部按"文件可能被模型改坏"来处理**：坏行跳过并报数、缺 `block.md` 当作空块（而不是"这一组没了"）、
库根下的散落文件忽略。都不自愈——一个悄悄修好自己的库，等于什么都没教会人。

---

## 3. 证据是引用，不是复制

`block.md` 里写结论，结论后面写 `[l-3f2a9c11]`。读这一组时，被引用的行原文贴在正文下面。
被引用的行已经不在了（被删掉、被搬到别处）就**如实说那一行不在了**。

这一条替代了旧设计里"笔记必须把原文抄进 `evidence` 字段"：

- 行不可变 → 引用永远不会因为有人编辑而失真；
- 引用比复制省一个数量级；
- 折叠（把 `lines.jsonl` 搬进 `history/`）不会让引用烂掉——读取时扫的是整棵树。

**代价**：行的 id 一旦被正文引用，就不能再回收复用。所以 id 是随机的，而且没有"压缩 id"这一步。

## 4. 谁在什么时候看得到什么

| 时机 | 看到什么 | 为什么 |
|---|---|---|
| **每一轮** | 全部组名，一行：`记忆库（3 组）：关系-小林、项目-ALN、运维` | 一个连"有什么组"都不知道的模型会用不上记忆；把主体倒进来会在每轮为这一轮不需要的组付钱 |
| **打开某一组**（`read_memory`） | 整棵树（相对路径 + 字节）+ `block.md` 全文 + 被引用的碎片原文 | 树回答"我把它整理成什么样了"，块回答"结论是什么"，引用回答"凭什么" |
| **检索**（需要时） | 按 query 打分的前 N 条碎片 | 从几百条碎片里挑相关的，需要模型自己对问题的理解；所以它是工具，不是每轮的固定开销 |

**组多也全列，不截断。** 选择性注入等于替这一轮判断哪些主题重要，而这个判断需要它没有的上下文；
"已经有 40 组"是有人该去处理的事实，不是该藏起来的东西。超过上限时那一行**多一句**提示（合并/删掉），
只提醒，不隐藏。

## 5. 工具只有两个，其余交给文件系统

| 工具 | 参数 | 做什么 |
|---|---|---|
| `remember` | `group`、`text`、`who`（可选） | 往那一组的 `lines.jsonl` 追加一行；组不存在就建 |
| `read_memory` | `group` | 树 + 主体 + 被引用的碎片 |

**没有 `recall`，没有 `forget`，没有 `consolidate`。** 整理记忆的每一种动作都是一次文件操作，而文件系统模块已经提供了：

| 想做的事 | 怎么做 |
|---|---|
| 把碎片折成结论 | `fs_write` 重写 `block.md`（引用 `[l-…]`） |
| 折叠完腾空活跃文件 | `fs_move` 把 `lines.jsonl` 搬到 `history/lines-<年月>.jsonl`（下次 `remember` 自动重建） |
| 合并两个主题 | 把文件 `fs_move` 到另一组，再重写两边的 `block.md` |
| 删掉一整组 | `fs_remove` 那一组的目录 |

这条分工是刻意的：**记忆模块只定义"记忆是什么形状"，文件系统模块只提供"受控的文件动作"。**
如果记忆模块自己长出一个"整理"工具，它就得为今后每一种整理方式再长一个。

### 为什么组名会被校验，而不是被改写

组名同时是目录名。`../x` 那种名字一律**拒绝并说明是哪一段不对**，绝不改写成 `.._x`——
改写会让两个不同的名字在磁盘上撞成一个，而调用方永远不知道自己写的那条记到了哪一组。

---

## 6. 容量：提醒，不自动删

| 数 | 值 | 到顶时 |
|---|---|---|
| 组 | 64 | **拒绝新建**并说明"先合并或删掉一组"——500 个主题的库等于没有人查的库 |
| 单组碎片 | 2000 | 写入**仍然成功**，返回里说明该折叠了 |
| 组内碎片提示线 | 400 | 每轮那一行把它点名 |
| `block.md` 单篇 | 256 KiB | 拒绝：这个大小的东西是别人该管的文档，不是一句结论 |

**没有任何自动过期、自动归档、自动删除。** 留存默认永久，清理是显式的——这一条沿用 `09 §8` 的裁定。
唯一会自己变小的机制是"追加撞到上限时那句提示"，它不删任何东西。

---

## 7. 明确不做

| 不做 | 为什么 |
|---|---|
| 每轮注入条目本身 | 会把有用的三条淹在三十条里，而且每轮都付一次 |
| 后台整理 daemon | 合并需要读原文、判断"这两句说的是同一件事"不是扫描器能做的事 |
| 让存储决定什么是真的 | 记忆库只有增、读、删；没有 `Consolidate()` |
| 把记忆挂在会话上 | 会话注定被替换；组是主题，比会话活得久 |
| 自动清理 / 墓碑 / 版本历史 | 见 §6；整理 = 写块 + 搬走碎片，一步到位 |
| 向量 / 全文索引 | 中文分词换不来什么，bigram 重叠 + 时间衰减够用；真要换，换的是检索实现 |
| 跨组"全局记忆" | 一组就是一切；没有"我是谁"这个实体之前不引入第二个维度 |

## 8. 这套东西自己的失效点

**① 组名选错，等于没记住。** 组太粗（`杂项`）→ 打开一次要读几百条；组太细（一人一组一条）→ 组名清单一长，
每轮那一行就开始挤占上下文。这一条没有技术解，只有"看清单、合并"。

**② 引用会失效，但会说出来。** 行被删掉之后 `[l-…]` 仍然在正文里，读取时会说"这一行不在了"。
不自动剔除引用，因为那是替作者改结论。

**③ 检索是启发式。** 同义改写、代词、跨语言都匹配不到。缓解办法是让 query 由模型自己写（它知道上下文），
而不是让框架从最后一条消息里抽词。

**④ 排序参数是拍出来的。** 半衰期 30 天、被引用行 ×1.25——能用的默认值，不是算出来的最优值。
