# 21 · 记忆：碎片、笔记，与笔记脚下的证据

> **现状**：已实现。契约在 `src/ALN.Contracts/Memory/MemoryContracts.cs`，存储是 `aln.db` 的 `memory` 表（schema v5），
> 会话侧是**一个模块的两个入口**：三个工具（`src/ALN.Runtime/SessionMemoryTools.cs`）与一行每轮重算的浮动摘要
> （`MemoryContextSource`），都由 `MemoryModule` 在初始化时注册进 `ISessionExtensionRegistry`
> （`src/ALN.Runtime/Kernel/MemoryModule.cs`），测试是 `MemoryStoreTests` / `SessionMemoryToolTests` / `MemoryModuleTests`。
> 本文回答一个问题：**上一次会话学到的东西，怎么到下一次去，而不会变成一堆没人能核对的摘要。**

---

## 0. 一句话

记忆分两层存：**碎片**（说过、看到过，便宜、可重复、可以是错的）和**笔记**（结论，必须带着它脚下的原文）。
整理不是后台任务——是模型在 `recall` 看到"碎片 40 条、笔记 0 条"时自己做的事。

---

## 1. 三层，只存两层

| 层 | 是什么 | 能不能再生 | 现在的落点 |
|---|---|---|---|
| **一手观察** | 会话自己的时间线：谁说了什么、模型调了什么工具、结果是什么 | 不能 | `sessions/<id>/history.jsonl`（`08 §5.2`） |
| **系统条目**（note） | 结论 + 边界 + **内联证据** | 能（从一手观察重新推出来） | `memory` 表，`kind = 1` |
| **碎片**（fragment） | 一句原话、一条观察 | 能（再听一遍就有） | `memory` 表，`kind = 0` |

只有两层进表，因为时间线本来就是一手观察：**记忆不该复制它，只该指向它、压缩它。**
一句话被记住两次（时间线一次、碎片一次）不是冗余，是分工——时间线回答"当时到底怎么说的"，碎片回答"这件事值得再想起"。

### 重复：一行，加一个计数

同一段话在同一段对话里被记第二次时，`AddAsync` **不新增行**：

| 变化 | 为什么 |
|---|---|
| `repeats` + 1 | 重复本身是信息："这件事他又提了一次" |
| `at` 刷到现在 | 排序按时间衰减，刷新等于"它又变新了"——这正是"重复"该有的效果 |
| `evidence` 换成最新的原话 | 读者要核对的是**最近一次**是怎么说的 |
| `id` 不变 | 别的行 / 笔记里提到过它，就不该在重复时变成悬空引用 |

判定"同一段话"的规则很钝（`MemoryText.Normalize`：去首尾空白、内部空白折叠）：

- **不做模糊匹配**。`部署改到周五` 和 `部署改到周一` 必须是两行；能合并这两句的规则，是会把事实删掉的规则。
- `kind` 不同就是两行：同一句话作为碎片和作为笔记，可信度不同（§1）。
- 工具的回答也分开：新建时"记下了 `mem-x`"，重复时"这条已经记过了，时间刷新到现在（第 2 次）"。
  悄悄 upsert 会让模型以为"我又记了一条新的"，于是每轮都再写一遍。

**`repeats` 不参与打分。** 它只让行的时间变新（时间衰减已经因此生效）；再把次数乘进分数，等于让"说得最多的"赢，
而 query 问的是"哪个更相关"。整理时它有用：一条说过五次、时间还在往前走的碎片，通常是写一条笔记的最佳素材。

### 为什么 `kind` 必须是两个值

两类东西的可信度不同。碎片是"我听到的"，允许重复、允许记错；笔记是"我判断的"，一旦错了，
后面每一次 recall 都在替它传话。混成一种，就只有两个坏结局：把闲聊当知识复述，或者把结论降级成闲聊。
分开之后，笔记被允许收紧一点（必须带证据），碎片被允许宽松一点（写就完了）。

## 2. scope：记忆属于对话，不属于会话

```csharp
public sealed record MemoryDraft(
    string Scope,          // 谁的记忆：adapter/channel 的地址文本（今天的连接键）
    MemoryKind Kind,       // Fragment | Note
    string Text,
    string? Evidence,      // 原文引用，笔记必填
    string? Source,        // 谁写的：写入那个会话的 id，用于追查一条坏记忆
    DateTimeOffset? At);
```

**scope 不是会话 id。** 会话是这套系统里唯一**注定被替换**的东西（归档、重启、重建），
记忆挂在它身上等于"换个人就失忆"。所以 scope 是这段对话的地址——会话 id 本来就是**由它哈希出来的**（`19 §1`），
换会话不换 scope，这正是"下一个人接着上一个人记住的事"能成立的原因。

scope 是**文本**而不是 `Address`：存储层不认识模块地址，也不需要认识。它只是一个键——和 `IStateStore` 的
`scope + key` 同一类东西（`17 §3`），只是这里一行一条，能查、能排序、能删。

> ⚠️ 这一条将来会动：`19` 的 connection 实体落地后，连接有了稳定 id，scope 应当换成那个 id。
> 现在用地址文本，是因为地址文本就是当下唯一稳定的对话标识。换的时候要迁移，不要新旧并存（见 §8）。

## 3. 证据内联，不是指针

笔记存证据的**原文**，而不是"见 `sessions/s-xxx/history.jsonl` 第 12 条"：

1. **指针会烂**：那条会话被归档之后，指针指向的东西就不在原来的位置了。记忆是最长寿的一层，
   不能依赖最短命的一层。
2. **没有证据的结论无法被反驳**：模型把"周五"记成"周四"，如果只存结论，下一个读者只能继承这个错误；
   存了原文，下一个读者能看见**结论和原文不一致**——这是"摘要洗白错误"的唯一解药。

代价也很清楚：同样的内容在库里出现两次，文本会更大（上限：笔记 8000 字、证据 20000 字，`IMemoryStore.Max*`）。

## 4. 排序：代码算，不用全文索引

`e_sqlite3` 这个原生库是带 FTS5 的构建，但这里**没有用它**，理由是中文：

- 全文索引靠**词边界**，而中文没有空格；`unicode61` 分词器对中文基本只能整段匹配，
  查 `部署` 找不到 `周五下午部署`。
- 于是匹配放在契约层用代码做：query 拆成词项，CJK 连续串**额外拆成字符二元组**（`部署时间` → `部署时间`、`部署`、`时间`），
  按"命中的权重 / 全部权重"算覆盖率；再乘**时间衰减**（半衰期 30 天，永不为 0）与**笔记加成**（1.25）。

放在 `MemoryRanking`（契约层静态类）而不是某个后端里，是因为**两个后端对同一个问题给出两种顺序**这种 bug 不会有人发现。

两条行为约定，测试里钉着：

- **空 query = 最近的**（"看看现在是什么情况"不需要编一个关键词）；
- **query 没有命中 = 空**，而不是"把最近的几条当匹配返回"。后者会让模型以为检索成功了。

代价：同义改写匹配不到（"推迟" 与 "改到"）。这是启发式的天花板，不是 bug；真要跨语义检索，换的是
`IMemoryStore.SearchAsync` 的实现，契约不用动。

## 5. 三个工具，和 `wait` 同一类

| 工具 | 参数 | 说明 |
|---|---|---|
| `remember` | `text`、`kind`（fragment / note）、`evidence` | 笔记没有 `evidence` 直接拒绝；`kind` 不认识也拒绝（不默认 fragment） |
| `recall` | `query`（可省）、`kind`（all / fragment / note）、`limit`（默认 20） | 返回条目 + **内联证据** + 本会话的碎片/笔记条数 |
| `forget` | `id` | 删一条；删不存在的不算错 |

### 为什么是模块提供的工具，而不是 spec 声明 + 工具箱

`08 §5.0` 说的是"spec 只点名、实现由模块提供"，`wait` 是唯一的例外。记忆不是例外：它现在就是一个模块
（`MemoryModule`），通过工具源把三个工具交给每个会话——和别的模块给工具的方式完全一样。它需要被特别照顾的
只有一点：

> **它必须能在"没有任何人说话"的那一轮里用。**

`20 §5` 的唤醒轮里，宿主交过来的工具箱是空的——那一轮没有任何频道事件，`speak` 本来就用不了。
而那一轮恰恰是会话最可能思考的时候。工具源是**按轮**产出的，不依赖频道事件，所以记忆在那一轮照样在。

### 失败要能被读到

- 没有存储 → 工具不出现；模型硬调 → 回合以"tool was not offered"失败（不是静默 no-op）。
  一个以为"我记住了"的模型，比一个知道"这儿记不了"的模型危险得多。
- 参数错 → 错误回到模型手里，它可以当场改（`08 §5.1` 的同一条）。

### 每轮那一行（浮动，不落盘）

工具有一个洞：**不调用 `recall` 的模型，不知道有什么可 recall**。于是"记住"会悄悄退化成"存着不用"。

补它的是一行浮动上下文（`MemoryContextContributor`，section = `memory`，`Order = -90`，在时间之后）：

```text
这个会话记住了 12 条碎片、2 条笔记。要翻用 recall，要写用 remember。
最近一条笔记（2026-11-01）：周五下午部署
碎片已经攒到 12 条、笔记还只有 2 条。把反复出现的、互相印证的那些整理成一两条 note（附上原文证据），
再用 forget 删掉被吸收的碎片——不整理的话，下次 recall 只会捞回一堆重复的碎片。
```

四条约定：

- **只报计数、最近的笔记、和缺口**，从不把条目本身倒进来。`recall` 之所以是工具，是因为"该捞哪条"需要模型对问题的理解；
  每轮灌三十条既花钱，又把有用的三条淹掉。
- **空记忆什么都不说**：每轮一句"你什么都没记住"是噪音，而噪音正是让真提醒看不见的东西。
- **存储读不了就不说，不失败**：记忆是加分项，它短暂不可用不该让这一轮答不上话。
- **缺口提示与工具里那句是同一句**（`MemoryGuidance.ConsolidationHint`）：阈值写在两处必然漂移，而它守的这个故障是无声的。

漂浮块不落盘（`11 §5.1`），所以这一行不会在历史里积成垃圾。

### 一条容易被忽略的细节：`actingTools` 不数记忆工具

会话循环用"本轮有没有能办事的工具"决定"只产出正文的一步算不算回复"（`08 §5.1`、`SessionManager.ShouldReplay`）。
记忆工具如果算进去，所有会话的这条判断都会翻转——包括那些什么都不记得的。
所以工具源交回每个工具时会说清它是否"对外办事"（`SessionToolOffer.ActsExternally`）：记忆的三个都是 `false`，
`speak` 是 `true`。循环只数 `true` 的那些，不需要记住任何工具名。

## 6. 整理：为什么没有后台任务

整理 = 把若干碎片折成一条笔记：

```
recall(query=…)  → 看到 12 条碎片、0 条笔记，结果末尾给出提示
remember(kind=note, evidence="他说：那就周五吧……")   ← 结论 + 原文
forget(id=mem-…) × 12                                ← 被吸收的碎片
```

**触发者是模型，不是扫描器。** 谁来决定"这两条碎片说的是同一件事、并且该合成一句什么"？只有读过原文的那个东西能决定。
后台任务只能在没人看的时候猜；猜错了要静默很久才发现，而且发现的人还是模型。

代价要诚实：**模型可以一直不整理**，碎片只增不减。缓解两条：

1. 提示就在 `recall` / `remember` 的返回里（碎片 ≥ 10 且 ≥ 笔记 × 5 时说一句），它每次用记忆都会看到；
2. 检索只读最近 5000 行（`SearchCeiling`），所以"不整理"的后果是**旧碎片搜不到**，而不是越来越慢到卡死。

## 7. 明确不做

| 不做 | 为什么 |
|---|---|
| FTS5 / 向量检索 | 中文分词与额外依赖；bigram 匹配已经够用，真需要时只换 `SearchAsync` 的实现 |
| 后台整理 daemon | 见 §6：合并需要读原文，判定"同一件事"不是扫描器能做的事 |
| 让存储决定什么是真的 | 存储只有增删查，没有 `Consolidate()`；有的话它就在替模型下判断 |
| 记忆挂在会话上 | 会话注定被替换（`19`） |
| 跨 scope 的"全局记忆" | 现在没有"我是谁"这个实体；等 connection / agent 身份落地（`19`）再说 |
| 墓碑 / `ReviewedAt` | 整理 = 写笔记 + 删碎片，一步到位；墓碑是另一套一致性，现在不需要 |
| 被遗忘的条目留审计 | 记忆是模型的工作笔记，不是证据链；需要证据的是 `audit` |

## 8. 这套东西自己的失效点

**① scope 仍然依赖地址文本。** 连接实体（`19`）落地后，地址文本会变成"由更稳定的连接 id 派生"。
如果那时候顺手改了地址的写法而没迁移 `memory.scope`，症状是**记忆还在、但再也 recall 不到**——
而且不会报错，只会"这次它不记得了"。所以换 scope 必须是一次显式迁移，不能新旧并存。

**② 模型可以不 recall，而浮动那一行只是提醒。** 每轮会带一句"记住了 N 条碎片、M 条笔记 + 最近一条笔记"（§5），
所以"存着不用"不再是默认结局；但**具体条目仍然只有模型主动 `recall` 才会进上下文**。这是刻意的：
每轮灌条目会把有用的三条淹在三十条里。它的代价是：模型如果连 `recall` 都想不到，它就只知道"有东西、最近一句是什么"。

**③ 排序是启发式。** 同义改写、代词、跨语言都匹配不到。缓解办法是让 `recall` 的 query 由模型自己写
（它知道上下文），而不是由框架从最后一条消息里抽词。

**④ 碎片无限增长的唯一刹车是模型自觉。** 见 §6 的代价。

## 10. 真跑一轮记录（2026-11-04）

环境：宿主 + `adapter.file` + `channel.conversation#chat-auto` + `channel.chat` 脚本 + `deepseek-flash`。
消息从 `io/file/file-1/inbox/chat-auto/*.ready.json` 投进去，回复落在 `outbox/chat-auto/`。

| 轮 | 投进去的话 | 模型做了什么 | 结果 |
|---|---|---|---|
| 1 | "记一下：部署改到周五了……用 remember 记成一条碎片" | 调 `remember(kind=fragment)` | `memory` 多一行，`source` = 该会话 id |
| 2 | "上次说的部署挪到哪天了？先用 recall 查" | 调 `recall(query=部署)` | 答"查到了：部署挪到周五，因为周四开始客户冻结" |
| 3 | "再记一次同一件事：……" | **不调工具**，只说话："这条已经在记忆里了，内容一模一样，再写一遍只是多一条重复，我就不加了" | 表里仍是一行 |
| 4 | "调用 remember 工具，参数用 kind=fragment、text=……" | 仍**不调工具**，同样理由 | 表里仍是一行 |

第 2 轮那次请求里，浮动块确实是活的（从 `artifacts/model-calls/` 里取原文）：

```xml
<section name="memory" source="system.memory" id="memory">
这个会话记住了 1 条碎片、0 条笔记。要翻用 recall，要写用 remember。
还没有笔记：碎片攒够了就整理成一两条（带原文证据），再 forget 掉被吸收的那些。
</section>
```

### 真跑抓到的东西

**① 一个真 bug（已修）**：第二轮直接 HTTP 422 `messages[14]: missing field `content``。原因是生成请求时，`content` 为 null 的消息会**整个省掉这个字段**，而"只调工具、不说话"的助手消息正是这个形状——`wait` 结束的一轮就是它。也就是说第一次真正重放这种轮次就会炸，而这件事在任何假模型测试里都看不见。现在 `content` 永远存在（空串），并抽成 `ChatPayload.Message` 好让这条规则能被单测钉住（见 `ChatPayloadTests`）。

**② 重复计数比预想的少见**：模型在"同一件事再记一次"和"明确要求调工具"两种说法下都**拒绝重复写**，理由说得比人还清楚。所以 `repeats` 主要来自"看不到早先那一轮"的会话（归档后新建、另一个 `scope` 相同但历史不同的会话），而不是连续几轮。这条不是缺陷，但它说明：**重复计数的价值在跨会话，不在同会话**。

**③ 一个真缺口（已修，`docs/11` 覆盖了原描述）**：第一轮失败之后，那条消息的正文**再也没进入过请求**。频道增量游标（`channel.delta`）是在拼请求时推进的，而请求失败之后游标不会回退；重启后"待处理消息重放"也没有把它捞回来（脚本自己把 `session.activate` 的失败吞成了一条日志，事件因此算处理完）。

现在改成：`ClaimDeltaAsync` 只读，交回一个 `ITurnCommit`；Session 在这一轮**写下来之后**才执行它。失败的一轮什么也不提交，于是那几句话还在，下一轮重新交付。重复交付由 timeline 的消息 id 幂等吸收，所以"至少一次"在这里比"最多一次"便宜。
证据：`ChannelDeltaTests.A_turn_that_failed_leaves_the_message_pending_for_the_next_one`——第一轮让 provider 失败，第二轮请求里那句话**出现且只出现一次**；修完再真跑一轮，回复"周五。周四开始客户冻结，所以挪到了周五"，游标 17 → 18。
