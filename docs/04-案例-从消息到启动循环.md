# 案例：一条消息 → agent 启动循环（全链路）

> 状态：早期案例草案。前置：[`01`](01-模块切分.md) / [`02`](02-图模块.md) / [`03`](03-自由逻辑.md)。
> 当前 Jint 脚本编排方向与最小闭环见 [`13-脚本编排与工程实施蓝图.md`](13-脚本编排与工程实施蓝图.md)；本文静态订阅链路和规则条件案例需要按新模型重写，暂不作为实现依据。
>
> **输入**：适配器收到一条消息。**输出**：agent 会话开始推进（"启动循环"）。
>
> ⚠️ 本文写于"订阅表"之前（[`02` §2](02-图模块.md)）。按订阅模型读：下面每张"图"都是**一条订阅（一条边）**，而 B 与 C **订阅的是同一个事件、互不影响**——这正是"接收方连发起方"的直接红利（加消费者不改发起方）。"一步"则已改为**过程**（[`02` §2.1](02-图模块.md)），不再是多节点图。
>
> 中间夹着一次**条件判断**（含关键字就回复/叫醒 agent）。本文把每一跳都写出来，用来检验"跨模块一律走图"是否自洽。

---

## 1. 全链路（入向）

| # | 谁在动 | 做什么 | 是否跨模块 |
|---|---|---|---|
| 1 | `adapter.qq#1` | 平台回调 → **清洗**成规范化消息（msgId / 频道 / 发送者 / UTC / 附件引用），原始报文留存 | 内部硬代码 |
| 2 | `adapter.qq#1` | `emit adapter.message.received`（经契约层 `IEmit`，模块不知道图存在） | 事件泵 |
| 3 | **图 A** `on adapter.*.message.received` | ① `resolve $source.storeRef → store` ② `call store.*.put(raw)`（原始数据入库）③ `call channel.*.intake(msg)` | **是** |
| 4 | `channel.group-1234` | **去重**（msgId）→ 整理（排序、窗口裁剪、参与者）→ 进内存窗口（**此处不落库**） | 内部硬代码 |
| 5 | `channel.group-1234` | `emit channel.intake.done` | 事件泵 |
| 6 | **图 B** `on channel.*.intake.done` | `call store.*.put(msg)`（去重清洗后的数据入库） | **是** |
| 7 | **图 C** `on channel.*.intake.done` | ① `map rules = $source.rules` ② `call logic.any.eval { rules, input: $event }` → `decision` ③ `call channel.*.apply { decision }` | **是** |
| 8 | `channel.group-1234` | `apply(decision)`：`kind ∈ {ignore, post, inject}`；`post` → 走模板直回；`inject` → `emit channel.decision.inject` | 内部枚举分派 |
| 9 | **图 D** `on channel.decision.inject` | `call session.*.inject(text)` → `call kernel.enqueue(sessionId)` | **是** |

⚠️ **条件判断只出现在第 7 步的第 ②个节点**，就是一次纯函数调用。`ignore / post / inject` 的分流发生在第 8 步的 `apply` 里，**目标端口是静态的**（`channel.*.apply`），数据只决定"哪一款"。

## 2. 全链路（出向：启动循环）

| # | 谁在动 | 做什么 |
|---|---|---|
| 10 | **调度器**（内核） | 判据：队列非空 ∧ 未被阻塞 ∧ 未在运行 ∧ 并发未满 ⇒ 推进一步 |
| 11 | **图 E**（出厂图 `session.step`） | ① `channel.*.read { since: $source.cursor }` ② `model.*.call(...)` ← **唯一重试点** ③ `tool.*.execute(calls)` ④ `session.*.apply(output)`（组装记录）⑤ `store.*.append(delta)` ⑥ `channel.*.post(text)` |
| 12 | 若模型还要继续调工具 | 回到 10，**同一张图 E 再走一遍**（这就是"循环"） |
| 13 | 收尾 | `kernel.dequeue` + 状态落盘（落盘是这一整段的原子边界） |

⚠️ **第 11 步的第 ⑥节点不需要分支**："模型没话说"就让它产出空文本，`post` 对空值是 no-op——**判定由接收方做，不由图做**。这条技巧在本链路用了两次（另一次是 `apply` 的枚举分派）。

## 3. 图的数量

| 图 | 一句话 |
|---|---|
| A | 当适配器收到消息时，存原始、交频道 |
| B | 当频道整理完时，存清洗后的消息 |
| C | 当频道整理完时，读表、求值、交频道执行决议 |
| D | 当决议是"叫醒会话"时，注入文本、入队 |
| E | 当被推进时，取用、调模型、执行工具、组装、落盘、投递（出厂图） |

**5 张**，全部一句话读懂，全部 ≤ 8 节点，全在 `≤12` 的预算内。规则加多少条，这 5 张都不动。

## 4. 这条链路暴露出的四个问题（必须定，否则实现时一定卡住）

### 4.1 实例绑定 vs 静态校验（★新增规则，建议采纳）

图 A 的第 ③ 节点要打到**某个具体的频道实例**（`channel.group-1234`），而实例是运行期才有的。若要求"目标必须完全静态"，图就写不出来。

**建议的规则**（对 `02` §J3 的细化）：

> **端口是静态的，实例是动态的。**
> - 加载期校验的是 `模块.类型.端口`（如 `channel.*.intake`）——它在描述符里存在即可；
> - 运行期解引用的是**实例**，且只允许两种来源：`$source`（事件来源实例）或**配置属性**（`$source.channelRef` 这类）；
> - **绝不允许从载荷（`$event`）里任意指定目标实例**——那是注入面，也让校验失去意义。

### 4.2 驱动必须有端口（★需定）

第 9 步要 `kernel.enqueue(sessionId)`，但"队列/调度器"目前既不是模块也没有端口。跨模块就过图 ⇒ **驱动层必须暴露端口**，否则图够不着它。

两个选项：

| 选项 | 形态 | 代价 |
|---|---|---|
| **A. 驱动是内核自带模块** | `kernel` 有母/抽象/实例三层，端口 `enqueue` / `dequeue` / `status` | 内核不再"纯空壳"，但它本来就是机制入口（同 ALC 的内建工具） |
| **B. 驱动是普通模块** | `queue` 模块，可替换、可停 | 更自举，但"谁来跑调度器"变成鸡生蛋 |

我倾向 **A**：调度器是"让一切动起来"的那件事，它不能是可选件（判据同 ALC 的"协议适配器焊死"）。

### 4.3 出厂图 `session.step` 有 6 个节点，逼近预算

`02` 定的预算是"单张 ≤ 8"。`session.step` 已经 6 个，若以后把压缩/审批/子会话也接进来就会顶到天花板。

**建议**：预算分两档——**出厂图 ≤ 12**（由内核维护，有正向求解测试兜底）、**用户图 ≤ 8**。并加一条：出厂图超过 8 时必须附一份"为什么不能拆"的说明（一句话即可），否则视为设计债。

### 4.4 执行记录的量

这条链路上，**一条消息产生 4 条图执行记录**（A/B/C/D），**一步产生 1 条**（E）。以 1000 条消息 + 500 步估算，一天就上万条。

**建议**：执行记录分两级——**摘要常驻**（图 id / 触发 / 结果 / 耗时 / 失败点，可查询、可统计），**明细按需**（节点级参数与中间值，只保留最近 N 条或按开关打开）。否则它会变成 ALP 那种"日志写到没人看"。

## 5. 这条链路的自检（对照台账）

| 台账条目 | 本链路如何满足 |
|---|---|
| `X-01` 引擎生态 | 全链路没有任何"要不要起一个引擎"的判定；驱动只有调度器一个 |
| `X-02` 池/claim/权重 | 无。会话是否被推进只看队列 + 四个判据 |
| `X-09` 新架构寄生旧扩展点 | 每个跨模块跳都是一张独立图，没有"图塞进某个判定内部" |
| `X-11` 图纸先于消费者 | 5 张图全部在链路上，一张不多；加载期接不上即失败 |
| `I-11` 会话是数据 | 第 11 步的"组装"是 `session.apply(output)`，会话不持有 channel/store 句柄 |
| `I-15` 核心是空壳 | 去掉 `logic`/`rule` 表，链路仍能跑（只是不会条件回复）；去掉 channel，adapter 还能收（只是没人管） |
