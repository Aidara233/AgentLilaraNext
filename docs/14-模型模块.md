# 模型模块与 OpenAI Chat

> 本文记录模型模块的分层、首个 Provider 类型和脚本调用闭环。上位设计见 [`10-接口契约.md` §2]；Agent 主循环由 Session 驱动，模型 Provider 只处理单次无状态请求。

## 1. 管理器、类型与实例

```text
model                         根管理器：Provider 类型、实例、模型档案与调用路由
└─ model.openai-chat           OpenAI Chat Completions 协议 Provider 类型
   ├─ model.openai-chat#main   Provider 实例：endpoint 与密钥引用
   └─ model.openai-chat#test   另一个独立 endpoint / 凭据实例

模型档案（例如 assistant-default）→ Provider 实例 + 供应商模型 ID + 默认采样参数
```

Provider 类型由模块包注册；Provider 实例由 Host 配置创建；模型档案为调用方提供稳定名称。Session 或获准脚本只引用档案，不需要知道供应商协议与实例地址。

## 2. 中间协议

Provider 每次收到完整 `ModelRequest`，不保存会话历史。输出 `ModelEvent` 流：文本增量、工具调用增量，最后恰好一个 `ModelCompleted` 或 `ModelFailed`。取消沿请求令牌传到 HTTP 调用与响应流。

首个 OpenAI Chat Provider 支持流式文本和 function tool-call 增量；不支持的能力应由 Provider 描述并在请求前拒绝，不能静默丢弃。供应商错误映射成带 `Retryable` 的统一 `Error`；重试决策归 Session。

## 3. Host 配置

配置采用 `<DataRoot>/<module>/<category>/<instance>.json` 分层。当前 Host 扫描 `models/<category>/*.json`；目录类别由已注册 Provider 工厂解析，文件名提供实例名，因此文件内不重复声明协议类型。每个 Provider 工厂声明一个唯一配置类别；若增加新的协议适配器，使用独立类别目录。其他模块可以复用相同目录约定。`apiKey` 直接保存在对应 Provider 实例文件中，因此该配置目录应放在数据目录内，且不要提交到源码仓库。Host 不会把密钥写入日志或模型事件。

当前开发机的模型实例文件为 `E:/Tools/AgentLilaraNext/storage/models/chat/deepseek_official.json`。仓库中的 `run-host.cmd` 会传入 DataRoot；直接启动 Host 时必须显式传 `--data-dir <path>`。

```json
{
  "enabled": true,
  "configuration": {
    "apiKey": "<provider-api-key>",
    "endpoint": "https://api.openai.com/v1/chat/completions"
  },
  "profiles": [
    {
      "id": "default",
      "modelId": "gpt-4.1-mini",
      "defaultSampling": { "temperature": 0.2, "maxOutputTokens": 1024 }
    }
  ]
}
```

`enabled: false` 的实例文件会被跳过，便于先填配置再启用。`endpoint` 可省略以使用 OpenAI 官方地址。生产使用 HTTPS；自定义 endpoint 应由 Host 配置者信任。密钥不会进入 Provider 列表、调用记录或模型事件。

## 4. 脚本直接调用（冒烟入口）

Graph 脚本需在 manifest 显式申请 `model.complete`。随后可用 `ctx.model.complete(profileId, request)` 发起调用；该能力经过 Graph 授权与审计，不暴露任意 HTTP 或 CLR 访问。

Host 内置 `model.smoke` 脚本在 `channel.message.accepted` 上工作：Adapter intake 先把消息交给绑定的 Channel，脚本再处理 `/model <提示词>` 或 `/agent <提示词>`。`/agent` 通过 SessionManager 调用同一个 `default` 档案，Session ID 以 Channel 为作用域，最终文本通过 Channel 的绑定 Adapter 发回原 conversation。Session 数据保存在 `<DataRoot>/sessions/<sessionId>/`，包含 `spec.json`、`state.json` 和 `history.jsonl`。Channel 消息以来源、发送者、时间和正文结构化写入 history；当前 Session 的频道文本消息汇总为一个 `<channel_context>` user 消息块。浮动上下文由 `IRoundContextContributor` 在请求前临场查询；模块可通过 `ISessionTimelineWriter` 幂等写入长期消息，也可通过 `IRoundContextWriter` 写入只用于本轮的上下文。Host 内置 `system.time`（每轮浮动注入当前时间）与 `system.channel-info`（首轮把频道身份写入 timeline）两个贡献者。Host 统一排序并 XML 转义；浮动内容不落 history。Host 通过 `IRoundContextContributorRegistry` 暴露注册入口；模块回调全部完成、writer 封存后才渲染并调用模型。`/agent` 的 SessionSpec 显式声明 `send_message` 工具；Graph 只允许它发回触发 Session 的 Channel 绑定对话。Session 串行执行工具并把结果回送模型，直到模型返回最终文本；用户消息在模型调用前先持久化，模型与工具结果逐步持久化。其他工具绑定、wait/恢复策略、流式实时转发仍待实现。

## 5. 重载与实例生命周期

Provider 模块类型由可替换模块包提供；Provider 实例在销毁前不能卸载其工厂包。模型档案引用实例，移除档案后才能销毁实例。当前 Host 启动时加载配置，尚未提供运行时档案原子替换与模型组统一重载接口；后续需为配置重载增加候选实例校验、档案版本切换和在飞请求保留旧实例的管理流程。
