# 模型模块与 OpenAI Chat

> 本文记录模型模块的分层、首个 Provider 类型和脚本调用闭环。上位设计见 [`10-接口契约.md` §2]；Agent 主循环由 Session 驱动，模型 Provider 只处理单次无状态请求。

## 1. 管理器、类型与实例

```text
model                         根管理器：Provider 类型、实例、模型档案与调用路由
└─ model.openai-chat           OpenAI Chat Completions 协议 Provider 类型
   ├─ model.openai-chat#main   Provider 实例：endpoint 与密钥引用
   └─ model.openai-chat#test   另一个独立 endpoint / 凭据实例

模型档案（例如 assistant-default）→ Provider 实例 + 供应商模型 ID + 默认采样参数
```

Provider 类型由模块包注册；Provider 实例由 Host 配置创建；模型档案为调用方提供稳定名称。Session 或获准脚本只引用档案，不需要知道供应商协议与实例地址。

**能力是档案上的事实，不是 Provider 上的**。`profiles[].capabilities` 写名字（`"Streaming, ToolCalls, Vision"`），
也可以写旧文件里的数字；写出时永远是名字。`Vision` 决定"这张图能不能给它看"（`docs/28 §4`）：
**没写就是看不见**——两个方向的代价不对称（多一句回执 vs 整个请求被拒，而且之后每个请求都被拒）。
同一个 OpenAI 兼容端点既服务看图的模型也服务一收到图就 400 的模型，所以这件事说不出在 Provider 上。
`streaming` / `toolCalls` / `reasoning` 同理：Provider 描述的是**协议能表达什么**，档案说的是**这个模型会什么**。

## 2. 中间协议

Provider 每次收到完整 `ModelRequest`，不保存会话历史。输出 `ModelEvent` 流：文本增量、工具调用增量，最后恰好一个 `ModelCompleted` 或 `ModelFailed`。取消沿请求令牌传到 HTTP 调用与响应流。

首个 OpenAI Chat Provider 支持流式文本和 function tool-call 增量；不支持的能力应由 Provider 描述并在请求前拒绝，不能静默丢弃。供应商错误映射成带 `Retryable` 的统一 `Error`；重试决策归 Session。

## 3. Host 配置

配置是一**个 provider 一个模块目录**：`<DataRoot>/modules/model.<type>#<instance>/module.json`（docs/22 §2）。文件里 `type` 说明用哪个 Provider 工厂、`config.configuration` 是它自己的配置（endpoint、key …），`config.profiles` 是这个 provider 服务的档案，`config.enabled: false` 表示"文件留着但不加载"。目录类别（category，如 `chat`）**不再是路径的一部分**：它是运行时由工厂声明的分组，设置页用它给 provider 归类，文件不需要重复一份。`apiKey` 直接保存在这个文件里，所以数据目录本身就是机密，不要提交到源码仓库。Host 不会把密钥写入日志或模型事件。

当前开发机的模型实例文件为 `E:/Tools/AgentLilaraNext/storage/modules/model.openai-chat#deepseek_official/module.json`。仓库中的 `run-host.cmd` 会传入 DataRoot；直接启动 Host 时必须显式传 `--data-dir <path>`。

```json
{
  "enabled": true,
  "configuration": {
    "apiKey": "<provider-api-key>",
    "endpoint": "https://api.openai.com/v1/chat/completions"
  },
  "profiles": [
    {
      "id": "default",
      "modelId": "gpt-4.1-mini",
      "defaultSampling": { "temperature": 0.2, "maxOutputTokens": 1024 }
    }
  ]
}
```

`enabled: false` 的实例文件会被跳过，便于先填配置再启用。`endpoint` 可省略以使用 OpenAI 官方地址。生产使用 HTTPS；自定义 endpoint 应由 Host 配置者信任。密钥不会进入 Provider 列表、调用记录或模型事件。

**改一个正在跑的 provider 不用重启**：`models.provider.save` 对已经建好的实例返回 `applied: "now"`，下一次请求就带着新的 endpoint / key 出去（`IModelProviderReconfigurable`，配置整体替换、请求开头读一次——在飞的那一个请求用它开始时的那份）。不支持这条的 provider 会返回 `applied: "restart"` 并在 `reason` 里说明：让它静默失败比让它说实话更糟。`enabled: false` 仍然是重启生效——那等于把实例从在用的人手里抽走。

**改一个 profile 也不用重建**：`models.profile.set {id, model?, provider?, defaultSampling?, contextWindow?}` 原地替换，没点名的字段保持原样，下一步就用新的。为什么不 remove+create：`ModelManager.CompleteAsync` 每一步都按 profile id 查表，中间那个空窗会让正在跑的一步吃到"profile not found"——一个关于宿主记账的错误，看起来却像对话坏了。

### 3.1 `contextWindow`：不声明就是一次猜测

一个 profile 能带 `contextWindow`（**一个请求最多带多少 token**），它决定三件事：什么时候开始折叠旧记录
（`SessionManager.ReplayBudgetPercent` × 窗口）、什么时候压缩、以及"这一轮还有多少地方"那句提示。

**没有任何 provider 的应答会告诉你这个数**，所以它只能由人写进文件。不写就按
`ModelProfile.AssumedContextWindow` 算——**现在是 1M**（`1024 * 1024`）。猜这个方向是有意的：多留余量比
提前折叠更接近用户的期待，但代价必须写明白：

- **猜大了**：预算算得比模型的真实窗口宽松，请求长到 provider 拒绝为止。而"拒绝"不是一次性的——让请求
  过大的那段历史还在，**下一轮还会被拒绝**（`docs/28 §4.1` 是同一件事）。
- **猜小了**：折叠和压缩来得比必要更早，模型忘掉的东西比它本可以记住的多。这是**可恢复**的一侧。

所以：**模型实际比 1M 小，就必须显式写 `contextWindow`**。启动回执会点名还在用猜测的 profile
（`context window unsaid for default — those plan against 1024k`），那一行就是"该写还是不该写"的提醒。

窗口放大到 1M 的连带后果是**折叠与压缩都晚得多才发生**：`replayBudget` 是窗口的 55% = 576k，一次请求可能
带着几十万 token 的历史出门，又慢又贵。这是大窗口的代价，不是 bug；觉得慢就调 `ReplayBudgetPercent`
（`docs/11`），那里才是"多大开始折叠"的旋钮。


**endpoint 只填前半段**，协议自己补路径。以下写法等价，都会被归一化成 `https://api.deepseek.com/v1/chat/completions`：

```
https://api.deepseek.com
https://api.deepseek.com/
https://api.deepseek.com/v1
https://api.deepseek.com/v1/chat/completions
https://api.deepseek.com/v1/chat/completions?x=1
```

规则（`ChatEndpoint.Normalize`）：

1. 必须绝对 URL，`https`；`http` 只允许回环地址（本地 Ollama 之类）；URL 里不得夹带用户名密码。
2. 丢掉 query 与 fragment——它们属于某次请求，不属于 base。
3. 剥掉末尾的方法段：`chat/completions`、`completions`、`responses`、`models`，可重复剥离。
4. 末尾若已是版本段（`/v1`、`/v1beta`、`/v4` 这类 `v` + 数字开头）就保留，否则补 `/v1`。
5. 最后拼上 `/chat/completions`。

代理前缀会保留：`https://gateway.example.com/openai/v1` → `…/openai/v1/chat/completions`，`https://gateway.example.com/proxy` → `…/proxy/v1/chat/completions`。也就是说"只认前缀路径、只自动补版本与方法尾巴"。归一化失败时 Provider 创建直接失败并给出原因，不会带着错 URL 上线。

### 3.1 调用记录落在存储模块，不进信号日志

一次模型调用的完整请求（system prompt、目标、整块 `channel_context`、工具 schema）加上响应文本、工具调用、用量与 stop reason，实测一条就有 4 KB、950 input tokens。塞进信号日志会让日志失去"可扫读"这个唯一价值，所以模型模块把调用记录交给**存储模块**（`IArtifactStore`），信号日志只留一条 `model` 组的边记录（profile、tokens、stop、耗时）。

- 路径：`<DataRoot>/artifacts/model-calls/<yyyyMMdd>/<HHmmssfff>-<callId>.json`。按日分目录，保留策略将来是删目录，不是扫文件。
- 内容：`ModelCallRecord`——`profileId`、`provider` 地址、`modelId`、完整 `request`（渲染后的 messages 与 tools）、`responseText`、`toolCalls`、`stopReason`、`usage`、`durationMs`、`eventCount`、错误。
- 写入时机：事件流结束的 `finally` 里（成功、失败、取消都写）；先写 `.partial` 再原子改名，避免读到半截文件。
- 失败语义：存储失败**不会**让这次模型调用失败，只在信号日志记一条 `Mechanism = persist / Outcome = failed` 的 Warn。单条上限 16 MB，超限直接拒绝并记 Warn，不做截断写入。
- 分层：存储模块只认字节和路径（`StoreAsync(category, name, bytes)`），不认识 `ModelManager`；Provider 配置里的密钥不进入记录。

## 4. 脚本直接调用（冒烟入口）

Graph 脚本需在 manifest 显式申请 `model.complete`。随后可用 `ctx.model.complete(profileId, request)` 发起调用；该能力经过 Graph 授权与审计，不暴露任意 HTTP 或 CLR 访问。

Host 内置 `model.smoke` 脚本在 `channel.message.accepted` 上工作：Adapter intake 先把消息交给绑定的 Channel，脚本再处理 **显式前缀** `/model <提示词>` 或 `/session <文本>`（其余消息一律忽略——它曾经对每条消息都回一次，会与真正的回复策略抢话，见 `16`）。`/session` 通过 SessionManager 调用同一个 `default` 档案，Session ID 以 Channel 为作用域，最终文本通过 Channel 的绑定 Adapter 发回原 conversation。Session 数据保存在 `<DataRoot>/modules/<sessionId>/`，包含 `module.json`（spec 在它的 `config` 里）、`state.json` 和 `history.jsonl`。Channel 消息以来源、发送者、时间和正文结构化写入 history；当前 Session 的频道文本消息汇总为一个 `<channel_context>` user 消息块。浮动上下文由 `IRoundContextContributor` 在请求前临场查询；模块可通过 `ISessionTimelineWriter` 幂等写入长期消息，也可通过 `IRoundContextWriter` 写入只用于本轮的上下文。Host 内置 `system.time`（每轮浮动注入当前时间）与 `system.channel-info`（首轮把频道身份写入 timeline）两个贡献者。Host 统一排序并 XML 转义；浮动内容不落 history。Host 通过 `IRoundContextContributorRegistry` 暴露注册入口；模块回调全部完成、writer 封存后才渲染并调用模型。`/agent` 的 SessionSpec 显式声明 `send_message` 工具；Graph 只允许它发回触发 Session 的 Channel 绑定对话。Session 串行执行工具并把结果回送模型，直到模型返回最终文本；用户消息在模型调用前先持久化，模型与工具结果逐步持久化。其他工具绑定、wait/恢复策略、流式实时转发仍待实现。

## 4.5 启动与关闭：一个信号，并发，互不干扰

核心启动时**自己什么都不做**：不建适配器、不读频道、不开心跳。它只把同一个 `LifecycleSignal` 交给所有管理器。

**不是流水线。** 参与者**并发启动**，失败**互相隔离**：某个管理器起不来只记 failed、只跳过它的依赖者，其余照常运行。顺序只来自真实的数据依赖。

```text
core ── lifecycle.start ──┬─▶ adapters 管理器 ── lifecycle.start ──▶ 每个 Adapter（自己起自己的轮询计时器）
                          └─▶ channels 管理器 ── lifecycle.start ──▶ 每个 Channel（+ 挂载脚本）
                                （channels 依赖 adapters：频道绑定必须有适配器实例，所以晚一拍）
core ── lifecycle.started ──▶ 观察者
```

- `ILifecycleParticipant`：`Name` + `StartAsync(signal)` + `StopAsync(signal)`。
- `Register(participant, dependsOn...)`：**只在数据上真的依赖时才写**。`channels` 依赖 `adapters`，因为 `Channel.CreateAsync` 校验绑定适配器存在；没有这层依赖的参与者一律同波并发。
- 一波内的参与者用 `Task.WhenAll` 同时启动，互不等待。
- 失败隔离：失败的管理器记 `failed`，**依赖它的**记 `skipped` 并写明"依赖未启动"，其余继续。启动返回 `LifecycleReport`，Host 打印非 ok 项；只有**全部**失败才拒绝运行。
- 关闭是逆序（用户先于依赖），同样收集失败而不中途搁浅。
- 幂等：重复发信号是空操作；启动后再注册返回冲突。
- 每次启动/关闭写一条 `lifecycle` 信号记录（管理器名、成败、原因），跳过也留痕——"没出现"必须是可解释的。

两条硬顺序：`UseEvents`（给 Adapter 管理器装记录 sink；节奏由适配器自己声明）必须在 `StartAsync` 之前；规格文件是启动的输入而不是启动本身——Host 只在启动前确保 `modules/adapter.file#file-1/module.json` 存在。

## 5. 重载与实例生命周期

Provider 模块类型由可替换模块包提供；Provider 实例在销毁前不能卸载其工厂包。模型档案引用实例，移除档案后才能销毁实例。当前 Host 启动时加载配置，尚未提供运行时档案原子替换与模型组统一重载接口；后续需为配置重载增加候选实例校验、档案版本切换和在飞请求保留旧实例的管理流程。
