# 31 · 身份：一个人，与他在各处的账号

> 状态：第一期已实现（`ALN.Identity` + 三处接线 + 38 条测试）。
>
> 本文回答一个问题：**收到一条消息时，我怎么知道"这是谁"——不是他在这个平台今天叫什么，而是他这个人。**

---

## 0. 今天有什么，缺什么

消息从平台到模型，一路上带着四样关于"人"的东西，但没有一样是**人**：

| 有什么 | 是什么 | 为什么不够 |
|---|---|---|
| `AdapterEnvelope.Sender` | 平台的账号 id（QQ 号、用户 id、邮箱目录名） | 只在**一个平台的一个账号**里唯一。同一个人的小号是另一个人，同一个号在两个平台上毫无关系 |
| `SenderName` | 平台此刻给他的名字（群名片 → 昵称） | 会改。改了就换了一个"名字"，而历史里那条消息仍然叫旧名 |
| `SenderRemark` | 我这边的号给他起的备注 | 只在**那个号**的好友列表里存在。换一个适配器就没有 |
| `AccessLevel`（会话的） | 这段会话能碰多深 | 是**容器**的属性，不是人的属性。同一段群里谁说话都一样深 |
| `docs/09 §2.3` 的 `botIdentity[]` | "本频道名下有哪些我自己的账号" | **只在文档里，代码里从来没有过**（§6 补上） |

缺的那一样，是**一个人**：一个不管在哪、不管今天叫什么都成立的名字，和一组"这些账号是他"的认定。

这件事不能从任何现有字段推出来。平台 id 是别人的命名空间，昵称是别人的自由，备注是某一个号的私有数据——三个都不能拿来当身份。所以它必须是**一张写下来的表**，而且只能是人写的：**谁是谁，是认定，不是推断**。

---

## 1. 一个人的形状：一个目录

（用户裁定：一人一个目录，`info.json` 在里面，目录里还能放别的东西。）

```
<dataRoot>/identify/<人的 id>/info.json
```

```json
{
  "name": "小林",
  "note": "我妹妹。可以帮她查资料，别替她做决定。",
  "level": "operator",
  "self": false,
  "accounts": [
    { "adapter": "adapter.qq#main", "account": "1234567" },
    { "adapter": "adapter.qq#main", "account": "7654321" },
    { "adapter": "adapter.file#file-1", "account": "xiaolin" }
  ]
}
```

| 字段 | 必填 | 是什么 |
|---|---|---|
| 目录名 | 是 | **人的 id**。人起名，不改；改名就是换一个人（`C-01` 对 `id` 的规矩原样适用） |
| `name` | 是 | 显示名。**可以改**——改的是标签，不是身份。改了之后历史里那些消息也跟着显示新名（§4） |
| `note` | 否 | 一句给人看、**也给模型看**的话。这是"我该怎么对待他"唯一诚实的载体（§5） |
| `level` | 否，缺省 `agent` | 这个人**能发出的指令最多多深**。今天只是数据，将来是指令系统的闸（§7） |
| `self` | 否，缺省 `false` | 这组账号是**我自己**（§6） |
| `accounts[]` | 是，至少一条 | `adapter` 是适配器实例地址，`account` 是那个适配器里这个账号的 `Sender` |

目录里除 `info.json` 之外的东西，核心**一个都不读**。这一点是刻意的：将来往里塞头像、笔记、前情、他对我说过的话，都不需要动契约，也不需要动这里任何一条规矩。目录是"这个人的资料袋"，`info.json` 只是袋口那张卡片。

⚠️ 数据目录叫 `identify`（认人，动词），模块 id 是 `identity.people`。两者不必一致：目录名是"这件事叫什么"，模块 id 是"哪个模块"。`C-02`（id 与目录名逐字一致）管的是 `modules/<id>/`，不是这里。

### 1.1 为什么不是一个 `people.json`

一个文件放一群人，第一件事就是要在一个文件里做增删改的合并——而那正是"目录里塞更多东西"做不到的原因。一人一个目录之后：

- 加一个人 = 建一个目录（不需要读别人、不需要重写整份文件）；
- 那个人的任何附加数据有地方放；
- 坏一个不影响别人（§9）。

这和 `modules/<id>/module.json`、`memory/<记忆组>/` 是同一条路，不是新发明。

## 2. 唯一性只管一个方向

（用户裁定：一个人可以在同一个适配器下有多个账号——小号。）

```
一个 (adapter, account)  ──只能属于──▶  一个人
一个人                    ──可以拥有──▶  任意多个 (adapter, account)
```

两个方向不对称，理由不对称：

- **一个账号只能是一个人**：这是"识别"的定义。一个号同时是老王和小李，那收到的消息就无法归到某一个人名下——系统要么猜，要么分裂。所以这是硬约束，不是提示。
- **一个人可以有很多号**：小号、备用号、同一个平台的两个号、四个平台各一个。这是人的常态，限制它没有任何好处。**同一适配器下多账号是明确允许的**（主号和小号都在一个 QQ 上，是"小号"最常见的样子）。

冲突怎么处理（§9）：**后声明的整条不受理**，前面那个人保持有效，报一条错说明两个目录在抢同一个号。不静默覆盖——静默覆盖会让"我以为是他"变成"其实不是"，而这种错误没有任何地方能发现。

`adapter` 用**实例地址**（`adapter.qq#main`）而不是 `platformId`（`qq`），因为同一平台可以有两个号同时在线（主备，`docs/09 §2.3`），而它们的 `Sender` 空间是各自的。用 `platformId` 会把主号的 id 空间和副号的混成一片。

反向的代价也要说清：**适配器重建、换了实例名，表里那条就失效了**。所以查找失败时要说清是"这个适配器没有登记过这个人"还是"这个适配器地址根本不存在"（§9）——后者是配置过时，前者是陌生人，两件事。

## 3. 查找：唯一的热路径

```csharp
interface IPersonDirectory
{
    Person? Find(Address adapter, string? account);   // 每条消息一次
    IReadOnlyList<Person> List();
    Person? Self { get; }
    bool IsSelf(Address adapter, string? account);
}
```

`Find` 是同步的、O(1) 的、不会失败的：**消息路径上不能有一次可能超时的等待**。它回答三件事：这个人是谁（`id` + `name` + `note` + `level`）、是不是我自己、没有就是 `null`。

`null` 不是一个错误，是**一个答案**：这一条消息来自一个表里没有的人。（用户裁定：陌生人照常进，不拒收、不静默丢——§9.3。）

表在内存里，启动时扫一次目录建好；`identity.reload` 重扫（§8）。查找走的是 `(adapter.ToString(), account)` 拼成的键，一次字典查。

## 4. 名字：绝对名字取代平台昵称

`<channel_messages>` 里发言人的那一栏，现在的规则是 `群名片 → 昵称 → 账号 id`，再加括号里的备注（`ChannelMessage.Compose`）。

登记过的人，`sender` 换成 `info.json` 里的 `name`，并且**多一个 `person` 属性**：

```xml
<message id="…" sender="小林" person="xiaolin" at="…">帮我看看这个</message>
<message id="…" sender="路人丙"              at="…">路过</message>
```

| 情形 | 模型看到 |
|---|---|
| 表里有这个人 | `sender="小林" person="xiaolin"` |
| 表里没有 | `sender="测试人员"`，没有 `person` |
| 表的 `name` 空、账号登记了 | 退回平台名（`name` 必填，这是兜底不是常态） |

**为什么是 id 而不是一个布尔标记**：`person="true"` 只说了"我认得他"，`person="xiaolin"` 让模型能直接 `whois` 查下去，而 id 不会像名字那样撞车。**为什么未登记的人不写 `?`**：大群多是陌生人，每条都加标记是每轮都付的成本，而"属性缺席"在这个项目里已经是一种说法的表达（`self` 缺省即 false）。

`<channel_messages>` 头上会有一句说明，**只当本轮真有被归属的消息时才出现**：

```xml
<note>带 person 的消息来自我认得的人，值是他的身份 id（要更多就用 whois 查这个 id）。
没有 person 的是平台给的名字：可能是同名的另一个人，也可能是完全陌生的人。</note>
```

一个人都没登记的部署，一个字节都不花。

⚠️ **历史里的旧消息没有 `person`**，哪怕那个人今天登记了：写那条消息时我们还不知道，而 `docs/17 §⑤` 的规矩是"事后取不回来的不假装取得回来"。后果是同一个人的旧消息显示平台名、新消息显示 `name` + `person`，模型可能当成两个人——这一点只能靠会话往前走自然消退，改不掉。

理由不是"好看"，是**身份要稳定**：一个人今天把群名片改成"🔥龙傲天🔥"，明天改成空白，模型看到的是两个不同的人，而这个会话的记忆里明明只有一个人。用 `name` 之后，**在模型眼里他始终是同一个名字**——那正是"绝对身份"的外在表现。

⚠️ 这一栏**不是权限**，也不是"我该怎么对他"的全部。它只说"这是谁"。态度在 §5。

**存什么**：`ChannelMessage` / `StoredMessage` 各加一列 `person`（人的 id，不是名字）。名字在渲染时按 id 现查，所以改了 `name` 历史也跟着改——这正是要的：名字是标签，标签该跟着人走。人的记录被删了，就退回 `sender_name`（那一列仍然存着，`docs/17 §⑤` 的老规矩不动）。

## 5. 上下文：参与者名册

（用户裁定：`level` 要进上下文；后续要把"本会话所有已登记参与者"的身份信息给模型，方便快速回忆确认。）

每轮请求的浮动上下文里多一节，只列**这段会话里出现过的、登记过的人**：

```text
[参与者] 小林（L1 operator）：我妹妹。可以帮她查资料，别替她做决定。
         阿伟（L0 agent）：同事，一起打游戏。
```

五条规则：

1. **只列已登记的。** 陌生人一个都不列——大群里四十个没名字的 id 会把这节变成噪音，而噪音的代价是模型开始忽略整节。
2. **每轮重算，进浮动块，不进 history。** 名册是"我们现在知道什么"，不是"发生过什么"。落盘的历史里发言人已经带了名字（§4），够了。（`docs/11 §5.1`）
3. **谁最近说过话，谁在里面。** 会话记住的每个人带一个"最后说话时间"（`PersonSeen`），名册按它降序取前 12。理由很直接：**一段见过四十个人的会话，必须还能把正在说话的两个人摆到模型面前**；按"先来后到"或"按 id 截前 12"都会让后来的人永远进不来。
4. **进了名册的这 12 个，按 id 排序展示。** 选择按时间，展示按 id——同一批人在两轮之间顺序不变，变了就说明人变了。
5. **有上限，而且说出来。** 最多 12 个人，`note` 截到 120 字。超了写一句"还有 N 个登记过的人没列"——比默默截断好：模型知道自己看到的是不完整的。

⚠️ **旧会话没有时间戳。** `state.json` 里那份名单是从"只有 id"的形状升级来的，读到旧形状时时间记作 `DateTimeOffset.MinValue`（`PersonSeenJson` 干这件事）：意思是"他在这里说过话，但我们没记下什么时候"。它们排在所有有时间的人后面，于是慢慢淡出——这正是"以正在说话的人为准"想要的结果，而且不用假装知道一个没记过的时间。

### 5.1 `level` 怎么写，以及它为什么不违反 `docs/11 §5.3`

`docs/11 §5.3` 有一条硬纪律：

> 等级的措辞必须和 `RelayNote` 一致：**"深浅"说你能碰多深，从不说谁有资格命令你。** 把它写成地位，模型就会把"我比它深"读成"它得听我的"。

那条管的是**会话自己**的等级——把"我能碰多深"写成地位，模型就会以为自己有资格命令别人。

名册里的 `level` 是**关于另一个人的事实**，而且是一个具体的、可执行的量：**这个人的话最多可以被当作多深的指令**。这不是"他比你高"，是"他手里能发出的东西有多深"。所以措辞用：

- ✅ `小林（L1 operator）` —— 他的指令最多深到 operator
- ❌ `小林（比你低一级）` / `小林（你的上级）` —— 这是地位

**听不听，仍然不是等级决定的**，是 prompt 决定的。等级只说"他能要求多深"，不说"你必须服从"。这条界线要一直画着，因为下一步的指令系统正是靠它：一条来自 L2 的人的指令可以要求 L2 的动作；一条来自 L0 的人的同样一句话，只能被当作请求。

### 5.2 它和 `<self>` 那一节的分工

| 节 | 回答 | 谁的属性 |
|---|---|---|
| `<self>`（已有） | 我是谁、我有多深、我被拿掉了哪些工具 | **我**的 |
| `[参与者]`（本文） | 跟我说话的这些人是谁、他们能要求多深 | **他们**的 |

两节都不落盘，都是每轮重算。这是 `docs/11` 已经定好的形状，本文只是往里加一节。

## 6. `self`：顺带补上 `docs/09 §2.3` 的空洞

`docs/09 §2.3` 第 3 条写着：

> "自己发的"按身份判定，不按"是不是主"判定：Channel 维护本 Channel 名下的账号集合 `botIdentity[]`；只要发送者身份落在这个集合里，回声就标 `self`。

**代码里从来没有过这个集合。** 今天只有一个 `MentionsSelf`（平台告诉我"这条 @ 了我"），那不是"这条是我发的"。

一个人目录里 `"self": true` 的那一条，就是这个集合：

```json
{
  "name": "我（主号）",
  "self": true,
  "accounts": [
    { "adapter": "adapter.qq#main", "account": "10001" },
    { "adapter": "adapter.qq#backup", "account": "10002" }
  ]
}
```

于是"副号发的回声也是 self"（`docs/09 §2.3` 第 3 条的下半句）自然成立：**两个号在同一个 `self` 人下面就行**，不需要"哪个是主"这个字段。

⚠️ **第一期只提供判定，不改行为。** `IsSelf` 可用，但"self 回声不激活会话"（`docs/09 §2.3` 第 5 条）**没有接上**——那是另一个缺口，接它要改激活路径，和本文的"识别"是两件事。列在 §12。

## 7. 等级：现在是数据，将来是指令系统的闸

（用户裁定：人的权限一方面影响模型对其该有的信任度，另一方面是将来调用指令系统的权力。工具深浅不接。）

三条界线，一条都不能糊：

| 问题 | 谁回答 | 本文怎么处理 |
|---|---|---|
| 这一轮模型能碰多深？ | 会话的 `spec.Level`（`sessions.setLevel` 改） | **一个字不碰**。人的 `level` 不接工具闸 |
| 这个人能发出多深的指令？ | 人的 `level` | 存着，进上下文（§5），等指令系统来接 |
| 这个人说话算不算数？ | prompt + 名册里的 `note` | 由**人写的话**承载，不由系统判语 |

第二条是将来时。**今天没有任何代码按人的 `level` 放行或拦截任何东西**——这是刻意的：等级一旦在识别模块里接上工具闸，"我说了什么"就变成了"我能做什么"，而这两个问题现在都还没有指令系统来裁。等到那时，闸只有一处要接：**指令进来时，比 `指令深度 ≤ 这个人的 level`**。

第三条是最容易被做坏的一条。系统不能替人给"这个人有多可信"下判决——那是人的判断，写在他自己的 `note` 里（"我妹妹，可以信任" / "同事，别给密码"）。系统能确定的只有事实：他是谁、他有哪些号、他的指令能有多深。

## 8. 生效：人手写，显式重载

（用户裁定：人工编辑的改动靠显式 reload 生效。）

两条路，都能生效：

| 谁写 | 怎么生效 |
|---|---|
| 人编辑文件 | `identity.reload`，或者重启 |
| 走 `identity.people.set` / `remove` / `level` | 写完立刻重扫一张新表，不需要 reload |

和 `docs/07 §5.1` 同一条纪律：

**不做文件监视。** 理由和受信脚本那条一模一样：编辑器保存到一半、多文件改到中间都会触发，"自动生效"一旦存在，就没人说得清现在跑的是哪一版。而且身份错了比脚本错了更难发现——脚本错了会报错，身份错了只会安静地认错人。

`identity.reload` 是**整表替换**：新表一次建好再换上去，读它的地方永远看到完整的旧表或完整的新表，看不到半张。这与 `docs/07 §5.1` 的"原子的：全部通过才替换"是同一个形状。

一处细节要说准：**坏卡片不是"硬错误"**。它进 `rejected`，那一个人不在新表里，别人照常（§9.1）。只有**目录本身读不了**（权限、IO）才保留旧表继续用——一张过时的表还在认人，一张被清空的表谁都不认，后者更糟而且更难发现。

启动时扫目录，收据一行（和 `net` / `web` 的收据同形状）：

```
restored identity: 3 person(s): 小林 (L1), 阿伟 (L0), 我 (self)
```

一个人都没有时它不是空白，是一句话：

```
restored identity: none — every message arrives from a stranger (identify/ is absent or empty)
```

## 7.1 谁能改什么

（用户裁定：除 `level` 外，所有内容都允许**任何等级**的模型改；给有权限的人动账号需要高权限。）

| 什么 | 谁能写 | 通过什么 |
|---|---|---|
| `name`、`note` | 任何等级：模型、脚本、人 | `identity.people.set`（能力 `identity.write`，agent 级） |
| `accounts` —— **新建**一个人 | 任何等级 | 同上。新卡片的 `level` 恒为 `agent`，没有可继承的东西 |
| `accounts` —— 改一个 **L0** 的人 | 任何等级 | 同上。L0 的账号换给谁都不改变谁能说话 |
| `accounts` —— 改一个 **有等级**的人 | `operator` 及以上 | 同上，但处理器内部比 `actor.Level` |
| `self` —— 设上、摘掉、或新建时带上 | **`operator` 及以上**（与目标等级无关） | 同上 |
| 删一个 **L0** 的人 | 任何等级 | `identity.people.remove`（`identity.write`） |
| 删一个 **有等级**的人，或**删掉那个 self 人** | `operator` 及以上 | 同上 |
| `level` | **只有人**（`operator` 及以上），且只能授出 ≤ 自己的 | `identity.people.level`（`identity.control`），带 `AssignsLevel` |

四条理由，一条都不能省：

1. **`level` 不在写入口的类型里。** `PersonInput` 没有这个字段——不是"传了被校验掉"，是**表达不出来**。传了 `level` 的调用会被明确拒绝（不是静默忽略：静默忽略会让调用方以为升成功了）。

2. **换绑账号等于继承等级。** 这是唯一真实的提权路径：把某个 L2 的人的账号改成自己的号，然后从那个号说话，就会被认成 L2。所以"有等级的人的账号集合"这一格需要调用方自己也有等级——**判断按目标算，不按字段算**，因为字段是死的、目标是活的。`set` 只比较 `accounts`；只改名字和备注仍然是任何等级都能做的事。

3. **"哪些账号是我"也归人定。** `self` 与任何人的等级无关，所以它单独占一道门，不挂在"目标有没有等级"上。没有这道门的话，模型可以先摘掉一张卡上的 `self` 再给另一张卡设上——`level` 那道规则根本不会被走到，而"哪个号是我"已经被改了。**新建时带上 `self: true` 同样是设，不是新建的白送**。删掉那个 self 人也一样：那是"摘掉"顺着另一条路做。

4. **删一个有等级的人也要同样的门。** 删掉之后，那个人再说话就是陌生人——他的 L2 被悄悄抹掉了，而这和"改他的账号"是同一个后果的两面。

⚠️ 拒绝的话必须说清能做什么，否则模型会去试别的路：

```
'小林' is L1 operator, so which accounts are his is a person's decision: changing them needs
L1 operator or higher. His name and note you may change at any level; a level is not yours to write at all.
```

**这一格为什么在处理器里而不在等级表里**：`AccessLevels` 回答的是"这个动作多深"，而这里的深度取决于**目标是谁**——同一句 `identity.people.set` 改一个陌生人无害，改一个有等级的人就是提权。这和 `adapters.raw` 是同一类判断（`docs/16 §10`）：深度是数据、不是常量，所以判断写在唯一执行点内部，仍旧留审计、仍旧不可绕过。

### 7.2 写入的形状

- **整卡写，不是局部改。** `accounts` 必填（至少一个），`note` 不给就是没有。局部改会让"省略"同时表示"保持"和"清空"两件事。
- **只碰自己那几个字段。** 卡片是文件，人（或以后的版本）可能往里放了别的东西：实现先读现有 JSON 对象，只覆盖 `name` / `note` / `accounts` / `self`，**其余原样写回**。`level` 只有在 `identity.people.level` 里才会被改。
- **原子写。** 临时文件 + 改名。半张卡片是这张表最不该出现的状态——那会是"这个人存在，但读不出来"。
- **写完立刻重扫**，所以写动作之后不需要再 `identity.reload`。
- **删除只删 `info.json`，目录留着。** 那个文件夹是他的资料袋（§1），一个关于身份的动词没有资格清空它。
- **扫描是权威。** 写完的字节如果被自己的扫描器拒了（比如别处也占了这个账号），回答是失败，不是"写好了"——否则一小时后的"它不认得我了"就是今晚的谎。

## 9. 拒绝与坏数据

三种坏，三种处理。**都不会让进程起不来**（`C-27`：一个模块失败不否决别人一整轮）。

### 9.1 坏 `info.json`

`info.json` 读不出来、不是 JSON、缺 `name`、`accounts` 空、地址格式不对 —— 这一个人**整条不受理**，其他照常。报一条：

```
identity: identify/xiaolin/info.json rejected: accounts[1].adapter is not an instance address ("qq")
```

一份坏文件不该让另外九个人认不出来。

### 9.2 一个账号被两个人声明

后扫到的那个（按目录名 Unicode 序）**整条不受理**：

```
identity: identify/awei/info.json rejected: adapter.qq#main / 1234567 is already xiaolin's
```

前面那个保持有效。**不静默覆盖**——覆盖会让"这消息是谁说的"从确定变成猜。

### 9.3 表里没有的人

**照常进，标 unknown。**（用户裁定。）

不拒收、不静默丢。三个理由：

1. **消息是不可替代的。** 拒一条消息换来的"安全"，比不上丢掉一句别人认真说的话（`docs/09` 对"至少一次"的同一取舍）。
2. **陌生人不是敌人。** 群里第一次说话的人、换了号的老朋友，都在这条路上。
3. **拒收的地方不在这里。** 要不要理一个人，是频道侧脚本的判断（`docs/11 §5.6` 的"阀门"），那里能看到内容、能看到上下文。身份模块只回答"这是谁"，不回答"理不理"。

## 10. 明确不做

| 不做 | 为什么 |
|---|---|
| 用人的 `level` 接工具闸 | 用户已裁定：那是将来指令系统的事。今天接上就是"谁说话谁有权"，而群里随便谁都能说话 |
| 跨平台会话续接 | 用户裁定：交给 channel 系统拼。本文只管"是谁"，不管"把两段对话合成一段" |
| 让模型写 `level` | 用户裁定：除等级外都能改。等级决定将来的指令系统听谁的，写得了它 = 写得了自己的指挥链 |
| 从平台数据推断身份 | 昵称、备注、共同群、头像相似度都是猜。**谁是谁是认定**（§0） |
| 文件监视自动重载 | §8 |
| `admin` / `owner` / `friend` 之类的亲疏枚举 | 那会变成第二套等级，和 `AccessLevel` 打架。`note` 是自由文本，人想怎么写就怎么写 |
| 一个人的"曾用名" | 平台名每次都存着（`sender_name`），历史不会丢。要"这个人历史上叫过什么"是查询，不是身份 |

## 12. 现状、验证与没做的事

**已实现**：`ALN.Contracts/Identity`（`Person`、`PersonAccount`、`IPersonDirectory`、`IPersonDirectoryReload`、`IPersonDirectoryEditing`、`PersonIds`、`PersonDirectoryReport`）、`ALN.Identity`（`PersonDirectory` 的扫描/校验/查找/reload/写卡片/删卡片/写等级、`IdentityActionSet` 六个动词、`IdentityTools` 的 `whois`、`PersonRosterSource` 名册）、`ChannelManager` 的查找接线、`ChannelMessage`/`StoredMessage` 的 `person`（SQLite `user_version` 7 → 8，只加列）、`ChannelDeltaSource` 的绝对名字渲染、`SessionState.People` + `RoundContextRequest.People` + 名册源、宿主装配与收据行、能力 `identity.read` / `identity.write`（agent）与 `identity.control`（operator）。

**有测试的**（`IdentityTests`，38 条）：

- 读：一人一目录、同适配器多号、跨适配器同一人、坏卡片只拒一条、目录不存在 = 谁都认不出、账号冲突整条废、只有一个 `self`、实例地址/无账号/缺名字各一条拒绝、陌生人返回 `null`、改名不换 id；
- 渲染与名册：绝对名字、陌生人保留平台名、**端到端**（一条消息 `person="xiaolin"` + 说明行、下一轮名册里 `小林（L1 operator）：我妹妹。` 且陌生人不进名册）、名册按"最后说话时间"取最近 12（两个最久没说话的淡出、仍在的 12 个按 id 稳定排序）、**旧 `["a","b"]` 形状的 `state.json` 仍能读**（时间记 `MinValue`）、新形状往返、超限时说还有几个、没人就不出现；
- 查：`whois` 命中与未命中、`identity.people.list` 的返回形状；
- **写**：模型能建人（新卡 `level` = agent）、能改名字与备注、**不能**改有等级者的账号（拒且文件未变）、operator 能改、写卡片不会动原有 `level`、传 `level` 被明确拒、模型调不了 `identity.people.level` 而 operator 能、模型能删 L0 的人但删不了 L1 的人、删人只删卡片留目录、删不存在的人是错误；**`self` 单独一道门**：模型新建带 `self: true` 被拒、给 L0 的人设 `self` 被拒、摘掉 `self` 被拒、删掉那个 self 人被拒，operator 四件都能；
- 边界：账号不能从别人手里抢、第二个 `self` 被拒、卡里未知字段（`avatar`/`tags`）原样保留、无账号的卡在落盘前就被拒、`../elsewhere` 这种 id 被拒。

**没有验证的（明确的空白）**：

1. **真实数据零次。** 全部测试都在临时目录里手写 `info.json`。真实的 `storage/identify/` 还不存在。
2. **`[参与者]` 的 token 成本是拍的**：12 人 × 120 字的上限没有量过。
3. **`self` 只提供判定，没有接上"回声不激活会话"**（§6）。今天"自己发的消息会不会叫醒自己"仍然只靠 `MentionsSelf`。
4. **适配器改名/重建后表里的条目会失效**，只有一条 `unknown` 的答案，没有迁移手段，也没有告警。
5. **`whois` 的返回没有和模型对齐过**：它给整个人的记录（含所有账号）。
6. **WebUI 没有入口**：动作页能调，但没有"人"的专门页面。
7. **一个会话的 `People` 只增不减**：人从表里删掉之后名册那一行会自己消失，但 id 仍留在 `state.People` 里。现在它带时间了，长期不说话的会自然淡出，但仍然没有任何东西会把它真正删掉。
8. **写没有串行化**：两个调用同时写同一张卡，最后写的赢（临时文件名带 GUID，所以不会写出半张混合卡，但先写的那份改动会丢）。整卡写的语义本来就是这样，代价写在这里而不是藏起来。
9. **`self` 的写入要 operator**（§7.1 第 3 条），所以"模型把自己的号标成自己"这条路已经关上。但这道门**只认 `actor.Level`**：以 operator 身份说话的脚本或 API 令牌都能设 `self`，而它们之间没有更细的区分。
