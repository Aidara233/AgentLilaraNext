## 0. 一页速览

六层，各管一件事，不许串味：

| 层 | 管什么 | 归谁 | 怎么改 |
|---|---|---|---|
| **模块** | **做**（有副作用：收消息、存、发、算） | 内建 C# / 插件 | 换实现（进版本） |
| **Graph / 图** | **连与编排**（事件处理、流程控制、已授予接口调用） | Jint 脚本 + Host API | 版本化挂载 |
| **过程** | **序**（内核固定的生命周期与驱动步骤） | 内核（代码） | 改版本 |
| **纯逻辑** | **算**（无副作用的求值） | 可由 Jint 脚本实现；与 Graph 编排边界待收敛 | 随脚本包更新 |
| **驱动** | **时**（唯一队列 + 步调度器） | 内核（代码） | 改版本 |
| **能力 + 审计** | **界**（唯一碰 OS 的地方） | host（极小） | 改版本 |

## 1. 十条铁律（每条都能追到台账编号）

1. **模块实例的生命周期归其 Manager 所有**；模块实例不持有兄弟实例引用。
2. **跨模块动作经统一 Runtime/Graph 能力入口**；脚本不能绕过端口解析、授权、取消与记录。
3. **Jint 脚本是主要编排形式**：可表达条件与流程控制，调用范围由 Host 注入的接口和能力声明决定。
4. **Manager 全局唯一且类型化**：各自持有本模块实例并提供查询；脚本只拿目标实例与事件绑定的受限 facade，不拿任意 CLR 对象或全局目录。
5. **挂载目标声明抽象类型**；抽象不可实例化，具体子类继承父类型的可挂载关系。
6. **默认挂载随实例生命周期自动建立/撤销**；启动时先加载与挂载，再开放 Adapter 入站。
7. **程序与可变 DataRoot 分离**；所有模块收到同一解析后的根路径，不各自读取进程环境。
8. **ALN 自己不具备任意系统能力**：Host 是唯一碰 OS 的地方；脚本只得授予的 scoped facade。
9. **本地 shell 不存在**（`X-13`）；远端执行只走受限 `ISsh`（主机白名单 + 两档 + 全量审计）。
10. **能力调用过审计，审计不可关、拒绝也记**；Jint 不是 OS 隔离边界，受限域仍按 `06/07` 要求隔离。

## 3. 术语表（防串味）

| 词 | 在本文档集里的确定含义 |
|---|---|
| **模块** | 有实例、有端口、能做事的东西。代码里**只有一种**，不分类（`X` 台账有反例） |
| **Graph / 图** | 脚本包的管理、挂载与事件编排模块；Jint 脚本通过 Host API 调用获授能力。正式名称待职责稳定后再定 |
| **过程** | 内核固定的序列（一步、入站、出站、定时），负责生命周期与驱动步骤，不可插拔 |
| **端口** | 模块对外可调用/可观察的显式成员；脚本不可直接访问任意 public 方法 |
| **能力 / 拓展** | 能力的单位是**拓展**（extension）：`file` / `net` / `msg` / `clock` 为开放级；`store` / `state` / `secret` / `ssh` 为内部级。模块/脚本声明 `requires`，装配决定授予。域只是上限 |
| **脚本包** | manifest + JavaScript + 信任域 + 能力需求；挂载到抽象目标类型后，由 Manager 按继承关系关联具体实例 |
| **装配版本** | 一次配置/脚本/挂载变更的快照，可审计、可回滚；可重放能力与副作用语义待定 |
| **信任域** | 内建 / 受信（人写，主进程）/ 受限（人**或模型**写，子进程）。**不同域必须分引擎**（Jint 官方要求），且**装配表也分域** |

## 3.5 三个信任域（详见 [`07`](07-域与权限分级.md)）

| 域 | 作者 | 跑在哪 | 能力 | 谁能改 |
|---|---|---|---|---|
| **内建** | 开发者（C#） | 主进程 | 全部机制 | 进版本 |
| **受信** | **只有人**（JS） | **主进程** | 内部数据面 + 开放面 | 人，可热重载 |
| **受限** | 人 **或模型**（JS） | **子进程** | 只开放面 | 自举 |

一句话记住：**进程边界付给"不可信的那一侧"**；**受信域的特权是数据面，不是 OS 面**（受信也拿不到 shell、读不到密钥明文）。

| 原判断 | 何时被推翻 | 现在是什么 |
|---|---|---|
| 一步之内不走图（端口注入给推进器） | 用户裁定"跨模块再简单也得走图" | 一步由**过程**驱动，每次派发都走订阅 |
| 图的形状 = "触发 + 一串节点" | 用户提出 C# 广播模型 | **订阅表**（接收方连发起方） |
| 权限三层里 IL 扫描是主闸门 | 用户裁定"安全是绝对要求" | IL 扫描降级为事后防线；主闸门是**容器**（语言里没有的原语） |
| "防意外不防恶意"，隔离不作 v0 前置 | 同上 | **不可逃逸是前置**；接入群聊后威胁来自外部输入与第三方代码 |
| 自举产物 = C# 源码编译成模块 | 用户裁定"不给本地 shell" | 自举产物 = **订阅表 + JS 脚本**；C# 模块只能由开发者提供 |
| 脚本语言的价值 = agent 更喜欢代码 | 用户指出真正原因是安全 | 价值 = **正常 C# 太全**，受限语言才是能力边界 |
| L1/L2 = 自研表达式 + Lua/WASM | 用户提议 Jint + 官方文档核对 | **Jint**（另需进程级边界，见 `06` §6.3） |
| 派发有两种语义（`emit` / `dispatch`） | 用户指出"接口本来就有两条进路" | **信号与调用是两种机制**（1→N 不等待 / 1→1 等待），不是同一次派发的两种模式 |
| 工具 = 端口投影 + `exposesToModel` 标记 | 用户裁定"显式封装，靠标记太草率" | **工具是一份显式定义**（声明 + 绑定 + 渲染 + 副作用声明），加载期校验绑定目标存在 |
| 渲染在内核里做（纯计算） | 用户裁定"上下文注入是 session 的行为" | **③ 是一次 `call session.build-prompt`**；实现仍须纯，但知识的归属归会话 |
| 头槽位每步现算（ALC 的做法） | 用户裁定"系统提示词只在最开始请求一次" | **ALN 系统块走全局快照**；ALC 共享预设文件被修改会让所有引用者的下一步换头 |
| 每会话冻结系统块 + 单会话 `rebuild-header` | 用户裁定「系统提示词要可变——虽与缓存冲突但非常偶尔、可接受；依然用全局快照，框架重载时一并更新」 | **全局快照 + 全局重载**：重载一次，所有会话下次请求一起换；指纹相同即 no-op；**不再有单会话重建入口** |
| 全局失效 Stepper = 清理缓存 | ALC 代码核对显示 `InvalidateSteppers()` 只清本地 Stepper/适配器对象，不清供应商缓存；ALC Responses 又是全量重放、没有 `previous_response_id` | **头重建不做全局失效**；仅目标会话的请求头改变，变化点之后可能不命中，之前的共同前缀仍可能命中；远端缓存不由客户端清除 |
| 一个 Channel 可跨平台聚合（把 QQ 群与别的平台房间合成一条） | 用户指出"同一频道肯定出现在同一平台" | **Channel 单平台**；平台消息 id 因此只用于对账与排查 |
| 出站可广播到多个 Adapter；入站主副都投、靠去重合并 | 用户裁定"默认只用主适配器收发，不考虑去重；各 Adapter 自己存消息防丢；主报异常才切副" | **常态零去重**：只有主适配器投递，副连接着但只留存；重复只可能出现在切换瞬间，明确接受 |
| 发送结果不明要三选一（不重发/切副重发/分档） | 用户指出"适配器能收到自己发的消息，没发出也有回执" | **回执是一等结果**；Channel 不做重发决策，**由模型决定重发还是退避** |
| 健康由 Adapter 自己报告，Channel 只读不改 | 用户裁定「频道维护一个适配器可用性列表：喂狗、主动报错标红、报恢复标绿」 | **Channel 持有可用性表**：心跳超期或 `adapter.fault` ⇒ 红；`adapter.healthy` ⇒ 绿 + 冷却（**仅显式**，心跳恢复不升级）；全红则拒发不猜 |
| 健康不由发送失败推断（Channel 只读不改） | 用户裁定「发送失败标黄，多次失败再标红，成功一次恢复绿；自报无法连接 / 正在重连直接标红」 | **三色状态机**：`green` / `yellow` / `red`。单次失败只降黄（可能是内容或权限问题），连败达阈值才红，成功即清零回绿；`detail` 是 Adapter 给的自由字符串，Channel 只透传、不解析 |
| 回执时机待定（同步返回 / 事件推送） | 用户裁定「没超时就同步返回，超时就靠占位工具后续注入」 | **同步优先**：窗口内到达就当场返回；超时承认「已提交、回执未到」，随后由 `pending` 注入 |
| 主备是否允许跨账号（列为待定） | 用户裁定「多适配器本身就是为多账号而生的」 | **跨账号是设计目的**：一条连接 = 一个账号身份，`(platformId, accountId)` 唯一；`self` 按身份判定，不按「是不是主」 |
| 入站：Adapter 把 envelope 投给一个或多个 Channel（`§3` 原写法） | 用户裁定「适配器暴露自己收到的所有信息的瞬间事件，频道按需处理，不是自己需要的就抛弃；频道自己持有绑定的适配器 id 和群聊 id」 | **多对多广播**：Adapter 不知道谁在听、不做分派；Channel 用 `(adapterInstanceId, platformConversationId)` 自认领，丢弃是常态；瞬时事件不重放，补历史只能从 AdapterStore 读 |
| 通用功能 = 全覆盖 8 个 `ActionKind`（各给 native / fallback / noop） | 用户裁定「频道暴露足够基础，极端情况只剩收发；其余不通用都走特殊行为，成本不会太高，但代码干净很多」 | **Adapter 接口只有 receive + send**；其余不进通用接口 |
| Adapter 必须有入站（只有出站的算工具） | 用户裁定「只读或只写都是特殊情况；适配器定义扩展，但频道收缩——频道只能绑双向适配器」 | **Adapter 按方向拆**：`IInbound` / `IOutbound` / `IChatAdapter`（两者）；**方向是能力不是残缺**；**Channel 只绑双向**，绑单向 ⇒ 加载失败；单向 Adapter 的事件不由 Channel 消费 |
| 特殊行为 = 每个动作一个工具（edit / delete / … 各占工具表一格） | 用户裁定「会话越过频道操作时，本质是调用适配器操作工具；参数是适配器 id、动作、参数；没给就逐层报清单」 | **一个 `adapter` 工具逐层展开**：`adapter()` 列适配器 → `adapter(id)` 列动作 → `adapter(id,action)` 出 schema → 执行返回同构结果；**工具表恒定**，特殊行为全在参数里；通用工具另有 `speak` / `history`（读 ChannelStore）/ `pending` |
| Graph = 静态订阅表，Jint 只执行纯逻辑 | 用户提出让 Jint 灵活编排程序内接口 | **方向更新为 Jint 脚本主导 Graph 编排**；Manager 持有实例，脚本经受控 Host API 查询/调用。具体边界见 `13`，旧静态图细则待修订 |

| 共享预设影响面 | `preset.set` 只写共享文件，不失效 Stepper；测试明确验证“改文件 ⇒ 下一次渲染拿新内容” | `CommandDispatcher.cs:630-646`；`tests/Lilara.Core.Tests/PresetTests.cs:149-169` |
| Stepper 缓存含义 | 每会话缓存 Stepper（持有该会话的适配器）；全局 `InvalidateSteppers()` 清的是 Stepper 对象，不是供应商的 token cache | `CoreHost.cs:235-260`；provider 改动才调用全局失效：`CommandDispatcher.cs:2506` |
| 指纹含义 | `RequestFingerprint` 只哈希槽位 + 工具表，写在 usage 记录；代码里没有用它自动清缓存 | `Stepper.cs:313,761-770` |
| Responses 续链 | 不使用 `previous_response_id`；每次从本地 Timeline 完整构造 `input`；缓存由供应商按前缀处理 | `OpenAiResponsesRequest.cs:10-24,72-81,93-95` |
| 测试覆盖 | 有“头不变时指纹稳定、历史逐字节为前缀”的测试；没有“重建头后只影响目标会话”的测试 | `CacheStableTests.cs:182-275` |

**设计差异**：ALC 接受共享预设实时引用，因此编辑 `default.md` 会让所有引用该文件的会话在下一次调用换头，可能同时丢掉这些会话的前缀命中。ALN 要冻结会话快照，再由用户逐会话显式重建；不能把 ALC 的共享文件热引用照搬过来。

**缓存不是可清的本地链表**：供应商缓存不能由客户端精准删除。新头只会让目标会话的下一次请求不匹配旧前缀；旧缓存由供应商按自己的 TTL 回收。ALC 的 `InvalidateSteppers()` 既不是这个操作，也不能用作重建头的办法。

> 审计范围说明：ALC 当前工作树原本有未提交改动（本轮只读，未碰它）。涉及的 `Stepper.cs`、`CommandDispatcher.cs`、`OpenAiResponsesRequest.cs` 也处于修改状态；本表的提示词读取、预设写入、全量历史请求与缓存指纹结论已对照当前文件正文及相关测试检查，未据此声称整个仓库等于 HEAD。未运行测试。
