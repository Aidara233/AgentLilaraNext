# 图模块：连接层

> 状态：早期设计草案，核心执行模型已被用户最近方向重新打开。脚本主导编排的当前实施蓝图见 [`13-脚本编排与工程实施蓝图.md`](13-脚本编排与工程实施蓝图.md)；本文静态订阅表、禁止分支/循环等约束暂不作为新实现契约。
> 前置：[`00-继承与作废台账.md`](00-继承与作废台账.md)、[`01-模块切分.md`](01-模块切分.md)。

---

## 0. 一句话

> **图是一张表，不是一门语言。**

图唯一的价值是**让连接可见且可穷举**。任何让图"更通用"的改动，都在削弱它唯一的价值——通用的连接器描述不了任何东西，只描述了自己。

判据（设计时反复用）：**这份改动之后，我还能不能在一张纸上写出"系统现在会做什么"？** 写不出来就是错的方向。

---

## 1. ALP 为什么失控（五条，带证据）

不是"图的方向错了"，是这五条机制把它变成了不可知物。

| # | 症状 | 证据（ALP） | 根因 |
|---|---|---|---|
| 1 | **目录大于能力** | `NodeTypeCatalog` 从 `IntentCatalog` 投影 sink 节点，六个 `sink.*` 无执行方也照样出现在模型与校验器眼里；模型写图 → `wire_validate` 过 → apply 过 → mount 过 → 算出意图 → 全链路 `unsupported-intent` | 声明的能力与可执行的能力是两个派生源 |
| 2 | **语义抽象到无法心算** | 三阶段执行 + 求解器 + 网络 + 「类型图 ⊕ 实例图 overlay」（D2/D3 自己承认递归合成会把校验复杂度推高） | 图被设计成有算法，而不是有形状 |
| 3 | **声明与生效分离** | 16 张出厂图只挂 1 张；生产 `[Module]` 只有 5 个，30 余个只在测试里出现；靠 `KnownUnshippedSinks` / `NotWiredNote` 这类人工台账兜 | "图存在"与"图在跑"是两个状态 |
| 4 | **路径数量不可数** | 5 个环境变量开关（`LILARA_GRAPH_MODE` / `*_SHADOW` / `SESSION_BRAIN` …）+ `*ShadowRunner` 只对拍不提交 + 默认全 off | 开关成了第二套配置系统，且没人会删一个 off 的开关 |
| 5 | **连"现状"都要重新勘查** | 三个 `Graph*` 项目目录空、命名空间散在别处、两套 D 编号、淘汰清单列了没删 | 没有单一派生源 |

一句话总结：**ALP 的图同时是语言、编译器、注册表、开关面板和台账**，所以它既不能被人读，也不能被机器验。

## 2. 形状：一张订阅表（接收方连发起方）

> **形如 C# 的广播**：`publisher.Event += subscriber.Handler`。
> 订阅表里写的是**接收方连发起方**，发起方完全不知道有谁在听。

```jsonc
// 订阅：频道接适配器的"收到消息"
{
  "id":   "channel.intake",
  "from": "adapter.qq#*.message.received",   // 发起方（事件）
  "to":   "channel.*.intake",                // 接收方（端口）
  "args": { "msg": "$event" }
}

// 另一条订阅，订阅同一个事件，与上面互不影响
{
  "id":      "store.raw",
  "from":    "adapter.qq#*.message.received",
  "to":      "store.*.put",
  "resolve": { "store": "$source.storeRef" },
  "args":    { "raw": "$event" }
}
```

为什么是这个方向：发起方零改动即新增消费者；连接表天然是"边集合"；与所有权判据一致——**接收方声明自己接谁**。

**三条结构规则**：

1. **一张订阅 = 一次跨模块调用。** 中间可以有纯节点（`resolve` / `map` / `eval`）算参数，**但只有最后一个节点能是 `call`**。于是：**系统的连接图 = 订阅表，一条边 = 一张订阅，没有暗边。**
2. **信号不递归、分支互不干扰。** 上游发完就走；事件先进队列、随后派发；一个订阅抛错不影响兄弟分支（C# 多播是同步调用，这半边刻意不照抄）。⚠️ 但**失败必须可见**：审计 + 计数 + 死信，否则"发完不管"就是错误黑洞。
3. **信号无序并发，调用点对点串行。** 信号分支不保证先后——确定性靠"**同一模块实例内部方法串行**，跨实例并发"；调用只有一个接收方并且等返回。**不依赖注册顺序/安装顺序**（ALP"安装序号"的教训），也不需要排序键——因为已经不允许靠顺序表达语义。

⚠️ **反查视图是必需品。** 订阅方向是"接收方连发起方"，正面看不出"谁在听这个事件"。必须提供**由事件名反查订阅者**的视图，且它是**派生**的、不落盘。没有它，就回到 ALP 的"不知道系统会做什么"。

### 2.1 那"一步"怎么办：过程（procedure）

一步（`session.step`）要**按序**做四五件跨模块的事，还要把中间结果搬给下一步。订阅是"一次调用"，装不下序列。若为此放宽"只有最后一个节点能是 `call`"，连接图立刻出现暗边，前面所有规则当场失效。

所以引入第三种东西（前两种是模块、订阅）：

| | 是什么 | 归谁 | 怎么改 |
|---|---|---|---|
| **模块** | 做事（有副作用） | 内建 / 插件 | 换实现 |
| **订阅表** | 连（一条边一次调用） | **数据** | 随时改 |
| **过程** | **序**（固定的若干步，每步发一个事件） | **内核（代码）** | 改版本 |

```
过程「一步」= 发 session.need-context → session.need-model → session.need-tools
            → session.need-apply   → session.need-persist → session.need-output
```

- 每一步的跨模块调用**仍然是订阅**（可见、可校验、可反查）；
- 过程自己**不调任何端口**，只按序发事件、并把上一步的结果搬进下一个事件的载荷；
- 过程是**代码**，固定几条、有正向测试、不进图、不可插拔——这是它不会重演 `X-01`（SpawnCheck）的原因：**它不是扩展点，是内核的固定序列**。

⚠️ 代价如实记：一步变成约 5 次派发 + 5 次订阅调用（查表 + 委托，不是求解）；执行记录要按"过程"聚合成一条，否则日志会碎掉。

**节点只有四种**（v0 定为有限集，加一种都要过 §4 预算那一关）：

| 节点 | 作用 | 备注 |
|---|---|---|
| `call` | 调某个端口的某个方法 | 唯一的"动作"，**只能出现在最后** |
| `resolve` | 用来源实例/配置属性解出一个地址 | 就是你说的"根据 id 获取存储模块" |
| `map` | 从事件/上一步结果里取值填参数 | 无表达式、无运算 |
| `eval` | 调 `logic` 求值（纯，见 [`03`](03-自由逻辑.md)） | 自由度都在这里，且碰不到世界 |

**参数只有三个来源**：`$event`（触发载荷）、`$source`（来源实例地址）、`$prev`（上一步结果）。没有表达式、没有函数、没有变量作用域。

> 例：你说的「计数器 +1」= `{ "call": "stat.any.counter.incr", "args": { "by": 1 } }`。它确实要走图（跨模块），而它走图的样子就这么一行。

## 3. 生命周期：校验 → 编译 → 挂载 → 执行记录（定）

```
写图（数据）
  → 加载期校验（成员存在 / 类型匹配 / 能力满足 / 地址可解）
  → 编译成委托链（一次性，运行期只做查表 + 调用）
  → 挂载（不挂载 = 不存在）
  → 执行 → 一条执行记录
```

四条硬规则：

1. **接不上即硬失败**（启动期，不是运行期）。修 `X-11`：ALP 的"静默跳过"是 16 张图只挂 1 张的成因。
2. **只有两种状态：在跑，或不存在。** 取消"已装载但未挂载"。这一条消灭了"图纸先于消费者"的整个类别。
3. **加载期编译成委托，运行期不做求解。** 这是"一步之内也走图"能成立的唯一原因——每步过图的代价是字典查表 + N 次调用，不是跑一遍求解器。也因此原子性仍然由内核的落盘把握，不受图影响。
4. **每次执行产生一条执行记录**（图 id、触发、节点序列、每步参数/结果/耗时/失败点），**默认开、不是开关**。"不知道变成了什么情况"的唯一解药就是这个，而且它在图模块之外可读（头的页面、控制台命令都能读）。

## 4. 预算：防它长大（定）

| 预算 | 值 | 超了怎么办 |
|---|---|---|
| 单张图的节点数 | ≤ 8 | 拆图；若拆不开，说明这条流程本该在**一个模块内部** |
| 全局图数量 | v0 ≤ 12 | 需要架构讨论，不是"再加一张" |
| 可读性 | 每张图能读成**一句话**：「当 <模块>.<事件> 时，依次调 <端口>.<方法>」 | 读不成 ⇒ 设计错了 |
| 图的层数 | 1（图不能触发图） | 复用就复制；数据便宜，图依赖网昂贵 |

> **长的连线通常意味着你把一个模块该干的事拆到了多个模块。** 这是设计信号，不是图不够灵活。

---

## 5. 禁止项（图的"能"与"不能"）

| 禁止 | 为什么 |
|---|---|
| **条件 / 分支 / 循环** | 判定留在模块里：模块决定发**什么事件名**（`message.received.private` vs `.group`），图决定**接到哪**。判定一旦进图，图就成了编程语言 |
| **图触发图** | 否则形成隐式调用网，"系统会做什么"不再可穷举 |
| **图持有业务状态** | 图只持装配态与执行记录；状态住在各模块的实例层 |
| **图做"要不要执行"的判定** | 权限/能力/模式判定住内核与模块；图只接线 |
| **由数据决定目标端口** | 目标必须在加载期可知；数据只能选"动作的哪一款"（有限枚举，由执行模块分派）。否则静态可求解性失效 |
| **模块自动注册接线** | 接线必须**显式挂载**，否则回到"谁连了谁不可知"。模块可以**携带**图（作为自己的资源），但携带 ≠ 生效 |

## 6. 「一步」与图（已被 §2.1 取代）

**跨模块就过图，没有例外**——哪怕只是把一个跨模块的计数器 +1。而"一步"作为一项需要按序完成多项跨模块工作的事，由**过程**（§2.1）驱动：过程按序发事件，每次派发都走订阅。

原结论保留，只在措辞上更新：

- 图在**加载期**编译成确定性调用序列，运行期没有求解 ⇒ "每步过图"的代价是查表 + 委托；
- 原子性由**内核**把握（过程开始到落盘为一段），不由图把握；
- 重试只发生在"调模型"那一次订阅上（它是唯一允许重试的端口，由端口自己声明）。

⚠️ **出厂订阅与用户订阅的边界**（原 `J8`）：出厂订阅随内核版本发布、只读；用户订阅物理分目录；同名以出厂为准。`session.step` 那组订阅属于出厂，因为它们定义的是"一步怎么走完"。**可换的是装配（挂哪些订阅），不是出厂那套的核心序列。**

## 7. 案例：条件回复（含关键字 → 回复）

> 这个案例用来检验「图不带条件」这条规则能不能撑住真实需求。答案是：能，但**条件必须换一个住处**。

### 7.1 先说为什么不能把条件写进图

直觉做法是在图里加一个 `if` 节点。三个后果：

1. **图的数量随条件数量增长。** 用户每加一条关键词就要改图（或新增一张图）⇒ 12 张的预算立刻失效，"在一张纸上写出系统会做什么"也就不可能。
2. **加一条关键词从"改数据"变成"改程序"。** 而改程序要过版本、过评审、过重启。
3. **判定散进图里之后，无处能列出"现在有哪些条件"。** 这正是 ALP 的病：条件、算子、插槽都进了图，最后没人说得清。

### 7.2 条件的三个合法住处

| 住处 | 例子 | 变化成本 |
|---|---|---|
| **模块内的代码**（形态固定、语义固定） | 私聊 / 群聊、被@ / 未被@、撤回 / 正常 | 改代码（新版本） |
| **模块内的数据表** | 关键词规则、静默时段、黑白名单、回复模板 | **改数据（热生效）** |
| **图的参数映射**（不是判定，是取值） | 把 `$event.sender` 传给端口 | 改图 |

**禁止的住处**：图的控制流。

### 7.3 落法：规则是数据，图只接「命中」

```
数据   channel.group-1234.rules = [
         { id: r1, when: { kind: contains, text: "报时" }, do: { post: "现在几点？" } },
         { id: r2, when: { kind: regex, pattern: "^/help" }, do: { inject: "用户求助" } }
       ]
       
模块   rule    —— 订阅"频道整理完毕"，逐条跑规则，命中则发事件 rule.matched { ruleId, source, msgId }
图     on rule.matched → 按规则的动作类型接下去（见 7.4）
```

**新增一条关键词 = 往表里加一行**；图的张数不变。这就是"条件不进图"换到的东西。

### 7.4 四条一句话的主链（出厂图）

| # | 图（读成一句话） |
|---|---|
| 1 | 当 `adapter.*.message.received` 时，调 `channel.*.intake` |
| 2 | 当 `channel.*.intake.done` 时，调 `rule.*.evaluate` |
| 3 | 当 `rule.matched` 时，调 `channel.*.post`（或 `session.*.inject`） |
| 4 | 当 `channel.*.outbound.requested` 时，调 `adapter.*.send` |

⚠️ 注意第 3、4 两条：**跨模块就过图，哪怕只是"把一段文本发出去"**。它们在一条链上串着，但每一跳都是独立的一张图——这保证了"任意两个模块之间没有暗线"。

⚠️ 也因此：**图的条数 ∝ 主链数，不 ∝ 规则数、也不 ∝ 模块数平方**。上面的链是出厂图，用户加规则不动它。

### 7.5 两个实现细节

1. **规则挂在 `channel` 之后，不是 `adapter` 之后。** 它拿到的是**清洗 + 去重后**的消息，所以：同一消息不会重复触发回复（去重的红利）；规则作者看到的是规范化字段，不是平台原始报文。
2. **命中之后可以接不同动作，不改代码。** 直接模板回复（快、便宜、确定）和"注入会话让模型决定怎么回"在图上只是第 3 条链的目标不同。想要两种都用，就挂两张图。

### 7.6 如果需求是"任意逻辑的自动回复"

那不是图该扩展的边界，而是**匹配器类型**该扩展：`rule` 模块提供一组封闭的匹配器（contains / regex / 时间窗 / 名单），要新类型就写一个模块实现它（代码）。判据：

> **"能表达什么条件" 由代码决定，"具体哪条规则" 由数据决定，图只负责 "命中之后接到哪"。**

三者混一层，就是 ALP。

### 7.7 这个案例暴露的新模块

`rule`（子实例 = 一条规则集，按频道/会话分区）——它不持有外部输入，只消费内部事件，按 [`01` §2](01-模块切分.md) 的判据属于"没有自己输入源的模块"。★待确认是否独立成模块，还是并进 `channel`。我倾向独立：`channel` 已经背了去重、整理、缓存、出向编排，再加规则匹配会让它变成第二个 `ChannelContextService`。

## 8. 挂载规则：持久化的是意图（定）

早期这里只区分 `default` / `manual`，那回答的是**"谁把脚本挂上去"**。它回答不了另外两个问题，而这两个才是重启之后会疼的：

- **活多久**：一直挂着，还是处理一次就退场？
- **挂给谁**：这一个实例，还是这一类实例（含以后新建的）？

于是拆成三个正交的轴：

| 轴 | 取值 | 说明 |
|---|---|---|
| `source` | `bundle` / `manual` | 随包自动挂（不落盘，随实例重新推导）/ 人点名挂（落盘） |
| `budget` | `null` / `N` | 每个命中目标最多分发 N 次；`1` 就是一次性。**先扣后用**：宁可漏一次，不可重一次 |
| `scope` | `instance` / `type` / `module` | 一个实例 / 某类型的所有实例 / 某模块下所有类型 |

关键的一条：**存的是规则（选择器），不是解析出来的挂载列表。**

- "`channel.chat` 挂在所有 Channel 上"是**一条**规则；重启后、以及以后新建的频道出现时，它继续成立，不需要任何人重新挂一次。
- 规则可以**暂时解析不到任何实例**（图先起来、频道后复活），这叫 pending，不叫失败，也不该被清理——清理它等于把"以后新建的频道自动获得"这件事悄悄取消。
- `instance` 作用域是例外：它必须指名一个此刻存在的实例。往不存在的地址挂不是意图，是打错字，当场报错。

配套的两件事写进 [`17`](17-状态与恢复.md)：规则的落盘位置与格式（`state/graph/mounts.json`，人能读），以及脚本自己的记忆 `ctx.state`（按目标或按规则一段命名空间）——一次性脚本和"每个频道各记各的"都靠它。
