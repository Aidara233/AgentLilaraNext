# 25 · 模型写脚本

> 给模型一块可以写脚本的地，并且让"写了"和"生效了"始终是两件事。

## 0. 一句话

脚本可以写进 `<dataRoot>/scripts/draft/`，可以被加载、被列出；只有一次显式挂载会让它生效，而挂载会把它移到
`<dataRoot>/scripts/live/` —— **目录就是它是否在生效的答案**。

## 1. 为什么要有草稿区

模型能写文件之后，"写脚本"立刻变成一道判断题：它写出来的东西，该不该直接跑？

- 直接把 `scripts/trusted` 的写权限给它，等于允许它接管任何一类实例的行为，一次手滑就是全局；
- 完全不给写，自举就只剩"读"这一半。

草稿区是第三条路：**可写、可被加载、默认不参与任何挂载**。可写和可生效分开，是这一整节的全部内容。

## 2. 五个来源与权威顺序

| 根 | 谁写 | `trustDomain` | 能不能自己运行 |
|---|---|---|---|
| `resources/scripts/builtin` | 随程序发布 | `builtin` | 能：`default` 或 `manual` 都行 |
| `<dataRoot>/scripts/trusted` | 人（出厂脚本的第一份副本也落在这里） | `trusted` | 能 |
| `<dataRoot>/scripts/draft` | 人、模型 | `trusted` | **不能：`mount` 必须是 `manual`** |
| `<dataRoot>/scripts/live` | 挂载动作（草稿晋升而来） | `trusted` | 是：它在这里就说明它被挂载着 |
| `<dataRoot>/scripts/restricted` | 人 | `restricted` | 不加载：没有进程隔离运行器 |
| `<dataRoot>/plugins/<id>/scripts` | 插件包 | `trusted` | 能 |

`draft` 与 `live` 是同一批脚本的两个状态，由挂载/卸载移动，不由人手工摆放：挂载成功 → `draft` 移到 `live`；
最后一个挂载点消失 → 移回 `draft`。因此**看目录就知道它在不在生效**，不必去查数据库。`trusted` 不在这条移动线上：
那份属于把它放进去的人，宿主不搬别人的文件。

同名的权威顺序，只有一条例外：

- **运营者的副本可以覆盖出厂脚本**（种子复制需要在第二次启动时不撞车）；
- 其余一律"先到的赢、后来的被报告"：草稿不覆盖别人，插件也不能占一个已经存在的名字。

`trustDomain` 与所在目录必须一致。这是"冒充内置"唯一能被发现的地方，也是草稿必须写 `trusted` 的原因。

## 3. 草稿的硬约束

1. `mount` 必须是 `manual`。这条让"能写"不等于"能接管"—— 模型写的脚本只能等人挂。
2. `trustDomain` 必须是 `trusted`。
3. 能力仍受那 8 个白名单约束，且每次调用都再校验一次：**草稿不因为它是草稿而多拿任何权限**。
4. 目录形状照旧：`<目录>/manifest.json` + `<目录>/main.js`。

## 4. 一条坏脚本不该弄挂宿主

原来任何一个文件出错（缺 `id`、`trustDomain` 不符、`main.js` 缺失、JSON 坏了）都是"整份目录加载失败"，而宿主对加载失败的响应是**退出**。这条在草稿存在之后不可接受：模型的错误会变成"下次启动起不来"，而且发作在重启时，中间没人察觉。

现在的规则分三层：

- **catalog 逐文件跳过**：说清是哪个文件、为什么，继续读下一个（`IGraphScriptCatalog.LastIssues`）；
- **graph 逐脚本拒绝**：清单校验、能力校验、源码校验都按单个脚本判（`IGraphRuntime.RejectedScripts`）；
- **被拒的新版本不顶掉旧版本**：同一个 `id` 已经在跑，新版本被拒时旧版本继续工作。改坏的后果是"这次不生效"，不是"这个脚本消失"。

歧义仍然是歧义，只是不再致命：两个同名脚本，第一个赢，第二个被点名报告，不合并、不静默挑一个。

## 5. 加载与重载

`scripts.reload` 动作：重读所有根 → `graph.LoadAsync`（这是全量替换，不是追加）→ 返回 `{ loaded, scripts, rejected }`。

- 失败时保留旧版；
- 没有文件监视：什么时候重载是人（或控制台）的决定，不是磁盘事件；
- 写草稿的人看到"出现在 `scripts.list` 里"之后，还需要一次 `modules.edge.mount` 才真的开始工作。

模型这一侧有四个工具，都**不对外说话**（`ActsExternally = false`）：

| 工具 | 作用 |
|---|---|
| `scripts_list` | 每个已加载脚本的 id、来源（bundled/user/draft/live/plugin）、是否启用、挂载方式、监听什么；外加"被 graph 拒绝的"和"作为文件就读不出来的"两份原因清单。空图时明说"没有任何东西会应答"。 |
| `scripts_reload` | 与动作同一份语义（`ScriptReload.RunAsync`），返回重载后的清单与拒绝原因。 |
| `scripts_mount` | 把一个脚本挂到一个实例上（任何已加载、非 `default` 的脚本，任何类型兼容的实例）。挂载成功且脚本在 `draft`，它会移到 `live`；从 `live` 加载不起来就移回 `draft` 并如实说明。 |
| `scripts_unmount` | 从某个实例上摘下；若那是它最后的挂载点且在 `live`，移回 `draft`。 |
| `instances_list` | 图上所有实例的地址与类型，并标出每个实例上已经挂了哪些脚本。`query`（地址或类型的子串）与 `type`（类型前缀，`channel` 也包含 `channel.conversation`）用来缩小范围，`limit` 默认 50、最多 200。 |

四个工具里只有 `scripts_mount` 会让脚本生效，而它是一次**显式**的动作：写在草稿里、被加载、出现在列表里，都不等于在生效。挂载本身不往对话里写任何东西——下一轮才开口。

两个重载入口共用一份实现（`ScriptReload.RunAsync`），是因为"问同一件事的两扇门给出不同答案"就是两套实现等着打架。挂载顺序也是固定的：先挂上（失败就什么都不动），再移动目录——挂了却加载不起来时把目录移回去，因为一个谎称"正在生效"的目录比一条指向草稿的规则更坏。

## 6. 能力仍然受限

脚本拿到的是 `event`、`ctx`、语言本身和 `JSON`。没有 CLR 互操作、没有文件、没有网络、没有 `require`；执行受 `maxStatements` / `timeoutMilliseconds` / `memoryLimitBytes` 三条限制，超了是一次失败而不是一次等待。草稿不改变其中任何一条 —— 它是同一种脚本，只是放在一个还不能自己生效的地方。

## 7. 手册放在哪

`<dataRoot>/scripts/draft/GUIDE.md`，随宿主启动写一次（`ScriptSeed.EnsureDraftGuideAsync`），用模型已经在用的文件工具就能读。

**不进每轮上下文**：它是"写的时候才需要"的参考材料，一整页塞进每个回合，成本远大于它省下的。

手册里的例子（`ScriptSeed.ExampleManifest` / `ExampleSource`）是常量，并且有测试把这两个常量真的喂给 catalog 和 graph。理由很直接：一份教人写出会被拒绝的形状的文档，比没有文档更糟。

## 8. 不做

- **不因为脚本在某个目录就让它生效**。目录跟着挂载走，不反过来：只有一次显式挂载会让脚本运行，而挂载会把它移出草稿目录。
- **不做文件监视自动重载**。改了文件不等于改了行为，重载是个决定。
- **不因为草稿而扩大能力白名单**，也不给草稿单独的更高配额。
- **不做"草稿合并"**。同名只报告，不合并。

## 9. 尚未做

- 草稿区没有"从草稿晋升到 trusted"的自动化；复制仍是一个人的动作。
- `restricted` 域仍缺进程隔离运行器，那边的脚本一律拒绝加载。
- 挂载工具只支持实例级：`scripts_mount` / `scripts_unmount` 收 `target`，没有 `scope`/`selector` 与 `budget`/`stateScope` 那几档——它们仍只在 `modules.edge.mount` 动作上。
- 没有"晋升到 trusted"的动作：草稿被挂载即生效，但不会被复制成一份属于人的脚本。
