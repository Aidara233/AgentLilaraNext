# 19 · 会话连接（会话怎么接上一个频道）

> 这是一篇**设计**文档：说该是什么样，代码尚未实现。
> 它回答一个问题：**一个会话和一段频道之间是什么关系，上下文从哪进、话往哪出。**
> 收尾（`wait` 之后会发生什么）见 [`20`](20-会话收尾.md)；记忆见 [`21`](21-记忆系统.md)（未写）。

---

## 0. 一句话

会话不"属于"频道。会话**连接**频道，连接是一个独立实体：它记着水位，决定上下文从哪进、话往哪出。

---

## 1. 今天的形状，以及它为什么脆

现在有三条隐含约定，各自都成立，合起来是一条链：

| # | 约定 | 出处 |
|---|---|---|
| 1 | 会话 id 由「挂载目标 + 频道地址」哈希出来 | `GraphManager.cs:762-763`、`:798-799` |
| 2 | 持久状态里只记一个频道地址字符串，不记 binding | `SessionContracts.cs:42`、`SessionManager.cs:548` |
| 3 | binding 每轮由当轮那条消息现传，用完即弃 | `SessionTurnInput.Binding`（`SessionContracts.cs:86-89`）→ `RoundContextRequest`（`SessionManager.cs:322`） |

链是这样的：**id 由地址推出 → 状态只记地址 → binding 只活在"当轮消息"里。**

所以它脆在三个地方，都不是理论问题：

1. **改 binding 不迁移会话。** 平台会话 id 变了、适配器换了，会话 id 不变（它只认频道地址），但每轮传进来的 binding 变了。旧消息属于旧 binding，新消息属于新 binding，却躺在同一份历史里——而 `<channel_messages>` 是每轮从历史重渲染的，模型会把两段不同的平台会话当成一段对话读。
2. **一个频道可以有多个 binding** 时（`CoreActions.cs:548-553` 里 `channels.send` 自己都要求 "exactly one binding"，说明数据结构允许多个），`speak` 打哪条取决于当轮是哪条消息带来的 binding。
3. **非频道来源驱动不了会话。** 定时唤醒、另一个会话的委托，都没有"当轮消息"，也就没有 binding 可传。而 `session.activate` 今天还硬性要求来源是 channel 消息（`GraphManager.cs:748-749`）——两处一起把会话钉死在频道上。

**没有一处会报错。** 这三条都是"输入变了但推导规则没变"，系统照常运转，只是内容悄悄错位。

---

## 2. 一条原则

> **凡是被持久引用的东西，身份必须显式记录，不能从别的字段推导。**

两个真实反例：ALP 的 `utterance_id` 用进程内自增（重启归 1，三个月撞号 71 组）；我们的 `sessionId` 用地址哈希。共同点不是"写法不好看"，而是**推导规则不变而输入变了的时候，身份会静默错位，而没有任何地方能报错**。

边界要划清，否则这条原则会被用错：**把"每次动作时明确写下来的值"再读回来，不算推导。** 水位就是这样——它每次注入都被写进履历（§5），不是猜出来的。区别在于：身份错了没人能发现，水位错了能对账。

---

## 3. 三件事分开

现在这三件事都压在脚本身上，同时又有一半漏在宿主里。

| | 是什么 | 归谁 |
|---|---|---|
| **触发** | 这条消息（或这个时刻）值不值得跑一轮 | **脚本**（策略：过滤、@ 检查、冷却） |
| **身份** | 这一轮属于哪段持续对话 | **宿主**（状态，必须落库） |
| **目的地** | 话往哪条平台会话发 | **连接**（数据，可移动） |

脚本仍然决定"要不要"，宿主只保证"要的时候拿到的是同一个"。**没有脚本就永远没有会话**——这是正确行为，不是缺陷。

---

## 4. 连接是独立实体

放在 `aln.db`，与其他需要被查询的状态同库（理由见 `17` §2）。

```sql
CREATE TABLE connection(
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    channel        TEXT NOT NULL,
    session_id     TEXT NOT NULL,
    adapter        TEXT NOT NULL,
    conversation   TEXT NOT NULL,
    watermark_at   TEXT NULL,      -- 已注入到哪一条：时间戳
    watermark_id   TEXT NULL,      -- 已注入到哪一条：消息 id
    established_at TEXT NOT NULL,
    closed_at      TEXT NULL);

-- 一个频道同时只被一个会话连着
CREATE UNIQUE INDEX connection_active_channel ON connection(channel)          WHERE closed_at IS NULL;
-- 一个会话同时只连一个频道
CREATE UNIQUE INDEX connection_active_session ON connection(session_id)       WHERE closed_at IS NULL;
```

### 为什么不塞进任何一边

- 塞进会话 → 会话得知道"每个频道补到哪了"，`SessionState` 里就会长出频道字段（今天已经有 `Channel` 这一个残留）。
- 塞进频道 → 频道得知道"我连着哪个会话"，而 channel spec 是人写的声明式文件，不该承载运行时关系。
- 放进连接 → 会话不知道频道，频道不知道会话，**只有连接同时提到两边，而它只记地址和计数，不描述对方在干什么。**

### 两条唯一约束都在 active 状态上

`closed_at IS NULL` 的部分索引保证"当前"的 1:1，同时保留历史连接记录（一个频道换过几个会话、一个会话换过几个频道，都能查）。这两条约束是把"一个频道只该有一个会话"这个不变式**放进数据**，而不是交给每个脚本各写一遍。

竞态在这里消失：两条消息同时到达，两个脚本都调 `connect`，后到的那个插入撞唯一索引，读到同一行。不需要加锁、不需要先查再建。

---

## 5. 水位：注入的唯一入口

### 水位是什么

**这个会话从这个频道已经补到哪一条消息。** 记成 `(at, id)` 两个字段，不是一个。

为什么必须是组合：`message.id` 是 GUID（`ChannelManager.cs:282` 用 `envelope.EventId.ToString("D")`），**它没有顺序**；顺序来自 `ORDER BY at, id`（`SqliteStore.cs:145`、`:220`）。所以"水位之后"是 `(at, id)` 的字典序比较，不是 `id >`。

### 一个入口，两种触发

```
connect(channel, limit?)
    1. 读这个连接的水位（没有就是"从最早开始"）
    2. 取该频道 (watermark_at, watermark_id) 之后、至多 limit 条消息
    3. 追加进时间线，块里写明这一批含哪些消息
    4. 更新水位
```

**重连**和**日常来新消息**走的是同一段代码：前者要补的多，后者通常补 1 条。没有两套逻辑，也就没有"重连路径没测到"这种事。

### 顺序不能反

**先追加块，再更新水位。** 崩在这两步之间，下次连接会重放同一批，而时间线里的消息是按 id 索引的（`CollectChannelTimeline` 用 `byKey` 字典，同 id 配不同内容会直接抛错，`SessionManager.cs:1142-1152`），渲染时自动去重。

反过来先更新水位：崩了就**真丢**，而且没人知道丢了。

> 宁可重复，不可丢。这条比"找一个能跨两个存储的事务"便宜得多，也更符合履历的性质。

### 需要补的存储能力

`IMessageStore` 现在只有 `ReadAsync`（全部）和 `ReadRecentAsync(owner, limit)`（最近 N 条），没有"某位置之后"。要加一个：

```csharp
ValueTask<Result<IReadOnlyList<StoredMessage>>> ReadAfterAsync(
    Address owner, DateTimeOffset at, string? id, int limit, CancellationToken cancellationToken);
```

`owner` 就是频道地址（`ChannelManager.cs:283` 写的是 `channel.Address`）。

## 6. 话往哪出

**`speak` 的目的地 = 这个会话当前连接的 binding。**

没有连接就报错，**不回落**。回落只能落到"当轮消息的 binding"，而那正是 §1 里最脆的那一环；而且在非频道来源驱动的那一轮里，它根本不存在。

这条同时解释了为什么 `speak` 与连接必须一起做：**连接是 `speak` 唯一不依赖"谁叫醒了我"的地址来源。**

---

## 7. 连接块：每次连接都留一条出处

每次连接往时间线注入一个块，写清：频道地址、binding（适配器 + 平台会话）、连接时刻、这一批补了多少条、从哪条到哪条。

**每次连接都写，不只在第一次写。** 现有 `ChannelInfoContributor` 用 `StepNumber == 1` 来表达"只在开场说一次"（`BuiltinRoundContextContributor.cs:92`）——但"开场"不是一个步骤数，是**一次连接**。而且它只在第一次写，换绑之后那段首次信息就是错的，且不会重发。

**旧块不删。** 时间线是履历不是视图：模型在那些轮里做过推理、得出过结论，后面还会引用。删掉出处等于让它对着自己不知道来源的结论继续想——那不是整洁，是制造幻觉。

---

## 8. 谁触发连接

**脚本。宿主不提供"自动连接"。**

```
on channel.message.accepted:
    if not worth_answering(message): return
    sid = resolve(channel)              // lookup-or-create，幂等
    connect(sid, channel, limit)        // 拉上下文 + 定目的地
    session.turn(sid)                   // 或 session.activate
```

`resolve` 与 `connect` 分开：前者管身份（可复用于"我还有没有会话"），后者管上下文与目的地。"没有会话就建一个"是脚本的判断，不是宿主的策略。

---

## 9. `limit` 与脚本配置

`limit` 由**调用者**给：模型主动调 `connect` 时必须写，脚本调时可不写走默认。

默认值落在配置里，不是一个散在代码里的常量：

```
<dataRoot>/config/scripts/<脚本id>.json
{ "default": { "limit": 20 },
  "targets": { "channel.conversation#qq-…": { "limit": 5 } } }
```

解析顺序：**目标覆盖 → 脚本默认 → 宿主内置默认**。

四条规则：

1. **配置是文件，不是 `state`。** `SqliteStore` 的注释已经把这个界划好了：spec 留在文件里，因为那是人写、人读的（`SqliteStore.cs:12-15`）。配置属于这一类。
2. **脚本对配置只读。** `state` 是脚本自己写的记忆，`config` 是人写的意图。给脚本一个改自己运行参数的口子，它就不叫配置了。
3. **未知键要报错，不静默忽略。** ALP 用 `default: return` 吃掉了 12% 的情绪信号，几个月没人发现。配置拼错一个键名，行为悄悄变成默认值——同一类事故。
4. **读取时机写清楚**：每轮读盘（和提示词一致，改完立刻生效），还是挂载时读一次（变更要重挂）。两种都行，不能含糊。

顺带一句成本提醒：**20 是"消息条数"不是 token 数。** 这条路径没有任何截断，20 条长文能把上下文撑爆，而且撑爆时不会有报错——只会变贵、变慢、或被上游拒。

## 10. 明确不做

| 不做 | 为什么 |
|---|---|
| 一个会话同时连多个频道 | `speak` 的目的地会含糊。要跨频道干活，是开多个会话，不是让一个会话脚踏两条船 |
| 按 binding 过滤渲染时间线 | 时间线是履历，不是视图。两段对话混在一份历史里，靠连接块标注出处来分辨，而不是靠隐藏 |
| 在 channel spec 里记"我连着谁" | 频道是声明式配置，不该承载运行时关系；而且重建 channel 时这份关系会跟着漂 |
| 频道侧决定"要不要开会话" | 那会把 @ 检查、冷却、重复抑制压进 JSON，并且每次重建都要重做一遍，幂等性只能靠猜 |
| 宿主自动连接 | 唯一索引会让"两个脚本都觉得自己该连"变成一个静默的赢家/输家，而输家不知道为什么 |

---

## 11. 一个我按自己判断定下的口子

**身份（subject）默认就是频道地址，但允许脚本显式给一个。**

理由：review、定时任务这类没有频道的会话需要一个容器。默认值必须安全（频道地址），例外必须显式（脚本写死一个名字）。危险的地方是"脚本能命名就能分裂历史"——写错一次就会多出一段永远长不大的历史，所以这个能力只给需要的脚本，不给默认路径。
