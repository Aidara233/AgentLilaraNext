# 能力与审计

> 状态：草稿（**本文推翻 [`05`](05-自举.md) §3.3 / §4 的判断**）。
> 用户裁定：**所有接口都受限；ALN 本身不该具备"随意访问系统"的功能；安全性是绝对要求，不允许放宽**——尤其因为它要接入群聊。

---

## 0. 四条绝对要求

1. **ALN 本身不具备能力，只有"被授予的能力"。** 内核与模块都不直接碰 OS；**唯一碰 OS 的是一层极小的 host**。
2. **默认拒绝。** 没声明 = 没有；声明了 = 还要准入。
3. **能力是 scoped 句柄，不是权限位。** 不是"允许文件 IO"，而是"只能访问 `<dataRoot>/…/x` 之下、只读、单次 ≤N 字节"。
4. **一切能力调用过审计，审计不可关、不可裁剪。**

---

## 1. 为什么"编译 C# 再扫 IL"不合格

我上一版把 IL 白名单当成第三层闸门，那是错的：

| 问题 | 说明 |
|---|---|
| 缝 | 反射、动态加载、`Type.GetType`、P/Invoke、委托链——静态扫描永远追不上 |
| 方向错了 | 事后**检查**能力是否存在 ≠ 构造上**不存在**该能力 |
| 目录大于能力 | 正是 ALP 的老病：声明了一堆，真正能执行的不是那批 |

> **判据（与 `I-18` 同源）：能力必须在构造上不存在，而不是被检查出来。**

这条判据直接决定了脚本语言的选型（§5），也决定了 ALN 的整体形状。

---

## 2. 唯一碰 OS 的地方：host 层

```
host（极小；代码评审最严；其余一切都不能碰 OS）
 ├ file  → ScopedPath 句柄：前缀绑定 + 只读/读写 + 单次限额 + 条目数限额
 ├ net   → AllowlistHttp 句柄：域名白名单 + 方法白名单 + 体积/超时上限
 ├ time  → 确定性时钟（可注入，保证可重算）
 ├ proc  → ⚠️ 默认不存在（见 §8）
 └ audit → 每次调用落一条（不可关）
```

上层（内核 / 模块 / 脚本）**只拿得到句柄**，拿不到 OS。

---

## 3. 能力接口的形状：只给"范围"，不给"系统"

```csharp
// ✅ 正确：句柄绑定范围
interface IWorkspace
{
    ValueTask<ReadOnlyMemory<byte>> Read(string relPath, CancellationToken ct);
    ValueTask Write(string relPath, ReadOnlyMemory<byte> data, CancellationToken ct);
    IReadOnlyList<string> List(string relDir, int maxEntries);
}

// ❌ 错误：这就是"随意访问系统"
interface IFileSystem
{
    bool Exists(string absolutePath);
    void Delete(string path, bool recursive);
    string[] EnumerateAll(string root);
}
```

三条硬规则：

1. **契约层不出现绝对路径**；`relPath` 由句柄在创建时绑定的根解析，**越界（`..`、符号链接、盘符）一律拒绝**。
2. **没有"删除整棵树"这种原语**；删除是独立能力（`IDestructive`），单独授予、单独审计。
3. **`Contracts` 程序集不得引用 `System.IO` / `System.Net`**——这一条可以写成反向测试（并入 `E2`）。

## 4. 端口调用也要受限

"所有接口都受限"包括模块之间的端口调用：

- 每个端口声明 `RequiredCapabilities`；
- 调用前检查**调用方的能力集**（不是"端口存在就能调"）；
- 能力集 = 该实例被授予的句柄集合；**授予发生在绑定前**，运行期只做包含检查。

> 这与 `I-06`（能力声明）是同一条，只是从"模块级"下沉到"端口级 + 调用点"。

### 4.1 能力名回答"哪一类"，等级回答"多深"（2026-10 落地）

一个能力名（`models.control`）说得出这是哪类活，说不出"你被信到多深"。只靠能力名，就必须给每个调用者手抄一份名单；
而名单会漂，漂的方向总是更宽。所以判定改成两半：

- **接口**带 `MinLevel`（`agent` / `operator` / `full`），表在代码里，没有运行期入口能改；
- **调用者**带 `Level`，会话的可以热改（`sessions.setLevel`，下一轮生效），脚本的由它住的目录决定；
- 放行 = **能力名被授予 ∧ `caller.level ≥ 接口.MinLevel`**；未登记的接口算 `full`。

§1 的"能力必须在构造上不存在"因此有了可配置版本：名称决定**是哪一类**（构造上不给就别想），等级决定**多深**（给了也要够深）。
细节与目录映射见 [`07-域与权限分级.md` §9](07-域与权限分级.md)。

## 5. 脚本语言为什么必须是受限的（修正 `05` 的理由）

你在上一轮说"坚持脚本语言"，我把它当成了**好用性**的理由（agent 更喜欢正常代码）。真正的原因是**安全性**，而这一点决定了形态：

> **正常 C# 太全了——BCL 就是全部能力。**
> **受限语言的价值不是"有但被拦住"，而是"语言里根本没有那个原语"。**

所以：

- 脚本 = **能力容器**。它的 import 列表 **就是**它的能力清单；
- 没有注册 `file` import 的脚本，**语法上写不出读写文件**——这比任何扫描都硬；
- 于是 `05` §3.3 的 IL 扫描**降级为事后防线**（保留，但不作为主要机制）。

## 6. 选型（我的推荐）

| 方案 | 结构性安全 | agent 友好 | 成本 | 结论 |
|---|---|---|---|---|
| C# + Roslyn + IL 扫描 | ❌ 有缝 | ✅✅ | 低 | **不满足"绝对要求"**，不能作主闸门 |
| 自研 DSL / 解释器 | ✅ | ❌ | 极高 | 不划算（要写语言、工具链、文档） |
| **内置表达式（自研极小解释器）** | ✅ | ✅ 够用 | 低 | 只做纯计算：算术/比较/布尔/字符串/索引。**无编译、无 import** |
| **Lua（sandbox 模式）** | ✅（不注册就没有 IO） | ⚠️ 中 | 低 | 轻量可选；语言小、成熟 |
| **WASM（Wasmtime .NET）** | ✅✅（无 import 即无能力 + 线性内存隔离 + fuel 中断） | ⚠️ 需工具链 | 中 | **推荐：任意逻辑的唯一容器** |
| 进程隔离 + OS 权限降级 | ✅✅ | ✅ | 高 | 最外层兜底 |

**推荐组合**：

1. **L0 内置匹配器**（纯数据，零代码）
2. **L1 内置表达式**（极小 AST 解释器，无 import、无编译、确定、可缓存）——覆盖 90% 规则
3. **L2 WASM**（唯一"任意逻辑"容器：host function 白名单 = 能力清单；fuel 上限 = 可终止）
4. **L3 内建模块**（我们自己的代码，走 §2 的 host 句柄）

### 6.1 实际选型：Jint（JavaScript 解释器）

**结论：推荐 Jint 作为 L2 容器**，理由恰好就是 §5 那条判据——**它默认没有 CLR**。

| 判据 | Jint 表现 |
|---|---|
| **语言里没有的原语** | ✅ 默认不暴露 .NET；必须显式 `AllowClr()` 才给 BCL。**不调用 = 脚本里 `System.IO` 根本不存在**（不是"被扫描拒绝"，是标识符都解析不到） |
| **能力注入** | ✅ `engine.SetValue("cap", 窄对象)` —— 与我们 `IWorkspace` / `AllowlistHttp` 同构；没注入的就没有 |
| **可终止** | ✅ `TimeoutInterval` / `MaxStatements` 一类选项（**具体 API 名需实测**） |
| **内存上限** | ⚠️ 有 `LimitMemory` 一类选项（**需实测**）；但见下方"资源层不绝对" |
| **确定性** | ⚠️ **默认有 `Date` / `Math.random`**，必须在引擎启动时用飞书式 prelude 覆盖掉（`Math.random = () => 0.5`、`Date` 换成注入的确定性时钟）。**不覆盖就不纯** |
| **工具链** | ✅ 纯托管、无原生依赖、无编译步骤 —— 这一点对自举是决定性的（见下） |
| **性能** | ⚠️ 解释执行，比 V8/WASM 慢一个量级；规则场景够用，**必须池化引擎 + 缓存已解析脚本** |

### 6.2 已核对的事实（来源：Jint 官方 README，main 分支，2026-10 抓取）

| 事实 | 对我们的意义 |
|---|---|
| **"Jint is an in-process interpreter, not an operating-system security boundary."** | 官方自己划了线。**能力层可以靠它，进程/资源层不能**——正好印证 §6.1 的拆分 |
| **`Options().ForUntrustedCode(limits)` 硬化工档**：禁用 broad CLR / 反射 / 模块加载 / 字符串编译 / CLR 写投影 / CLR 数组实时视图 / 扩展方法 / 阻塞 `Atomics.wait`；并对解析、执行、内存、递归、正则、promise、结果施加**有限上限** | 这就是"构造上不存在"的现成实现——不是我们自己去堆选项，而是用它的 hardened profile |
| **`UntrustedCodeLimits`**：`TimeoutInterval` / `MaxStatements` / `MemoryLimit`，配合 `limits.BeginOperation(engine, ct)` | 对应我们的超时 / 体积 / 可终止三个闸 |
| **"Constraints are cooperative and cannot preempt arbitrary host callbacks."** ⚠️ | **极其重要**：如果我们的 host 能力是同步阻塞的，超时管不住。**所以所有能力必须是 async + 自带超时**（这条要写进能力接口规范） |
| **`Prepared<Script>` / `Prepared<Module>` 线程安全、可跨引擎共享**；JS 对象属于创建它的 realm | 引擎池 + 脚本按源码哈希缓存是官方推荐路径 |
| **支持 modules / promises / async functions / generators / Intl / Temporal**；test262 97.9%… 实为 99.9% | 脚本可以 `await`，端口签名不必为解释器降级 |
| **`ScriptPreparationOptions.CollectReferencedGlobals` + `Prepared.ReferencedGlobals`**：给出脚本**真正引用到的自由标识符** | 这是个意外收获：可以**按脚本实际引用**来投影能力（用不到的能力连注入都不做），最小授权可以做到"逐脚本"粒度 |
| **"Use a fresh engine across trust domains."**；全局快照**不是**隔离边界 | 不同信任域（内建 / 用户 / 群聊）必须分引擎，不能靠快照复用 |
| **官方建议**：hostile input 要加 **process-level boundary**（least-privileged disposable process 或容器） | "绝对安全"的最后一环不在 Jint 里，在进程外——这必须写进架构而不是留作愿望 |
| 版本：**5.x 在 main 未发布**，4.x 是维护线，3.x 仅安全修 | ⚠️ `ForUntrustedCode` 是否已进 4.16/4.17 稳定版**需实测**（`dotnet add package Jint` 后确认类型存在），否则手工组合 `LimitMemory`/`TimeoutInterval`/`MaxStatements` |

### 6.3 结论与剩余实测项

**结论：Jint 可作 L2 容器，但必须配三件外部措施**，否则达不到"绝对安全"：

1. **进程级边界**（官方明确要求）：脚本执行跑在低权限、可丢弃的子进程/容器里，主进程只通过 IPC 收发数据；
2. **能力全部 async + 自带超时**（因为 cooperative constraints 管不住同步 host 回调）；
3. **信任域分引擎**，且 `Prepared` 只缓存"纯脚本"，不跨信任域共享 realm。

剩余必须实测（本地跑一遍即可，不需要外部资料）：

1. 稳定版里 `ForUntrustedCode` / `UntrustedCodeLimits` 是否存在；不存在则手工组合三闸。
2. 不注入 CLR 时脚本里写 `System.IO.File` 的实际结果（应解析不到）。
3. `Date` / `Math.random` 能否在 prelude 里整体替换（确定性需要）。
4. 默认 `new Engine()` 与 `ForUntrustedCode` 档的差异清单（逐项对比，别凭印象）。
5. 子进程边界的实现选型（本地进程 + 受限账户 / Job Object / 容器）。

## 7. 接群聊之后的威胁模型（为什么必须绝对）

| 威胁 | 来源 | 对策 |
|---|---|---|
| **prompt injection** | 群友消息即不可信输入 | 输入带来源标记；**权限随来源降级**（见下） |
| 第三方插件 | 不是自己写的代码 | 默认能力集为空；安装即准入审计 |
| 脚本作者 | 可能是 agent 写的，也可能别人给的 | §5 的能力容器 |
| 出站滥用 | 被诱导往别处发消息 | 出站也是能力（§3），按频道授权 + 审计 |

**权限随来源降级**（重要）：会话的可用能力集 = **它的输入来源所获授权的交集**。来自群聊的会话，能力集通常为空 ⇒ 被注入也只能"说话"，不能读盘、不能发别的群。

## 8. 裁决：不做本地 shell；SSH 做成受限能力

（用户裁定：**不给本地 shell；只给封装好的 SSH，有限安全——起码本地安全。**）

### 8.1 本地命令执行：不存在

`shell` / `Process.Start` / 任何"在本机跑一段命令"的能力**一律不提供**，并写成台账作废项（`X-13`）。

理由不是"别人能用它干坏事"，而是：**本地 shell 会绕过 §2 的整个能力层。** 有它，`IWorkspace` 的前缀绑定、`IHttp` 的域名白名单、审计里的"对象"全部失去意义——一条 `cat` 就把一切抹平。

⚠️ 两个连带推论（很重要）：

1. **自举不能靠"编译"回头。** 没有 shell 就没有 `dotnet build`；**自举产物只能是解释执行的东西**（订阅表 + Jint 脚本），不可能是"C# 源码编译成模块"。真正需要新 C# 模块时，那是**开发者行为**（改版本、进发布），不是 agent 的自举行为。
   ⇒ 由此得到一条干净的界线：**自举能加"行为"，不能加"能力"。**
2. **编译服务（`ICompiler`）如果存在，它是能力不是 shell**：只接受受控输入、只产出程序集、不经命令行、不执行任意命令。见 `C1`。

### 8.2 SSH：能力，不是工具

| 维度 | 约束 |
|---|---|
| 目标 | **主机白名单**（逐个登记 host/port/user/凭据引用），不是"任意 host" |
| 凭据 | 只以引用形式存在（`secret://ssh-main`），脚本拿不到私钥原文 |
| 动作 | 明确区分**只读采集**与**写操作**两档能力；写操作单独授予、单独审计 |
| 审计 | 每条命令一条：主机 + 命令摘要（哈希 + 首行）+ 结果 + 触发来源 |
| 限额 | 并发、单命令超时、单次输出上限、每分钟命令数上限 |

⚠️ **诚实标注**：SSH 天生是"远端任意执行"，命令内容**管不住**。它的闸门重心在**"哪些主机 + 谁能用 + 全量留痕 + 可撤销"**，而不是"命令长什么样"。这就是你说的"有限安全"——安全边界是：**本地安全（§8.1）+ 远端可信主机（白名单）+ 可追溯（审计）**。

### 8.3 其余高危能力：默认不授予

`git`（写操作）、`dotnet build/test`、浏览器自动化、装包/卸载、系统服务控制、进程管理——**全部是能力，不是内建工具**，默认不授予，按需逐个登记。

## 9. 审计：一等机制，不可关

每次能力调用落一条记录：

```
谁（会话 id / 模块 id / 脚本实例 id）
什么能力（file.read / net.http / proc.exec …）
什么对象（相对路径 / 域名 / 命令摘要）
结果（成功 / 拒绝 / 越界 / 超限 / 超时）
耗时、触发的输入源（messageId / 会话 / 用户）
```

四条要求：

1. **写在能力边界**（host 层），不是写在调用者——调用者可以省略，边界不会；
2. **拒绝也记**：越界、限额、未授予，都是最有价值的审计事件；
3. **不可关**：不是开关（直接对应 `X-08`：不许有"关掉审计"的环境变量）；
4. **可反查**：按会话、按输入源、按对象三种检索——"这条消息导致谁读了什么"必须答得出。
