# 28 · 媒体与图片：会话能看、能发，但不收藏

> 状态：第一期实现完成（读图、入站、出站三条链都通了；真机部分未验，见 §8）。
>
> 本文回答一个问题：**怎么让会话看见一张图、发出去一张图，而这不会变成"聊天记录里塞满二进制"。**

---

## 0. 一句话

图片是**一份存储、一个引用、三个闸**：字节在 `media` 里只存一次（按内容命名，宿主写、模型只读），
记录里只有 `MediaRef`（scope + 路径 + 格式 + 尺寸），能不能给模型看由三道闸决定，看不到时留一句回执。

---

## 1. 三条入口，一条出口

图片进入一个请求只有三条路，三条路都通向同一处：`MediaImages.LoadAsync`。

| 入口 | 谁产生 | 记录里留下什么 | 模型看不到时 |
|---|---|---|---|
| `fs_read` 打开一个图片文件 | 模型自己 | 工具结果带 `MediaRef`，`history.jsonl` 的 `attachments` 里留引用 | 回执句（"本模型看不到图像…；要看就用 fs_read"） |
| 对话里有人发了一张图 | 适配器 → 通道 → 时间线 | `ChannelMessage.Media` / `StoredMessage.Media` / 历史条目的 `Media` | 消息正文里的一行 `【图片：…】` |
| 模型自己写出来的图（截图、脚本产物） | 模型写进 `workspace` | 它要发就用 `speak` 提到那个路径 | 同上 |

**出站唯一的出口是 `speak` 的 `blocks`**（§6）。`channels.send` 仍然只发文字：它是脚本说一句话的动词，
"按版式说一句话"是模型自己的工具。

**回执是这套设计里的第一原则**，不是兜底：模型看不见图时拿到的不是失败，是**一句说清楚"东西在这里、
我没看到、你要怎么才能看到"的话**。一个只被告诉"不行"的模型会重试；一个被告知路径的模型会去 `fs_read`。

---

## 2. 存储：一个 scope、按内容命名、只有宿主能写

```
<dataRoot>/media/<kind>/<hash 前两位>/<hash16>.<ext>
```

`kind` 是 `image` / `voice` / `video` / `file` / `card`，由**字节**决定（§5），不由文件名决定。

### 2.1 为什么是内容寻址，不是日期目录

产物按天分目录是因为它们**是派生物**：一次调用记录是已经回答过的请求的副本，删了不心疼。
媒体是**别人发来的东西**：转发一次、重发一次、两个人发同一张表情包，都是**同一条内容**。
按内容命名得到三个后果，都是想要的：

- **同一张图两次 = 一个文件**：第二次只要一次 stat，不写字节；
- **记录可以和学习对质**：`MediaRef.Hash` 就是文件名，"这个文件还是不是当初那个"有答案；
- **没有日期目录**，所以没有"按天清理"这条规则——清理媒体不是清理缓存，那是另一件要人决定的事。

### 2.2 `media` 是一个只读 scope

它和 `memory` / `workspace` / `scripts/draft` 并列，由宿主登记（`docs/24`）。区别只有一条：
**宿主以外没有人能写它。**

- 端口层（`LocalFileSystemAccess`）带 `readOnlyScopes`，`Save/Write/Append/Move/Delete` 一律 `Denied`
  并列出可写的 scope；
- 宿主的写入走三个 `AsHost` 方法（`SaveAsHostAsync` / `MoveAsHostAsync` / `DeleteAsHostAsync`）——
  是同一条写入路径，只是"谁在写"这件事在调用点就说清楚了；
- 于是"模型能整理媒体"这种事从结构上不可能：它既不能改一张图，也不能把它挪走，
  更不能把自己看过的那张换成另一张（那会让"记录里写着我看过什么"变成假的）。

默认配置里 `media` 在 `filesystem.local` 的 `scopes` 里——只读，所以放心给。

### 2.3 上限

| 位置 | 上限 | 为什么在这个位置 |
|---|---|---|
| 入库（`IMediaStore.MaxIngestBytes`） | 32 MiB | 入库要先把整段字节拿在手上才能算哈希；一个桥接塞过来的磁盘镜像必须在这里被拒 |
| 文件邮箱（非文本输入） | 32 MiB | 同上：读之前先看长度，不做"先读进内存再说不行" |
| 一条请求里的图（`maxImagesPerRequest` / `maxImageBytesPerRequest`） | 6 张 / 24 MiB | 再多这个请求就主要是图了，对话没了 |
| 单张进请求（`maxImageBytes`） | 8 MiB | 手机照片、截图、表情包；海报扫描件不是 |

## 3. 记录里只有引用，没有字节

`MediaRef` = `Scope` + `Path` + `Kind` + `MediaType` + `Bytes` + `Width/Height` + `Hash`。
它出现在这些地方（都是**指针**）：

- `SessionHistoryEntry.Attachments`（`history.jsonl`，工具结果带回来的图）；
- `StoredMessage.Media`（`aln.db` 的 `message.media` 列，JSON 数组）；
- `ChannelMessage.Media`、`SessionChannelMessage.Media`、`SessionTimelineContribution.Media`；
- `通道接受未完成标记`（`channel.pending` 队列行，重放时拿到同一批指针）；
- `OutboundMessage.Blocks` 里的 `ImageBlock.Picture`。

字节只在三个瞬间出现在内存里：**入库那一刻**、**组装成请求那一刻**（`ImageDataUrl`），
**发给适配器那一刻**（`base64://`）。

三处刻意**不**存字节：

| 位置 | 为什么不 |
|---|---|
| `history.jsonl` | 追加式、整份读进内存、有 64 MiB 上限；往里塞图等于让每次读历史都付费 |
| 模型调用工件 | 一次调用的请求是"已经答过的请求"的副本；图在里面是每步一次的复制。存进去之前图被替换成 `[图片 image/png 1920×1080 N 字节；内容未存进调用记录]` |
| 适配器的入站日志 | 日志的承诺是"崩溃后这条消息还能再投一次"。图进了队列行就是每收一张图多写一份字节；所以日志只记文字（图片那一半靠平台重发） |

---

## 4. 看图的三个闸

```
profile 声明了 Vision ？  ×  media.local 的策略  ×  这个请求的预算
```

### 4.1 第一个闸：模型能不能看

`ModelProfile.Capabilities` 里有 `Vision` 才算能看；**没写就是不能看**。"没声明"读成"不能"，
因为两个方向的代价不对称：多给一句回执，成本是一句话；给看不见的模型塞图，成本是这个请求被拒，
以及之后每一个请求都被拒（历史里还留着那张图）。

`Vision` 放在 profile 上而不是 provider 上：同一个 OpenAI 兼容端点既能服务看图的模型，也能服务
一收到图就 400 的模型，provider 描述符说不出这件事（`docs/14`）。

**怎么确认它真的开了**：启动时 `models:` 那行会列出能看图的 profile；一个都没有时它会明说
`no profile declares Vision — every picture will arrive as a receipt`。在加这一行之前，唯一的确认方法是发一张图，
然后从回执里猜——而这正是它藏了很久的原因：`module.json` 里写了 `capabilities` 也没用，宿主恢复 profile 时
逐字段重建，把这一项丢在了路上。

**但那一行只证明文件里写着 Vision，不证明运行时问得到。** 判定在 `SessionManager.ModelSeesImages`，它必须
**通过目录按名字找** model manager（`Models` 属性，找不到时回退到构造时交进来的那个）。曾经它读的是私有字段
`_models`：宿主是用 `catalog:` 装 SessionManager 的、没传 `models:`（构造函数明确允许），于是那个字段是 null，
判定永远是「看不见」——**回执把结论归咎于 profile 的文件，而文件是对的**。症状与「图根本没到」
（`16 §12.1.1`）一模一样，区别只在那句原因：`profile 没有声明 Vision` 说的是**判定走错了路**，不是文件缺东西。
`SessionImageTests.A_model_manager_reached_through_the_catalog_sees_pictures_too` 钉住这条路径。

同类错误的形状值得记住：**主构造函数 + 一堆可选参数 + 一条「或者自己去找」的回退**，三样凑齐时漏一个参数
编译器不会响，而回退路径只要漏了一处调用点，那一处就静默降级。`ChannelManager` 的 `media` 是同一个病。

**顺带一件容易看错的事**：`<dataRoot>/models/<category>/<instance>.json` 是**历史路径**，`FileModelInstanceStore`
只读 `modules/<instance>/module.json`（`docs/22 §2.2` 说明了为什么搬过去）。2026-11-10 已把 `models/`（连同
`adapters/`、`channels/`、`sessions/` 三个同类遗留目录）整体备份到 `legacy-backup-20261110-203607/` 后删除
（`docs/22 §2.4`）——留着它们唯一的作用就是让人照着改一遍配置却发现没有变化。

**声明错的代价**：给一个读不了图的模型写上 `Vision`，被拒的不是这张图，是这个会话之后的每一轮——历史里的
图会随每轮重发。所以拿不准时先发一次带 `image_url` 的请求验证，确认了再写。

### 4.2 第二个闸：`media.local` 模块

一个 `module.json`，六个参数，都是"不重启就生效"：

| 参数 | 默认 | 意思 |
|---|---|---|
| `autoView` | `first` | 收到图自动看多少：`off` 一张不看 / `first` 只看**每条消息**第一张 / `all` 都看 |
| `allowed` | png, jpeg, gif, webp | 可自动看的格式 |
| `maxImageBytes` | 8 MiB | 单张进请求的上限 |
| `maxImagesPerRequest` | 6 | 一次请求最多几张 |
| `maxImageBytesPerRequest` | 24 MiB | 一次请求图片总字节 |
| `maxAutoViewsPerTurn` | 3 | 一回合最多自动看几张 |

**`first` 数的是每条消息里的位置，不是整个 `<channel_messages>` 里的位置。** 这一点曾经写错：计数器跨整个块累加，
于是时间线里一旦出现过第二张图，之后每一张的 `index` 都大于零、一律被拒，回执还说「一次到达多张，只自动看
第一张」——**一段带过两张图的对话从此再也看不到图**，而那句原因指向的"这一批"根本不存在。修的是
`SessionManager.RenderChannelContextAsync` 里的那个下标（`SessionImageTests.Every_message_that_carried_a_picture_gets_its_turn_not_only_the_first_in_the_block`）。
`maxAutoViewsPerTurn` 仍然是**这一回合**的累计，那个语义没变。

所以想在上下文里留住更多图，调的是 `maxAutoViewsPerTurn`（和 `maxImagesPerRequest` 对齐），不是 `autoView`。
**默认的 6 / 3 在正常对话里太紧**：第 7 张图开始就只能拿到回执，而"这张图刚才还在"是最容易被当成 bug 的那种体验。
真机上三个数都放开了（`maxImagesPerRequest` 与 `maxAutoViewsPerTurn` = 100，`maxImageBytesPerRequest` = 128 MiB），
于是 `ImageBudget` 在正常对话里**根本不动作**。

**为什么这件事比"少几张图"重要——前缀缓存。** `ImageBudget` 是"从最新往回保留，超了把最旧的换成一句话"。它对
**一个请求**是合理的，对**一串请求**是灾难：每来一张新图，窗口里最旧的那张就从请求里消失，于是**前缀每轮都变**，
provider 的 prompt cache 一次也命中不了——每轮全价重算，又贵又慢，而且模型看到的上下文还在悄悄漂移。
`addRange` 之前那段前缀（system prompt、objective、重放的历史）本来可以逐字节稳定，被这一步毁掉。
所以"放开的收益"不是多几张图，是**同样的历史产生同样的前缀**。

**放开的代价，和墙在哪。** 现在唯一的墙是**模型窗口**。窗口是 1M（`ModelProfile.AssumedContextWindow`，见
`docs/14`），`turnCeiling` 是它的 85% = 891k；一张 1080×2412 的图按 `TokenEstimator` 是 `85 + 170×(3×5)` = 2635
tokens——**约 338 张才撞满**（1080×1080 那种约 1.1k，能到八百多张）。撞墙的表现是 provider 拒绝这个请求，而历史
没变，**下一轮还会拒绝**（`§4.1` 那条"声明错的代价"是同一件事）。换句话说：这是拿"可能撞窗口"换"缓存稳定"，
不是拿它换"没有上限"。

**窗口放大到 1M 的连带后果**：`replayBudget` 是窗口的 55% = 576k，所以**折叠和压缩都晚得多才发生**——一次请求
可能带着几十万 token 的历史出门，又慢又贵。这是"大窗口"的代价，不是 bug；觉得慢就调 `SessionManager.ReplayBudgetPercent`
（`docs/11`），那里才是"多大开始折叠"的旋钮。

`module.json` 里的数字不受参数动作的 `Maximum` 约束（`MediaModule.Parse` 只校验非负），所以文件里写多大就是多大；
`params.set` 才是被卡在 0..100 / 128 MiB 的那个入口。两条路都落在同一组 `MediaOptions` 上。

模块自己**没有工具**：看图是 `fs_read`，发图是 `speak`，存图是宿主的事。它只拥有那个答案——
"这张能不能给看、能多大、一回合几张"。这正是 `module.json` 该管的东西（`docs/18`）。

**没有模块时**（测试、或没配的宿主）用的是 `DefaultMediaPolicy`：同样的默认值，绝不是"没有上限"。
一个缺失的策略被读成"无预算"，失败形态是"这个会话从此每个请求都太大"。

### 4.3 第三个闸：这个请求的预算

`ImageBudget.Apply` 在**每一轮**跑，不是每回合一次（一轮里可能有工具又带回一张图）：

- 从**最新**往回保留：超过张数、超过总字节、超过单图、格式不在白名单的，换成一句话——
  "（一张图：… 这次请求没有带上它。要重新看，用 fs_read 打开那个文件。）"；
- 被丢掉的张数写一条信号（`media.budget`），于是"为什么模型说它没看到"在信号日志里查得到；
- 最新优先的理由：对话里刚发生的事最重要，最旧的那张图代价最高、用处最小。

### 4.4 时间线渲染：文本不变，图在说的那句话后面

`RenderChannelContextAsync` 把对话块拆成部件序列：头部文本 → 每条 `<message>` 的文本（末尾是该消息的
回执行）→ 这条消息带来的图片部件 → 尾部。**硬不变量**：没有任何图片的对话，文本部件拼起来与加图之前
**逐字节相同**（相同到"没有图片时 `Parts` 上是 null，走原来的字符串路径"）。
一条没图的对话产生的请求与从前一模一样，这是这次改动敢上线的原因。

### 4.5 重放：图跟着记录一起回来

**时间线里存的一直是指针**（`SessionHistoryEntry.Attachments` 是 `MediaRef`，不是字节），但从前的重放只重建文本，
于是「工具看过的图」过一轮就变成了一句关于某个文件的话——**模型记得自己看过，却再也看不到**。

现在补齐了，代价和边界都很具体：

| 谁 | 什么时候读 | 上限 |
|---|---|---|
| 频道消息的图 | **每一轮**重新渲染（`RenderChannelContextAsync`），因为它们来自 Channel 的历史而不是 Session 的 | `RecentChannelMessages` 条消息窗口 + 上面那三个闸 |
| 工具带回的图（`fs_read`） | 重放时由 `AttachReplayedPicturesAsync` 读一次 | 每请求 `maxImagesPerRequest` 张 / `maxImageBytesPerRequest` 字节，**从新往旧** |

两条边界，都不是"有时候图没了"的谜，而是写下来的规则：

1. **被折叠的旧记录不带图**。折叠的意思是"这条只留轮廓"，它出现在 `KeepRecentActivations` 之外——那里的图按
   定义已经旧了，重新读它是用最贵的东西换最小用处。留在时间线里，模型要看就再 `fs_read` 一次。
2. **看不到的图留话不留空**。`MediaRef` 读不出来（文件没了、超上限、这个模型没有 `Vision`）时，消息保持它原本
   的文本（`这是图片：media/…`）——**回执本来就在文本里**，所以不会出现"一条说这里有图却没有图的空消息"。

**为什么不是"每轮把所有历史图都读一遍"**：那是每轮 N 次文件 IO 加上 N 张图的 token，而 `ImageBudget` 的
三个上限正是为了不让一次请求变成相册。最新优先，是因为一轮回答的通常是"刚刚发生了什么"。

`SessionReplay` 仍然是同步的纯构造器：它只**记下**哪些消息带了图（`ReplayPlan.Pictures`），读文件是
`SessionManager.AttachReplayedPicturesAsync` 的事——构造请求归构造请求，碰文件归碰文件。

## 5. 只看文件头，从不解码

`MediaProbe.Detect(header)`：读开头几十个字节，回答"这是什么、多宽多高"。**这个进程里没有图片解码器。**
解码器是喂陌生人字节的解析器，而这里的图来自聊天平台。

认的：PNG（IHDR）、JPEG（走 marker 链找 SOFn——**不吃 EXIF 缩略图里的假 `FF C0`**）、GIF（LSD）、
WebP（VP8X/VP8/VP8L）；另认出 ogg/mp3/flac/wav/mp4/webm 作为 voice/video。

刻意不认的：

| 格式 | 为什么 |
|---|---|
| **SVG** | 它是 XML：在一个程序里是图，在另一个里是文档，多个 provider 直接拒收。存成 `file` 是诚实的描述 |
| BMP / TIFF / AVIF / HEIC | 每个都是一个本构建没有的解码器；少见的格式不值得这个面积 |

**字节说了算**：`MediaRef.MediaType` 只用来做展示，判断"能不能给模型看"永远看 `Kind`/`IsViewable`。
一个 `.txt` 里装着 PNG 头，会变成一张图；一个 `.png` 里装着文本，会变成一个 file。
上传方声明的类型是**声明**，不是结论。

## 6. 出站：块是排版，段是边界

一条消息可以是有版式的：文字、@、图片、表情，按顺序排在一起。

```json
{"blocks":[
  {"type":"text","text":"看这个 "},
  {"type":"at","who":"sender"},
  {"type":"face","id":"1"},
  {"type":"image","path":"media/image/ab/<hash>.png"}
]}
```

### 6.1 契约

`MessageBlock` = `TextBlock` / `MentionBlock` / `ImageBlock` / `FaceBlock`，有序表；
`OutboundMessage.Text` 保留成**纯文本降级视图**（`Flatten`）：转录、日志、只会发文字的平台读的都是它。
一条消息永远不是"只有块、没有文字"。

**块是消息内的排版，段是消息间的边界。** `mode: segments` 只切纯文本；`blocks` 恒定是一条消息。
两者同时给会被拒——给了两者，说明还没决定哪个是这条消息。

### 6.2 谁能发什么：不问，直接发

**没有能力声明。** 曾经有一个 `IChatAdapter.Capabilities`（`Text` / `Mentions` / `Images` / `Faces`），
由实现声明、由发送方在发送前查——它被删掉了，因为两次证伪指向同一件事：
**它让别人替适配器回答一个只有适配器知道的问题。**

- **它把每次发送变成两次调用**：先问"你能发吗"，再发。合并成一次就够。
- **它是必须与代码保持一致的第二个地方，而它可以错在很不诚实的方向**：文件适配器把整个
  `OutboundMessage`（含 `Blocks` 与 `MediaRef`）写进 outbox 的 JSON，图片引用**本来就是它交付得了的东西**，
  但它声明的是"文字"，于是被自己门前那道检查拒掉了——同一个邮箱，丢进去的图能收，要发的图不能发。

所以只有一个出口：`IOutboundAdapter.SendAsync`，版式就在 `OutboundMessage.Blocks` 上。
**能不能发是适配器的结论，不是发送方的猜测**：一张图变成段、变成 URL、变成 base64、变成邮箱里的一个引用，
还是变成别的什么，是对某一个协议的事实，属于唯一能说那个协议的那个类。频道、脚本、`speak` 都不掌握
任何适配器的模型，也不应该掌握——模型正常情况下不需要知道对面是什么适配器，除非出了事。

发不出去的部分，由适配器在这一次调用里回答，只有两种形态：

| 形态 | 什么时候 | 模型读到什么 |
|---|---|---|
| **拒绝** | 发出去就是撒谎：那一块到不了，而消息的意义就在它身上 | 指名哪一块、为什么 |
| **降级并说出来** | 那一块没过去，但消息剩下的部分还有意义 | 消息到了；`SendResult.Detail` 说清哪一块以文字形态过去了 |

第二种是 §6.5 那条"绝不静默少一块"在代码里的落点：QQ 适配器把降级的图片 locator 列进 `SendResult.Detail`，
它随 `speak` 的返回一起回到模型手上。整条消息因为一张图太大而丢掉，比到了一句话更糟；
而**安静地**到，比前两者都糟。

拒绝的措辞里不写"换一个能发的频道"：`speak` 的回复必须走同一个 binding，模型手上没有第二个频道可换，
一句做不到的建议只会让它重试。

### 6.3 @ 只认两种

- `"sender"` → 由 core 用"这条消息的发送者 id"解析。模型从没打过这个 id，也不该打。
- 纯数字 → 平台号。
- `all` / `everyone` / `全体成员` → **拒绝**。能用一个词叫醒整个群的模型，一定会试一次，
  代价是每个人的手机。

### 6.4 表情是方言，原样透传

`face` 带着平台自己的编号（QQ 的 `1` 是微笑），不做跨平台映射：造一套可移植的表情词汇表是一个自己的项目，
而"拒绝表情"等于拒绝群里人们真的在用的东西。`AsText` 记成 `[表情]`。

### 6.5 图片出站是 `base64://`

QQ 适配器把图片变成 bridge 能接受的东西，**默认走 URL**、base64 是备用（`docs/16 §12.4`）：
宿主 **默认开**一个只读媒体门（`--media-endpoint off` 关掉/换地址），适配器把引用换成那个门上的地址，
由桥接自己来取；拿不到门或文件时，那一块以它自己的文字形态发出去，消息照常到。
适配器设置 `imageDelivery` 也在这里：`auto`（默认）/ `url`（只发 URL）/ `base64`（从不发 URL）。
**发送上限 8 MiB**（≈11 MiB base64）不是我们的口味——桥接要在自己的内存里握着整段；
NapCat 在 ~40 MB base64 上被看到退出，5 MB+ 已有压力（`docs/16 §12.3`）。
不用文件路径：桥接可能在另一台机器上，即使在同机它的文件系统也不归我们写。
读不到（没有端口、文件没了、太大）→ 那一块以它自己的文字形态发出去，消息照常到。
**绝不静默少一块**：模型以为它发了图而其实没发，比被拒绝更糟。所以降级必须留痕——
QQ 适配器把降级的图片 locator 列进 `SendResult.Detail`（§6.2），它随 `speak` 的返回回到模型手上。

### 6.6 文件：一处改动不够，是一条链

文件不是"大一点的图片"，差别有三处，每一处都改变了设计：

| | 图片 | 文件 |
|---|---|---|
| 是不是消息段 | 是：`image` 段，和文字同一条消息 | **不是**：`upload_group_file` 是一次独立调用，群文件不进聊天流 |
| 上限由谁决定 | 桥接的内存（8 MiB） | 磁盘、耐心、平台自己的配额 |
| base64 能不能兜底 | 能，几 MB 还行 | **不能**：33% 膨胀 + 整份进对方内存，几十 MB 就是事故 |

第一处带来一个诚实的、让人不快的后果：一条消息里"文字—文件—文字"的顺序**在 QQ 上兑现不了**。
`FileBlock` 仍然进版式，因为发送方不该知道哪个平台能不能把文件放进气泡（`I-33`）；适配器把它拆成
"先发文字、再逐个上传"，而这个顺序让位**写在 `SendResult.Detail` 里** —— 模型读到的是"文件在消息之后单独上传"，
而不是一个它以为发成了一条的谎。

#### 6.6.1 四道闸，抬一处没用

| 闸 | 值 | 为什么是这个数 |
|---|---|---|
| `IMediaStore.MaxIngestBytes` | 32 MiB | 入站要先把一样东西整个拿在手里才能命名 |
| `IBinaryFileAccess.MaxTransferBytes` | 64 MiB | 回答的是"一次**搬运**多大"：ssh 拉一个包、工具挪一个 tar |
| `OpenReadStreamAsync(scope, path, ceiling)` | 调用方给 | **新的一条路**：同一套 scope 规则，上限由调用方说 —— 一串从磁盘到 socket 的字节不是搬运 |
| `MediaEndpoint` | 图片 8 MiB / 文件 `--media-max-file`（默认 2 GiB） | 按 kind 分开：图片要过桥接内存和模型上下文，文件不用 |

**抬出口不会让大文件出现。** 文件得先能进（入站、ssh 下载、模型自己写进 `workspace`）才能发；这几处的数字
连成一条链，任何一环卡着，500 MB 就永远到不了出口。同一个道理也改了 `DescribeAsync`：它现在不带上限地打开，
因为**描述不是读取** —— 它只看头几十个字节，一个太大而不能搬的文件照样描述得了。

#### 6.6.2 四条传输路

适配器设置 `fileDelivery`：`auto`（默认）/ `url` / `path` / `base64` / `two-step`。

| 路 | `file` 参数里是什么 | 谁付代价 | 什么时候用 |
|---|---|---|---|
| `url` | 宿主媒体门上的地址 | 谁都不付 | 默认首选：本进程零拷贝，多大都行 |
| `path` | 桥接那台机器上的路径（`pathMap` **反向**映射） | 零 | 两台机器共享卷时最省 |
| `two-step` | 先 `download_file`（桥接自己来取），再拿回答的本地路径 upload | 两次调用 | 实现只认路径时（go-cqhttp 的文档就是这么写的） |
| `base64` | `base64://…` | 两边各一份内存 | 只在 ≤8 MiB 时；没有门又没有共享卷的兜底 |

**没有"失败了再试下一条"**：一次失败的 upload 可能已经到了一半，所以路在调用前就定好，走了哪条写进日志
（`outbound file` 的 `transport` 字段）。真机数字见 §8。

每次投递留一条**结构化日志**（文件、字节、哪条路），而不是一条审计行：审计行需要一个事件 id 来归属，
而适配器手上没有；现编一个会是第二套审计约定。这是明确的空白，不是遗漏。

#### 6.6.3 为什么没有"能发什么"的白名单

发文件意味着**模型能把磁盘上的东西送到外面**。这里刻意没有新增一道出口名单，理由和 `I-33` 是同一条：
能发什么由**已经在管字节的那个东西**回答 —— `IBinaryFileAccess.BinaryScopes`。今天它是 `workspace` + `media`，
所以 `memory` 和 `scripts/draft` 发不出去，不是因为为这个功能加了规矩，而是因为它们本来就不接收字节。
`MediaEndpoint` 也从"只服务两个 scope"改成问同一份列表：**一条规矩，问一次**。

代价写在这里，免得以后读的人以为是不小心：文本出口有 `MaxSpeakChars` 挡着，文件块没有。所以一个跑偏的模型
可以一次把整个 `workspace` 发出去，而用文字得发很多条。这是明确接受的取舍 —— "先试探再发送"那类提前拦截的
代价，比它挡住的损失更确定（`I-33`）。

### 6.7 收文件：两个动词，一个不碰落点的适配器

发出去是"块进版式、段是边界"（§6）。**取回来是另一个形状，因为它回答的不是同一个问题**：不是"替我说点什么"，
而是"平台手上有什么、把其中一个的字节给我"。所以契约是一个**可选**接口上的两个动词（`IFileCatalogAdapter`）：

| 动词 | 回答 |
|---|---|
| `ListAsync(conversation, limit)` | `PlatformFileListing`：`Handle` / `Name` / `Bytes` / `At` / `From`，加**两份说明**——没进去看的文件夹名，和一句 `Note` |
| `FetchAsync(conversation, handle, maxBytes)` | `PlatformFileContent`：一个**打开的流** + 名字 + 平台上声明的类型 |

**这不是 `I-33` 那种能力表。** 那一个是替别人声称（发送方问适配器"你能吗"，于是多一份要与代码同步的副本）；
这一个描述的是适配器**在同一次调用里自己做的事**。没实现这个接口 = 没有这个功能，调用方得到一句"这个平台不提供
文件目录"，中间没有任何一份声明可以漂。

**四种回答，其中一种不是成功：**

- **不能列 → 失败，带原因。** 私聊没有文件区（QQ 上群才有），这和"什么都没有"是两句话。
- **能列但列不全 → 成功，带 `Note`。** 群文件根目录里常有文件夹，本构建不进去看；说出这句话，比回一个看起来
  完整的数组更接近事实。
- **能取 → 流。** 不缓冲：几十 MB 的文件从平台到一个 scope，不该先变成一个数组。
- **超过 `maxBytes` → 拒绝，不截断。** 与 `ssh_get` 同一条：看起来完整而其实短了的文件，是"备份"这个词出事的方式。

**handle 是 `f:` 开头的，适配器自己写、工具只读。** 为什么要前缀：`files_get` 有三形态（列 / 搜 / 取），靠"试一种、
失败就换一种"来分发，会把"平台拒绝了"变成"那大概是搜"（§6.8）。前缀让形态可读，失败就还是失败。

**字节怎么来，QQ 上是四条路**（`docs/16 §12.6`）：`base64://`、data url、http(s)、桥接盘上的路径。最后一条只有在
**共享卷 + `pathMap`** 时才读得到，而且是从宿主自己的字节端口、在某个 scope 里读——不是"适配器读任意路径"。

**落点不是适配器的决定。** 契约里没有 scope、没有路径、也没有"放哪"的意见：这一层只负责"把字节交出去"。
落在哪儿由模型说、由宿主的字节端口执行（§6.8）。

### 6.8 `files_get`：三形态，一个必填的落点

模型这边只有一个工具 `files_get`（模块 `files.control`），三个形态由**参数长什么样**决定，不由"哪一次失败了"决定：

| `target` | 做什么 |
|---|---|
| 不写 | 列：平台上有什么，最近的在先 |
| 不是 handle | 按名字搜（在整张架子上搜，不是在前二十条里） |
| 是 handle（`f:` 开头） | 取：把这个文件拿到盘上 |

**为什么不能"试一种、失败换一种"**：那样"平台拒绝交付这个文件"会变成"那它大概是关键词"，于是要字节的人拿到一份
列表，而且没有任何东西告诉他什么都没到。所以形态判定只发生一次（`I-37`）。

**取的时候 `scope` 和 `path` 都必须由模型给，没有默认值。** 三个理由：

- 落在哪是模型的用途决定的——解压、diff、喂脚本、再传出去，各自要放的地方不一样；
- 一个"它自己找的地方"就是下一轮要满地找的那个地方，而写下来的路径只有一份；
- 报错一次比猜错一次便宜：错误里直接列出这个宿主收字节的 scope（问 `BinaryScopes`，不硬编码），下一轮就对了。

**能不能落，由字节端口说了算。** `scope` 允不允许字节、是不是只读（`media` 就是只读）、`path` 在不在里面——全部
是 `IBinaryFileAccess.SaveAsync` 的判断。这个工具**不预判、不维护名单**：那会是与端口并行、要一起维护的第二份答案。

**回执说真话。** 大小取自真正到的字节，不是平台上声明的大小（`PlatformFile.Bytes` 是个声明）；名字也是适配器
交出来的那个。一个说"已取回 2 KB"而实际只有 20 字节的回答，比报错更坏。

**大文件不进这一轮。** 平台**声明**超过 8 MiB 的取法会写一行账本、在后台取、结束由账本叫醒会话（§9.4）：
一轮等一分钟，读的人只会以为卡住了。判断靠"取之前先问一句它多大"（多一次列表调用，没有下载），**问不到就不猜**——
同步取，并受 `MaxTransferBytes` 限制。落点在派活那一刻就定死，后台任务不自己挑路径；没有账本时照旧同步取
（账本才是"之后告诉你"的那一半）。

### 6.9 入站：一个指针，不是一次下载

有人发来一个文件时，**我们不发下载**。这一条是刻意的，和图片正好相反：图片会随消息带着字节进来（因为要能看它），
文件不会——它可能几百兆，而且"取它"这个决定本身带着一个落点，而落点只有想要它的人知道（§6.8）。

于是入站只做一件事：**把指针交给会话**。两种到达方式，同一种文本：

| 怎么来的 | 平台事件 | 有没有 message_id |
|---|---|---|
| 聊天里发的一个文件 | `message` 里的 `file` 段 | 有 |
| 上传到群文件区 | `group_upload` **notice** | **没有**，聊天里也什么都没有 |

两条都变成同一句话，附在那条消息的文本里：

`[文件：周报.zip（2.3 MB），files_get 取它：f:0|abc123]`

三个要点：

- **handle 就在文本里**，因为文本是唯一会被持久化、被下一次请求重放的东西。放进一个新的结构化字段要动消息表的
  schema，而这一段的价值恰恰是"模型读得懂的一句话"。
- **`group_upload` 是 notice 不是 message**（`docs/16 §12.6`）：桥接不会把它放进聊天流，`message_id` 也没有。
  所以那条 envelope 的 `PlatformMessageId` 是**空**的——这也是唯一一处允许它空的地方。
- **桥接只给了名字、没给 id 时，会明说取不到**，而不是编一个 handle。一个编出来的 handle 只会换来一次注定失败的
  调用（`I-37`）。

**原先计划的那条"入站把文件入库（流式）+ 入站盘配额"因此不需要了**，而且不该做：文件不进 `media`，就没有第二份
副本、没有第二次计算哈希、也没有"盘上悄悄多了几百兆"这件事。要配额的地方是 `workspace` 那一侧，而那是人的决定
（`docs/24`），不是入站路径的决定。

## 7. 明确不做的事

| 不做 | 为什么 |
|---|---|
| 转码 / 压缩 / 缩放 | 那是解码器，本构建没有；而且"我们把它改小了"会让记录里那张图和发出去的那张不是同一个 |
| 生成图片 | 需要一条本构建没有的模型能力（图像生成），不是媒体模块该顺手做的事 |
| OCR / 描述 | 那是模型的事，它已经在请求里（或拿到回执）。塞一个本地识别器进来是第二个做不到位的实现 |
| SVG / BMP / TIFF / AVIF / HEIC | §5 |
| 跨平台表情映射 | §6.4 |
| 语音识别 / 视频抽帧 | 存、引用、登记了，但没有任何东西去听或去看。`docs/` 里写"存了"就只说"存了" |
| 按天清理媒体 | 媒体是记录不是缓存（§2.1）。要清理得由人决定删什么 |
| 模型写 `media` | §2.2：只读，四个写工具全部 `Denied` |
| 图进模型调用工件 | §3：替换成一行说明 |
| 让"看不见的模型"也能看图 | 没有这个模式。做不到就是回执，不做假装 |
| 文件的 Stream API（`upload_file_stream`） | 要 v4.8.115+，而且是**多帧响应**（`stream:"stream-action"`，chunk / complete / error 三段），我们的 `CallAsync` 按 `echo` 匹配一条响应。真机上 80 MB 走 URL 是 21 秒（§8），先用这条 |
| 断点续传 | 没做过，也不知道桥接半路放弃时会不会留下半个文件 |
| 从群文件列表回捞一个文件 | §6.7 已经做了（`get_group_root_files` + `get_file`），但**只在离线上验过**：假桥接的往返有了，`616565017` 那个群上还没跑过。另外只列根目录，不进文件夹 |
| 每次文件投递一条审计行 | §6.6.2 末：适配器没有事件 id 可归属，编一个就是第二套审计约定 |

文件邮箱把引用原样交付进 outbox 的 JSON、OneBot 段顺序与 `base64://`（真 Kestrel 上的假桥接）。

   "模型真的看懂了那张图"没有。

5. **`fileDelivery=path` 只在单元测试里走过**：真机上宿主与 NapCat 没有共享卷，`pathMap` 反向映射没有对着
   真桥接验证过。
6. **收文件这条路在当前部署上取不到字节**（这一条是实测出来的，不是推测）：NapCat 的 `get_file` 回的是**它自己
   容器里的路径**，而这台宿主在另一台机器上，所以 `pathMap` 帮不上（那是"共享卷"才成立的前提）。三条出路，都
   需要人或部署来决定：①宿主与桥接同机/共享卷（然后 `pathMap` 就有意义了）；②桥接那边能回答 base64（本构建
   已经支持，NapCat 现在不回）；③让桥接把文件放到一个宿主能取到的 HTTP 位置上——那是桥接要加的事。
   **列、搜、入站回执这三半是可用的**，只有"取字节"这一半在这个部署上不可用，而且失败信息说清了为什么。
6b. **`group_upload` 的活推送没有观测到**：形状与 NapCat 的类型定义一致，但机器人自己上传不会触发（25 秒内没有），

7. **大文件半路失败的形态未知**：桥接传到一半放弃会留下什么，没有测过。

## 9. 后台任务：写下它，而不是驱动它

有一类事情不会在一轮里做完：桥接替我们下一个几百兆的文件、SSH 上跑一条 build。它们在**某个时刻**开始，在
**另一个时刻**结束，而中间模型要么在等，要么已经睡着了。`docs/26` 管的是"什么时候该起来做事"，这一节管的是
"我正在做的事现在怎么样了"。

### 9.1 一张表，一份状态

`IJobRegistry`（`FileJobRegistry` 落在状态库里，一个会话一份 JSON 文档）：

| 字段 | 为什么它在 |
|---|---|
| `Kind` / `Label` | 重启之后要靠这两个说清"那是什么"——`file.fetch` / 「群文件 周报.zip」。名不存，事后就说不出来 |
| `State` | `Running` / `Done` / `Failed` / `Killed` / **`Interrupted`** |
| `Done` / `Total` / `Unit` | 进度。"总数未知"与"总数是零"不是一件事，所以 `Total` 可空 |
| `Result` / `Error` | 结束时模型读到的那一句 |
| `Announced` | 这件事**是否已经告诉过模型**。有它才能"只说一次" |

**`Interrupted` 是这里唯一一个只因为"进程会死"而存在的状态。** 重启时它还写着 `Running` 的任务，既不是失败
（没有人做决定）也不是被停掉（没有人要求）——说成 `Failed` 是一个模型会试图去修的谎，说成 `Running` 更糟：
它会一直等一件不存在的事。

### 9.2 写的是那一行，不是那件活

**重启之后 job 不能续跑，这一点不打算假装。** socket 关了、文件句柄没了、读它的那个线程属于一个不存在的进程。
所以持久化的是**行**：它是什么、到哪了、怎么结束的。下一次起来，`Running` 的行变成 `Interrupted`，留着，直到
这个会话被告知过为止。

告知发生在一个具体位置：**下一次这一轮开始的时候**，`SessionManager` 把还没说过的那些取走（取走即标记），
拼成一段系统附注。被人说话的那轮，它是真消息**之前**的一条独立条目（不去改人家的话）；被唤醒的那轮，它并进
唤醒理由里。说过就删掉——一个旧任务不是新闻，留着只会让文档随对话历史一起长，而不是随"还在等什么"长。

**"取走"不等于"等着"**：除了开头的对账，行还有一处是被推上去的——job 结束的那一刻就写，而且写它的那一层顺手
把这个会话叫起来（§9.4）。所以拉与推各有分工：**结束是推的，进度是拉的**。进度没人问就一直是旧值，那是对的，
因为"做到哪了"只在一件事正在发生时才有意义；而"它已经结束了"过一会儿就只剩历史价值。

### 9.3 它不是调度器，也不是能力表

- **不是调度器**：它不决定何时开始、不重试、不排队。开始是别人叫它开始的；它只记录。真正的"什么时候"在
  `docs/26` 的定时里，两者不重叠。
- **不是被删掉的那种能力表（I-33）**：那一个是**替别人声称**——发送方问适配器"你能吗"，于是一份必须与代码
  保持同步的副本。这一张表**就是**状态本身，没有第二个地方要与它一致。判据写在这里：**一个有第二真相来源的
  抽象不要做；本身就是那个来源的可以做。**
- **不是控制器**：它记着 SSH 的后台命令，但**它停不掉那条命令**——停是在另一台机器上取消一个进程，那属于
  起它的那个工具（`ssh_job kill`）。所以给模型的入口只有两个动词（§9.5）。同一条判据的第二次应用：**替别人
  回答"我能做"和替别人做"我做了"是同一种错**。
- **不持久化的代价是写下来的**：重启后行还在、活没了，模型得到的是"被打断了，要接就重开一个"。

### 9.4 谁把人叫醒：结束是推的，其余是拉的

**原本的想法是"拨表"**：把发起这个 job 的会话的 `WaitUntil` 拨到当下，让现有的到期扫描去叫它，一条唤醒口都不新开。
**没有这么做**，因为它错在三处，而且第三处是最要紧的一处：

1. **扫描是粗的**。`SessionDeadlineHandler.Interval` 是 30 秒。到期扫描为一个以分钟和小时计的承诺设计，这条
   路配它是对的；"你的 build 完了"只有十几秒的时效。
2. **拨表会改掉那句话的形状**。`wait {release:true}` 的会话被拨到当下，扫描不会叫醒它，而是**归档**它——一个
   后台任务结束，因此把等它的会话送进档案。若为了绕开这一点顺手把 `WaitRelease` 清掉，那就是**替会话改它自己
   说过的话**。
3. **唤醒理由会变成假话**。拨表之后扫描走的是 `DeadlineDue`，那一轮会被告知"你自己声明的等待到期了"。不是。

所以走正路：`ISessionWaker` → `ActivateAsync(JobFinished)`。这个接口只有**一个方法，而且不带任何"什么结束了"
的描述**——不是偷懒，是怕漂：调用方若能带自己的说法，就会和账本各说一套，模型读到的是错的那套。它只说"这个会话
有新闻"，新闻本身由同一轮从表里取（`TakeUnannouncedAsync`）。

**谁叫：写账本的那一层。** `CompleteAsync` / `FailAsync` **第一次**把一行写成结束的时候叫；第二次（轮询补写、
观察者和轮询撞上）那一行已经不 `Running`，`MutateAsync` 不动它，于是也不叫。`KillAsync` 不叫：杀是某人在某一轮
里做的决定，叫醒他就是打断那一轮去复述他自己的请求。这条判断只有账本做得到——它正好是唯一知道"这次结束是新的"
的地方；把它推给每个生产者，就是让每个生产者自己去读一遍再猜。

**忙碌时跳过，不排队。** 这一行仍然是"没说过的"，所以下一次开口会读到：**是迟到，不是丢失**。唤醒本身失败了也
一样——行是事实，通知是一次尝试，因为通知没落地就把行回滚掉，等于因为没人听就把发生的事抹掉。

**重启不叫人。** 起来的那一刻没有东西"刚结束"，只有"不知道"：把每个还有行的会话都叫醒，是个开局就打断所有人、
还说不清打断了什么的宿主。那一刻的事实在下一次开口时说（§9.2）。

**装配顺序上有一个环**：会话是拿着账本构造的，所以账本不能拿着会话构造。`FileJobRegistry.Waker` 因此是一个可写
属性，宿主在构造完会话的下一行接上（`Program.cs`）；没接的时候账本照样记，只是不叫。

**SSH 侧唯一的"推"是 `ISshJob.WaitForExitAsync`。** `ssh_run {wait:false}` 起一个不等它的观察任务，结束即写行。
理由还是那句：行只在有人看的时候收敛，这对记录够了，对会话不够——"完了"得在它还是新闻的时候说出口。

**顺序：先写行，再停进程。** `ssh_job kill`、换设备、空闲回收都是这样。反过来的话，观察者会把一次故意的停止
记成"它做完了"。

**现状**：表、持久化、重启对账、只说一次、50 行上限、完成与失败各唤醒一次、杀不唤醒、唤醒失败不撤销事实、
重启不叫——`JobRegistryTests` 13 条。**SSH 已经接上**：`ssh_run {wait:false}` 写一行并起一个观察者，结束即写行、
由账本叫醒会话；`ssh_job list` / `output` 仍会把行补上（写失败时靠它收敛）；`kill` 记成 `Killed` 且不通知
（`docs/27 §6`）。**这一路只在离线验过**：真实的 SSH 后台命令要一台真设备，本轮没有跑真机，所以"观察者在一条
跑了十分钟的命令上确实在结束那一刻醒来"这句话，是一条推论，不是一次观测。**接上的第二个生产者**：文件下载
（`files_get`，kind `file.fetch`）——平台声明超过 8 MiB 的取法不进这一轮，而是写一行、在后台取、结束时由账本叫醒
会话（§6.8）。它只用账本已有的东西，没有为它新开任何机制，这也正是这一节想证明的：**加一个生产者不需要改唤醒**。
**仍然没接的**：真机——两个生产者的"结束即唤醒"都只有离线观测。

### 9.5 给模型的口：两条只读的

`jobs`（模块 `jobs.control`，`docs/28` 这一节就是它的说明书）两个动词：

| 动词 | 回答什么 |
|---|---|
| `list` | 这个会话的所有行，最早的在最前：状态、是什么、到哪了、怎么结束的 |
| `get` | 一行，加上"为什么没成"和一句"还在跑的任务活不过重启" |

**没有第三个动词。** 账本记不住怎么停一条命令，因为那不是它的事（§9.3）；而一个只会把行写成 `Killed`、
让命令继续在别人机器上跑的 `kill`，比没有这个动词糟得多。模型要停东西，用它自己的工具——
`ssh_job{"action":"kill"}`。这也是 `I-33` 那次删除的同一条道理，只是这次真的没写出来。

**五种结局分开说**，不折叠成"没做完"：`跑着` / `完成` / `失败` / `被停了` / `被打断`。前四种是四种不同的
下一步（等、用结果、修、重开），第五种是"进程没了，做完没有没人知道"——说成失败，模型会去修一个不存在的错。
