# 脚本编排与工程实施蓝图

> 状态：工程设计草案，面向 .NET 10。本文根据当前方向重新规划 Adapter + Graph 闭环，目标是让后续实现可以直接拆项目、定契约、逐片验收。
>
> 本文与早期图设计冲突时，以用户最近明确的方向为准：**Jint 脚本作为主要编排形式；全局唯一管理器持有模块子实例并提供查询；脚本按目标抽象类型及挂载模式绑定到具体实例。**
>
> 标记规则：**已定**表示用户明确过；**建议**表示本文推荐、尚待用户确认；**待定**表示开始实现相关部分前要裁定。

---

## 0. 当前方向

### 已定

- 目标框架为 **.NET 10**。
- **Jint** 是脚本宿主选型；脚本编排是 Graph 的主要使用形式。
- 全局唯一的各类 Manager 持有各自模块实例，并提供实例查询方法。
- Adapter 抽象不能实例化；具体子类继承父类的可挂载类型。因此挂载到 Adapter 抽象的脚本适用于 FileAdapter。
- 脚本可以表达条件、顺序和循环，并使用 ALN 提供的程序内接口；其能力由宿主接口和授权决定。
- `default` 挂载在启动时作用于所有兼容实例；`manual` 由调用方显式选择脚本和目标实例。
- **ClockSource 是独立时钟脉冲模块**；有周期需求的模块实例在 Start 时注册目标与间隔，在 Stop 时注销；ClockSource 只发定向 RoutedEvent，不直接调用订阅者的方法。
- 可变数据根目录与程序/源码目录分开。

### 本文建议

- 保留 **Graph / 图** 作为模块和管理器的暂用名称。其内核实现从静态订阅表转为脚本加载、挂载、事件匹配和受控接口调用。等职责稳定后再评估改名。
- 一个脚本包由静态 manifest 描述目标类型、挂载模式、事件入口、信任域和所需能力；JS 文件描述处理逻辑。
- 脚本通过 `ctx` 等宿主注入的窄 facade 调用模块能力。每次调用均回到统一 Runtime/Dispatcher 解析端口、检查授权、传递取消，并写执行记录；脚本不获得任意 Manager 实例或任意 CLR 反射能力。
- 管理器拥有子实例生命周期；GraphManager 只持有脚本定义和挂载登记（登记引用地址，不拥有 Adapter 实例）。
- 首个切片使用单一逻辑派发队列，入站、脚本触发和状态提交串行；网络 IO 异步。

## 运行时装配与插件边界（建议，方向已确认）

### 核心、固定发布扩展、可插拔插件

ALN 不以“每个项目都必须独立成 DLL”为目标。边界由替换需求、依赖稳定性和生命周期所有权决定：

| 层 | 内容 | 装载与热重载 |
|---|---|---|
| 核心框架 | 插件发现与校验、注册表、依赖解析、生命周期协调、事件路由、基础诊断 | 核心实现随 Host 发布；不运行时替换 |
| 核心内部实现 | 过于基础、必须与框架不变量保持原子一致的功能 | 可直接编入核心；不为形式独立拆 DLL |
| 固定发布扩展 | 默认 Manager、Clock、Graph、脚本执行器等可独立实现但与当前发行版绑定的能力 | 可使用独立 DLL，由发布清单固定版本；启动装载，不支持运行时插拔或替换 |
| 可插拔插件 | 需要由部署者增加、替换或移除的业务模块与类型实现 | 独立插件包，运行时发现；通过统一生命周期与能力契约接入 |

核心不引用具体插件实现。Host 只负责组装核心和读取发布/插件清单，不直接 `new FileAdapter` 等具体类型。固定发布扩展可依赖稳定核心契约；插件只能依赖公开契约及其声明的扩展服务。契约程序集在单个进程内共享，不能由插件私自加载第二份副本。

Manager 是否作为扩展 DLL 由其替换需求决定。即便 Manager 实现放在固定发布扩展中，实例注册、依赖闭包计算、卸载屏障与事件入口的最终协调权仍属于核心；普通插件提供类型实现和工厂，不自行绕开注册表创建跨插件引用。

### 插件包与依赖

插件包清单至少声明稳定 ID、版本、ALN 契约版本范围、提供的模块类型、依赖的插件/服务、能力请求、装载来源和生命周期策略。核心先解析整个候选依赖闭包，再激活它；缺依赖、重复提供者、版本不兼容或能力拒绝时，不进入运行态。依赖图用于确定替换/卸载的影响集合，避免只卸载一个 DLL 却留下活对象引用。

发布扩展与可插拔插件使用同一份模块描述和初始化协议，但由不同来源策略约束：发布清单中的扩展可以声明固定且不可热重载；插件目录中的组件必须显式声明是否可热卸载。核心内部组件不需要伪装成插件。

### 受控卸载屏障

正常卸载/替换按插件及其依赖影响集合执行：

1. 核心将目标标记为 `Draining`，拒绝该集合的新实例、新挂载和新调用。
2. 核心计算受影响的 Manager、实例、Graph 挂载、Clock 订阅和事件处理器，向生命周期参与者发送带截止时间的准备卸载请求。
3. 各参与者停止产生新工作，结束或显式报告在途工作，撤销外部订阅并返回就绪/失败状态。只在所有必需参与者就绪后继续。
4. 核心撤销路由和注册，销毁拥有的实例，调用异步释放，随后才卸载可卸载程序集。
5. 替换插件先在隔离的候选加载上下文完成清单校验、依赖解析和初始化/健康检查，再切换注册与路由；失败时旧版本保持可用。

准备失败或超时的默认行为是取消正常卸载，并恢复已响应的参与者；若准备阶段有参与者超时仍未结束，包会标记为 `UnloadFailed`，避免把状态误报成已恢复。显式强制卸载会在有界等待后继续移除包注册、类型和服务，尝试从 AdapterFactoryRegistry 与 Graph 路由中切断目标，并把未就绪或清理失败列入报告。强制操作表示框架不再路由到该包，不能保证 CLR 当场回收仍被活动线程、异步调用或外部引用持有的程序集；需要硬终止插件代码时应采用独立进程。未持久化的在途事件不能承诺重载后恢复，队列持久化/重投语义需单独定义。

### 分阶段迁移

1. 先统一生命周期、来源和所有权描述，仍使用静态组合运行现有实现。
2. 将 Host 中的具体构造和类型硬编码迁移到注册工厂；完善实例目录变化事件。
3. 将固定发布扩展从 Host 项目引用迁移到发布清单装载，验证核心不依赖实现 DLL。
4. 实现依赖注册、Draining、准备就绪屏障、失败回滚和强制断开；先覆盖当前进程内组件。
5. 再添加插件包目录、可卸载 `AssemblyLoadContext` 与单插件替换；对需要强制终止的插件采用进程隔离。

当前已落地的基础：`ALN.Runtime.ModuleUnloadCoordinator` 可注册插件包与卸载参与者，计算必需依赖的受影响闭包，维护包级 Draining/UnloadFailed 生命周期标记，执行准备屏障、失败恢复和强制断开请求，并返回逐参与者报告；参与者等待有界，正常卸载失败会保留包，强制卸载会继续切断框架资源并报告未完成项。`ModulePackageLoader` 从 `module.json` 加载 DLL 到可回收 `AssemblyLoadContext`，共享核心契约程序集并注册包提供的类型；当前依赖版本约束支持 `*` 或精确版本。`ReplaceAsync` 要求新旧版本位于不同目录，先排空旧依赖闭包，再启动新版本并按依赖顺序恢复受影响插件，失败时尝试恢复旧包集合；插件可通过核心的短期 JSON 状态槽传递实例配置，FileAdapter 用它在替换时重建并恢复原有实例/运行状态。Host 不再静态引用 Channel、Clock、Graph 或 Jint 实现：它从固定发布包 `modules/bundled.runtime` 加载这些扩展，从 `modules/adapter.file` 加载 FileAdapter 插件。AdapterManager、事件队列、类型/工厂注册表和包生命周期协调保留在 Runtime 核心；Channel/Clock/Graph/Jint 实现由固定发布包提供。Adapter 工厂按包注册和排空，销毁前 Graph 会等待在途脚本处理完成。当前还没有管理命令或文件监视器触发 `ReplaceAsync`；热替换能力是 Runtime API，整套固定发布 Manager 不支持运行时替换。

## 2. 模块、管理器与脚本所有权

### 2.1 三种所有权

| 对象 | 所有者 | 职责 |
|---|---|---|
| `AdapterManager` | Host 创建的全局单例 | 创建、登记、查询、启动、停止和销毁 Adapter 实例 |
| `ChannelManager` | Host 创建的全局单例 | 创建、登记、查询、启动、停止、销毁 Channel；精确匹配 `(adapterAddress, conversationId)` |
| `GraphManager` | Host 创建的全局单例 | 加载脚本包、按模块抽象类型匹配、维护挂载登记、触发事件处理 |
| `ClockSource` | Host 创建的单一时钟源模块 | Adapter/其他模块按目标实例和间隔注册；到期后发布 RoutedEvent 脉冲；订阅者确认处理后才开始下一周期 |
| Adapter 实例 | `AdapterManager` | 持有连接与自身状态；不持有 Channel 或其他模块对象引用 |
| Channel 实例 | `ChannelManager` | 持有 Adapter 地址和 conversationId 绑定；不持有 Adapter 对象引用 |
| 脚本定义/挂载登记 | `GraphManager` | 登记脚本版本和目标实例地址；登记跟随目标实例生命周期创建/撤销 |
| Jint Engine | 脚本执行器 | 执行一次事件处理；不持有跨调用业务状态或模块实例注册表 |

Manager 的全局唯一性是**每个模块类型一个管理器实例**，不是系统里所有管理器合并成一个万能对象。Manager 对外提供类型化 `List/Get/Describe` 等查询，不把内部集合或可变模块对象直接泄漏给调用方。

### 2.2 脚本挂载兼容

脚本 manifest 声明抽象目标类型，例如 `adapter` 或 `channel`。`adapter.file` 实例继承 `adapter`；`channel.conversation` 实例继承 `channel`。匹配规则等价于“实例类型可赋值给目标抽象类型”。抽象类型只作匹配锚点，不可创建实例。

```text
script.targetType = adapter
adapter.file instance -> inheritance chain [adapter.file, adapter]
=> compatible; default script is mounted on that instance
```

同一实例可挂载多个脚本。脚本顺序不表达业务先后；若多个脚本对同一事件有副作用，manifest 必须允许明确的优先级，或系统拒绝冲突。**推荐 v0 默认并行度为 1、按稳定 ScriptId 排序串行执行**，但要避免把注册顺序当语义；更好的最终规则是“无顺序依赖，彼此失败隔离”。需在运行契约阶段裁定。

### 2.3 Manager 查询与脚本调用

区分三类脚本 API：

1. **Adapter → Channel 接入**：Adapter 事件脚本只能把当前事件交给 `ChannelManager.AcceptAsync`；不能提交另一个伪造的 Adapter 身份或改写来源 conversation id。
2. **来源 Adapter 自发**：`ctx.self.adapter.send` 只在 Adapter 事件脚本中可用，且仅能回复触发事件的原会话。
3. **Channel 绑定回送**：Channel 事件脚本通过 `ctx.channel.reply` 发回当前 `ChannelMessage` 的 Adapter/conversation 绑定；Graph Runtime 再向 ChannelManager 核验绑定，目的地不能由脚本改写。

各 Manager 的 C# `List/Get` 是内核运行时查询面；初版不把裸 Manager 或全局实例目录交给脚本。

## 3. 脚本包与挂载声明

### 3.1 建议目录形状

```text
<programRoot>/resources/scripts/builtin/
  adapter.channel-intake/manifest.json
  adapter.channel-intake/main.js
  channel.bound-reply/manifest.json
  channel.bound-reply/main.js

<dataRoot>/scripts/
  trusted/<human-authored-script>/manifest.json + main.js
  restricted/<user-or-agent-script>/manifest.json + main.js
```

内建脚本随程序版本发布、运行时只读；受信/受限脚本放在 DataRoot 的分域目录。受限域的 workspace/脚本写权限不得覆盖 builtin 或 trusted 路径。manifest 中重复声明 `trustDomain` 以便校验路径与声明一致，冲突即拒绝加载。

### 3.2 Manifest 最小字段（建议）

```json
{
  "id": "adapter.channel-intake",
  "version": 1,
  "targetType": "adapter",
  "mount": "default",
  "trustDomain": "builtin",
  "events": ["adapter.envelope"],
  "entryPoint": "onEvent",
  "capabilities": ["channel.accept"],
  "limits": { "timeoutMs": 1000, "maxStatements": 10000 }
}

{
  "id": "channel.bound-reply",
  "version": 1,
  "targetType": "channel",
  "mount": "default",
  "trustDomain": "builtin",
  "events": ["channel.message.accepted"],
  "entryPoint": "onEvent",
  "capabilities": ["channel.bound-send"],
  "limits": { "timeoutMs": 1000, "maxStatements": 10000 }
}
```

首版加载期至少校验：JSON 合法、必需字段、稳定唯一的 `id`、目标类型存在且为可挂载抽象、挂载模式合法、事件名存在、入口函数名合法、能力属于对应信任域可授予集合、预算不超过 Host 上限。未知字段默认拒绝，避免拼错配置被静默忽略。

`default` 不要求模型逐实例安装；`manual` 只在显式 `Mount(scriptId, targetAddress)` 后生效。内建包只读；人写或模型写包的落盘位置和准入由信任域控制。

## 4. Jint 执行与 API 契约

### 4.1 脚本入口形状（建议）

脚本 1 把 Adapter 入站交给 Channel：

```javascript
async function onEvent(event, ctx) {
  await ctx.channel.accept();
}
```

ChannelManager 按 `(event.adapter, event.platformConversationId)` 找唯一 Channel，认领成功后发 `channel.message.accepted`。脚本 2 通过该 Channel 的绑定回到原 Adapter/会话：

```javascript
async function onEvent(event, ctx) {
  await ctx.channel.reply({
    platformConversationId: event.binding.platformConversationId,
    text: event.text,
    replyTo: event.platformMessageId
  });
}
```

ChannelMessage 与绑定来自内核事件；`channel.bound-send` 只能向这个绑定发送，脚本改写目标会被拒绝。这样 Adapter 收发、两段脚本、Channel 精确认领和回路目标约束都走生产路径。

### 4.2 C# 侧概念契约

以下为职责示意，不是最终接口签名：

```csharp
public interface IGraphManager
{
    ValueTask<Result> LoadAsync(string dataRoot, CancellationToken ct);
    ValueTask<Result> MountAsync(string scriptId, Address target, CancellationToken ct);
    ValueTask<Result> UnmountAsync(string scriptId, Address target, CancellationToken ct);
    IReadOnlyList<GraphScriptInfo> List();
}

public interface IAdapterManager
{
    ValueTask<Result<Address>> CreateAsync(AdapterSpec spec, CancellationToken ct);
    ValueTask<Result> StartAsync(Address adapter, CancellationToken ct);
    ValueTask<Result> StopAsync(Address adapter, CancellationToken ct);
    ValueTask<Result> DestroyAsync(Address adapter, CancellationToken ct);
    Result<AdapterInfo> Describe(Address adapter);
    IReadOnlyList<AdapterInfo> List();
}

public interface IScriptApi
{
    Task<string> SendSelfAsync(string outboundMessageJson, CancellationToken ct);
    Task<string> AcceptIntoChannelAsync(CancellationToken ct);
    Task<string> ReplyThroughChannelAsync(string outboundMessageJson, CancellationToken ct);
}
```

注意：脚本访问的是 script facade，而不是 `IAdapterManager` 或 `IAdapter` 的 CLR 实现对象。`SendSelfAsync` 检查挂载记录与能力授权；目录查询也可能因信任域而返回过滤结果。

### 4.3 运行边界

- Jint 负责 JS 语言语义；ALN 负责暴露对象、把调用映射到端口、参数校验和授权。
- 不调用 `AllowClr`；不把 `IServiceProvider`、反射入口、任意 `System.*` 类型交给 JS。
- 注入给 JS 的外部调用全部 async、带 deadline/cancellation；禁止同步阻塞回调。
- 建议每次事件调用使用新的 Engine/realm，Prepared 脚本按源码指纹缓存；脚本全局变量不跨调用保留。跨事件状态放到明确的模块或受限 state 能力，不依赖解释器池里的偶然状态。
- 不同信任域使用不同 Jint options/engine；受限域继续要求子进程边界。Jint 的超时与语句预算是附加限制，不代替 OS 隔离。
- 当前选择的 Jint 4.17.0 已有 `EvaluateAsync` / `ExecuteAsync` / `InvokeAsync` 与 Task→Promise interop，但 TaskInterop 在文档中仍标注为 experimental。首版验证后再决定是否依赖它；若使用，必须固定版本并覆盖 async handler、异常、取消、timeout/statement budget、能力回调失败等测试。
- Jint async 执行的 CancellationToken 不会抢占正在同步运行的 JS 循环；需配执行约束限制该阶段，且运行在受限域的脚本仍需进程边界。

### 4.4 能力、执行记录与失败

每次脚本调用记录：`executionId`、脚本 id/version/hash、信任域、挂载目标、触发事件 id、开始/结束时间、终态、错误摘要、每次能力调用的能力名/目标/结果/耗时。执行记录与安全审计分开：journal 可以轮转；涉及能力准入、拒绝和副作用的审计不可关闭。

- 未声明/未授予能力：调用拒绝并审计；脚本可收到结构化失败结果。
- 脚本异常：本次执行失败并记录；不影响同事件上其他脚本继续执行（建议）。
- 超时：取消该执行的所有在途能力；不能保证取消的适配器操作必须由端口自行 deadline 并在结果中说明。
- 默认不自动重试脚本副作用；调用可能已产生外部效果时，重试须有幂等键或由上层明确决定。
- Engine 全局对象不得被跨信任域或跨实例共享；脚本静态 Prepared 缓存是否可跨信任域共享，按 Jint 稳定版本保证验证，保守实现按域隔离。

## 5. 生命周期与启动顺序

### 5.1 Host 启动

```text
1. 解析 DataRoot，建立 journal、audit、driver 和脚本运行时
2. 创建各全局 Manager（Adapter / Channel / Graph）并登记抽象/具体类型
3. 发现、校验脚本包，准备 GraphRuntime
4. 创建 Adapter 实例但保持入站关闭
5. 从 FileAdapter `inbox/<conversationId>/` 子目录发现会话；每个绑定创建一个 Channel 实例并装好 default 脚本
6. 所有必需脚本和挂载成功后启动 Channel 与 Adapter，开放入站
7. Host 标记 Running；FileAdapter 后续由 ClockSource 脉冲触发 PollOnce，不由 Host 循环驱动。新会话目录在下次启动时创建对应 Channel
```

推荐启动采用原子边界：任一必需脚本或 default 挂载失败，Host 不开放入站。是否允许某个非关键 Adapter 标记 degraded 属于后续部分启动策略；首个闭环一律 fail-fast。

### 5.2 Adapter 动态生命周期

- 新建：实例先处于 `Created/Stopped`；AdapterManager 建立实例；GraphManager 为其计算兼容 default 脚本并挂载；挂载成功后才允许 `Start` 接入事件。
- 停止：先拒绝新事件，等待有界在途脚本执行完成或取消，再撤销挂载，最后断开 Adapter。
- 销毁：Stop 成功/超时处理完成后由 AdapterManager 移除实例；GraphManager 挂载登记不得残留。
- 脚本重载：新版本完整校验并准备后原子替换；旧版本在途执行按选定 drain 规则完成；失败时保留旧版本。
- 手动挂载：验证目标实例类型、脚本域、调用者挂载权限和能力集合后登记；目标停止/销毁时自动撤销。
- ClockSource：AdapterManager 启动 FileAdapter 时，FileAdapter 自己注册 200ms 时钟订阅；Stop 时注销。脉冲以定向 RoutedEvent 进入 Graph，Adapter 脚本调用 `ctx.self.adapter.poll()`；Host 只启动时钟服务并等待关闭，不维护轮询计时器。
- Channel：Host 启动时从 FileAdapter inbox 会话子目录创建 `channel.conversation` 实例；ChannelManager 校验绑定的 Adapter 地址/conversationId 唯一且存在。Host 运行期间新建子目录要重启后才建立 Channel，避免 Host 另造一套定时重扫循环。

### 5.3 事件执行

```text
ClockSource 按每个订阅的间隔到期
  -> 发 RoutedEvent(clock.pulse, target=FileAdapter 地址)
  -> EventPump / Graph 找到 Adapter 上的 intake script
  -> ctx.self.adapter.poll() 调用同一 FileAdapter
  -> PollOnce 扫描 inbox/<conversationId> 并把消息 RoutedEvent 入队
  -> intake script ctx.channel.accept() 调用 ChannelManager.AcceptAsync
  -> ChannelManager 按精确 (adapterAddress, conversationId) 认领
  -> 命中时发 RoutedEvent(channel.message.accepted, source=channel.conversation#<conversationId>)
  -> Graph 找到该 Channel 上的 reply script
  -> ctx.channel.reply(message) 验证绑定后调用原 Adapter.send
  -> 写入 outbox/<conversationId>/<attemptId>.json
```

ClockSource 只维护时间与订阅；它不调用 Adapter 方法。FileAdapter 在 Start 注册订阅，在 Stop 注销；脉冲本身仍走有界 RoutedEvent 队列和 Graph。单个订阅在上一脉冲完成 Graph dispatch 并 ack 前不会再发下一脉冲，避免 poll 重入与积压。没有匹配 Channel 的 envelope 会由 intake 脚本正常处理，但不会产生 Channel 事件，因此不会回传。

## 6. .NET 10 解决方案与依赖方向

### 6.1 推荐初始项目树

```text
ALN.slnx
src/
  ALN.Contracts/             # net10.0：地址、Result、消息模型、模块/能力契约
  ALN.Clock/                 # net10.0：周期订阅、脉冲投递与 ack
  ALN.Channel/               # net10.0：Channel 与 ChannelManager，绑定和入站认领
  ALN.Runtime/               # net10.0：Host composition、Managers、Driver、事件队列、授权/记录入口
  ALN.Graph.Contracts/       # net10.0：脚本执行接口、manifest/挂载模型
  ALN.Graph/                 # net10.0：GraphManager、脚本包加载、挂载/事件匹配
  ALN.Scripting.Jint/        # net10.0：Jint 集成与 JS facade adapter
  ALN.Adapter.Abstractions/  # 若不放 Contracts：Adapter 基类与方向契约
  ALN.Adapter.File/          # 测试/开发文件 Adapter
  ALN.Host/                  # net10.0 可执行入口、配置引导、数据根目录解析
 tests/
  ALN.Contracts.Tests/
  ALN.Runtime.Tests/
  ALN.Graph.Tests/
  ALN.Scripting.Jint.Tests/
  ALN.IntegrationTests/
```

Host 的组合根把 Managers、ClockSource、Graph、Channel、Jint 执行器和 Adapter 具体实现接起来；Graph 与 Channel 只依赖 Contracts 中的接口，不互相引用实现程序集。若接口数量太少，`Graph.Contracts` 可先并入 `Contracts`，但程序集依赖方向不变。建议保持无环：

```text
ALN.Contracts <- ALN.Runtime
ALN.Contracts <- ALN.Clock
ALN.Contracts <- ALN.Channel
ALN.Contracts <- ALN.Graph.Contracts
ALN.Contracts <- ALN.Graph
ALN.Graph.Contracts <- ALN.Scripting.Jint
ALN.Contracts <- ALN.Adapter.File
ALN.Runtime + ALN.Clock + ALN.Channel + ALN.Graph + ALN.Scripting.Jint + ALN.Adapter.File <- ALN.Host
```

功能 Adapter 不引用 Graph、Channel、Session 或其他功能模块实现。各 Manager 的实现均由 Host 注入；Jint 执行器只实现 Graph Contracts。所有项目统一 `TargetFramework=net10.0`、nullable、implicit usings；Jint 固定包版本，SDK 由 `global.json` 锁定。

### 6.2 可变数据根目录

Host 启动必须显式提供 `--data-dir <path>`；不使用隐式默认目录。`--data-dir` 的相对路径按进程当前工作目录解析。不要在各模块独立读取环境变量；程序只解析一次绝对 `DataRoot`，通过只读配置传入各管理器。DataRoot 下的模块子路径再相对这个根解析。开发机可用仓库根目录的 `run-host.cmd` 固定传入本机存储路径。

```text
<dataRoot>/
  adapters/<type>/<instance>/adapter.json   # Adapter 配置，只放配置
  io/<type>/<instance>/                      # Adapter 的传输态：inbox/processed/rejected/outbox/<conversationId>/
  channels/<type>/<instance>/channel.json  # Channel 规格、绑定与窗口
  state/<scope>/<key>.json       # 组件自己的小状态（游标、限流窗口……），由 IStateStore 统一落盘
  scripts/                        # trusted/ 与 restricted/ 脚本包；builtin 随程序只读发布
  models/                         # Provider 实例与 Profile
  sessions/ messages/ artifacts/  # 会话、消息历史、模型调用记录
  api/server.json                 # 网络接口：令牌摘要与 CORS 名单（无此文件则不监听）
  audit/ logs/                    # 安全审计与信号日志，只追加
```

两条规则：

1. **配置与传输态分树**。`adapters/` 只放配置：一个实例一个目录，目录名与代码里的类型/实例一致
   （`adapter.qq#qq-1` → `adapters/qq/qq-1/adapter.json`）。信箱、暂存、待重试这类 IO 走 `io/`，
   同样的 `<type>/<instance>` 形状。两者的生命周期与备份规则不同——配置该进版本控制，IO 不该。
2. **目录名与文件内容必须一致**。规格里的 `address` 若与所在目录不符，加载直接失败并指出两处路径，
   而不是按文件内容去"纠正"目录：一个被悄悄解释的文件，就是一个被悄悄迁移了一半的文件。

仍在纸面、尚未落地的部分（`cache/`、`tmp/`、`secrets/`、`journal/`）不在当前实现里；上面这棵树是**实际**
存在的形状。

`tests/Fixtures/` 留在源码树，测试运行时通过临时 DataRoot 复制/装载；测试不触碰用户默认数据目录。程序升级不覆盖 DataRoot；数据格式迁移由 Store/脚本 manifest 版本承担。具体 Store 文件格式、加密与备份策略不属于本闭环，保持待定。

## 7. 逐阶段实施与验收

| 阶段 | 交付 | 失败验收 |
|---|---|---|
| A. 骨架 | .NET 10 solution、Contracts、Host、临时 DataRoot resolver | 任一实现项目反向引用业务实现程序集则失败；Host 可从临时根启动后干净退出 |
| B. Adapter/Manager | AdapterManager 持有 FileAdapter；分会话目录输入输出 | 抽象 Adapter 不可实例化；路径越界/reparse point、非法 conversationId 被拒绝 |
| C. Channel | ChannelManager 持有 `channel.conversation` 实例及 Adapter/conversation bindings | 未绑定的输入零 ChannelMessage；同一 binding 不能注册两次；停止/销毁撤销挂载 |
| D. Graph/Jint | manifest、抽象继承匹配、两个 default handlers、受限 `channel.accept` / `channel.bound-send` | 未知事件/类型/能力、无效预算拒绝；跨频道回复目标被拒绝；CLR/Process 不可访问 |
| E. 队列和 Host | 单一有界 RoutedEvent FIFO；发现 inbox 会话目录并创建 Channel | 新目录先创建 Channel/挂载再读取消息；慢 send 时入站仍可排队；停机先停 Adapter 再排空队列 |
| F. 多群回环 | Adapter intake script → ChannelManager 认领 → Channel reply script → 原 Adapter outbox | 两个会话消息分别回到各自 outbox；未绑定会话零回复；platformMessageId 保持 replyTo |
| G. 故障路径 | timeout、异常、stop、reload、目录隔离 | 脚本超时不拖死 Host；一个脚本异常不阻断其他脚本；reload 失败保留旧版；不同临时 DataRoot 互不污染 |

FileAdapter 输入格式：`inbox/<conversationId>/<messageId>.ready.json`，内容至少为 `{ "text": "..." }`；可附 `messageId`，若附 `platformConversationId` 必须等于目录名。输出写到 `outbox/<conversationId>/<attemptId>.json`。这两个目录是 FileAdapter 的模拟传输协议；每个 input 子目录在 Host 启动/轮询发现后对应一个 Channel binding。

## 8. 初版契约选择

下面的值作为 Adapter + Channel + Jint 回环切片的默认契约；它们都可以在有数据和测试后另行调整，不表示全系统永久定型。

| 项目 | 初版约定 |
|---|---|
| 脚本入口 | 每个包声明一个事件白名单和一个函数名，默认形式为 `async function onEvent(event, ctx)`；同一个实例上的处理按事件串行；匹配到的多个脚本按 `ScriptId` 序列执行，单脚本失败记账后继续下一个 |
| Manager 生命周期 | 每类 Manager 是进程内单例、拥有自身实例集合；创建时执行绑定/默认挂载后才允许启动；销毁时先停止实例、撤销挂载、再从 Manager 移除 |
| 脚本可调用面 | `channel.accept` 仅把当前 Adapter 事件交给 ChannelManager；`channel.bound-send` 只向当前 ChannelMessage 绑定发送；`self.adapter.send` 仅回复来源 Adapter 事件。Manager 的 `List/Get` 作为内核 API，初版不把全局实例目录开放给脚本 |
| Jint 执行 | 使用 Jint 4.17.0；每次事件创建新的 Engine，设定 statement、memory、deadline 上限；启用 TaskInterop 供 `await`；关闭一般 CLR interop、反射入口和 CLR 写入；不共享 JS 全局状态 |
| 信任域 | `builtin` / `trusted` / `restricted` 必须与来源目录相符。`builtin` 随 Host 只读发布；`trusted` 由宿主进程执行；未实现进程隔离前，出现 `restricted` 包会拒绝本次脚本目录装载，不静默降权执行 |
| 事件队列 | 单读者 FIFO，容量 256；满载时立即返回可重试 Unavailable，不阻塞事件处理器本身。事件进入内存队列不代表已持久化 |
| 默认挂载 | manifest 声明抽象目标；类型目录从具体实例向父类型链匹配。Adapter/Channel 创建后先建立 default 挂载，再开放其生命周期；销毁时注销依赖、detach 后移除 |
| 时钟脉冲 | ClockSource 用 20ms scheduler resolution 处理订阅；Adapter 启动时注册默认 200ms 轮询，Stop 时注销；一个订阅同时最多一个未确认脉冲，Graph 完成 dispatch 后确认 |
| 数据目录 | 默认 `%LocalAppData%/AgentLilaraNext`；FileAdapter 的 `<DataRoot>/adapters/<instanceId>/{inbox,processed,rejected,outbox}/<conversationId>/` 子目录各代表一个群聊；启动时 inbox 子目录映射到 `channel.conversation` 实例，新群聊目录要重启 Host 后发现 |
| FileAdapter 输入 | `inbox/<conversationId>/*.ready.json`，Conversation ID 只接受 1–128 个 ASCII 字母/数字/`-`/`_`；JSON 需要 `text`，可选 `platformConversationId`（如提供必须等于目录名）与 `messageId`；单文件 ≤64 KiB，每次最多 64 个，按 Conversation ID/文件名排序；有效消息入队后归档到 `processed/<conversationId>/`，无效输入到 `rejected/<conversationId>/` |
| FileAdapter 输出 | `outbox/<conversationId>/<attemptId>.json`，先写该会话目录内临时文件再原子移动；这是本地文件观察口，不是聊天平台回执 |
| 停机 | 先停止 Adapter 接收入站，再关闭队列，排空最多 10 秒；超期后取消剩余处理并关闭实例 |

⚠️ 入站队列是内存队列；FileAdapter 输入移动到 `processed/` 的时点是“成功入队”，不是“Graph 已完成”或“事件已持久化”。进程若在入队后、脚本处理前崩溃，可能丢失该条处理机会。这版只验证调用链和生命周期，不承诺崩溃一致性或 exactly-once。

> 上面两条"不承诺"中，**挂载、脚本记忆与频道期望状态**已在 [`17-状态与恢复.md`](17-状态与恢复.md) 里补上；入站 ack 时机与重复投递语义仍是 §9 的第一条缝。

### 8.1 脚本可见的 `ctx`（现状）

| 成员 | 能力位 | 说明 |
|---|---|---|
| `ctx.eventName` | — | 当前事件名，免去脚本按 `event` 形状猜 |
| `ctx.channel.accept()` | `channel.accept` | Adapter 事件 → 交给绑定的 Channel；**不自动建频道** |
| `ctx.channel.route(options)` | `channel.route` | Adapter 事件 → 缺频道时建一个（`{channelId, name}`） |
| `ctx.channel.reply(message)` | `channel.bound-send` | 向当前 Channel 的绑定回送；目的地由内核核验，脚本改不了 |
| `ctx.session.run(spec, input)` | `session.run` | 直接跑一轮并拿回结果 |
| `ctx.session.activate(spec)` | `session.activate` | 只叫醒会话，不带内容；内容在组装请求时由频道 delta 补齐 |
| `ctx.model.complete(profile, request)` | `model.complete` | 单次模型调用 |
| `ctx.self.adapter.send/poll` | `self.adapter.send` / `self.adapter.poll` | 仅对来源 Adapter 有效 |
| `ctx.log.info/warn/error` | — | 点日志，不改变脚本结果 |
| `ctx.state.get/set/delete` | — | **脚本自己的持久记忆**：默认按 (脚本, 目标) 一段命名空间，规则声明 `stateScope: "shared"` 时按规则共享；值为 JSON，上限 64 KB |

`ctx.state` 不需要能力位：它只写自己的命名空间，不产生外部副作用——但正因如此，它是"一次性/幂等/已见过"这类判断的落点（见 [`17`](17-状态与恢复.md) §5）。
