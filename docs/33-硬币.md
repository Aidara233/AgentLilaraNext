# 33 · 硬币：框架自己的钱包

> 状态：**第一期（钱包 + 商店 + 背包 + 工具 + 指令）已实现**，投币（`//coin toss`，见 §5.1）已加上，全量测试通过（这一提交单独构建时是 1112 个）。脚本结算路径已接上但**没有用真脚本跑过**，见 §7；投币没在真 Adapter 上跑过，见 §8。

---

## 0. 它是什么

Lilara 自己的钱包，**全局一份**，不属于任何会话或人。商店卖的东西与背包里的东西**完全独立**：买 A 得到两个 B、或者什么都没得到，都由 A 对应的**脚本**决定。

四层各管一件事：

| 层 | 在哪 | 管什么 |
|---|---|---|
| 钱包 | `state(scope=coin, key=state)` | 一个数字 `balance` + 背包 + 已售 + `revision` |
| 商店 | `<dataRoot>/market/goods.json` | 花多少钱、跑哪个脚本 |
| 物品 | `<dataRoot>/market/items.json` | 这是什么、用起来跑哪个脚本 |
| 脚本 | `<dataRoot>/scripts/...` | **买到什么、用掉几个** |

## 1. 结算协议

购买与使用同形。脚本收到：

```json
{ "kind": "buy", "good": "test-box", "count": 1, "paid": 30, "balance": 70,
  "bag": [ { "item": "test-candy", "count": 1 } ], "actor": "model:s-1" }
```

脚本（必须是 callable 的工具脚本）返回：

```json
{ "bag": [ { "item": "test-candy", "count": 2 } ], "text": "滚出两块糖。", "used": 1 }
```

- `bag.count` 为负 = 从背包拿走；`used` 只在使用时有意义：`0` 不消耗、`1` 消耗一件、`-1` 全部。
- **余额不在返回值里**：脚本要动钱就调 `coin.credit`，见 §3。

## 2. 交易的三个步骤，以及为什么

```
① 事务内：扣费（余额不足直接失败，不跑脚本）
② 事务外：跑脚本（慢脚本不能占着钱包的锁）
③ 事务内：校验库存 → 应用 bag/used → 记 sold/revision
```

②和③之间可能失败（库存被别人买走、包满了）。失败就 **③ 退款**（`refund:<reason>`），因为“付了钱什么也没拿到”会被模型合理地读成偷窃。

所以**脚本不需要是纯的**——它可以有副作用，宿主也不会假装能回滚它。代价是：脚本已经跑过而交易最终失败时，脚本那边的副作用留下了，只有钱退回来。审计里两笔（`debit` + `credit`）对得上。

## 3. 谁能动钱

| 谁 | 怎么动 | 深度 |
|---|---|---|
| 模型 | `coin_buy`（只能花，不能赚） | `agent` |
| 人 | `//coin buy|use|topup` | `full` |
| 人 | `//coin toss`（每人每天 1 枚，只认人物表） | `agent`，名单之外一律拒绝 |
| 脚本 | 商品/使用脚本里调 `coin.credit`（计划中） | `full` |

余额只有两个写入口：`CoinLedger.DebitAsync` / `CreditAsync`。**“买东西反而赚钱”是合法的**（脚本可以 credit 回去），审计里是 `debit` 与 `credit` 两笔，不是一笔净额。

## 4. 模型侧五个工具（全部 `agent`，前三个免费）

`coin_wallet` / `coin_shop` / `coin_bag` / `coin_buy` / `coin_use`。

看价格不收费：否则模型连决策都做不起。`coin_buy` 失败以**工具结果**返回而不是调用失败——它要读“还差 20”再决定，而调用失败是它会盲目重试的东西。

## 5. 人侧一棵 `coin` 子树

`//coin`（无参 = 列出子指令）· `coin.wallet` / `coin.shop` / `coin.bag` = `agent` · `coin.buy` / `coin.use` / `coin.topup` = `full`。

`full` 只能人手写 `identify/<id>/info.json`，所以**“第一笔钱”要么人手写一张 full 卡，要么 `//coin topup`**。这是有意的：印钱必须有人在场。

### 5.1 投币：`//coin toss`，一天一枚，只认人物表

别人给 Lilara 硬币的**唯一**入口，也是唯一一条“加钱但不需要 `full`”的路。

- **认人**：用的是内置人物表（`identify/<id>/info.json`），不另立名册。判断写的是 `CommandContext.Person is null` → 拒绝，**不是等级**：陌生人到达时也是 `agent`，用 `MinLevel` 挡等于放所有人进来。
- **一天一枚**：按**本地自然日**（`TimeProvider.GetLocalNow()`，与白饭的“今日”同口径），0 点重置。按**人**算（`person.Id`），一个人有几个平台账号都只算一个。
- **记在哪**：`CoinState.Gifts`（`personId → yyyy-MM-dd`），和余额在**同一份文档、同一个事务**（`CoinLedger.ChangeAsync`，reason `gift:<id>`）。加钱和记账分开写，就会出现“钱加了、明天还能再给”。写入时只留今天的条目，所以这张表的大小天然就是“今天投过的人”，不长也不需要清理；被拒的投币什么都不写。
- **不给模型开工具**：`coin_buy` 只能花，一个 `coin_give` 工具等于让模型自己印钱。投币是人的动作，走指令。
- **通知**：投进去之后，`CoinNotice` 找到这条指令进来的对话所绑的 Channel，再找服务它的 Session，用 `ISessionManager.DeliverAsync`（`from=coin`、`agent`、`wake=true`）投一条转交消息，内容写明是谁投的、今天第几枚、余额多少。所以她会**当场**被叫醒，可以道谢。
  这三个问题（哪个 Channel、哪条 Session、怎么放进去）走的是硬币模块自己的窄口 `ICoinConversations`，实现 `SessionConversations` 才碰 `IChannelManager`/`ISessionManager`：不为了三个角落去依赖两个各十三条方法的全过程管理器，测通知时也不必假装自己是那两个管理器。
  **是尽力而为**：钱已经进钱包了，所以“这个对话没绑 Channel”“那个频道还没有 Session”“Session 正忙（`Conflict`，note 已写下去、唤醒被跳过）”都只往信号日志写一行，不会把一次成功的投币变成失败的指令。
- **回话**：成功 → “收下了 1 枚硬币，Lilara 现在有 N 枚（今天是第 K 位）。明天再来。”；同日第二次 → `Conflict`“今天已经给过了”（失败返回不是静默成功：审计要答得准“这条指令有没有真的改成东西”，而拒绝的话拦截器照样发回给人）。

## 7. 没验证的部分（如实）

1. ~~脚本结算没有用真脚本跑过~~ **已补**：`CoinScriptTests` 用真的 `JintScriptExecutor` 跑一个 JS 盲盒脚本——五成空盒、五成两块糖，价格固定 30；脚本抛异常则购买失败并退款。契约（`JSON.stringify(call(args, ctx))` 的返回值就是结算）因此是验证过的。仍然没验的是 `GraphCoinScripts.CanRun`（依赖 loader 把包标成 callable）。
2. ~~样例脚本不存在~~ **已补**：七件商品/物品各有一个脚本目录，`CoinSampleTests` 用真的 `JsonScriptCatalog` 把它们加载了一遍——七个包全部解析、`call` 绑定正确、`scripts/trusted` 定级为 `Full`。
   **顺带发现两件真事**：① 目录解析（`JsonScriptCatalog`）只产出文件与 `call`，**不产出工具定义**——`Tool` 在 `GraphManager.LoadAsync` 阶段才由脚本自己的 `describe()` 填上；② 因此每个样例脚本都必须有 `describe()`，否则 `GraphManager.InvokeToolAsync` 会以"没有这个可调用脚本"拒绝，而货架看起来完全正常。降级保护：`GraphCoinScripts.CanRun` 从"必须在 `ToolScripts` 里"改成"有 `Call` 且已启用"，避免一个没有定义但有入口的结算脚本让整排货架消失。
3. ~~幂等未做~~ **已补**：`coin_buy` / `coin_use` 用 `(sessionId, toolCallId)` 作键，同一个 id 第二次直接拒绝（`Conflict`），state 里保留最近 64 个键。
4. **没有做成可装卸插件**：`src/ALN.Coin` 是独立项目 + 宿主装配 3 行，不是 `IKernelModule` + `module.json`。理由同指令系统：它要挂扩展点，而模块的 `InitializeAsync` 晚于这些装配。
5. ~~`coin.credit` / `coin.debit` 没注册~~ **已补**：两个 verb 已注册，能力名 `coin.control` 不在 `AccessLevels` 里，因此 `RequiredLevel = Full`（有测试钉住）。脚本改钱的路径通了，但**没有用真脚本跑过一次**。
6. **容量上限是构造参数（默认 12）**，没有接 `IParameterRegistry`。
7. **`purchased` 按会话记**，键是 `session:<id>` 或 `command:<person>`，指令购买与模型购买因此分得开——但没有做每会话限购的判断。
8. **没有计费/结算**：token 与轮次的自动扣费按你说的“有方案”，本期只有一个 `DebitAsync`/`CreditAsync` 原语等着接。

9. **`GraphManager.InvokeToolAsync` 这条路没走通**（本期最后一处卡住的地方）：`/tmp` 里的端到端测试用真的 `GraphManager` + 真的 `ScriptPackage`（显式给了 `Tool`）调 `InvokeToolAsync`，仍然返回 `No callable script is called shop.box`。也就是说包在 `LoadAsync` 阶段就被拒了，或者 `_packages` 里没有它——原因没定位到（候选：`AdapterTypeCatalog` 是空的，`targetType: "channel"` 因而不被认；或 `WhyRejected` 另有条件）。测试被撤下，不留一个红着的东西。**这意味着"复制样例市场后真能买"仍未端到端验证过**：catalogue 能解析（已验）、Jint 能跑结算（已验）、`CanRun` 不管这条（已改），但"货架 → 图 → 脚本"这条装配线没跑通。

## 8. 投币（`//coin toss`）没验证的部分

1. **没在真 QQ 群里跑过**：认人（`Person is null` 拒陌生人）、一天一枚、隔天重开、通知的去向、以及“没人可通知时不失败”，都在 `CoinTests` 里用真的 `CommandRegistry` + 假的 Channel/Session 验过；真 Adapter 上的一次实投没做过。
2. **`wake: true` 会在指令拦截器里同步跑完一整轮**（`//coin toss` → `DeliverAsync(wake)` → `ActivateAsync`）：这期间事件泵被这一轮压着，投币的人要等这一轮结束才收到回话。行为上是“她已经知道了”的样子，但真机上的耗时、以及这一轮里会话再发消息会不会绕回来，没测过。想保守就把 `CoinNotice` 的 `wake` 改成 false：note 照样写下去，她下一轮才看到。
3. **“一天”用的是进程本地时区**（`TimeProvider.GetLocalNow()`）。宿主换时区、或者部署在 UTC 机器上而人在 +08:00，重置点会跟着机器走而不是跟着人走。要按人/按频道算日界，得再引一个时区来源，本期没做。
4. **通知只发给“服务该 Channel 的那一条 Session”**（`ListAsync` 里第一个 `Channel` 对得上的）。同一条 Channel 上若真有第二条 Session，它不会收到——这是有意的（一个对话不安排两个声音），但没有在真数据根上验过“会不会有第二条”。
5. **`from=coin`、`agent`、`wake=true` 这三个实参本身没有断言**：它们写在 `SessionConversations.PostAsync` 里，测试只到 `ICoinConversations` 这一层就停了（验了“投了会去通知”“没人可通知也不失败”，没验“通知用的是这三个实参”）。要覆盖这一点就得在测试里实现完整的两条管理器接口，为一个实参值得不值得另说。
