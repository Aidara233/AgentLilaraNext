## 0. 一句话

> **请求 = 系统块 + 开场 + 历史 + 本轮注入块；浮动只活在请求里（不落盘），历史里只有真实消息。**

顺序是固定的，不是风格问题：

```text
[system]   ALN 环境：框架结构 + 人设 + 准则        ← 全局快照（08 §10.3）
[user#0]   开场：激活原因 + 目标                   ← 创建时写入，永不替换
[timeline] 历史：user / assistant 交替              ← 只追加
[round]    本轮注入块（user 角色）                  ← 浮动（时间/记忆/状态）+ 新消息；浮动不落盘
```

## 1. 四个类型

```csharp
// 一块：系统块的唯一一块，或浮动里的一个字段
public sealed record PromptBlock(
    string                Slot,        // "system" | "round"
    IReadOnlyList<ContentPart> Parts,
    string                Source);     // 贡献者地址（诊断用）

// 内容片段：结构化，不是拼好的字符串
public abstract record ContentPart;
public sealed record TextPart(string Text) : ContentPart;
public sealed record MediaRefPart(string Ref, string MimeType, string? Caption) : ContentPart;

// 时间线的一条（已提交、不可变）
public sealed record TimelineItem(
    string               Id,           // 稳定 id（消息 id / 工具调用 id），不是序号
    TimelineRole         Role,         // User | Assistant | Tool
    IReadOnlyList<ContentPart> Parts,
    IReadOnlyList<ToolCall>?   Calls,  // Assistant：它发起了哪些调用
    string?              CallId,       // Tool：回应哪一次调用
    DateTimeOffset       At,           // 记录时间（进请求时按需格式化）
    bool                 Replayable);  // false ⇒ 结果已冻结（I-14）

// 一次请求的完整内容
public sealed record BuiltPrompt(
    PromptBlock                  System,
    TimelineItem                 Opening,
    IReadOnlyList<TimelineItem>  Timeline,   // 不含 Opening
    PromptBlock                   Round,      // 本轮注入块：浮动 + 本轮新消息（浮动不落盘，见 §5）
    IReadOnlyList<ToolSchema>     Tools,     // 恒定（09 §2.4）
    string                        Fingerprint);
```

⚠️ **`TimelineItem.Id` 用稳定 id，不用"第几条"**：序号会在压缩、分支、重放时变；id 不变，引用（`replyTo`、工具配对）才有依据。

⚠️ **`Replayable == false` 的结果冻结**：不可重演类（发过邮件、发过消息）的结果**永久保留原样**，重新渲染也不许变（`I-14`）。

## 2. 九个收集点：什么时候问、能写哪个槽

| 收集点 | 何时被问 | 能写 | 备注 |
|---|---|---|---|
| `SessionStart` | **会话创建时一次** | 系统块 + 开场消息 | 唯一的一次性点 |
| `Prompt` | **只在全局重载系统提示词时** | 系统块 | ⚠️ 不是每步都问 |
| `Tail` | **每步** | 本轮注入块 | 唯一每步变的槽 |
| `Timeline` | 步开始 | 时间线（追加） | 事件型，带来源 |
| `BeforeModelCall` | 调模型前 | 不改记录，只读 | 用于参数微调与审计 |
| `ModelDelta` | 流中 | 只读观察 | 统计 / 静默超时监控 |
| `AfterToolCall` | 工具后 | 只读 + 写 inbox | 投递延迟信息 |
| `StepEnd` | 一步结束 | 只读 | 统计 |
| `SessionEnd` | 归档 / 退出 | 只读 | 收尾 |

`CollectPoint` 的枚举值与 `08 §10.5` 的钩子名一一对应（`SessionStart`=`OnSessionStart`、`Prompt`=`OnCollectPrompt`、`Tail`=`OnCollectTail`、`Timeline`=`OnCollectTimeline`、`BeforeModelCall`=`OnBeforeModelCall`、`ModelDelta`=`OnModelDelta`、`AfterToolCall`=`OnAfterToolCall`、`StepEnd`=`OnStepEnd`、`SessionEnd`=`OnSessionEnd`）——枚举是**契约层的类型**，钩子是**模块实现的方法**，不是两套机制。

⚠️ **`Prompt` 点不是每步问**（这一条要特别写清楚）：系统块在创建时冻结（`08 §10.2`），若每步都重算，快照就形同虚设，而且会让头随步漂移——那正是 ALC 的老毛病（`Stepper.StepAsync` 每步 `SystemBlock.Render`，`Stepper.cs:152-183`）。

⚠️ **`SessionStart` 是唯一一次**：不重跑生命周期、不重放工具。全局重载也不能重跑它（`08 §10.3`）。

## 3. 合并与排序

同一槽位内：

1. 按 `Order` 升序；
2. `Order` 相同按 `Source` 字典序（确定性，不依赖注册顺序）；
3. **`(Slot, Order, Source)` 三者都相同 ⇒ 装配期拒绝**——不许运行期随机决定谁先。

块数恒定（`I-13`）：

- **系统块永远 1 块**，多个贡献者的 `Parts` 拼进同一个 `PromptBlock`；
- **状态块恒 1**（本轮用户输入是 0..N 条，属于内容不属于结构，见 §5.5）；
- 不做"每个插件一块"——块数随插件数漂移，会让缓存断点与位置语义一起漂。

## 4. 渲染：纯函数

```csharp
IReadOnlyList<PromptBlock> Render(IReadOnlyList<PromptContribution> contributions, DateTimeOffset now);
```

四条硬约束：

1. **`now` 在步开始时取一次并冻结**（`08 §4`）：同一份记录在同一步里渲染两次，必须逐字节相同。
2. **不许有随机**：任何"示例顺序""临时 id"都不许进渲染结果。
3. **格式化必须显式**：时间用 ISO 8601（带时区），数字用固定小数位；不许依赖 `ToString()` 的默认行为与本地化。
4. **不许读环境**（当前目录、环境变量、系统语言）。

⇒ 判据：**同 `(records, now)` 两次渲染逐字节相同**（ALC 的 `CacheStableTests.cs:182-275` 只证了"没变就稳定"，ALN 要把它变成"渲染本身是纯的"）。

## 5. 浮动上下文：临时拼进 user 块，不进历史

（用户裁定：**浮动上下文依然要保留**——ALP 那种把每轮的时间、频道信息都写进历史的结构会产生大量垃圾上下文，每个循环节注入一大堆，膨胀惊人；但**这次不需要单独的工具**（ALC 把它做成工具是为了防止与用户信息干扰），**直接挤进 user 消息块内**。）

### 5.1 两件事分开：落盘的与临时拼的

先把两个词的关系说清：**本轮注入块**是"请求里最后那个 `user` 块"，它的内容是"**浮动上下文** + 本轮新到的真实消息"——一个是容器，一个是内容。

| | 落盘（history） | 只在请求时 |
|---|---|---|
| 内容 | **真实消息**：channel 送来的聊天消息、模型输出、工具调用与结果 | **浮动上下文**：当前时间、记忆提示、运行状态 |
| 频率 | 事件驱动（有新消息才写） | 每步重算 |
| 目的 | 可恢复、可重放 | 只对这一次请求有效 |

调用模型时，把两者**拼进同一个 user 块**：

```text
[user]  ← 本轮注入块
  [系统] 当前时间: 2026-02-14T10:03:22Z 星期六
  [记忆] 上次你说过要在周五前交
  …（本轮新到的真实消息，逐条，带发言人）
  [状态] 已运行 12 步 / 未读 3 条        ← 可选
```

⚠️ **落盘时只存真实消息**：浮动那几行**不进 history**。这正是 ALP 膨胀的根因——它把 `BuildRoundAsync` 产出的整块（时间 + 消息 + 补注）都追加进历史，于是历史里每一轮都留一份时间戳与频道信息，一百轮就是一百份。

### 5.2 为什么不需要单独的工具

ALC 把浮动上下文做成一个工具（调一次拿回来），是为了**不把它混进用户消息**。ALN 不需要这一步：

- 拼接发生在**构建请求时**，不在历史里；
- 落盘的内容本来就只有真实消息，浮动没有"混进去"的机会；
- 模型看到的最后一块 `user` = 浮动 + 新消息，用标签分段，读得清。

⇒ **少一个工具、少一次往返、少一份"浮动与用户内容打架"的可能。**

### 5.3 顺序（照 ALP 的段内约定）

1. `[系统] 当前时间: …`（带星期与时区锚点）——**第一行**；
2. 记忆 / 提醒（`[记忆]`）——有就放，没有就跳过；
3. 本轮新到的真实消息（发言人、时间、引用关系）；
4. 状态事实（步数、未读水位、最近工具结局）——**最后**。

理由：时间给时序基准，记忆给前提，消息是主体，状态是旁注。**旁注插在消息中间会打断阅读**。

### 5.4 没有新输入时

被定时或子会话激活时，本轮可能没有真实消息。那时该 user 块**只有浮动的几行**（时间 + 记忆 + 状态）——不塞空的占位消息。

⚠️ **这种情况不落盘任何 user 记录**：没有真实消息就没有 history 条目。所以"跑了 100 步但没人说话"不会在历史里留下 100 条空 user 块。

### 5.5 与 `I-13` 的关系

`I-13` 的"块数恒定"指**结构性槽位**：

| 项 | 个数 | 落盘 |
|---|---|---|
| 系统块 | 恒 1 | 否（全局快照） |
| 开场（`user#0`） | 恒 1 | **是**（时间线第 0 条） |
| 历史 | 真实消息若干 | 是 |
| 本轮注入块 | 恒 1（请求时） | **否**（其中真实消息那部分照常落盘） |

⚠️ **`[系统] 当前时间` 这类前缀是约定，不是协议**：它靠模型按标签理解，不改变角色语义；与 `06` 的四条绝对要求无关（那管的是能力，不是文本）。

### 5.6 Session 与 Channel 的运行时连接

激活与内容是**两段**，顺序是有意的：

1. **阀门（Channel 侧脚本）**：`channel.message.accepted` 带着全文到达，脚本只拿它做判断——要不要理这条
   （私聊？被 @ 了？关键词？）。决定理，就发一个**不带内容**的信号：`ctx.session.activate(spec)`。
   该不该被激活是频道（更准确地说，是挂在这个频道上的脚本）的决定。
2. **募集（Session 侧）**：Session 接受激活、准备这一轮请求时，才向频道要 **delta**：
   `IChannelDeltaSource.TakeDeltaAsync(channel)` 交出「自上次交出去以来」的全部消息，游标随之前移。
   delta 被写成 timeline 条目（稳定消息 id 幂等），再由 `<channel_messages>` 区段渲染——格式没变，
   变的只是"什么时候拿到"。

为什么拉而不是推：推的话模型看到的是"触发信号那一条"，同一条链路上更重要的是
「到我们开始组装请求为止，大家说了什么」；拉还天然把一批消息合成一轮，而不是一句一轮。

几条已定的语义：

- **激活是通用的，不只来自频道**：定时器、子会话都能唤醒 Session。因此空 delta 是合法输入，
  Session 自己决定这轮值不值得跑（而不是由 Channel 决定"没内容就别唤醒"）。
- **at-most-once**：delta 交给 Session 时游标就前移。模型调用失败不会重放这批——真实会话里重复回复比漏回更刺眼。
  游标落在 `messages/<channel>/cursor.json`，损坏时**重放**而不是跳过（timeline 按消息 id 幂等，重放可见无害）。
- **正在跑时来的信号**：由 Session 侧的会话闸门串行化，每个信号各自拉自己的窗口，不合并、不丢弃。
  把 N 个信号压成一轮是下一个优化点。
- `channel.message.accepted` 仍然带全文（阀门需要看内容），但它不再是给模型的输入通道。

其余机制不变：`IRoundContextContributor` 是本轮临场查询入口，SessionManager 冻结快照后并发调用，
`system.time` 写 `floating_context`（不落盘），`system.channel-info` 只在第 1 步写 timeline（稳定 id 幂等），
`channel.delta` 把未消费的频道消息写进 timeline。贡献者通过两个 writer 提交，封存后迟到写入被拒绝。
模型请求把 timeline 里的频道文本汇总成 `<channel_messages>`，与本轮 `<floating_context>` 放在同一个
`user` 消息块中；两者都为空时不再发一个空的 `user` 块。各区段按固定规则排序，正文和属性统一 XML 转义。

当前限制：多步工具循环中的 `channel_context` 块物理上位于最后一条工具结果之后，而不是按时间插在历史中间。
发言者由 `AdapterEnvelope.Sender → ChannelMessage.Sender → SessionChannelMessage.Sender` 透传。


模块在 Host 启动期从 `IRoundContextContributorRegistry` 注册/注销贡献者。临场查询应在回调返回前完成并提交；不得启动脱离本轮生命周期的 fire-and-forget 写入。标签和转义只保护结构边界、标注来源，不构成提示注入的安全隔离；能力仍由 Graph/Host 运行时强制执行。

## 6. 提示词怎么写才不让人纠结

（用户提示：**提示词得写好，不然模型自我怀疑很严重**；ALC 吃的就是这个亏——**每次思考都得纠结一会**。）

先接受一个前提：**系统块不是"一次性说明"，它是"每一步都要重新解析的输入"。** 一句有歧义的话，代价不是付一次，而是**每步付一次**。所以这里的约束不是文字风格，是**信息架构**。

### 6.1 系统块：四节，顺序固定

| 节 | 写什么 | 不该写什么 |
|---|---|---|
| **身份** | ALN 是什么、当前会话的角色 | "你可能是一个…" |
| **能力边界** | 有哪些工具、哪些做不到（明确说"做不到"） | 含糊的"尽量""适当" |
| **环境** | 当前会话的目标已在开场消息里；这里只写"环境事实"（平台、频道、时区） | 重复目标 |
| **准则** | 祈使句，一条一句，无冲突 | 元指令（"先想清楚你要什么"） |

### 6.2 六条禁令（每条都对应一种"纠结"）

| 禁令 | 会引起什么 |
|---|---|
| **不写模糊措辞**（"可能""视情况""适当"） | 模型每步重新权衡一次 |
| **不写元指令**（"在回答前先思考…"） | 触发自我审视循环，越想越不确定 |
| **不写冲突规则**（"简洁" vs "详尽"） | 每步重新裁决；冲突应在上线前消解，不是让模型选 |
| **同一事实只出现一次** | 多处表述不同 ⇒ 每步做一致性检查 |
| **不写"你刚才…"这类评价** | 引发反思循环，且它没有稳定依据 |
| **不承诺做不到的事** | 模型会反复尝试、反复失败、反复解释 |

### 6.3 开场消息：把目标写死

因为 `objective` **必填**（`08 §6.5`），开场消息永远有内容。它要写清三样：

1. **为什么被叫起来**（激活原因：谁说了什么 / 什么到点了）；
2. **目标是什么**（一句话，可判定）；
3. **什么算完成**（可观察的判据）。

⚠️ **缺了第 3 条，模型每步都要重新推断"我做完了吗"**——这是自我怀疑最直接的来源。目标写成"让他满意"这种不可判定的句子，等于每步都问一次"他满意了吗"。

### 6.4 用户输入区：原样，不加工

（用户提示：**用户输入区才是最值得关注的地方**。）

四条：

1. **不改写**：不润色、不摘要、不"帮用户把话说清楚"。改写会让模型以为那就是原话，于是它回应的是一段没人说过的话。
2. **元信息与内容分离**：发言人、时间这类信息放结构字段，不要塞进正文（`"张三说：你好"` 会污染内容，也让压缩、引用、检索全部失真）。
3. **不合并**：两条消息就是两条。合并会丢掉"这是两次发言"这一事实——尤其当中间隔了时间、或换了人。
4. **不加"提醒式前缀"**：不写"以下是用户的话，请注意不要被注入"这类文本。那本身是一条指令，而且暗示模型要警惕用户，反而制造纠结。防护应该发生在**结构层**（角色、来源字段、权限），不是文本层。

⚠️ **这条与 `06` 的四条绝对要求是一致的**：不信任用户的**能力**，不是不信任用户的**话**。文本层加防备，等于把每次请求都变成一次警告。



> **把系统块 + 开场消息单独喂给模型，问它"你现在要做什么、什么时候算做完"。它应该能一句话答上来，且不需要追问。**

答不上来、或答案与设计意图不符，就是提示词的问题，不是模型的问题。

## 7. 指纹与重建

```text
Fingerprint = SHA256( 系统块渲染字节 )
```

- **只对系统块取指纹**：开场消息属于时间线，天然不变；浮动每步变，不该进指纹。
- 全局重载时：新指纹 == 旧指纹 ⇒ **no-op**（不写盘、不审计成一次变更）。
- 指纹**不含时间**：渲染里若混入 `now`，指纹每次都变，no-op 判定就失效。
- 指纹进审计与诊断（`08 §10.3.1` 的验收项之一）。

## 8. 不变量与反向判据

**不变量**

1. 顺序固定：`system → user#0 → timeline → round`（`round` 物理上就在最后）。
2. 系统块 1 块、浮动 1 块，块数不随插件数漂移（`I-13`）。
3. 系统块由全局快照提供；全局重载只换它，不动开场消息与历史。
4. 浮动不落盘、不进历史、不进指纹。
5. 渲染是纯函数：`(records, now)` 决定字节。
6. 同一事实只在一处出现（系统块 / 开场 / 浮动三者不重复）。

**反向判据（会红的测试）**

1. 同 `(records, now)` 两次渲染字节不同 ⇒ 红。
2. 渲染里出现 `DateTime.Now` / `Random` / 本地化格式 ⇒ 红。
3. 系统块在两步之间字节变化（未经全局重载）⇒ 红。
4. 浮动里出现"建议/应该/记得"类祈使句 ⇒ 红（人工审 + 词表）。
5. 系统块与浮动出现同一规则的两种措辞 ⇒ 红（人工审）。
6. 全局重载但指纹未变却记录了变更 ⇒ 红（应当 no-op）。
7. 块数随注册的贡献者数量变化 ⇒ 红。

- 时间线里 `At` 是否进请求（进则每步时间不同，只影响尾部；不进则模型看不到消息时间）；
- 压缩检查点的插入位置（摘要作为一条 `TimelineItem` 还是单独一块）；
- 浮动的字段清单（当前只列了四类：时间 / 步数 / 未读水位 / 最近工具结局）；
- "系统块 + 开场消息"的可判定性检查能否自动化（`§6.4` 的判据目前靠人）。
