# 22 · 模块图与生命周期

> 设计定稿。本文定的是"模块"这个概念的最终形状：
> 图上的**实例**、实例之间的**三种关系**、磁盘上的**一个目录**、启动的**五步**。
> 实现按 A（定稿）→ B（图化）→ C（扩展点）→ D（运行期）推进；与今天的差距集中在 §8。
>
> 本文回答一个问题：**一个模块，从哪里来、跟谁连、什么时候算活、怎么算没了。**

---

## 0. 一句话

每个模块都是图上的一个实例：**向上一条恒定的核心边**（谁都拆不掉），**向主声明自己接哪些接口**，
**向下在自己的模块目录里列出自己持有哪些从**。启动是五步（Load → Initialize → Wire → Ready → Stop），
删除是一边一边拆干净，最后连目录一起归档。

---

## 1. 三种关系，不许混

今天的代码里"关系"至少混了四种含义：谁是它的主人、它属于哪个二级分类、它挂在哪条脚本规则上、
它的数据存在哪个目录。这四种含义混在一起时，任何一个动作都要同时改四个地方，而漏掉一个地方不会有任何报错——
只会有一个"看起来还在跑，其实已经不连了"的模块。所以先把关系拆成三种，每种只回答一个问题。

| 关系 | 回答什么 | 谁定义 | 存在哪里 | 方向 | 能否成环 | 运行期能否改 |
|---|---|---|---|---|---|---|
| **核心边** | 它归谁管、谁让它启动与停止 | 核心 | 不落盘（恒成立） | 模块 → 核心 | 不适用 | 不能 |
| **主从边** | 它接谁的调用、在哪一类事情上接 | **主**（接口定义在主的契约里） | 主的 `module.json` 的 `slaves` | 主 → 从 | **能** | 能（增删条目即可） |
| **创建关系** | 谁在运行时把它造出来 | 管理器 | **不落盘** | 管理器 → 实例 | 不适用 | 能（实例生灭） |

### 1.1 核心边：恒成立、不可删、不写文件

每个模块都有一条到核心的边，承载 `initialize / ready / stop / abort` 四个相位。它**不是**配置：

- 不写进 `module.json`，不参与坏边判定，不参与拓扑排序（所有实例的入度都至少有这一条）。
- 不能删除。一个"不归任何东西管的模块"不是自由，是没有人能让它停下来。
- 管理器（`adapters`、`channels`、`models`、`sessions`…）也在这条边上，和普通模块没有区别。

> 为什么不让模块自己决定归谁管：那样"谁负责让这个模块停下来"就变成了一个需要推导的问题。
> 而清理逻辑一旦需要推导，就一定会有一条路径推不出来——那正是**泄漏**的定义。

### 1.2 主从边：接口归主，成员列表在主方

这是本文最要紧的一条，因为它决定了**代码往里写什么、文件往里写什么**。

```csharp
// 契约归主：这个接口是 ChannelManager 的，不是 "从模块" 的
public interface IChannelSlave            // 主方定义
{
    ValueTask<Result> OnMessageAcceptedAsync(ChannelMessageAccepted message, CancellationToken ct);
}
```

- **接口由主定义，从实现**。从不需要知道还有哪些兄弟，也不需要（不可能）知道主内部还有什么。
- **成员列表存主方**。`module.json` 里写 `slaves` 的是主；从的目录里**不写**"我的主是谁"。
  因为接口归主：谁定义接口，谁就知道这张表长什么样；从只知道自己实现了什么接口。
- **派发是直接调接口方法**，不是字符串事件总线。事件总线的好处是两端互不认识，代价是"有没有人接"
  在运行时才知道；主从边在 Wire 相位就把接口对象绑好了，接不上就是一条**坏边**（§5），不是一条沉默的事件。
- **多对多，允许成环**。一个模块可以是 A 的从、同时是 B 的主；成环（互为主从）是允许的，
  因为"能成环"是真实系统的样子（会话 ↔ 频道、脚本 ↔ 宿主的互相调用）。环不禁止，但**必须被报告**（§7 I6）。
- **每个从条目带一个策略**：`{ "requireAll": true }` 表示"主就绪前，这些从必须都就绪"；
  `false` 表示"有就绪的就行"。默认 `requireAll: true`——少一个从就开动的系统，
  出问题时看起来和正常一模一样。

管理器的每个实例（一个 Adapter、一个 Channel、一个 Session）也是主从边上的从，
只不过这些从是**运行时创建**的、**不落盘**的：`_channels` 这个内存集合本身就是成员表（§1.3）。

“实例”指的是**管理器此刻持有的东西**，不是磁盘上可能存在的东西，两者在会话与模型上会分开：

| 实例 | 什么时候成为实例 | 为什么 |
|---|---|---|
| Adapter / Channel | 创建时（恢复进来的那些在 Ready 里创建，所以也在启动内） | 管理器就是它的生命周期所有者 |
| 模型 provider | 宿主从文件里建好、**启动之前**就宣告 | 启动前的宣告按 `Declare` 处理：进入 Initialize/Wire/Ready，收据照常计数 |
| Session | **载入时**（按需），归档 / 覆盖恢复 / 删除时摘除 | 磁盘上有一千个旧会话不该长出一千个实例；图上说的是"这个进程现在持有谁" |

两类失败的处理也不同，而且是有意的：Channel 宣告失败就回滚（它还没被创建，回滚没有代价）；
Session 宣告失败只记一条 warn 并继续（它已经有目录、可能有历史，把图的问题变成丢一段对话是更坏的失败）。

### 1.3 创建关系：不写文件

今天有一个 `createdBy` 字段，用来回答"这个实例是谁造的"。它被删掉：
- 谁造的，内存里就有谁：`ChannelManager` 持有它造的 Channel，`AdapterManager` 持有它造的 Adapter。
  重启之后这些实例是从磁盘恢复的，不是"被谁造出来的"，这个问题不再有答案——而它本来也不该有。
- 落盘的 `createdBy` 会腐烂：管理器换了实现、实例被手工搬了目录、配置文件被手改了一半，
  这个字段就变成一句没人维护的断言。
- 归属靠两件事就够了：**目录**（它存在磁盘上的哪里）与**管理器自己的集合**（它现在由谁持有）。

### 1.4 触发关系：不是边，是"我愿意被叫"

有些模块需要被**推**一下才干活：文件适配器要隔一会儿看一眼收件箱，某个模块要定时把缓冲刷出去。
把这件事写成边是错的——先写成"它是时钟的从"，就把"多久看一眼"与"从谁那儿看"绑死了。

所以它是第三种关系，**由接收方声明**：

```csharp
public interface ITriggerSink
{
    TimeSpan? PreferredInterval { get; }   // null = 我没有节奏，别给我排班
    ValueTask<Result> OnTriggerAsync(TriggerSignal trigger, CancellationToken ct);
}

public interface ITriggerSource
{
    string Source { get; }
    Result Attach(ModuleId sink, ITriggerSink trigger);
    Result Detach(ModuleId sink);
}
```

| 谁 | 是什么 | 今天有谁 |
|---|---|---|
| **sink** | 想要被叫的模块；用 `PreferredInterval` 说明要不要节奏 | `FileAdapter`（200ms，可被参数覆盖）、测试里的计数 sink |
| **source** | 能发触发的模块；**不持有所有权**，一个 sink 可以同时挂在多个 source 上 | `ClockSource`（`Schedule`），脚本按需触发（`Push`/`Demand`）走 `ctx.self.adapter.poll()` |

为什么不写成边：

- **边的另一端是谁取决于今天谁在推**。同一份"我要盯收件箱"的声明，时钟推也对、脚本推也对、HTTP 回调推也对。
  画成边就必须现在回答"另一端是谁"，而那个答案会变；
- **它不该影响就绪顺序**。一个 sink 晚一点被推不会有任何问题，所以它不该进 SCC，也不该让 master 等它。

代价要说清：图里**看不到**"这个适配器在按 200ms 被推"。补偿是让收据和 `system.info` 各报一行——
把"谁在推"记成运行期事实，因为它确实会变：

```
restored rhythm: adapter.file#file-1 200ms by Clock      ← 收据（Host 打印）
"rhythm": ["adapter.file#file-1 200ms by Clock"]         ← system.info 的同一条文本
```

这行的来源是 `Kernel` 自己记的"哪一次 `Attach` 成功了"，**不是**问 source 要一份名单：
source 拒绝过谁，恰恰是最该被看见的那种情况，而问它只会得到"我不服务任何人"——和"没人找过我"长得一模一样。
间隔读的是 sink 此刻的 `PreferredInterval`，因为它才是排班依据；相位不是 `Ready` 的 sink 不出现。`RhythmInfo` 只有这三个字段
（`Sink`/`Interval`/`Source`），刻意不带 source 的地址：触发关系不该有第二份"地址表"。

装配规则（`Kernel` 在每个实例 Ready 之后、以及每次加减实例之后做）：

1. 找出所有**能当 source 的实例**（自己是 `ITriggerSource`，或包着一个）；
2. 对每个 `PreferredInterval != null` 的 sink 实例，逐个 `Attach`；
3. 挂不上就记一条 warn（和坏边同一条规则：不阻断，但必须看得见）；
4. 实例被移除时 `Detach`——源继续服务其它人。

## 2. 目录形状：一个模块一个目录

```
<DataRoot>/
  modules/
    adapter.file#file-1/
      module.json                 ← 这个模块的全部配置：类型、开关、主从边
      <它自己的东西>              ← 缓存、临时文件、按会话分的子目录
    channel.conversation#chat-auto/
      module.json
    model.openai-chat#deepseek_official/
      module.json                 ← config 里是 provider 自己的配置（含密钥），见 §2.2
    s-521035cf.../
      module.json                 ← 会话的 spec（config）
      history.jsonl               ← 这一层的时间线，跟着会话活
      state.json
  aln.db                          ← 存储模块：跨重启、跨模块读写的东西
  api/server.json                 ← 控制面的地址与令牌（不是模块）
```

**旧的四层分类目录（`adapters/`、`channels/`、`models/`、`sessions/`）已经不存在了。**
它们回答的是"这是什么种类的东西"，而这个答案在 `module.json` 的 `type` 字段里已经有了（§3）。
两处都写种类，就一定会有一处是旧的。

四个 store（适配器、频道、模型 provider、会话）现在都写这一棵树，于是每棵树的使用者都必须回答
"这个目录是不是我的"——答案一律是看 `type`，不看目录名：

| 谁 | 认领条件 |
|---|---|
| 适配器 / 频道 / provider | `type` 前缀 `adapter.` / `channel.` / `model.`（`SpecTree`、`FileModelInstanceStore`） |
| 会话 | `type` 是 `session.chat`，**或**目录里有它自己的 `state.json`（规格坏了也要能被回收站看见） |
| 内核扫描 | `type` 不是本进程会造的类型就跳过——由宿主回答"这个类型归管理器"（`hostOwnsTypes`），不报警 |

会话的 id 仍是它本来的名字（`s-<hash>`），没有加前缀：`session#…` 只是文档里的一个例子，
而 id 是名字不是形状（§3.1）——加前缀等于给每一个已经存在的会话换身份。

### 2.1 `module.json`

```json
{
  "id": "channel.conversation#chat-auto",
  "type": "channel.conversation",
  "enabled": true,

  "config": {
    "name": "chat-auto",
    "maxMessages": 40,
    "modelProfile": null
  },

  "slaves": [
    { "id": "adapter.file#file-1", "kinds": ["message.accepted"], "policy": { "requireAll": true } }
  ],
  "dependencies": ["clock.system"]
}
```

| 字段 | 必填 | 含义 | 谁读 |
|---|---|---|---|
| `id` | 是 | 唯一身份键，边引用它（§3） | 所有 |
| `type` | 是 | 实现类型，决定怎么实例化。**不从 id 推导** | 装载器 |
| `enabled` | 否 | 默认 `true`；`false` 时装载但不 Ready | 装载器 |
| `config` | 否 | 这个类型自己的配置，核心不解析 | 模块自己 |
| `slaves` | 否 | 我持有的从：接口、策略（§1.2） | 主的 Wire 相位 |
| `dependencies` | 否 | 启动顺序上的前置（不是接口），影响 Ready 的拓扑序 | 装载器 |

> `config` 是**不透明**的：核心只负责把它原样交给模块，模块自己解释、自己校验、自己决定怎么存副本。
> 一旦核心开始理解 `maxMessages` 是什么意思，这类字段就会在核心里长出一份永远不会被删的副本。

### 2.2 模块目录 vs 存储模块

一句话：**跟着模块活的，放模块目录；要跨模块或跨重启读的，走存储模块。**

| 数据 | 放哪 | 为什么 |
|---|---|---|
| 会话时间线（`history.jsonl`）、会话状态 | 模块目录 | 只属于这个会话；会话删掉/归档，它跟着走 |
| 频道的 `maxMessages` 覆盖值 | 存储模块（`state`） | 用户改过的旋钮要跨重启；而且 UI 是"读全部旋钮"的形状 |
| 记忆碎片与笔记 | 存储模块（`memory`） | 按 `scope` 跨会话读，会话没了记忆还在（`21`） |
| 审计、信号日志 | 存储模块 / `logs` | 全局顺序，不属于任何模块 |
| 模型 provider 的配置（含密钥） | 模块目录（`config`） | 它就是这个模块自己的配置 |
| 消息历史（`message` 表）、`channel.delta` 游标 | 存储模块 | 频道与脚本都要读，谁也不拥有它 |

判断标准的反面同样重要：**不要把"跨重启"当成"必须进数据库"**。一个只有自己能读的东西，
放在自己目录里既便宜又不需要协调；放进库里就要一个 scope 名、一个清理时机、一次 schema 迁移。

### 2.3 目录怎么结束

模块结束时（§4 的 Stop / Abort），它的目录**归档或删除**，二选一：

| 结束方式 | 目录 | 为什么 |
|---|---|---|
| 销毁（用户明确删除） | 删除，但先复制进 `archive/` | 删一个频道不等于要求忘掉这段对话（`20`） |
| 卸载（换实现、临时停用） | 保留 | 它还会回来，回来的应该是同一个 |
| 崩溃中退出 | 保留原样 | 目录的形状本身就是"崩溃后能恢复"的输入 |

### 2.4 数据根的迁移口径（dev 阶段，**已经执行过**）

**不做迁移器。** 这个仓库的数据根只有一个开发者的实验数据，为一次性的形状变化写迁移代码，
等于把旧形状的每一条假设再养一遍。所以这件事是手工做完的，下面是当时的口径和结果：

| 现存 | 处置 | 结果 |
|---|---|---|
| `aln.db` | **保留在原处** | 记忆、审计、消息、`state` 都没动 |
| `api/server.json` | 保留 | 控制面地址与令牌，与模块形状无关 |
| 模型 provider（`models/chat/*.json`，含密钥与 profiles） | **手工包进** `modules/model.openai-chat#deepseek_official/module.json` 的 `config` | 唯一不能重新生成的东西；文件内容逐字保留 |
| `adapters/*/spec.json`、`channels/*/spec.json` | 手工包成 `modules/<id>/module.json` | 四个文件，字段一一对应；`address` 字段被丢掉（id 就是目录名） |
| `sessions/*/` | 手工搬进 `modules/<id>/`：spec 包成 `module.json`，`history.jsonl`、`state.json` 原样复制 | 历史仍在：搬完之后的一轮回答引用了搬家前说过的事实 |
| `scripts/trusted/` | 未动 | 脚本加载器还没迁到 `modules/script#…` |
| `io/`、`artifacts/`、`logs/` | 未动 | 传输目录、模型调用留档、信号日志，都与模块形状无关 |

旧的 `adapters/`、`channels/`、`models/`、`sessions/` 目录**留在原处没删**，旁边各有一份 `*.backup-<时间戳>`
的副本：搬完之后没有任何代码再读它们，删不删是数据主人的决定，不是这次迁移的一部分。

以后再出现这种形状变化，办法还是这一条：**一次性、手工、留备份**，而不是往仓库里加一个只在某一天用过的迁移器。

## 3. `id` 就是身份键：没有形状，没有别名

`id` 只有一个用途：**在边上指一个实例**。一个 `id` 属于且只属于一个实例，边上写的就是它。

### 3.1 不解析

禁止从 `id` 里读出任何结构信息：

| 想知道的 | 从哪读 | 不从哪读 |
|---|---|---|
| 它是哪个实现（怎么实例化） | `module.json` 的 `type` | ✗ `id` 的前缀 |
| 它是"实例"还是"管理器" | `type` 的实现（是否声明为单例） | ✗ `id` 里有几个 `#` |
| 它属于哪一类（频道/适配器/模型） | `type` 的类别声明 | ✗ `id` 的第二段 |
| 它是不是核心的一部分 | 它在不在核心边的那一侧 | ✗ `id` 的写法 |

今天的 `Address` 是 `kind.module#instance` 的三段式，代码里到处是 `IsInstance`、"必须形如 `channel.conversation#<id>`"
这类检查。这些检查是历史包袱：它们让**名字**变成了**结构**，于是改名就变成了改类型。目标形状里：

```
adapter.file#file-1          ← 只是名字，看不出它是从还是主，读 module.json 才知道
session#s-521035cf…          ← 同上
chat-auto                    ← 合法（只要文件系统允许），只要能唯一
```

> 为什么要走这么远：只要有一条代码路径从名字里推导出结构，那么"把名字起得好看一点"这个完全无害的愿望，
> 就会随时变成一次结构性变更。而人起名字的习惯，恰恰不是结构。

### 3.2 字符集的唯一来源是文件系统

`id` 会被用作目录名（§2），所以它的约束就是"能不能落成一个目录"：

| 约束 | 原因 |
|---|---|
| 不含路径分隔符（`/`、`\`）、不是 `.` / `..` | 否则它能指到目录外面去 |
| 不含控制字符，长度有上限 | 文件系统与日志可读性 |
| 大小写按文件系统语义 | Windows 上不敏感、Linux 上敏感，落盘前统一拒绝只差大小写的重名 |

除此之外**没有**规则：不要求分段、不要求前缀、不要求像某个类型。这些约束是"落盘"的约束，
放在装载器里，不放到"身份"的定义里——两者混在一起时，一个纯粹的文件系统限制会被误读成一个语义规则。

### 3.3 改名等于换身份

没有"改名"这个操作，只有"这个实例没了、那个实例出现了"：

- 旧的 `id` 从图上消失，所有指向它的边在 Wire 相位变成**坏边**（§5）：红日志、跳过、启动继续。
- 指向它的模块会因此少一个从——这件事必须被看见，所以是红日志而不是静默忽略。
- 将来若真的需要"改名但不断线"，那是一个**动作**（在一个事务里重写所有引用它的 `slaves` 条目），
  不是文件里的一个字段。现在不做（§9）。

### 3.4 不做别名，不做 uid

| 方案 | 为什么不做 |
|---|---|
| 别名表（`id` + `alias` → 同一个实例） | 两个键指向一个实例，就要保证两个键始终一致；而"一处不一致就指向空气"正是最贵的故障形态 |
| 内部 uid + 外部名字 | 那等于每次读文件都要查一次翻译表；而翻译表本身的 id 又需要翻译。文件里从此没有一个人能直接读懂的东西 |
| 名字里编码版本/时间戳 | 名字会腐烂，而腐烂的名字比没有名字更糟：它看起来像有信息 |

要给人看的标签放在模块自己的 `config` 里（§2.1）：标签可以随便改、可以重复、可以没有，因为它不指任何东西。

### 3.5 两种查询，不许混

| 问法 | 用途 | 例子 | 找不到时 |
|---|---|---|---|
| **按类型**：`ofType("channel.conversation")` | 找"能力"：这个系统里谁会处理频道消息 | 单例类型即"该类型唯一的那个"（`clock.system`） | 空集合，或该能力不可用 |
| **按 `id`**：`find("adapter.file#file-1")` | 指"具体哪个"：这条边、这个实例 | 边上写的那个字符串 | 坏边（§5） |

混用这两种问法会造成两类事故：用类型去指一个具体实例（"给我一个适配器"→拿到别人那个），
或用 `id` 去找能力（"名字里带 channel 的都算"→改名即失效）。所以接口上也分成两个方法，不是一个 `Find(string)`。

## 4. 生命周期：五步，一步不许省

启动不是一个"把所有东西 StartAsync 一遍"的循环。它是五个相位，每个相位的**完成条件**和**失败处理**都不同：

| 相位 | 做什么 | 并行度 | 单个失败怎么办 | 完成条件 |
|---|---|---|---|---|
| **0 Load** | 扫 `modules/*/`，读 `module.json`，校验必填字段与 `id` 唯一 | 并行读 | 这个模块不进图，记录一条红日志 | 磁盘扫完 |
| **1 Initialize** | 模块建自己的东西：连库、开文件、造句柄、读自己的 `config`。**只碰自己** | 全并行 | 该模块标记失败，其余继续 | **屏障：全部结束**（不论成败） |
| **2 Wire** | 按 `id` 解析边、拿接口对象、绑定；收集坏边；算 SCC | 单线程 | 坏边记录，跳过（§5） | 所有边都有结论（接上或坏边） |
| **3 Ready** | 按 SCC 拓扑序通知"可以开始干活了" | 同层并行，环内并行 | 该模块标记失败 | 所有实例都有结论 |
| **4 Stop / Abort** | 逆拓扑序：先停用户，再停被依赖者；每步带超时 | 同层并行 | 记一条，继续停下一个 | 全部有结论或超时 |

### 为什么 Initialize 必须是一道屏障

Wire 要按 `id` 解析接口。接口对象是**模块在 Initialize 里造出来的**——今天就是这样：
`AdapterManager` 的实例是 `CreateAsync` 造的，`ChannelManager` 的频道是 `CreateAsync` 造的。
如果 A 在 Initialize 结束前就去 Wire 它指着的 B，拿到的可能是"B 还没造出来"，而这条边会被误判成坏边。
所以：**全部 Initialize 结束（成功或失败）之后，才 Wire。** 这条是 I4（§7）。

### 为什么 Ready 按 SCC 拓扑序，而环内并行

- 依赖关系是"主就绪之前，它的从不能先开始干活"（§1.2 的 `requireAll`）。
  这是一张有向图；有环时不存在拓扑序，所以先把**环凝聚成一个点**（SCC），环内成员**并发**一起就绪。
- 环内并发不是妥协，是唯一正确的做法：A 等 B 就绪、B 等 A 就绪，串行会死锁。
- 环必须被报告（I6），因为它是"这里的启动顺序不能靠推理保证"的标记，值得一个人看一眼。

### Stop 与 Abort 的区别

| | 顺序 | 等不等 | 超时 |
|---|---|---|---|
| **Stop** | 逆拓扑序：先停用户，再停被依赖者 | 等每个模块答"停好了"（或超时） | 有，逐模块配置，默认同一值 |
| **Abort** | 不排序，谁先谁后都一样 | **不等** | 无 |

为什么要分开：进程要退出时，"有序停机"可能比"停下来"更贵。Abort 的唯一承诺是"我给过你机会"，
它不承诺清理是完整的——而这一点必须写在这里，否则停机日志会被读成"一切都干净了"。

### Error 相位

还有一个不在正常路径上的相位：模块在生命周期方法里抛出异常，或 `OnErrorAsync` 自己也失败时，
核心把它推进 `Error`（§6）。`Error` 不是"死掉"：模块可以被人手工 `ready` 一次再试，但核心**不自动重试**。

> 为什么不在生命周期里做重试：重试需要判断"这次失败是不是暂时的"，而模块抛上来的异常里没有这个信息。
> 一个猜错的重试循环会把一个可诊断的失败变成一段卡住的启动。

## 5. 宽容启动：坏边不拦路，但必须被看见

一条边在 Wire 相位只有三种结局：**接上**、**对端不存在**、**对端不实现这个接口**。后两种都是**坏边**，
处理方式是：**红日志 + 跳过 + 启动继续**。

### 5.1 为什么不拦路

因为主对从的依赖，绝大多数不是"没有它我不能活"：

| 例子 | 少一个从会怎样 | 应该拦启动吗 |
|---|---|---|
| 频道少一个适配器 | 这个频道暂时发不出去，其它频道照常 | 不 |
| 主少一个 `model.profile` | 这一轮请求失败并报出来，落库与审计照常 | 不 |
| 脚本的挂载目标不在 | 这条规则不生效，其它规则照常（今天就该这样） | 不 |
| 核心少一个存储模块 | 那才是灾难 | 这时应该由**模块自己的 Initialize 失败**说出来，而不是靠"边不存在" |

如果坏边拦启动，那么装配错误会表现成"整个系统起不来"，而人面对一个起不来的系统，第一件事是猜。
宽容启动把问题缩到最小可复现的那一格：**起得来、但这块不工作、日志里写着为什么**。

> 这里曾经定过相反的规则（坏边致命）。推翻它的是这个想法：一条边坏了，最容易修的时机是系统正在跑、
> 能就地试的时候；而"起不来"会把修的时间推到下一次启动，那时现场已经不存在了。

### 5.2 收据：启动的账本

启动结束必须返回一张**收据**，各段分开列（实例 / 边 / 坏边 / 环，外加触发节奏），不能合成一个 `ok / not ok`：

```
nodes:  14 loaded, 13 ready, 1 failed (memory.store#main: initialize threw InvalidOperationException)
edges:  9 wired
bad:    2 dropped (channel.conversation#chat-auto → adapter.file#gone: no such module)
                    (channel.conversation#chat-auto → script#reply: type does not implement IChannelSlave)
cycles: 1 (session#s-1 ↔ channel.conversation#chat-auto: ready together)
rhythm: adapter.file#file-1 200ms by Clock   ← 触发关系，一行一条（§1.4）
```

| 行 | 意思 | 人该怎么读 |
|---|---|---|
| `nodes` | 装载/就绪/失败各几个 | 失败的要有人去看那一个 |
| `edges` | 接上的边 | 数字变小通常意味着改名了 |
| `bad` | **坏边单列**，每条带原因 | 静默丢边是这套设计最不能接受的失败 |
| `cycles` | 环（SCC） | 环不是错，但它意味着"就绪顺序不能靠推理保证" |
| `rhythm` | 谁在被谁按什么间隔推 | 一行没有 = 这件事今天没人做；间隔不对先看参数 |

三条硬要求：

1. **坏边必须逐条**（谁 → 谁、哪一种坏）出现在收据里，不能只给个数。只给个数的话，
   修的人得自己去把图算一遍——而这正是收据要替他做的事。
2. **红日志**：坏边写进信号日志（`level = error`），和收据里的那条对应得上。
3. **`system.info` 给 degraded 计数**：`degraded: 2`。这是唯一一个能让"健康检查"看见坏边的数字——
   否则一个少了两个从的系统，从外面看和满配的系统一模一样。
   同一个动作还给 `nodes` / `ready` / `badEdges`（逐条）与 `rhythm`（与收据同一行文本），
   所以"现在是不是退化"不需要有人去翻启动日志。

坏边**留着**，不只是启动时返回一次：`Kernel` 把它们记在实例上，运行期新增/移除产生的也算进去
（`ModuleGraphStatus`）。只活在返回值里的坏边，等于十分钟后就没人知道它存在过。

钉住这一节的三条：`KernelTests.The_live_graph_is_what_the_receipt_said_and_not_only_a_startup_memory`（现状与收据同数）、
`KernelTests.A_source_that_refuses_a_sink_leaves_no_rhythm_behind`（拒绝挂接 → 无节奏行 + 一条 warn）、
`ControlPlaneTests.System_info_reports_the_live_graph_in_the_same_words_as_the_receipt`（外面能读到同一批数字与同一行文本）。

实例那条边另有三条：`KernelTests.An_instance_announced_before_startup_is_initialized_wired_and_counted_like_any_other_node`、
`KernelTests.An_instance_announced_while_the_graph_is_starting_gets_its_phases_and_is_in_the_receipt`（在 Ready 里宣告 ≠ 声明，
这条是**真宿主**先崩出来的：它当时丢了四个实例还报 6/6）、
`ModelConfigurationTests.A_provider_is_a_node_while_it_is_held_and_stops_being_one_when_it_is_destroyed`、
`SessionLifecycleTests.A_loaded_session_is_a_node_and_stops_being_one_when_it_is_put_away`。

### 5.3 边为什么只在这三种结局里选

不给边留第四种状态（"稍后重试"、"等对端出现"）：Wire 发生在 Initialize 屏障之后，
此刻所有模块都已经把自己造完了，对端要么在、要么不在。留一个"稍后"的窗口，就等于留一个
"这个边现在不知道算不算数"的状态，而它会在每一个读到图的地方都要被处理一次。

运行期新增模块（D1）不走这条路：那是"新建一个实例并把它的边接上"，接不上就直接报错给调用者，
不会留下一个半接的实例。

## 6. 错误处理链：抛出来，转一圈，吃掉

模块方法（生命周期方法、被主调用的从方法）抛出异常时，只有一条路：

```
模块方法抛出异常
   → 核心把它转成该模块的 OnErrorAsync(ErrorContext)
        ├─ 正常返回  → 记一条错误，模块进入 Error（§4 的 Error 相位）
        └─ 又抛 / 超时 → 核心吃掉，只记一条错误
```

**不重试、不传播、不回滚。**

| 规则 | 为什么 |
|---|---|
| 不重试 | 异常里没有"这次失败是不是暂时的"这个信息。核心猜一次，就把一个可诊断的失败变成一个卡住的循环 |
| 不传播 | 抛给上游只会让"一个模块坏了"变成"整条调用链坏了"；而上游并不比下游更知道该怎么办 |
| 不回滚 | 回滚需要事务边界，而"一条消息处理到一半"不是一个可回滚的单位。宁可留下一条明确的错误记录，让下一次读的人知道边界在哪 |
| 只记一条 | 一次失败一条记录。失败会连锁（A 失败 → B 的调用失败 → C 超时），把它们全记下来，日志会变成一个谁也读不完的雪崩现场 |

### 6.1 `OnErrorAsync` 是什么，不是什么

- **是**"这个模块对自己出错时的最后一次发言机会"：可以把内部状态标脏、可以关掉自己的句柄、
  可以决定"我还能继续"还是"我该停下"。
- **不是**上层重试的钩子，也**不是**异常的上行通道。它拿到的是 `ErrorContext`（谁调的、哪个方法、
  什么异常、什么时候），没有"上游是谁"的信息——因为它不需要知道该找谁负责。

### 6.2 为什么把"再抛"吃掉而不是让进程崩

因为进程中还有别的模块在正常工作，而一个已经出错的模块再抛一次，只是把自己知道的又说了一遍。
让核心吃掉它，规则只有一条：**失败的模块停下，其它的不受影响**——这条规则能被执行，是因为
模块之间没有共享状态（§1：模块之间不互相持有引用，只通过边上的接口调用），一条路径出问题不会污染另一条。

> 代价要说清：吃掉意味着**有些错误永远不会有人看见**，除非有人去看信号日志。
> 这是这套设计选择的交易：让故障被隔离，代价是故障必须被记录、也必须有人读记录。
> 所以错误记录的等级是 `error`，不是 `debug`，而且不可关（`06` 的"审计不可关"同理）。

## 7. 八条不变量

不变量是"任何一次改动之后都必须仍然为真"的句子。它们不是愿望，是**可以被测试钉住**的断言——
所以每条后面都跟着它将来由哪个测试证明（清单见 E1）。

| # | 不变量 | 说人话 | 违反时会发生什么 | 由谁证明 |
|---|---|---|---|---|
| **I1** | 核心边恒成立 | 每个模块都归核心管，谁都拆不掉 | 没人能让它停下 → 泄漏 | 装载器不接受没有核心边的实例（构造上不可能） |
| **I2** | 磁盘模块集合 == 内存实例集合 | 图上有的，目录里都有；目录里有的，图上都有 | 手改目录之后，跑的系统与你以为的不是同一个 | 启动后比对两边 |
| **I3** | 恢复即还原 | 两次启动，实例/边/状态/相位一致 | "重启一下就好了"成为日常，且没人知道好在哪 | 两次启动比对收据 |
| **I4** | 全部 Initialize 结束后才 Wire | 边只在大家都有东西可接的时候接 | 边被误判成坏边，或接到一个半成品句柄 | 屏障上的探针（后到的模块能看到先到的都在） |
| **I5** | 会话的主是 SessionManager | 会话归会话管理器，不归频道 | 没频道的会话（自己醒来的那种）无处可挂 | 一个没有频道的会话也能就绪 |
| **I6** | 成环允许，但必须报告 | 环不是错，"我不知道顺序"才是信息 | 环静默存在 → 某个启动顺序永远靠运气 | 收据的 `cycles` 行 |
| **I7** | 坏边只报告，不阻断 | 少一条边不会让整个系统起不来 | 装配错误变成"起不来"，诊断从"看日志"变成"猜" | 悬空边/接口不符的启动照常完成 |
| **I8** | `id` 唯一，但不参与解析 | 名字只指身份，不携带结构 | 改名 = 改类型，重构一次名字就要动一次代码 | 把 `id` 写成 `foo` 仍然按 `type` 工作 |

### 7.1 这些不变量之间不是独立的

- **I2 与 I3 一起**才成立"重启是安全的"：只有磁盘与内存一致，两次启动才可比。
- **I4 与 I7 一起**才成立"宽容启动"：先保证大家都造完了（否则宽容会掩盖真实的顺序错误），
  再让接不上的边被跳过。
- **I1 与 I5 一起**才成立"会话可以没有频道"：会话的核心边不经过频道，所以它不需要频道存在。
- **I8 单独**看像洁癖；它实际上是在保护 **I2**——只要名字能被解析成结构，
  "改个目录名"就会静默改变内存里的实例集合。

### 7.2 不在这一组里的东西

| 不是不变量 | 为什么 |
|---|---|
| "模块方法不许抛异常" | 会抛；处理方式是 §6，不靠禁止 |
| "边不许坏" | 会坏；处理方式是 §5，不靠禁止 |
| "一个从只能有一个主" | 可以是多个（§1.2 多对多）；代价是就绪条件要按边声明 |
| "启动必须是确定顺序" | 环内并发；确定性来自"同一份输入得到同一张收据"，不是来自串行 |

### 7.3 断言清单与它落在哪个测试上

每条不变量都要有一个能跑的东西钉着，否则它只是文档里的一句好话。

| # | 断言 | 落在哪 |
|---|---|---|
| ① | 两次启动同一份磁盘内容 → 同一张收据（实例/类型/相位/边数/坏边数/环数） | `KernelTests.Two_startups_of_the_same_disk_produce_the_same_receipt` |
| ② | 全部 Initialize 结束之后才 Wire（慢模块还没造完时，主看不到它） | `KernelTests.Nothing_is_wired_before_every_module_has_finished_initializing` |
| ③ | 互为主从的环**并发**就绪，且收据列出这个环 | `KernelTests.Modules_that_hold_each_other_are_ready_at_the_same_time_and_the_cycle_is_reported` |
| ④ | 悬空边 / 主方拒收 / 主方不接从 → 启动照常完成，坏边逐条可查 | `KernelTests.A_startup_with_broken_edges_completes_and_reports_each_one` |
| ⑤ | 模块方法抛错 → 走它自己的 `OnErrorAsync`；钩子再抛 → 吃掉并只记一条 | `KernelTests.A_module_that_throws_goes_through_its_own_error_hook_and_the_others_still_start`、`An_error_hook_that_throws_too_is_swallowed_and_recorded_once` |
| ⑥ | 两个模块同 id → 报冲突并保留其一，启动不因此失败 | **只能半个**：`id` 必须等于目录名，而同一目录在同一文件系统上只能有一个名字，所以本平台造不出这个冲突。已测的是它的近邻：`ModuleManifestTests.A_directory_whose_case_differs_from_its_id_is_refused_rather_than_guessed`（拒绝而不是猜），以及扫描器里给大小写敏感文件系统准备的那条去重分支（无测试，因为没有平台能跑） |
| ⑦ | `id` 写成 `foo` 仍按 `type` 工作 | `KernelTests.A_module_whose_id_says_nothing_still_works`、`KernelTests.A_type_finds_capability_and_an_id_names_one_module` |
| ⑧ | 模块结束 → 目录归档或删除，而持久数据仍在存储模块 | `KernelTests.Unloading_takes_it_out_of_the_graph_and_puts_its_directory_in_the_bin`、`ModuleDataRootTests.What_belongs_to_the_store_survives_the_directory_being_deleted` |

⑥ 是唯一一条**没有满分证据**的：它在哪个平台上都跑不出来，所以它现在的保证是"代码里有这条分支 + 相邻行为有测试"。
这条要留着——将来若有人做迁移器或跨平台同步，它就会变成能跑的。
