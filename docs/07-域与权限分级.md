# 域与权限分级

> 状态：草稿。前置：[`05-自举.md`](05-自举.md)、[`06-能力与审计.md`](06-能力与审计.md)。
> 当前 Graph 脚本主导方向见 [`13-脚本编排与工程实施蓝图.md`](13-脚本编排与工程实施蓝图.md)。本文 §5“受信脚本只能做钩子、主链硬编码”与新方向冲突，暂不作为 Graph 编排限制；信任域、能力白名单和受限域进程隔离要求仍有效。
>
> 用户提出：**脚本分内核态与用户态**——内核态只能由人定义（数据统计、消息入库这类**不希望模型去动**的东西），可访问更多资源；用户态由人或模型写，可访问大部分开放资源，但**部分内部资源不可及**。
>
> 本文把它形式化，并指出一个必须现在定的东西：**不只是脚本分域，装配表也得跟着分域。**

---

## 0. 三个域（不是两个）

| 域 | 我们叫它 | 作者 | 运行位置 | 能力 | 修改方式 |
|---|---|---|---|---|---|
| **内建** | 内建模块 | 开发者 | 主进程 | 全部机制 | 进版本 |
| **受信域** | 你叫"内核态" | **只有人** | **主进程** | 内部能力 + 开放能力 | 热重载 + 校验（人改） |
| **受限域** | 你叫"用户态" | 人 **或模型** | **子进程** | 只有开放能力 | 自举（模型可改） |

两个域的差别不是"功能多少"，而是**两件事**：谁能写、能看见什么。这两件事必须一起收，缺一个就漏。

---

## 1. 运行位置：受信在主进程，受限在子进程

这是本轮最需要定的一条。

| | 受信域 | 受限域 |
|---|---|---|
| 谁写 | **只有人** | 人 / 模型 |
| 干什么 | 数据统计、消息入库、字段映射——**每条消息都跑的热路径** | 规则判定、自定义回复——**可能被群消息诱导**的路径 |
| 代价权衡 | IPC 太贵 ⇒ **必须同进程** | 隔离值得付 IPC ⇒ **必须子进程** |

⚠️ 反过来说更清楚：**进程边界要付给"不可信的那一侧"**。把受信脚本也塞进子进程，等于让最热的路径背 IPC；把受限脚本留在主进程，等于让最不可信的代码和内核同住。

---

## 2. 域的边界怎么落实（全部结构性，不靠纪律）

1. **路径不在 agent 可写范围内。** `IWorkspace` / `IStorage` 的 scoped 根**不覆盖**内核域脚本目录。⇒ agent 物理上写不了受信脚本，不靠"它答应不写"。
2. **跨域分引擎。** Jint 官方要求"across trust domains use a fresh engine"；两个域用不同的 options（受限域用硬化工档，受信域用常规档）。
3. **能力注入按域白名单**（见 §3 矩阵），未列即无。
4. **装配表也分域**（见 §4）。

---

## 3. 能力怎么打包：拓展（extension）

**能力的单位不是"域的特权"，也不是"端口"，而是拓展**——一个能力包，由 host 实现、按接口暴露。

| 拓展 | 内容 | 等级 |
|---|---|---|
| `file` | `IWorkspace`（scoped 路径：前缀绑定 + 限额） | 开放 |
| `net` | `AllowlistHttp`（域名 / 方法白名单） | 开放 |
| `msg` | 出站投递（仅本频道、限条数） | 开放 |
| `clock` | 确定性时钟 | 开放 |
| `store` | 内部存储读写 | **内部** |
| `state` | 内部状态读（游标 / 队列 / 会话状态） | **内部** |
| `secret` | 密钥引用（受信只能引用，内建才能读明文） | **内部** |
| `ssh` | 白名单主机远端执行 | **内部** |

三条规则：

1. **域是上限，不是答案。** 受限域**最多**只能拿"开放"级拓展；受信域可拿开放 + 内部。**域不直接决定"给不给网络"。**
2. **模块自己声明需求**：模块/脚本在清单里写 `requires: [file, net]`；**未声明即无**（默认拒绝），声明了还要过装配。
3. **装配决定授予**（谁签字）：内核域装配（人写）可批内部级；用户域装配（自举）**只能在开放级里选**。

⇒ 你那句话的准确版本：**网络是拓展；"开放给谁"不是域的问题，是装配（谁签字）的问题。**

红利很直接：**加一个新能力 = 加一个拓展，域模型一个字不用改。** 域只有三档、几乎不动；拓展可以一直长。

⚠️ **"受信"不等于"万能"**：受信域也拿不到 shell（`X-13` 是全系统级作废项），读密钥也只能拿引用。**受信域的特权是"内部数据面"，不是"OS 面"。**

---

## 4. 装配表必须跟着分域（否则整条边界漏掉）

如果装配表只有一份、且模型可改，那么模型只要把**受信脚本**接到别的事件上，就能借它的内部能力做别的事——**这就是权限提升**，虽然脚本没变、能力没变。

所以：

| | 内核域装配 | 用户域装配 |
|---|---|---|
| 谁写 | **只有人** | 人 / 模型（自举） |
| 能指向 | 任何端口、任何脚本 | **只有用户域成员** + "开放的内部端口白名单"（如 `channel.post`） |
| 何时生效 | 进版本 / 人显式批准 | 自举闭环（校验 → 装配版本 → 生效） |
| 冲突 | 内核域优先 | 同名以内核域为准 |

⇒ **自举的准确形态**：模型能改的是"用户域装配 + 受限脚本"，改完走装配版本。它**加不了能力，也借不到能力**。

---

## 5. 受信脚本的正确用法：钩子，不是主链

这一条是性能与可预测性的纪律，容易被忽略：

- **主链硬编码**（接收 → 去重 → 入库 → 触发），快、可预测、可测试；
- **受信脚本挂在钩子上**（`before_put` / `after_intake` 这类），做字段映射、统计聚合、补充条件。

⚠️ 反例：把"消息入库"整条链写成受信脚本——每条消息都要过解释器，还丢了类型检查与调用链可见性。**如果某个钩子最终变成了主链，说明它该进代码（内建模块）。**

判据：**脚本做"同一件事的可配置变体"，不做"这件事本身"。**

---

## 5.1 生效方式：一律显式触发（不做自动加载）

（用户裁定：受信脚本**必须手动触发**重载，防止"改一半被自动加载直接爆炸"。）

| 对象 | 生效方式 |
|---|---|
| 受信脚本 | **人手动触发重载**（显式命令）；**不做文件监视** |
| 受限脚本 | 自举闭环：显式 `apply`（校验全绿才替换） |
| 装配表 | 显式 `apply` |
| 拓展 | 进版本（随发布）或人显式重载 |

每次生效是**原子的**：编译 / 校验全部通过 → 一次性替换 → **失败则保持旧版并告警**，绝不部分生效。

理由两条，都很硬：

1. **文件监听 + 自动加载 = 把"半写状态"直接送进运行系统**。编辑器保存到一半、多文件改动中间态都会触发；出问题时现场已经没了。
2. **"自动生效"这个默认值一旦存在，就没人说得清现在跑的是哪一版**——这正是 `X-08`（开关矩阵自发漂移）的同一形态。

⇒ 一条通用纪律：**任何装、改、生效，都必须是显式动作，并留下一个可回滚的装配版本。**

## 6. 审计分档

| 域 | 记录粒度 |
|---|---|
| 受限域 | **每次能力调用一条**（谁、什么能力、什么对象、结果、输入源） |
| 受信域 | **每次脚本执行一条**（行为级）+ 能力调用计数与失败计数 |
| 拒绝（任意域） | **一律单独一条**：未授予 / 越界 / 限额 / 超时 |

理由：受信域是人写的、热路径上高频，逐次能力调用会淹没日志；但**它的失败与越界必须显式**，否则"受信"变成"无人看管"。

---

## 7. 命名：已定

**受信域 / 受限域**（用户裁定）。文档里不再使用"内核态 / 用户态"作为正式术语，只在[本文开头](07-域与权限分级.md)保留一次对照，说明它们指同一件事。

理由：正式术语取"信任"这个真正的判据，避免与"内核（常驻进程 / 机制层）"撞词。
