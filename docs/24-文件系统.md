# 24 · 文件系统：模型能碰的那一半磁盘

> 本文回答一个问题：**一个模型可以改文件，怎么让"它能碰哪些目录"是一处决定，而不是散落在各个模块里的约定。**

---

## 0. 一句话

模型不碰 `System.IO`。它通过一组工具操作**受控文件系统**：`scope`（宿主登记过的名字）+ **相对路径**。
越权是 `Denied`，路径写错是 `Invalid` 且指出哪一段——**拒绝，从不改写**。

---

## 1. 为什么要有它

在它之前，写盘的东西各写各的：信号日志、模型调用原文、文件邮箱、会话目录。对**宿主自己调用的代码**，这没有问题。
一旦"模型可以改它"出现，问题就来了：

- 谁能碰哪些目录，会变成 N 个调用点各自记得的一条约定；
- 每个想"顺便让模型也能编辑"的模块，会长出自己那套略有不同的路径检查；
- 路径穿越、软链接、Windows 保留名这类事，会被重新发现一遍。

所以只有一个端口、一套路径规则、一处"哪些目录可达"的登记。

---

## 2. 两个名字

| 词 | 是什么 | 例子 |
|---|---|---|
| **scope** | 宿主登记过的一个根目录，名字是一段合法路径 | `memory`、`workspace` |
| **路径** | 相对那个 scope 的路径，用 `/` 分段 | `关系-小林/block.md` |

契约不认识真实路径：`scope` 只是名字，根目录由宿主登记（`<dataRoot>/<scope>/`）。
于是"这台机器上数据放哪"是宿主的事，"这个模块能碰哪"是登记的事，两者都不进模块的代码。

---

## 3. 两种拒绝，不能混

| 情形 | 码 | 给谁看 |
|---|---|---|
| scope 不在这个调用方允许的清单里 | `Denied` | 不是笔误，是一次越权。给调用方列出它**可以用**的 scope |
| 路径不合法：绝对路径、`..`、任何一段是 `.`、空段、Windows 保留名、控制字符、以点开头、以空格或点结尾、盘符 | `Invalid` | 是笔误，**指出是哪一段错**——模型能当场改对 |

把两者混成一个"失败"，模型会拿越权去试错；把 `Invalid` 只报一句"denied"，它会把同一句再试一遍。

**拒绝而不是改写**：把 `a/b` 改成 `a_b` 会让两个不同的名字在磁盘上撞成一个，而调用方永远不知道自己得到了哪一个。
这条政策和 `ModuleId`、记忆组名是同一条。

---

## 4. 白名单从哪来

文件系统模块是一个**由 `module.json` 构建的模块**：`<dataRoot>/modules/filesystem.local/module.json` 里

```json
{"scopes":["memory"]}
```

- 只写一个 scope 的人，就只开放这一个；**没有配置就什么都不开放**（缺席的默认是"没有授权"，不是"全给"）。
- 配置里写了一个没登记的 scope → **启动即失败并列出已登记的**。悄悄丢掉它，症状会和"模型手里没有文件"一模一样。
- 宿主第一次启动会写一份默认的 `module.json`，四个区：`memory`、`workspace`、`scripts/draft`、`media`。之后
  **永不重写**：从那以后白名单是人在文件里写的值（`C-03`）。
- **`media` 是后加的一项**，这一条值得单独说：`media` 出现之前就存在的 dataRoot，它的 `module.json` 里没有这一
  项，而宿主**不会**替它补上。启动时 `stderr` 会打一行，说清缺了哪个 scope、该去 `config.scopes` 里加。不补的后
  果不是"少一个目录"：图片回执里那句「要看就用 `fs_read` 打开它」会变成一句走不通的话，而症状——模型坚持说它看
  不见图片——与「图根本没到」（`16 §12.1.1`）一模一样。这个项目已经为此付过一次代价。

三个默认成员各有各的理由，都不是"顺手多给一个"：

| 区 | 是什么 | 为什么默认给 |
|---|---|---|
| `memory` | 记忆库（一组组片段 + 每组的 block） | 记忆本来就是一组文件（`21 §5`），模型要用这七个工具整理它 || `workspace` | **工作目录**：摘录、算到一半的结果、生成的中间文件、给人看之前的草稿 | 不给它一个地方，杂活就会写进它手上唯一能写的那个区——也就是记录。工作目录是"删光也不心疼"的房间，所以可以放手让它在里面干 |
| `scripts/draft` | 脚本草稿（`scripts/trusted` 的隔壁，不是同一个） | 写脚本要一个能写的地方，而"写在草稿里"必须是"还没生效"的意思（`25`） |
| `media` | 别人发来的图、语音、文件，和模型自己产出的图（`28`） | **只读**：记录里写着"我看过这个文件"，能改它就能改"我记录里看过什么"。宿主写，模型读 |

`media` 是唯一一个**只读**的成员：它在 `scopes` 里（模型能 `fs_list` / `fs_read`），
但端口的 `readOnlyScopes` 让四个写工具对它一律 `Denied` 并列出可写的 scope（`docs/28 §2`）。

`workspace` 与其他区在端口眼里完全一样：同样的路径规则、同样拒绝 `..` 与链接。不一样的只是**含义**——
这台进程里没有任何东西读它，所以模型可以随便写、随便删；它的内容是草稿，不是事实。

---

## 5. 工具

| 工具 | 做什么 | 注意 |
|---|---|---|
| `fs_tree` | 一棵子树（相对路径 + 字节 + 时间，含目录） | 空路径 = scope 根；超过 2000 个节点报错而不是悄悄截断 |
| `fs_list` | 一层目录 | 目录不存在是错误，不是"空目录"——两者是不同的 事实 |
| `fs_read` | 读一个文本文件 | **不存在 → 说"不存在"**，不是空文件；非 UTF-8 / 含 NUL → 拒绝，不猜 |
| `fs_write` | 整篇写（覆盖），父目录自动建 | 临时文件 + rename + fsync：读者只会看到旧版或新版 |
| `fs_append` | 追加，父目录自动建 | 同一个文件上的追加**串行**：一次调用的文本是一整段，不会和另一次交错 |
| `fs_move` | 改名/移动 | 目标已存在 = `Conflict`；目标的父目录必须存在 |
| `fs_remove` | 删文件，或删目录（`recursive`） | 非空目录不给 `recursive` = `Conflict`：删掉的子树要不回来 |

七个工具**都不"对外办事"**（`ActsExternally = false`）：一条只整理了文件的回合没有对任何人说话，
会话循环据此判断这一回合的文本是不是它的回复（`08 §5.1`）。

---

## 6. 什么走它，什么不走

| 走它 | 为什么 |
|---|---|
| 记忆库（`memory`） | 模型要整理它 |
| 工作目录（`workspace`） | 模型要有个地方干杂活：草稿、摘录、中间产物。这是它唯一可以随便写随便删的区 |
| 脚本草稿（`scripts/draft`） | 写的脚本在被人批准之前住在那里（`25`） |
| 以后的插件数据 / 脚本产物 | 同上：模型能读能改的东西 |

| 不走它 | 为什么 |
|---|---|
| 会话目录、信号日志、模型调用原文、文件邮箱 | 不是模型能读能改的对象：只有宿主写，或只写不可枚举。把它们迁进来是无收益的爆炸，而且会让"模型能碰的范围"变得难以解释 |

判断标准只有一条：**这个东西的形状是不是模型的责任。** 是 → 走受控面；不是 → 宿主自己拿着。

---

## 7. 落点与保证

- 位置：`<dataRoot>/<scope>/…`；scope 根在启动时建好，所以"空 scope"是一个可回答的问题。
- 包含性：绝对路径在计算出来之后还会再校验一次是否在 scope 内，并且**拒绝 reparse point / 软链接**
  （scope 里出现链接 → 该目录列不出来，并说明原因）。
- 原子性：写 = `.tmp` + rename；追加 = 每文件一把锁 + `Flush(flushToDisk: true)`。
  一次成功意味着这个文件扛得住断电，不只是扛得住进程退出。
- 文本：只接受 UTF-8；单文件 4 MiB 上限；读取超过 32 000 字符由调用方（工具）截断并声明截断位置。

---

## 7.1 字节面：`IBinaryFileAccess`

文本面只吃 UTF-8，这是对的——它是"模型能读回来整理"的东西。但**"模型只能写文本"和"模型只能在机器之间搬文本"
不是同一条规则**：搬一个 tarball、一张图、一个编译产物是正常需求，而且字节**根本不需要经过模型的上下文**。
所以字节有自己的契约（`IBinaryFileAccess`），由同一个 `LocalFileSystemAccess` 一并实现：

| 规则 | 内容 |
|---|---|
| 哪些区收字节 | 只有**显式登记**为字节区的 scope（`new LocalFileSystemAccess(root, scopes, binaryScopes)`）；宿主默认给 `workspace` 与 `media` |
| 路径 | 与文本面完全相同：scope + 相对路径，拒绝绝对路径、`..`、链接 |
| 上限 | 单次 64 MiB（`MaxTransferBytes`）；超了**拒绝**，不截断 |
| 上限（流式读，另一条路） | `OpenReadStreamAsync(scope, path, ceiling)`：同一套 scope 与路径规则，上限由**调用方**说。它存在的理由是这个数回答的是"一次**搬运**多大"（ssh 拉一个包、工具挪一个 tar），而"把一份文件交给一个往外发的 socket"根本不是搬运 —— 字节从磁盘到 socket，本进程只占一个缓冲区（[`28 §6.6`](28-媒体与图片.md)） |
| 原子性 | 临时文件 + rename，读者只会看到旧版或新版；写超限时临时文件被删掉 |
| 读 | 流式（`FileShare.Read`，不许有人同时写）；调用方负责 Dispose |
| 写 | 流式（`SaveAsync(scope, path, Stream)`），从不把整份内容塞进内存 |
| 谁在用它 | `ssh_put` / `ssh_get`（见 [`27 §6.1`](27-SSH.md)）、媒体入库与出站发图/发文件（见 [`28`](28-媒体与图片.md)）、`fs_read` 出图（读头部判断"这是图片"）、媒体门（`docs/28 §6.6.1`）；`fs_*` 七个工具**不改**，仍然只碰文本 |

**`BinaryScopes` 是"哪些东西能出去"的唯一答案。** 媒体门问它（不再自己写一份 `media`+`workspace` 的名单），
`speak` 的 file 块问它，`ssh_put` 问它。所以 `memory` 与 `scripts/draft` 发不出去，不是因为某个功能加了禁令，
而是因为它们本来就不接收字节 —— 一条规矩，问一次（[`28 §6.6.3`](28-媒体与图片.md)）。

为什么不让 `fs_*` 直接支持字节：那会让"模型可以随便写的东西"与"模型读得懂的东西"变成同一个集合，
而 `workspace` 存在的理由恰恰是后者不必对前者成立。`fs_read` 打到图片时不报"不是 UTF-8"，
而是**说这是什么、把引用带回去**——但那仍然不是"工具能写字节"。

---

## 8. 明确不做

| 不做 | 为什么 |
|---|---|
| 工具层的二进制读写 | 这是"模型可以整理的文字面"。字节有它自己的入口：`ssh_put` / `ssh_get`、媒体入库、出站发图——都不经过 `fs_*` 的写路径（见 §7.1） |
| 让模型写 `media` | 只读是它的定义：记录里写着"我看过什么"，能改它就能改记录 |
| 权限位 / 可执行 | 不在这一层的问题里：能写就等于能毁，位置隔离才是边界 |
| 跨 scope 移动 | 一次一个 scope：跨根移动是"复制还是迁走"这种要靠人决定的事 |
| 版本 / 历史 / 回收站 | 删除就是删除；需要历史的场景（会话、频道）自己有归档 |
| 自动清理 | 见 `09 §8`：留存默认永久，清理接口显式触发 |
