# 24 · 文件系统：模型能碰的那一半磁盘

> 本文回答一个问题：**一个模型可以改文件，怎么让"它能碰哪些目录"是一处决定，而不是散落在各个模块里的约定。**

---

## 0. 一句话

模型不碰 `System.IO`。它通过一组工具操作**受控文件系统**：`scope`（宿主登记过的名字）+ **相对路径**。
越权是 `Denied`，路径写错是 `Invalid` 且指出哪一段——**拒绝，从不改写**。

---

## 1. 为什么要有它

在它之前，写盘的东西各写各的：信号日志、模型调用原文、文件邮箱、会话目录。对**宿主自己调用的代码**，这没有问题。
一旦"模型可以改它"出现，问题就来了：

- 谁能碰哪些目录，会变成 N 个调用点各自记得的一条约定；
- 每个想"顺便让模型也能编辑"的模块，会长出自己那套略有不同的路径检查；
- 路径穿越、软链接、Windows 保留名这类事，会被重新发现一遍。

所以只有一个端口、一套路径规则、一处"哪些目录可达"的登记。

---

## 2. 两个名字

| 词 | 是什么 | 例子 |
|---|---|---|
| **scope** | 宿主登记过的一个根目录，名字是一段合法路径 | `memory`、`workspace` |
| **路径** | 相对那个 scope 的路径，用 `/` 分段 | `关系-小林/block.md` |

契约不认识真实路径：`scope` 只是名字，根目录由宿主登记（`<dataRoot>/<scope>/`）。
于是"这台机器上数据放哪"是宿主的事，"这个模块能碰哪"是登记的事，两者都不进模块的代码。

---

## 3. 两种拒绝，不能混

| 情形 | 码 | 给谁看 |
|---|---|---|
| scope 不在这个调用方允许的清单里 | `Denied` | 不是笔误，是一次越权。给调用方列出它**可以用**的 scope |
| 路径不合法：绝对路径、`..`、任何一段是 `.`、空段、Windows 保留名、控制字符、以点开头、以空格或点结尾、盘符 | `Invalid` | 是笔误，**指出是哪一段错**——模型能当场改对 |

把两者混成一个"失败"，模型会拿越权去试错；把 `Invalid` 只报一句"denied"，它会把同一句再试一遍。

**拒绝而不是改写**：把 `a/b` 改成 `a_b` 会让两个不同的名字在磁盘上撞成一个，而调用方永远不知道自己得到了哪一个。
这条政策和 `ModuleId`、记忆组名是同一条。

---

## 4. 白名单从哪来

文件系统模块是一个**由 `module.json` 构建的模块**：`<dataRoot>/modules/filesystem.local/module.json` 里

```json
{"scopes":["memory"]}
```

- 只写一个 scope 的人，就只开放这一个；**没有配置就什么都不开放**（缺席的默认是"没有授权"，不是"全给"）。
- 配置里写了一个没登记的 scope → **启动即失败并列出已登记的**。悄悄丢掉它，症状会和"模型手里没有文件"一模一样。
- 宿主第一次启动会写一份默认的 `module.json`（只含 `memory`），之后**永不重写**：从那以后白名单是人在文件里写的值（`C-03`）。

`memory` 是第一个成员，因为记忆本来就是一组文件（`21 §5`）：模型用这七个工具整理记忆，
记忆模块不必再为"折叠 / 归档 / 合并 / 删除"各长一个工具。

---

## 5. 工具

| 工具 | 做什么 | 注意 |
|---|---|---|
| `fs_tree` | 一棵子树（相对路径 + 字节 + 时间，含目录） | 空路径 = scope 根；超过 2000 个节点报错而不是悄悄截断 |
| `fs_list` | 一层目录 | 目录不存在是错误，不是"空目录"——两者是不同的 事实 |
| `fs_read` | 读一个文本文件 | **不存在 → 说"不存在"**，不是空文件；非 UTF-8 / 含 NUL → 拒绝，不猜 |
| `fs_write` | 整篇写（覆盖），父目录自动建 | 临时文件 + rename + fsync：读者只会看到旧版或新版 |
| `fs_append` | 追加，父目录自动建 | 同一个文件上的追加**串行**：一次调用的文本是一整段，不会和另一次交错 |
| `fs_move` | 改名/移动 | 目标已存在 = `Conflict`；目标的父目录必须存在 |
| `fs_remove` | 删文件，或删目录（`recursive`） | 非空目录不给 `recursive` = `Conflict`：删掉的子树要不回来 |

七个工具**都不"对外办事"**（`ActsExternally = false`）：一条只整理了文件的回合没有对任何人说话，
会话循环据此判断这一回合的文本是不是它的回复（`08 §5.1`）。

---

## 6. 什么走它，什么不走

| 走它 | 为什么 |
|---|---|
| 记忆库（`memory`） | 模型要整理它 |
| 以后的工作区 / 插件数据 / 脚本产物 | 同上：模型能读能改的东西 |

| 不走它 | 为什么 |
|---|---|
| 会话目录、信号日志、模型调用原文、文件邮箱 | 不是模型能读能改的对象：只有宿主写，或只写不可枚举。把它们迁进来是无收益的爆炸，而且会让"模型能碰的范围"变得难以解释 |

判断标准只有一条：**这个东西的形状是不是模型的责任。** 是 → 走受控面；不是 → 宿主自己拿着。

---

## 7. 落点与保证

- 位置：`<dataRoot>/<scope>/…`；scope 根在启动时建好，所以"空 scope"是一个可回答的问题。
- 包含性：绝对路径在计算出来之后还会再校验一次是否在 scope 内，并且**拒绝 reparse point / 软链接**
  （scope 里出现链接 → 该目录列不出来，并说明原因）。
- 原子性：写 = `.tmp` + rename；追加 = 每文件一把锁 + `Flush(flushToDisk: true)`。
  一次成功意味着这个文件扛得住断电，不只是扛得住进程退出。
- 文本：只接受 UTF-8；单文件 4 MiB 上限；读取超过 32 000 字符由调用方（工具）截断并声明截断位置。

---

## 8. 明确不做

| 不做 | 为什么 |
|---|---|
| 二进制读写 | 这是"模型可以整理的文字面"，二进制有别的归属 |
| 权限位 / 可执行 | 不在这一层的问题里：能写就等于能毁，位置隔离才是边界 |
| 跨 scope 移动 | 一次一个 scope：跨根移动是"复制还是迁走"这种要靠人决定的事 |
| 版本 / 历史 / 回收站 | 删除就是删除；需要历史的场景（会话、频道）自己有归档 |
| 自动清理 | 见 `09 §8`：留存默认永久，清理接口显式触发 |
