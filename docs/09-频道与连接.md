# 频道与连接

> 状态：草稿。用户给定的主定义：**频道连接多个适配器、被会话连接**。
>
> 频道出现的两个理由：
> 1. **Adapter 可能冗余**：同一平台可以接多条连接。频道**默认只用主适配器收发**，主异常才切副；副照常接收并自行留存，用来兜底而非常态并行。
> 2. **Adapter 行为不一**：不同平台的数据与动作形状不同，需要频道把它们统一成会话可消费、可发送的公共形状。
>
> 本章的目标是把这个边界讲清。回执形式、切换窗口等没足够依据的细节明确列为待定，不伪装成已决定。

---

## 0. 一句话

> **一个 Channel 只归属一个平台的一条逻辑对话**（如 QQ 群）。多个 Adapter 实例可以接入同一 Channel，作为冗余入口与主备出口；不同平台的协议差异由各自 Adapter 归一成公共形状，但**不把 QQ 群与 Discord 房间合成同一个 Channel 实例**。

```text
平台 A ⇄ adapter.a ─┐                   ┌─ Session.Chat#x
                     ├─ Channel.Conversation#… ──┼─ Session.Chat#y
平台 B ⇄ adapter.b ─┘                   └─ Session.Chat#z
```

这是**逻辑拓扑**，不表示模块之间直接持有引用：任何跨模块动作仍由图的订阅/调用边连接（`02` §2；`X-09`）。

**连接是显式的、而且多对多**：Adapter 只广播"我收到了什么"，**不知道谁在听**；每个 Channel 用自己持有的绑定键（`adapterInstanceId` + `platformConversationId`）判断"这条是不是我的"，不是就丢弃（§3）。

### 0.1 唯一模块、模块类与实例

按前面定下的模块形状：

- `ChannelManager` 是唯一模块（单例），管理所有 Channel 实例；
- `Channel.Conversation` 是模块类，规定逻辑消息流、身份映射与读写函数；
- 每个实例（`Channel.Conversation#…`）是一个逻辑对话，可以挂接多个 Adapter 实例，也可以被多个 Session 实例连接。

Channel **不保存 Adapter / Session 对象引用**。连接关系以图/装配数据表示；管理器只管理自己的 Channel 实例，不替图保存跨模块对象引用。

## 1. 为什么不能让 Session 直接连 Adapter

| 如果 Session 直连 Adapter | 会出现什么 |
|---|---|
| 同一个逻辑对话接两个 Adapter | Session 要认识两条连接的账号、限流与故障切换 |
| 两个 Adapter 上报同一条消息 | 每条连接的消息形状不同，Session 得自己分辨 |
| 由一个 Adapter 切换到另一个 | 会话持有的平台引用需要迁移；旧连接语义容易泄漏到新路径 |
| Session 要向外发送 | 每个 Session 都得实现平台分支、失败处理和目标选择 |

**Channel 收拢的正是这条边界**：同一逻辑对话只呈现一条规范化消息流；下游 Session 不需要知道消息由哪个平台、哪个 Adapter 实例接到。

## 2. 三层消息形状：原始 → Adapter 规范化 → Channel 逻辑消息

归一化与消息留存不能一股脑全塞进 Adapter，也不能让 Channel 直接解析各平台原始报文。划分如下：

### 2.1 Adapter 负责平台到通用传输事件

Adapter 读取平台协议并产出一个通用的 `AdapterEnvelope`：

```text
AdapterEnvelope
  adapterInstanceId
  platformId
  platformConversationId
  platformEventId / platformMessageId（若平台提供）
  sender / timestamp / content parts / platform flags
  rawPayloadRef（可选；原始字节留在 AdapterStore）
```

Adapter 负责**协议层清洗**：字段解析、平台事件类型识别、附件取数与引用、时间戳转换、平台错误与断线处理。它不决定“这条消息是否与另一个 Adapter 的消息重复”，因为它看不到其它 Adapter 的观察结果。

### 2.2 Channel 负责跨 Adapter 的逻辑归一

Channel 把一个或多个 `AdapterEnvelope` 归到逻辑会话空间，产出 `ChannelMessage`：

```text
ChannelMessage
  channelId
  canonicalMessageId
  canonicalSender
  canonicalTimestamp
  canonical content parts
  reply / thread / edit / delete 等可选语义
  observedBy[]（来源 Adapter 与平台事件引用）
```

Channel 负责：

- **归属校验**：判定这条消息属于哪个逻辑 Channel；
- **逻辑身份映射**：平台用户 / 群组 / 频道身份映射到该 Channel 的身份。**落点见 [`31-身份.md`](31-身份.md)**：`(adapter, 平台账号) → 人` 是一张人手写的表，Channel 收到消息时查一次，把人的 id 连同消息一起留下；公式本身没有变，变的是这条映射终于有了一个地方；
- **公共消息形状**：将平台差异转换为 Session 面统一模型；
- **来源保留**：记录哪个 Adapter 送达、哪些平台 id 能定位原消息（诊断与对账用）；
- **下游读取**：让已连接的 Session 用自己的游标各自读取，不让 Channel 持有单个消费者的读取位置。

⚠️ **Adapter 规范化与 Channel 归一化是两层**：前者回答“平台发来了什么”；后者回答“这在这条逻辑流里算什么”。

### 2.3 多适配器 = 多账号：身份是一条连接的属性

（用户裁定：**多适配器本身就是为多账号而生的**，这部分要明确。）

一条 Adapter 连接对应**一个平台登录身份**，不只是"一条网络通道"：

```text
AdapterInstance
  platformId      : qq
  accountId       : 某个具体账号（主号 / 备用号 / 小号）
  priority        : 在该 Channel 上的候选顺序
  capabilities    : 这个账号能做什么（发言 / 私聊 / 发图…）
```

五条由此产生的硬规定：

1. **`(platformId, accountId)` 全局唯一**：同一账号被两个 Adapter 实例同时登录，多数平台会互相踢下线。这是**加载期校验**，不是运行期祈祷。
2. **主备跨账号是设计目的，不是待定项**：主号掉了切副号——群里看到的是**另一个号在说话**。这是被接受的行为，必须在切换事件里记明（`from: accountId` / `to: accountId`），否则事后没人解释得清"为什么这句话换了个头像"。
3. **"自己发的"按身份判定，不按"是不是主"判定**：Channel 维护本 Channel 名下的账号集合 `botIdentity[]`；只要发送者身份落在这个集合里，回声就标 `self`——**副号发的回声也是 `self`**，哪怕它当时不是主。
4. **回执必须带 `adapterInstanceId`（或 `accountId`）**：同一条 Channel 上有多个身份能发，模型必须分得清"是主号发出去了还是副号"。没有这个字段，"重发"与"已发"就分不开（§6.2 约束 1 的前提）。
5. **`self` 回声不激活任何 Session**：它只用于回执、统计与对账。若回声能激活会话，bot 的每句话都会推着会话空转一步——这是自激的第二条入口（第一条是 §6.3 的不进模型上下文）。

⚠️ **切换窗口里 `self` 判定仍然成立**：副号连接在切换前就看到了主号发的消息并自行留存；切过去后若补交，那些"已经由主号投递过"的消息会以 `self` 身份再出现一次。既然常态不去重（§4），这里**不建去重表**，靠 `self` 不激活会话把危害压到零，`observedBy[]` 留痕供对账。

⚠️ **Session 对账号仍然无感**：它只连逻辑 Channel（§5），多个账号的差异在 Channel 内被消化成 `canonicalSender`。但**权限判定要看到账号**（`06`「权限随来源降级」）：备用号通常不该拥有主号的全部授权，来源标识里必须带 `accountId`，不能只带 `channelId`。

### 2.4 适配器是什么、不是什么；频道暴露又要多小

#### 识别判据（三条；方向不是判据）

| 判据 | 不满足时它是什么 |
|---|---|
| 1. 有外部对端，并且要说它的协议 | 内部模块 |
| 2. **有需要被维护的通道状态**（连接 / 重连 / 缓冲 / 游标 / 限流节奏） | 工具 / 能力（一次性调用） |
| 3. **至少具备一个方向**（能收、能发，或两者） | 不是 Adapter |

一句话：**Adapter 是一条有名字、有身份、需要被维护的外部通道，至少有一个方向。**

⚠️ **方向是能力，不是残缺**——这一条改掉了上一版的"必须有入站"：

```text
IInbound      { receive }                    只收：RSS、webhook、邮件收件、目录投递
IOutbound     { describe, send }             只发：指标上报、告警推送、日志汇集
IChatAdapter  = IInbound + IOutbound         双向：聊天平台
```

上一版把"对端会主动推东西过来"当判据，于是只有出站的通道（它有缓冲、有重连、有批量节奏）被判成了"工具"——那不对。**判据是"要不要被维护"，不是"朝哪个方向"。**

一个 Adapter = **一个身份 / 端点 + 一条连接**（不一定是账号：RSS 是一个订阅源，指标上报是一个目的端）。

- **是**：聊天平台连接（双向）、外部事件源（webhook / RSS / 邮件 / 目录投递，只收）、指标与告警的推送端（只发）。
- **不是**：HTTP 工具、SSH、定时器、文件与数据库、子会话、本地命令执行（`X-13`）、命令解析（那是 logic / 模块的活）。

#### Channel 收缩：只绑双向

（用户裁定：**适配器定义扩展，但频道收缩——频道只能绑定双向适配器**。）

```text
Channel 的绑定集合里，每个 Adapter 必须是 IChatAdapter（两个方向都有）
  绑到单向 Adapter ⇒ 装配错误，加载期拒绝
```

三条推论：

1. **Channel = 双向对话的一条逻辑流**，这是定义，不是它的某个可选属性。
2. **工具集因此恒定**：`speak` / `history` / `pending` 永远都在——不存在"只收频道没有 `speak`"这种分支。
3. **单向 Adapter 的消费者不是 Channel**：只收的，谁订阅 `adapter.envelope` 谁处理（模块 / 图）；只发的，谁拥有那个 `send` 谁调用。它们不经过 Channel 的归一、身份映射与游标。

⚠️ 这条收缩是**刻意的**：Channel 承担"归一 + 身份映射 + 游标 + 持久化屏障"，这四件事只在"双向对话"里**同时**成立。让单向数据流也进 Channel，等于给它加一堆"这条流没有发送方 / 没有发言人"的特判——正是它在做减法时要避免的东西。

#### 通用面只有两个：收与发

（用户裁定：**频道暴露本身最好足够基础，甚至极端情况只剩下收发也行；其余功能不通用都走特殊行为**——不通用就明确不提供，成本不会太高，代码干净很多。）

```text
通用接口（每个 Adapter 必须实现，且没有"替代实现"这回事）
  receive   入站：adapter.envelope 广播（§3）
  send      OutboundMessage → SendResult
```

**Adapter 接口就这两个。** 上一版要求"覆盖 8 个 ActionKind、各自给 native / fallback / noop"，**已推翻**：那等于逼迫每个平台为它做不到的事编一层假实现（还要检测 fallback 环），代码反而脏。

**为什么这两个必须通用**：所有对话都只有这两件事，差的只是协议细节（切段、上传、转义、限流），而那些全部藏在 Adapter 内部（§6）。

#### 通用工具：收发，加"读频道自己的历史"

上面那"两个"是 **Adapter 接口**的方法数。**工具层**还有一个不经过 Adapter 的通用能力：

| 工具 | 做什么 | 依赖 |
|---|---|---|
| `speak` | 往逻辑频道发消息（Channel 选路、走健康与额度） | 任一可用 Adapter 的 `send` |
| `history` | 读**频道自己保存的**历史（ChannelStore，按游标分页） | 只依赖 ChannelStore |
| `pending` | 取异步结局 / 在飞任务快照（`08 §5.3`） | 不依赖平台 |

（用户裁定：**拉取历史消息是可用的通用工具，因为它完全可以拉取频道自己保存的历史；拉取平台消息是适配器功能。**）

`history` 之所以通用：它读的是 ChannelStore 里**已 accepted** 的消息，与"哪个平台、连没连上、用的是哪个号"全都无关。而**拉平台侧的历史**（平台 API 里的旧消息）不是通用能力，它是下面那个工具里的一个动作。

#### 越过频道时：一个 `adapter` 工具，逐层展开

（用户裁定：**会话试图越过频道操作时，本质上是在调用适配器操作工具，而不是频道暴露**；它暴露得足够底层——**目标适配器 id、动作、参数**；**没给 id（或 id 错）就报出所有适配器（以及与本频道有关的适配器）；没给动作（或错）就打对应适配器的动作列表；以此类推**。）

特殊行为因此**不是"一个动作一个工具"**，而是一个工具的分层调用：

```text
adapter()                          → 列出全部适配器（标出与本频道有关的）
adapter(adapterId)                 → 列出该适配器支持的动作
adapter(adapterId, action)         → 该动作的参数 schema + 一个合法示例
adapter(adapterId, action, params) → 执行，返回与 `speak` 同构的结果
```

四种"信息不全"都**不是失败，而是一个更好的问题**：

| 输入 | 返回 |
|---|---|
| 无参数 | 适配器清单：id、平台、账号、健康色、是否本频道的 |
| 只有 id，且 id 不认识 | 同上，并指出"没有这个 id" |
| 有 id，动作缺失 / 不认识 | 该适配器支持的动作表 |
| 有 id + 动作，参数缺 / 不合法 | 该动作的 schema + 一个合法示例 |

⇒ **参数在 schema 里全部可选**，校验发生在工具内部：框架不拦，工具**回答**。

四样直接收益：

| 收益 | 说明 |
|---|---|
| **工具表恒定** | 工具表就是那几个（`speak` / `history` / `pending` / `adapter`），**无论会话空转还是挂着频道都一样**；特殊行为再多也只占 `adapter` 一个位置。**切号不改工具表**——没连频道时调 `speak`，就是如实报告"没有 channel" |
| **模型可探索** | 不需要预先知道"这个平台支持什么"，空调用即得清单 |
| **显式重试有了形状** | `adapter("a2","send",{…})` 就是打向指定适配器的定向重试（`§6.1.3` 里 red 回绿的那条路） |
| **不给 Channel 加方法** | 动作是 Adapter 自己的事，Channel 不必为每个特殊行为扩接口 |

三条硬约束：

1. **它不是特权旁路**：仍过权限检查与审计（`06`）；能列出、能操作哪些适配器由会话能力集决定——群聊会话能力集为空时，连清单都看不到。
2. **返回值同构**：`{ status, detail?, refs? }`，不因动作不同而换形状；否则模型要为每个动作学一套读法。
3. **清单必须短**：每行一条（id + 平台/账号 + 健康色 + 本频道相关标记），不带散文。否则"探索"本身就成了上下文负担——这是它唯一真正的成本。

⚠️ **与 `speak` 的分工**：`speak` 是**逻辑发送**（自动选主、走健康与额度）；`adapter(id,"send",…)` 是**直指某个适配器**的底层发送，故意绕过选路。后者存在的理由正是"选路不成立时，我仍要试那一个"。

⚠️ **特殊行为怎么凑，仍是 Adapter 内部的事**（如 QQ 用"撤回 + 重发"实现 edit），留 `via` 痕迹进审计与信号日志（§6.5）——对模型透明，对人不透明。

#### 为什么这样代码更干净

| 更早的版本（全覆盖 8 个动作） | 现在（两个动词 + 一个 `adapter` 工具） |
|---|---|
| 每个 Adapter 必须为 8 个动作交出实现或假实现 | 只要实现收与发 |
| 需要 `native` / `fallback` / `noop` 三态与环检测 | 三者都不需要 |
| 接入门槛由"动作覆盖度"决定 | 门槛降到"能收能发" |
| 每个特殊行为一个工具 ⇒ 工具表随频道漂移 | **工具表恒定**，特殊行为全在 `adapter` 的参数里 |
| 要给调用方一个能力探测端口 | **空调用 `adapter()` 就是探测** |

#### 统一的三层界线

| 层 | 统一？ | 例子 |
|---|---|---|
| 动作（动词） | **统一**（只剩两个） | receive / send |
| 参数语义 | **统一** | 发给谁、内容是什么、回复谁 |
| 回执语义 | **统一** | sent / accepted / failed |
| 平台特有结构 | **不统一** | 卡片、embed、按钮、表情包 → `extensions` 区 |
| 时序与延迟 | **不统一** | 限流、重连、切几条段 |

判据：**动词统一，名词不统一**。

#### 接口形状

```text
IInbound
  receive   入站：adapter.envelope 广播（§3）

IOutbound
  describe() → { platformId, accountId, limits }
  send(OutboundMessage) → SendResult

IChatAdapter : IInbound, IOutbound     ← Channel 只绑这个
  // 特殊行为不在接口上——它们通过 adapter 工具暴露

OutboundMessage（平台无关）
  target: { conversationId, replyTo?, mentions?: [identity] }
  parts:  [ text | mediaRef | … ]
  hints?: { markdown?, silent? }

SendResult
  status: sent | accepted | failed
  attemptId
  platformMessageIds?: [...]   ← 切段后 N 条聚合成一个结果
  detail?: 字符串              ← 平台原话，不解析
```

#### 反向判据（会红的测试）

1. 工具表里出现平台名（`send_qq` 之类）即红；
2. Channel / Session 侧出现 `platformId` 分支即红；
3. **方向不许混**：`IInbound` 上出现 `send`、`IOutbound` 上出现 `receive` 即红；
4. **Channel 绑到单向 Adapter ⇒ 加载失败**（正向测试：给一个只收的源绑上 Channel，必须装不上）；
5. **通用接口上出现第三个方法即红**——收与发之外的一切都必须走 `adapter` 工具；
6. 把某个特殊行为**单独注册成一个工具**即红；`adapter` 的执行结果与 `speak` 不同构即红。

#### 待定

- **单向 Adapter 的 envelope 由谁消费**：Channel 不再承担（只绑双向）。现在默认是"谁订阅 `adapter.envelope` 谁处理"（模块 / 图）——但要不要有个显式的"消费者"抽象，还是就靠订阅表；
- **动作名要不要一份建议表**：现在动作名是 Adapter 自报的字符串、不设封闭枚举（同 `detail` 的思路），模型靠 `adapter(id)` 查得到。但不同平台可能把同一件事叫 `edit` / `modify` / `update`——建议给一份推荐名表，**不强制**。

## 3. 入站：多对多广播，Channel 自己认领

（用户裁定：**适配器暴露自己收到的所有信息的瞬间事件，频道按需处理，不是自己需要的就抛弃**；**频道自己持有自身绑定的某个群聊的适配器 id 和群聊 id 来做匹配**——所以**不是一对多，是多对多**。）

```text
Adapter 收到平台回调
  → Adapter 清洗成 AdapterEnvelope
  → emit adapter.envelope（瞬时广播：不等待、不知道谁在听、不选投递对象）
  → 每个 Channel 收到后自己匹配：
       envelope.adapterInstanceId + platformConversationId ∈ 我的绑定集合？
         ├─ 不是我的 ⇒ 丢弃（常态：零成本，不通知 Adapter、不产生回执）
         └─ 是我的   ⇒ 归一成 ChannelMessage
  → emit channel.message.candidate
  → Store 持久化 candidate（经图）
  → 收到 store.channel.committed 后，Channel 确认 canonicalMessage
  → emit channel.message.accepted
  → Session 被激活后，在自己的步中按游标读取
```

约束：

1. **Adapter 不做分派，也不知道有哪些 Channel**。它只发"我收到了这个"。这是解耦的第三层：它不认识 Channel，正如 Channel 不认识 Session。
2. **匹配键归 Channel**：`bindings: [{ adapterInstanceId, platformConversationId }]`，写在 Channel 的装配配置里；加载期校验所引用的 Adapter 实例确实存在。
3. **多对多**：一个 Adapter 可被多个 Channel 绑定（一个号听多个群）；一个 Channel 可绑多个 Adapter（主备、多号，见 §2.3）。
4. **丢弃是常态，且必须廉价**：不属于自己的 envelope 直接丢——不写日志（可选计 debug 计数）、不回执、不通知 Adapter。"按需处理"的全部代价就是 Channel 一侧的比较。
5. **瞬时事件不重放**：`adapter.envelope` 是"收到的那一刻"，迟到的订阅者拿不到历史。要补历史只能从 AdapterStore 读——**留存（§4.2）是另一件事**：它防的是崩溃丢消息，不是为了重放事件。
6. **Channel 内的归一是同一实例内部行为**，可以硬代码；它不能直接调用 Store 或 Session，跨模块仍走图。
7. `message.candidate` 表示"待持久化"；`message.accepted` 只表示"逻辑消息已持久化、现在可读"。**Session 只能在 accepted 后被激活**。
8. 同一 Channel 可被多个 Session 连接；每个消费者有自己的游标，读者之间互不消费对方的消息。
9. 物理存储由 Store 模块负责；ChannelStore 保存逻辑消息、身份映射与来源记录，不由 Channel 自己打开数据库。

⚠️ **广播的代价如实记**：它是 O(Channel 数 × envelope 数) 次比较。到几十个 Channel、每秒几十条消息时仍然廉价（一次整数或字符串比较）；真正贵的是"该投给谁"的路由表，而它被删掉了——这正是换来"Adapter 不知道 Channel"的价格。若将来确实需要预筛，正确做法是在**广播点按 `adapterInstanceId` 分桶**（Adapter 仍不知道谁是 Channel，只按自己的 id 分），而不是把 Channel 名单塞回 Adapter。

### 3.1 信号分支的持久化屏障（必须解决）

signal 的分支互不等待，所以下面这种常见装法**不安全**：

```text
adapter.message.received ─┬─▶ Store 写入
                           └─▶ Session 激活
```

两个分支独立运行，Session 可能先被激活并读取，而 Store 尚未提交；Store 失败时消息已经被下游当成可读。**`channel.message.accepted` 不能与 `store.persist` 并列订阅**——这不是“理论上的顺序问题”，而是 signal 的语义直接保证了它们没有顺序。

最小安全语义是带提交确认的事件链：

```text
Adapter ─signal─▶ Channel intake
Channel ─signal─▶ channel.message.candidate
Store   ─持久化─▶ store.channel.committed
Channel ─确认────▶ channel.message.accepted
Session ─激活────▶ 只订阅 accepted
```

- Store 写入按 `canonicalMessageId` 幂等；重试不能产生重复逻辑消息；
- Channel 在 commit 确认前只把身份留作 pending，不能把消息对 Session 宣告为 accepted；
- 写入失败 ⇒ 不发 accepted；错误进入审计 / dead-letter / 重试通道；
- 副适配器此时到达的消息只进它自己的留存，不产生 accepted（副不投递，见 §4.2）。

⚠️ **本链的重试与 pending 状态仍待定**：如果进程在 candidate 发出后、Store commit 前崩溃，必须能从 Adapter 原始留存或可靠队列重放；不能依赖只存在 RAM 的 pending。确定了它，才能保证“重启不丢消息且不重复激活”。

实现可以采用满足此语义的 call / signal 组合；但禁止把“Store 写入”和“Session 激活”画成两条并列的无等待分支。

### 3.2 原始报文也有自己的持久化确认点

AdapterStore 负责保存原始报文，但“Adapter 发出 signal 后就不等”与“平台回调返回前原始字节必须落盘”不能自动同时成立。若平台在回调结束即确认消费，且 ALN 要保证崩溃可重放，就必须有**持久化接收点**：

- 要么平台回调路径通过图上的**调用**等待 AdapterStore 确认后再 ack；
- 要么 Adapter 模块先写自己的受限持久 spool，再异步 emit（之后由图归档进 AdapterStore）；
- 如果平台既不支持延迟 ack、Adapter 又不暂存，就只能承认进程崩溃窗口内可能丢原始报文。

这是原始留存与 Channel canonical commit **两道不同的屏障**。不能因为 Channel 已接受消息，就推断 AdapterStore 的原始报文也已经安全落盘。具体选哪种方案待功能切分阶段定。

## 4. 去重：默认不做

（用户裁定：**频道收发默认只用主适配器，不考虑去重**；但**每个适配器自己都存消息**，防止真的丢；这样省掉小概率事件的常态成本。）

| | 上一版 | 现在 |
|---|---|---|
| 常态入站 | 主副都投，Channel 去重 | **只有主适配器投递**；副只接收并留存 |
| 常态成本 | 每条消息一次去重查表 + provenance 写 | **零** |
| 防丢手段 | 靠去重合并 | **靠每个 Adapter 自己的消息留存** |

**为什么这样划算**：主备同时活跃是**小概率状态**（只存在于切换瞬间），为它给每条消息付常态成本不划算。而"防丢"不靠去重，靠**每个 Adapter 各自留存**——真出问题时从副的存储里补。

### 4.1 明确接受的代价：切换瞬间可能重复

主还没死透、副已接管的那一小段，同一条消息**可能被处理两次**。这是取舍，不是疏忽：

- **平台消息 id 仍然保留**，但用途从"常态去重"变成**事后对账与排查**（"这条为什么处理了两次"能查得清）；
- **不做任何事后标记、不建窗口去重表、不设"疑似重复"状态**（用户裁定：**切换重复不需要考虑**——概率太低、影响面太小，真要追查也极容易，不值得为它建任何机制）；
- `observedBy[]` 也从"去重合并的依据"退化为**诊断字段**（这条消息由哪个 Adapter 送达）。

### 4.2 Adapter 自己留存：防丢的真正机制

- 每个 Adapter 实例**独立保存**它收到的消息（含自己发出的回声）；
- **副适配器连接着但不投递**，照常接收并留存——这正是"主挂了能补"的前提；
- **留存默认永久，但必须有清理接口**（用户裁定：默认永久，保留清理接口）：AdapterStore 提供按时间 / 条数 / 会话的裁剪能力，由人显式触发——**不做自动过期**。留存量归 Adapter 侧的存储策略，不是 Channel 的职责。

⚠️ 由此 **AdapterStore 的写入可靠性比任何去重表都关键**：丢消息的风险在这里。§3.2 那道"原始报文的持久化确认点"因此从可选项变成**必答项**。

## 5. Session 如何连接 Channel

Session 不持有 Channel 实例引用。连接是**两条方向相反的东西**（`01 §6`、`01 §7`）：

```text
事件： Channel.Conversation#… ── channel.message.accepted ──▶ 挂在它上面的脚本     （无返回）
调用： Session.Chat#… ── provideContext(turn) ──▶ 挂在会话上的脚本 ──▶ 读频道        （有返回）
```

- **事件是通知**：频道发完就走；会话自己进入队列，何时得到运行机会归驱动器。
- **调用要指名**：会话向它 spec 里写死的那个脚本实例要上下文，拿到 `{ system, messages }` 后再组装请求。会话**不认识**频道，也不认识消息库。
- 频道消息由**脚本**按水位取（[`19`](19-会话连接.md) §5），取到的作为 `messages` 推给会话——**会话不自己拉**。
- **对模型暴露的 `history` 工具是这条调用的包装**（§2.4）：模型看到的是"读频道历史"，底下一层是脚本对频道的函数调用——**不直接碰 ChannelStore**，权限与连接校验仍然生效。
- **水位归连接**（[`19`](19-会话连接.md) §5）：同一频道的两个会话各有水位，一个的推进不会消费另一个的记录。
- Channel 可以对读请求做权限 / 连接检查，但“哪个 Session 能连哪个 Channel”在装配层显式声明，未连上的访问拒绝。

⚠️ `channel.message.accepted` 本身不携带整条消息供 Session 被动接收，避免“信号副本”和“read 结果”两份事实分叉。需要即时上下文时，信号只携带 Channel 标识与可读水位，Session 再通过 `read` 拉取。

## 6. 出站：Session 发给逻辑 Channel，再由图路由到 Adapter

Session 的模型 / 工具表达的是“往这个 Channel 发送”，而不是“调用 QQ Adapter 的 send”。

```text
Session →（call）→ Channel.post(canonicalMessage, replyTo?)
Channel → emit channel.outbound.requested
图订阅 channel.outbound.requested → 选中的 Adapter.send(OutboundMessage)
Adapter 把平台无关的 OutboundMessage 翻成平台请求（切段 / 上传 / 转义 / 限流）再发出
```

这把出站路径和入站镜像起来：**Session 只认识逻辑 Channel；Adapter 只认识平台协议；图负责连接两端。**

⚠️ **出站接口收的是平台无关的 `OutboundMessage`，不是打包好的 `platformPayload`**：切段、上传、转义、限流全在 Adapter 内部，Channel 与 Session 看不到平台差异。这是「统一功能暴露」的入口——通用面只有收与发、其余一切走 `adapter` 工具，见 §2.4。

### 6.1 主备 Adapter：默认主，可用性决定谁现在

```text
候选 = 该 Channel 上接入的全部 Adapter，按 priority 升序
选谁发 = 三色可用性的函数（§6.1.3），不是"坏了才换"
```

五条规则：

1. **优先级是装配数据**；同一 Channel 上两个 Adapter 声明相同优先级属于**装配错误**，加载期拒绝（否则"谁发"会由加载顺序决定）。
2. **可用性分三级：`green` 可用 / `yellow` 存疑 / `red` 不可用**（§6.1.1）。做成分级而不是二值，是因为"连不上"与"发不出去"的确定性根本不是一回事（§6.1.2）。
3. **`priority` 决定"谁先"，可用性决定"谁现在"**：优先级排的是候选顺序，不是接管权。
4. **切回保守**：恢复的 Adapter 还要过冷却期才重新接管，**不自动抖动**（§6.1.3）。
5. **健康由多路事实共同决定**（自报故障、心跳、发送结果），Channel 只跑状态机，不发明额外的判据。

### 6.1.1 可用性列表：三色 + 一句人话

（用户裁定：**频道自身维护一个适配器可用性列表**；适配器隔一段时间**喂狗**，也可以**主动报故障**让频道标定；报恢复时再标绿。）

```text
AdapterAvailability（每 Channel 一个，条目按 adapterInstanceId 索引）
  adapterInstanceId
  state               : green | yellow | red
  source              : heartbeat-timeout | adapter-fault | send-failure | adapter-healthy | send-success
  detail              : 自由字符串（Adapter 给的人话，如「无法连接：ECONNREFUSED」「正在重连：第 3 次」）
  consecutiveFailures : 连续发送失败次数（成功即清零）
  lastHeartbeatAt
  changedAt
  eligibleAt          : 何时允许被选为主（冷却期满）
```

**`source` 是 Channel 自己填的枚举，`detail` 是 Adapter 给的自由字符串**（用户裁定：**情况可以是字符串——Channel 只关心红没红，模型也只需要一句话**）：

- Channel **不解析** `detail`，只透传 ⇒ **不存在"允许报哪几种故障"的封闭清单**；
- 但 `source` 必须留着：事后解释"为什么红"，靠的是"谁改的状态"，而不是那句自由文本；
- 给模型 / 人的汇报就是一句人话：`adapter.b（#2 账号）不可用：正在重连：第 3 次`。

四路数据来源，权限各不相同：

| 来源 | 能做什么 | 不能做什么 |
|---|---|---|
| **心跳（喂狗）** | 超期 ⇒ **降级到 `red`** | **不能升级**（心跳恢复不自动转色） |
| **`adapter.fault`** | 自报"无法连接 / 正在重连" ⇒ **直接 `red`** | 不能标别人 |
| **发送结果** | 失败 ⇒ `yellow`（计数 +1）；连败达阈值 ⇒ `red`；成功 ⇒ **清零并回 `green`** | 单次失败不直接 `red` |
| **`adapter.healthy`** | `red` ⇒ `green`（起算冷却） | 不能立刻抢回主位 |

**两条实现约束**：

1. **"连上即报健康"写进 Adapter 契约**：Adapter 重建连接成功的那一刻发 `adapter.healthy`，不是"额外要记得做的一件事"。否则显式恢复会退化成"崩溃重启后忘了报，于是永远红"。
2. **正确性不依赖定时器**：选路时用 `now - lastHeartbeatAt > heartbeatTimeout` **现算**是否超期，而不是等某个定时器把状态改成 `red`。定时过程只负责**扫描并把变化发成事件**（可观测性），漏了扫描不会让判定出错。

⚠️ **心跳证明的是"这个 Adapter 认为它还活着"，不是"它真的能收发"**。Adapter 卡死但循环还在喂狗、平台已把它踢下线而它没察觉——这两种情况心跳都看不出。所以：**心跳只能降级，真相最终由平台回执给出**（§6.2）。这条限制必须写在这里，否则"喂着狗就是健康的"会变成一个假的安全感。

### 6.1.2 为什么分三色，而不是"健康 / 不健康"

（上一版我写"健康不由上次发送失败推断，Channel 只读不改"——**这条按裁定推翻**：发送失败要算数，只是不能一票否决。）

| 事实 | 确定性 | 落到哪一色 | 理由 |
|---|---|---|---|
| 自报"无法连接 / 正在重连" | **确定：它知道自己不行** | `red` | 自己承认，没有猜的成分 |
| 心跳超期 | **确定：它连"我还活着"都不说了** | `red` | 沉默够久就是故障 |
| 发送失败一次 | **不确定：可能是内容 / 权限 / 限流** | `yellow` | 一次失败不足以判死，但也不能当没发生 |
| 连续发送失败达阈值 | 高：换了内容换了时间都不行，倾向连接问题 | `red` | 阈值见 §8 待定 |
| 发送成功 | **确定：这条路通了** | `green`（并清零） | 成功是唯一无法伪装的证据 |

**为什么单次失败只标黄**：发送失败至少有三种来源——连接坏了、内容被拒、权限不够。后两种与"这条连接还能不能用"无关。直接标红，会让一次内容违规把主号踢下线；完全不理会，又会让"连接已死、但要等心跳超期"这一段继续吞消息。**黄就是"还没判死，但别再指望它"。**

**为什么黄仍然可以发**（§6.1.3 的选路）：黄的意思是**降级**，不是**停用**。否则"一次内容违规"和"一次网络抖动"就分不开了，而这两种本该由不同的证据升级。

**为什么成功一次就回绿**：成功是唯一无法伪装的证据（心跳可以喂、自报可以漏）。回绿不要求"成功 N 次"——失败已经被阈值拦在前面，既然连续失败才升级，那么一次成功就足以说明"它现在通了"。

### 6.1.3 选路：green → yellow → 拒发；red 只靠显式重试

```text
选谁发：
  ① priority 升序中第一个 (green ∧ now >= eligibleAt)     ← 常态
  ② 没有 green 时，priority 升序中第一个 yellow           ← 降级但仍可用
  ③ 只有 red（或都在冷却）⇒ 不选，拒发并给出回执
```

**③ 是"不猜"**：默认路径**永不**选 red。挑一个红的发出去，最坏结果是"以为发了、实际没发"——比明确失败更糟。

**但 red 不是单向棘轮**：red 仍可被**显式重试**——模型拿着 `attemptId`（或人指定 adapter）重发同一条消息时，允许打到 red 上，成功则回绿。否则"连续失败变红"之后，它没有任何被调用的机会，只能等自报 healthy，等于永久下线。

⚠️ 这**不是"随便试一个红的"**：默认选路永不碰 red；显式重试是**带着证据的一次定向尝试**，与"挑一个碰运气"是两件事。

- **入站不受影响**：任一 Adapter 只要能收到消息就照常收、照常自己留存（§4.2）。可用性是**选路依据**，不是"关掉这条连接"。
- Channel 发一条"无可选通道"事件，进日志（§6.5）。

**冷却期管的是"接管"，不是"颜色"**：`adapter.healthy` 到达 ⇒ `state = green`，同时 `eligibleAt = now + cooldown`。选路只在"`green` 且 `now >= eligibleAt`"里挑，于是"恢复了"与"接管了"是两件事——短抖动不会让出站方向反复横跳。

**选路是一个单点赋值**：`primary = ①或②选出的那一个`。切换是把这个变量改一次，**不存在"两个都是主"的中间态**，因此也不会出现主副同时投递（§4.2 的前提）。

### 6.2 发送结果：靠回执，不靠猜

（用户指出：**适配器能收到自己发送的消息，就算没发送也会有回执**；**由模型自己决定重发还是退避**。）

这条把上一版那个"结果不明"的灰区直接消掉了：

| 情况 | 证据 |
|---|---|
| 发送成功 | 平台回显自己那条消息（带平台消息 id） |
| 发送失败 | 平台 / 网关给出失败回执 |
| 根本没发出去 | **也有回执**，不是静默无响应 |

⇒ **Channel 不做重发决策，也不做"结果不明"分类**：它把回执作为一等结果交上去，**由模型决定重发还是退避**。

三条约束：

1. **回执必须可关联**：要能对上"这是哪一次发送尝试"（发送 id / 客户端标记），否则模型分不清是哪一条的结果。
2. **回声必须标记，否则自激**：Adapter 会把群里自己的消息当普通消息收到——必须标记为"自己发的"。这是**结构性要求**，不是过滤技巧：否则 bot 说的每句话都会变成新输入，触发下一轮。
3. **重发由模型决定 ⇒ 需要幂等证据**：同一内容发两次在群里长得一样，回执里的平台消息 id 是唯一能区分"已发"与"重发"的东西。

### 6.3 模型看不见自己发的消息（★本轮新定）

（用户裁定：**模型自己发的消息不会被模型自己看到**，它只能靠自己的工具调用记录知道自己刚才说了什么——与 ALP 同一设计。）

⇒ 回声的用途因此被限定：**只作回执与对账，不进模型上下文**。

四条推论：

1. **自激在结构上不可能**：bot 的输出永远不会回流成新输入，不需要靠"打标记再过滤"这种容易漏的补丁。
2. **模型的自知来自 `tool_use` 记录**：它说过的每句话都在自己的调用参数里，那是唯一来源（`I-14` 的"调用与结果是一块的两面"在这里第二次兑现）。
3. **回声仍要标记 `self`**：Channel 需要它来做回执与统计，也需要它判断"这条不必再投递"；只是**不喂给模型**。
4. **重发判断只能依赖回执**：既然看不到回声内容，模型就不能靠"群里有没有出现我说的话"来判断成败。

### 6.4 回执什么时候到：同步优先，超时走占位工具

（用户裁定：**没超时的话就同步返回，超时就靠占位工具后续注入**；占位工具的名字待定，见 `08 §5.3`。）

```text
Session 步内 ──call──▶ Channel.post(…)
  ├─ 同步窗口内拿到平台回执 → 直接作为这次工具调用的结果返回
  │                            ⇒ 模型在「这一步内」就知道成败，能当场决定重发还是退避
  └─ 同步窗口内没拿到       → 结果字段写「已提交、回执未到」；模型继续循环
                               ⇒ 回执随后由占位工具的一次调用注入
```

**这不是频道自己的一套超时**，而是 `08 §5.2` 那套双超时在频道上的表现：

| 概念 | 在频道上是什么 |
|---|---|
| `syncWait` | 模型愿意为这一条消息等多久（`speak` 之类的短窗口） |
| 同步期内回执 | 直接返回，模型当下决策 |
| 同步窗口到期 | 承认"已提交、回执未到"，**不装作还在等** |
| `asyncDeadline` | 回执最晚等到什么时候；到点仍未确认 ⇒ 经占位工具投递「未确认」 |

四条推论：

1. **回执只有一种形态：工具调用的结果**。同步时是原调用的结果，异步时是占位工具那一次调用的结果。模型只需学一种读法，频道也不必另造"事件推送"通道。
2. **`post` 的返回必须是"两种已知状态"而非"结果不明"**：`{ sent, platformMessageId, receipt }` 或 `{ accepted, attemptId }`。第二态**不是失败**，只是证据未到——把它叫"结果不明"会让模型无法区分"可能没发出去"和"肯定没发出去"。
3. **`attemptId` 是异步回执的关联键**：占位工具投递的结果里必须带它，模型才能对上"这是哪一次发送尝试"（§6.2 约束 1）。
4. **回执未到时重发要防重复**：不幂等的发送工具在"同一次逻辑发送仍在飞"期间拒绝第二次发起（`08 §5.2` 的幂等约束），否则模型看到"未确认"就会立刻再发一遍。

⚠️ **"未确认"是灰区，且必须如实叫这个名字**：`asyncDeadline` 到点只能断言"我没有证据"，**不能断言"没发出去"**。按裁定，这个灰区交给模型处理（退避重发或放弃）——但内核不能把它美化成任何一种确定状态。

### 6.5 切换与可用性变化是事件：进信号日志

（用户裁定：**切换本身会产生事件，这个需要产生在日志中**；**沿用 ALP 信号日志的思路**，尤其是**当前的图设计天然适合**。）

频道侧必须落的四类记录（它们都是**信号**——既是日志条目，也可被别的模块订阅，见 §6.5.2）：

| 事件 | 何时 | 必备字段 |
|---|---|---|
| `channel.adapter.availability.changed` | 某 Adapter 换色（绿 ↔ 黄 ↔ 红） | `channelId`、`adapterInstanceId`、`from`/`to`、`source`（五路之一）、`detail`（Adapter 给的自由字符串，不解析）、`lastHeartbeatAt`、`consecutiveFailures` |
| `channel.primary.changed` | 选主结果变了 | `channelId`、`fromAccountId`、`toAccountId`、触发它的那条 availability 事件 id、**当时全部候选的 `state`/`eligibleAt` 快照** |
| `channel.no-route` | 出站时无可用候选 | `channelId`、当时全部候选快照 |
| `channel.outbound.receipt` | 回执到达（成功 / 失败 / 未确认） | `attemptId`、`adapterInstanceId`、`platformMessageId?`、结局、耗时 |

**"当时全部候选的快照"不是冗余**：切换的原因几乎从不写在最终结果里。事后要回答"为什么那天切了"，必须能还原"当时副号是什么状态"。

### 6.5.1 ALN 为什么"天然适合"——三条结构性理由

ALP 的信号日志是**事后改造**出来的（`GraphTraceTool` 的注释自述：把日志从"人读的一句话"改造成带 `causes[]` 的依赖图数据流）。ALN 在第一次派发时就具备这个形状：

| 条件 | ALP | ALN |
|---|---|---|
| **因果来源** | 运行期靠时间戳与名称猜，后来才补 `causes[]` | **产生时就有**：每次派发必然经过某条订阅边，边有稳定 id 与两端模块身份（`02` §2），记录直接带 `edgeId` / `from` / `to` / `mechanism` |
| **聚合容器** | 一拍一条，但"一拍"要额外定义 | **过程就是容器**：一步内 N 次派发挂在同一个 `stepId` 下（`02` §2.1）⇒ 一条步记录 + N 条边记录，可聚合、可展开 |
| **分组键** | 字符串组名 | **装配期数据**：能按边做统计（哪条订阅最慢、最常失败），不必按运行期拼的名字分组 |

⇒ 于是 ALP 后来才做出来的"拍 + 因果边"，在 ALN 里是**派发的副产品**，而不是另一个需要维护的子系统。

### 6.5.2 记录点在驱动的唯一派发处，不在各模块里

```text
驱动 ──每次 emit / call──▶ 记录一条边记录（stepId, edgeId, from, to, mechanism, 结局, 耗时）
模块 ──自己的业务日志──▶ 另一条通道（不进链路可观测性）
```

- **不漏记是结构保证，不是纪律**：派发只有一个入口。
- **格式天然统一**：模块不需要注入 logger，也不需要"记得打"。
- **模块仍可打业务日志**，但链路复原**只认派发点记录**——否则又回到"某处忘了打就断链"。

### 6.5.3 信号日志 ≠ 审计：两条通道，不许合并

| | **信号日志** | **审计**（`06`） |
|---|---|---|
| 目的 | 行为可观测、排障、复盘 | 安全追责：谁、对什么、做了什么、拒绝了什么 |
| 能否过滤/关闭 | **能**（`MinLevel`、采样、保留期） | **不能**（绝对要求 ④） |
| 失败时 | 允许丢、允许落后，**绝不阻塞派发** | 关键判定点必须同步落盘 |
| 存储形态 | 可滚动、可清理 | 只追加、防篡改 |

⚠️ **把安全事件只写进信号日志，等于让"把级别调到 Warn"删掉追责数据**。审计不能建立在可过滤的通道上。

⚠️ **记录不能反噬链路**：写日志走异步队列，失败只计数告警。一旦"记录"变成必须成功的屏障，它就成了新的提交点（与 §3.1 的持久化屏障同理，但方向相反——那里要屏障，这里不要）。

### 6.5.4 沿用 ALP 的具体形状（与其教训）

沿用的三件：

1. **`IJournal` 形如 `ISignalLogger`**：`Open(group, name, detail)` / `Event` / `Debug` / `Warn` / `Error`——**分组 + 命名 + 结构化 detail**，不是自由文本一句话。
2. **级别由配置管**：ALP 的 `signalconfig.json` 只有 `MinLevel`（Debug=0 / Info=1 / Warn=2 / Error=3，默认 Info）。ALN 同构：**量靠级别与采样控制，不靠改代码**。
3. **可被工具读**：ALP 的 `graph_trace` 能把台账还原成依赖图（节点=拍，边=`cause`/`intent`/`parent`）。ALN 因为数据本来就是这个形状，读法只需按 `stepId` / `edgeId` 取。

不沿用的两条教训：

- **不许多文件**：ALP 留下 215 个根级 `.log`——日志必须进**统一通道**，一个模块一个文件等于没有日志。
- **不许把开关散落**：ALP 用一堆 `LILARA_*` 环境变量各自切片（`X-08`）。级别与采样都收进一个配置源，且带拒绝理由字段。

### 6.5.5 记录点放在哪里：每个跨边界调用一次

判据只有一条：**这条记录是否描述"谁调用了谁、经过哪条边、结局如何"**。是，就在那次调用唯一的入口处记一条；不是，就不记。日志节点由类型结构决定，不由模块自觉决定。

当前实现落了四类节点，各自只有一个写入位置：

| 组 | 位置 | 一条记录代表 | 级别 |
|---|---|---|---|
| `queue` | `EventPump.RunAsync` | 事件出队（`DurationMs` = 排队等待）与派发整体失败 | Debug / Warn |
| `dispatch` | `GraphManager.DispatchAsync` 的挂载循环 | 一条被走过的订阅边：`edgeId = scriptId@target#event` | Info / Warn |
| `capability` | `ScriptApi.InvokeAsync` / `DenyAsync` | 一次能力调用（含拒绝理由） | Info / Warn |
| `session` / `model` | `SessionManager.RunTurnAsync` / 模型请求前 | 一轮会话、一次模型请求（tokens、stop reason） | Info / Debug |
| `module` | `ctx.log.*`（脚本）与 `IModuleLogger`（模块） | 模块自己的叙述性记录，不代替边记录 | Info / Warn / Error |

### 6.5.6 一张图：点日志与链路日志共用同一棵树

"图流向"和"模块说了什么"如果分两条通道，读日志就得人肉对时间戳——那等于没有图。所以每条记录都带 `Id` 与 `ParentId`，最终**只组装一棵树**：

```text
queue(dequeue)                       ← 根：一次事件出队
└─ dispatch(scriptA@channel#accepted)
   ├─ module(scriptA · info "看到消息")  ← ctx.log 打点，挂在同一条边上
   └─ capability(session.run)
      └─ session(turn)
         └─ model(default)
```

- **位置由环境决定，不由调用者传**：进入一次跨边界调用时先分配记录 id 并开启 `SignalScope`（`AsyncLocal`），其内任何记录（点日志、嵌套能力、模型请求）自动继承 `ParentId`；`StepId` 也在 `SignalLog.Write` 里回填。模块不需要知道自己在哪条边上，也不可能记错父节点。
- **父记录晚于子记录落盘是正常的**：id 在进入时分配、结局在返回时才有，所以记录在完成时写；子记录先到、父记录后到，渲染按 id 组装，不按文件顺序。好处是长耗时的能力/模型调用期间点日志能立刻看到，而边的结局仍然如实（成功/超时/失败），不需要"started"这种半成品状态。
- **没有环境的记录是独立分叉**：例如启动期的模块日志，`ParentId` 为空、`StepId` 为空，图上表现为一条从自己的名字开始的 lane（对应 git graph 的一个新分支），而不是被塞进某个不相干的事件。
- **点日志三级封顶**：脚本/模块侧只有 `info`/`warn`/`error`，没有 `debug`——"先全记再 grep"是让日志变成垃圾的最快路径。脚本单次执行最多 200 条，超出时补一条 `Outcome = truncated` 的告警后静默，防止死循环刷盘。

接口：脚本内 `ctx.log.info(message, detail?)`（`detail` 为扁平对象，值截断到 512 字符，最多 16 项）；原生模块经 `IModuleLoggerFactory.For(moduleId)` 取 `Info`/`Warn`/`Error`。两者都禁止抛出——打点失败不得改变它所描述那次调用的结果。

### 6.5.7 分叉：多条 lane，不是一条线排下去

一个信号后续可能扇出（同一事件挂多个脚本），也可能在处理器内部再发出新事件。两种情况都**不是**并列的同级线，而是从某个节点长出来的分支：

```text
event(adapter.envelope)                    ← 扇出点：一个事件根
├─ dispatch(intake@adapter#envelope)       ← lane 1
│  ├─ module(intake · info)
│  └─ capability(channel.accept)
│     └─ event(channel.message.accepted)   ← 处理器内发出的事件挂在这里
│        └─ dispatch(reply@channel#accepted)
└─ dispatch(audit@adapter#envelope)        ← lane 2
```

三条结构保证：

1. **扇出有唯一父**：`DispatchAsync` 在每个事件上先落一条 `Group = event` 的根（经 `EventPump` 时它就是出队记录，直接调用时自建），所有处理器记录都是它的子节点。N 个处理器 ⇒ 一个节点的 N 个子节点，渲染器按 `ParentId` 分组就知道这是分叉，而不是 N 条互不相干的线。兄弟顺序取 `Sequence`，与执行顺序一致。
2. **处理器内发出的事件不断链**：`EventQueue.PublishAsync` 在入队时把当时的 `SignalScope.CurrentId` 抄进 `RoutedEvent.CauseSignalId`，出队记录用它当 `ParentId`。于是"哪个处理器发出了这个事件"是可查的，而不是靠时间戳猜。
3. **建树是显式 API**：`SignalTree.Build(records)` 返回 `SignalNode`（`Record` + 按 `Sequence` 排好的 `Children`），`Forks` 表示该节点确实分成了多条 lane。不靠渲染器猜，也不按文件顺序压平。

已知限制：

- **`ParentId` 只有一个**：这不是欠缺，而是模型本身。见下节。
- **父记录被过滤或轮转掉时，子记录降级为根**：宁可在图上多一条孤立 lane，也不要让它静默消失。`MinLevel` 调高正是会发生这种情况。
- `CauseSignalId` 只在经 `EventQueue.PublishAsync` 入队时打戳；绕过队列直接调 `DispatchAsync` 的事件不会继承外部因果（它是显式的新根）。

### 6.5.8 为什么不需要"合并"

（用户裁定：**两个事件调用的生命周期肯定不是同一个栈**；它们最多调用同一个模块的方法，而那里**必然有先后**，也必然有一方的结果保持静默。）

合并（多条 lane 汇成一点）在 git 里成立，是因为两个分支会**共同产生一个新提交**——存在一个属于两者的产物。派发里没有这样的产物：

- 每条 lane 是一次独立的调用，同步或异步都各有自己的栈；栈不会相交，所以不存在"两者共同返回"的那一刻。
- 两条 lane 若碰同一个模块，那是**串行进入同一个对象**（模块自身加锁/排队），先到的产生结果，后到的读那个结果或直接静默——这是状态交接，不是拓扑汇合。把它画成合并会让图说谎：看起来像共同产物，实际是"后来者观察到前者的结果"。
- 真要表达这种关系，正确的记录是**模块自己的点日志**（`module` 组，`ctx.log`/`IModuleLogger`）：它在自己的 lane 里、以自己那次调用的身份记下"我读到了某状态"。图保持树形，语义靠点日志说清。

所以：**树是正确形状，不是简化**。`ParentId` 单值不是预留不足；如果将来真的出现"一次调用由两条上游共同触发"，那也应当新增一个显式的多来源记录类型，而不是把两棵树糊成一张网。

### 6.6 Adapter、Channel 与消息的持久化

| 对象 | 落盘位置 | 说明 |
|---|---|---|
| Adapter 规格 | `modules/adapter.<type>#<instance>/module.json` | 地址、平台、账号、方向、实例私有 settings。手改即生效，不再硬编码在 Host 里；信箱等 IO 在 `io/<type>/<instance>/`，不进模块目录 |
| Channel 规格 | `modules/channel.<type>#<instance>/module.json` | 名称 + 绑定列表 + `maxMessages`（一轮最多带多少条，超出的以"省略更早的 N 条"出现）。频道名由人起（master），绑定里的另一半是适配器内部 id；两者对核心都是不透明字符串。频道是持久对象，不是目录的副产物 |
| Adapter 消息 | `aln.db` 的 `message` 表，`owner = adapter.<kind>#<instance>` | Adapter 收到的每条入站消息；频道发出的每条回复也在这张表里（`direction` 区分，`reply_to` 指向被回的那条） |
| Channel 消息 | 同上，属主是频道地址 | 频道自己的一条历史 |
| 会话 | `modules/<id>/{module.json,state.json,history.jsonl}` | 见 §5.6 |
| 模型调用 | `artifacts/model-calls/<date>/<call>.json` | 见 `14-模型模块.md` §3.1 |

**消息按属主分开存**，因为它们是两份事实：Adapter 记的是"平台给了什么"，Channel 记的是"本频道收进了什么"。同一 `id` 在两边出现是有意的——它就是上游事件 id，方便对齐；但两者不该被合并成一张表，否则频道历史会被别的适配器流量污染。

**绑定在创建时不校验、在投递时校验**：启动顺序没有任何保证，Channel 完全可能先于它的 Adapter 出现（脚本建频道、适配器后启动、或适配器临时销毁）。所以 `CreateAsync` 只校验绑定**形状**（地址是实例地址、会话 id 合法、不重复、一个绑定只属于一个频道），`AcceptAsync` 才检查该适配器此刻是否存在——不存在就明确失败 `Unavailable`，不投递、不入历史、不排队。把校验放在"最后一次能诚实判断的时刻"，是这两个管理器能完全互不等待的前提。

**适配器消息只有一处写入点**：`RecordingEventSink` 包住 `IEventSink`，在 Adapter 发布 `adapter.envelope` 的那一刻记录。Adapter 本身不认识存储，任何新适配器自动获得记录能力。频道消息则在 `ChannelManager.AcceptAsync` 记录——那是频道接受消息的唯一入口。

### 6.7 频道由脚本路由（`channel.route`）与"一个频道一个会话"

频道不再由 Host 启动时按 inbox 目录猜出来。`adapter.channel-intake` 脚本对每条入站消息调用：

```js
await ctx.channel.accept();
```

想让"没有频道就建一个"的策略归脚本时，用 `channel.route`：

```js
await ctx.channel.route({ channelId: event.platformConversationId });
```

`channel.route` 的语义是"投递到合适的频道，没有就建一个"，今天实现成三步的组合，而不是自己另写一套：

1. 按 `(Adapter, conversation)` 找一个运行中的频道——找到就直接投递（`created = false`）。
2. 没找到，就用脚本给的 `channelId` 定位 `channel.conversation#<id>`：
   - **不存在** → 建它（绑定当前 Adapter 与该会话），启动，投递；
   - **已存在但接的是别的会话** → 把会话**搬**过去（`channel.connect` 同一件事，不是第二个建频道实现），没在跑就启动。
3. 两种结局都记审计与信号；脚本拿到 `{ channel, created, acceptedChannels }`。

**一个频道一个会话，一个会话一个频道。** 这两句是同一个规则的两种读法：

- 一个会话（`(Adapter, conversation)`）只属于一个频道——这是原就有的唯一性；
- 一个频道只接一个会话——`ChannelInstance.Binding` 是单数，`CreateAsync` 拒绝第二绑定；`channels.list`
  仍按数组返回，所以对客户端而言形状没变。

所以"接线"有两条路：**建/拆**（`channels.create` / `channels.destroy`），和**搬**（`channels.connect` /
`channels.disconnect`）。搬是原子的：先把两端都解掉、再接上，一次状态写完成；回答里必须报出"被解掉的是谁"，
否则调用者看不出自己刚把另一个频道变成了收不到任何消息的状态。

`channel.route` 需要 `channel.route` 能力；只声明 `channel.accept` 的脚本仍可用于"只投递、不建频道"。
启动时 Host 只从 `modules/channel.<type>#<instance>/module.json` 恢复既有频道，并把文件里的绑定当初始值抄进
接线表（`22 §2.1.1`）；一个只有 inbox 目录、没有频道的会话，要等下一条消息被脚本路由时才会成为频道。




`edgeId` 由装配期数据推导（脚本 id + 目标地址 + 事件名），不依赖运行期拼字符串；`StepId` 直接取根 `EventId`。**派生事件复用了同一个 `EventId`**（`ChannelMessage.MessageId == AdapterEvent.EventId`），所以整条链——适配器入站 → 频道接受 → 脚本边 → 能力调用 → 会话轮 → 模型请求 → 出站发送——天然共享一个 `StepId`，不需要额外的 `causes[]` 字段。

**不记的地方**（否则量随采样点爆炸，且记录会变成第二套业务逻辑）：模型 SSE 的每个增量 token、history 的每次落盘、序列化与校验细节、重试循环内部的每一次尝试。这些要么已有结构化产物（history、审计），要么无法还原因果。

三条硬约束的实现方式：

1. **不漏记靠结构**：能力名在 `InvokeAsync` 里统一记，模块即使忘了打也不会缺边；脚本执行器（`JintScriptExecutor`）不再自带日志，因为它记录的是"处理器跑过"，而边的结局由派发循环判定。
2. **不成屏障**：`SignalLog.Write` 只做入队（有界、`DropWrite`），写文件在后台任务里；队列满就丢并计数，异常只累加 `FaultCount`，绝不抛出到派发路径。配置文件读失败也回落到默认值。
3. **与审计隔离**：`DenyAsync` 同时写信号（`Outcome = denied`，可被 `MinLevel` 过滤）与审计（不可过滤）；两者代码路径独立，级别调到最高只影响前者。

存储：`<DataRoot>/logs/signals-yyyyMMdd.jsonl` 单文件按日滚动，配置在 `<DataRoot>/logs/signalconfig.json`（`minLevel` / `capacity` / `memoryWindow`），无环境变量开关。


| 状态 | 归谁 | 是否持久化 |
|---|---|---|
| Adapter 原始 payload 与平台原始附件 | AdapterStore | 是（**默认永久**；提供显式清理接口，不自动过期） |
| Channel 逻辑消息 / canonical id | ChannelStore | 是 |
| 平台消息 id 与 canonicalMessageId 的对应 | ChannelStore | 是（排查与事后对账用，**不是常态去重**） |
| 某条逻辑消息由哪个 Adapter 送达 | ChannelStore（诊断字段） | 是 |
| Session 消费游标 | Session state | 是 |
| Adapter/Channel/Session 的连接拓扑 | Graph/装配存储 | 是；Channel 的绑定键（`adapterInstanceId` + `platformConversationId`）在装配里显式声明 |
| 消息归一的临时缓存 | Channel 实例 | 可重建；持久事实在 ChannelStore |

**Channel 不拥有**：平台 socket、Agent 循环、Session 的消费游标、数据库连接、业务规则。它只持有自己的逻辑身份映射、归一结果和必要的内存缓存。

## 8. 这一章明确没替你决定的事

本次定下的（不再列为待定）：**Channel 单平台**、**常态不去重（只主适配器投递，各 Adapter 自行留存）**、**出站与入站默认都走主，主自报异常才切副**、**发送结果靠回执、重发/退避由模型决定**、**多适配器即多账号（跨账号是设计目的）**、**可用性由心跳 + 显式红绿信号维护**、**回执同步优先、超时经 `pending` 注入**、**切换与可用性变化进信号日志**、**可用性分三色（黄 = 存疑，仅因单次发送失败；连败才红；成功即回绿）**、**`detail` 用自由字符串、Channel 不解析**、**red 不自动选路但可被显式重试**、**Adapter 留存默认永久并提供清理接口**、**切换重复不做任何标记**、**适配器只广播瞬间事件、Channel 按自己的绑定键认领（多对多）**。

仍然悬着的：

| 问题 | 为什么要单独定 |
|---|---|
| **冷却期 / 心跳间隔 / 超期阈值 / 连败阈值** 的数值 | 太短会抖动或误判、太长会让主长期闲置、让死连接多撑一会儿；连败阈值还决定「一次内容违规」会不会被当成连接故障。按平台特性定，且必须是配置项不是常量 |
| **编辑、撤回、回复、线程、附件**哪些进 canonical、哪些只留 adapter 扩展 | 关系到 Session 能看见多少语义，一次定清否则后续漂移 |
| **信号日志**的保留期与采样策略 | 量随步数线性增长；必须与审计分开算量（§6.5.3） |
